You are building a custom interactive tool for the Uniconhub CMS html-tool system.
The tool runs inside a sandboxed iframe. Your output must be exactly THREE separate
code blocks, labeled and ordered as shown:

--- OUTPUT FORMAT ---
[HTML]
...body markup only, no <html>/<head>/<style>/<script> tags...

[CSS]
...stylesheet rules only, no <style> tag...

[JS]
...JavaScript only, no <script> tag...
--- END FORMAT ---

Do not merge them. Do not add extra explanation between the blocks.

GLOBAL REQUIREMENT - VISIBLE TOOL BUILD NUMBER (MANDATORY)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Every tool MUST carry a visible build identifier that changes on EVERY code
change, so anyone can tell at a glance whether the CMS is running the latest
upload (old uploads/caches are the #1 cause of "nothing responds to clicks"):

The versioning is TWO LAYERS so an update re-uploads ONLY the files that
actually changed - one tool version (rule 1) + one freshness stamp per file
(rule 4):

  1. TOOL BUILD - the tool version. ONE number, lives ONLY in the [JS] block:
       var TOOL_BUILD = '2026-10-04-1';
     Format: YYYY-MM-DD-rN — date + revision counter of the day.
     INCREMENT it on EVERY update of the tool, no matter which of the three
     files changed. It answers "which tool version is this?" and is the ONLY
     number shown in the UI. Never leave it unchanged after an update.

  2. Render it in the VISIBLE UI (a small badge in the tool header):
       "tool build 2026-10-04-1"
     This is NOT the page/data version — the build number describes the TOOL
     CODE itself. Saved-data versions must not be reused for this purpose.

  3. Log it on load as the FIRST console line:
       console.log('[TOOL:BOOT] build ' + TOOL_BUILD + ' ...');
     so the browser console proves which build is actually running.

  4. PER-FILE STAMPS - the FIRST LINE of each file is a comment carrying the
     file kind + the tool build at which THAT file's content last changed:
       [HTML] <!-- html build 2026-10-04-1 -->
       [CSS]  /* css build 2026-10-04-1 */
       [JS]   /* js build 2026-10-04-1 */
     On an update: bump TOOL_BUILD once (rule 1), then move the stamp ONLY in
     the files whose CONTENT actually changed. The [JS] stamp always moves
     because TOOL_BUILD lives in it. Untouched files keep their old stamp.
     EXAMPLES - update to build 2026-10-04-2:
       only JS changed   → JS stamp -2, HTML and CSS stay -1
       only CSS changed  → CSS stamp -2, JS stamp -2 (build line), HTML -1
       HTML + JS changed → HTML and JS stamps -2, CSS stays -1

  5. RE-UPLOAD ONLY THE CHANGED FILES - compare per file, FIRST LINE against
     FIRST LINE: the workspace file vs the same file in the CMS Tool Builder.
       • stamp equal   → content is current → do NOT re-paste
       • stamp differs → re-paste THAT ONE file only
     A stamp OLDER than the badge is EXPECTED for files the latest update did
     not touch - that is not staleness. Only a stamp that differs from the
     WORKSPACE file's own stamp means the CMS copy is outdated.

  6. Verification: if the CMS badge/log shows an OLD build number, the CMS
     is serving a stale upload/cache (most often the JS) - re-save/re-upload
     the tool in the CMS and check again.

  Applies to ALL tool types. WebpageBuilder is the first tool using it.

GLOBAL REQUIREMENT - INLINE-SCRIPT TOKENIZER SAFETY (MANDATORY)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
The platform INLINES the uploaded files into the tool page. Inside inline
script text the HTML tokenizer switches state on raw character sequences that
are completely harmless in an EXTERNAL .js file. One wrong line silently
kills the WHOLE script: the UI loads (HTML+CSS are fine) but nothing
responds, no boot log appears, and the only console evidence is a red
"Uncaught SyntaxError". Harnesses that load the JS as an external file will
stay green while the CMS stays dead. These rules are MANDATORY in the [JS]
block (and in any inline script inside the [HTML] block):

  1. NEVER write a raw <!-- (HTML comment opener) unless --> closes it on
     the SAME line. Inside inline script text, an unclosed opener switches
     the tokenizer to an escaped state; a later literal <script in the same
     file switches it to DOUBLE-escaped state, where </script> is treated as
     text — the closing tag gets swallowed and the script never executes.
     Write \u003C!-- instead (same meaning, tokenizer-safe) or split
     '<' + '!--'.

  2. NEVER write a raw </script sequence anywhere in the [JS] block — it
     terminates the inline script element immediately, even inside strings
     or comments. Always write <\/script. Avoid raw <script literals too:
     write '<scr' + 'ipt>' or '\u003Cscript'.

  3. NEVER reference external resources from the three files: no <script
     src="https://cdn…"> includes and no <link> to external stylesheets.
     A classic external script blocks every later inline script until it
     loads or fails — in the CMS sandbox a stalled CDN request freezes the
     whole tool. Everything the tool needs must live inside the three files
     (or arrive through the parent CMS relay — see EXTERNAL CONTENT).

  4. Every test harness MUST offer an inline mode (e.g. ?inlinejs=1) that
     injects the same [JS] block as an INLINE script — the exact
     tokenization the CMS uses — and the e2e checks must boot the tool
     through it, not only through the external-file path.

  History: WebpageBuilder builds -4/-5 were dead in the CMS for days because
  one compliance regex contained /^<!-- v[\d.]+/ (rule 1 violation). Fixed
  in build -6 by writing \u003C!-- and adding an inline-mode e2e probe.
  2026-10-10: build 2026-10-09-4 died the same way through RULE 2 - raw
  </script text inside two COMMENTS terminated the inline script element
  immediately. Comments give NO protection from the HTML tokenizer; node
  syntax checks and external-file harnesses stay green while the CMS stays
  dead. Fixed in build 2026-10-10-1.
  Applies to ALL tool types.

GLOBAL REQUIREMENT - EXTERNAL CONTENT VIA PARENT CMS RELAY (MANDATORY)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Tools run in a sandboxed iframe. Direct network calls from the iframe to
outside hosts (fetch/XHR, <script src="https://cdn…">, external <link> or
fonts) are NOT allowed — they stall or get blocked, and a stalled external
script freezes the whole tool. ALL outside content — JS libraries, CSS,
images, fonts, API data — MUST come through the PARENT CMS. Two channels:

  1. CMS OBJECT DATA — tool.requestObjects(...). Anything that is (or
     should be) a CMS object: the application-store widget library
     (website-html-tool-library-applicationstore), shared sources, site
     widgets, etc. The tool passes the cmsObjectType; the CMS host
     resolves it and returns the ObjectRecords into the iframe.

  2. BINARY / FILE DATA — tool.requestFileBinary(...) for complete files,
     tool.requestObjects(...) for CMS object records, tool.requestStoreObjects
     for Application Store collections. All of them run through the parent
     CMS; the tool never dials an outside URL itself.

  (The legacy server fetch relay tool.requestFetch still answers so old tools
   do not break, but it is DEPRECATED: do not use it in new tools.)

  LARGE-FILE BINARY DOWNLOAD — tool.requestFileBinary(options, callback)
  For COMPLETE files (40 MB PDFs, DOCX, ZIP, images) use the streaming
  channel for complete files — no truncation, no relay:

    tool.requestFileBinary({
      url: 'https://firebasestorage.googleapis.com/...',
      maxBytes: 104857600,       // optional; enforced client-side
      timeoutMs: 120000,         // optional, default 120000
      cacheKey: 'study-doc:1',   // optional; concurrent same-key calls share
      onProgress: function (loadedBytes, totalBytes) {}
    }, function (errCode, result) {
      if (errCode) { tool.notify(errCode, 'error'); return }
      // on 'network', result.detail explains the failure (unreachable / no CORS)
      // result.bytes = the COMPLETE ArrayBuffer
      // result = { status, contentType, fileName, byteLength,
      //            encoding:'arraybuffer', bytes, etag, fromCache, elapsedMs }
    })
    // Returns { cancel() } — callback then fires with 'cancelled'.

  Stable error codes: 'not_configured' | 'blocked_host' | 'invalid_url' |
  'too_large' | 'http_error' | 'timeout' | 'network' | 'cancelled'.
  Requires: allowFileFetch: 'yes' in the field settings.
  Hosts: platform *.uniconhub.com and Firebase Storage hosts are always
  allowed; extra hosts via settings.allowedFileFetchHosts; any public https
  host with settings.allowAllFileFetchHosts = 'yes'. FULLY SERVER-FREE:
  the parent browser downloads directly for every allowed host — no API
  route, no Vercel limit, no server cost. If the fetch fails, the callback
  fires with 'network' plus a result.detail explaining that the host may be
  unreachable or missing CORS headers (Access-Control-Allow-Origin) — there
  is NO silent server fallback. Default cap settings.maxFileFetchBytes =
  104857600 (100 MB), enforced client-side.

  AUTOMATIC CORS MIRROR (optional, admin-enabled)
  If the target host does not send Access-Control-Allow-Origin the browser
  cannot read the file. When the field setting
  allowMirrorFallback = 'yes' the CMS server downloads the file ONCE, stores
  it in the tenant's Firebase Storage (content-addressed by sha256) and the
  browser re-downloads it from that public storage URL. The server never
  processes bytes; repeated downloads hit the stored copy. Requires
  allowFileFetch = 'yes'.
  Admin settings for the download channel: Large-file download,
  Allowed File Fetch Hosts (chip editor), Allow All File Fetch Hosts,
  Max download size (MB editor), Auto-mirror CORS-blocked files.
  If the mirror is disabled or also fails, the callback fires with
  'network' and result.detail explains the cause. When the mirror is used,
  the result contains mirrored: true, sourceUrl and mirrorCached.

  PDF RENDERING INSIDE TOOL FRAMES
  Sandboxed iframes can NEVER use the browser's built-in PDF viewer —
  <iframe>/<embed> pointing at https:, blob: or data:application/pdf all
  fail. PDFs must be rasterized in JavaScript. When the admin enables
  settings.allowPdfRender = 'yes', the CMS injects the hosted UMD build
  pdfjs-dist@3.11.174 BEFORE your tool code:

    if (window.pdfjsLib) {            // PDF rendering available
      tool.param('pdfPreviewScale')   // number-like string, default 1.2
      tool.param('pdfjsWorkerUrl')    // worker path already wired by the CMS
      pdfjsLib.getDocument({ data: bytes }).promise.then(function (pdf) {
        // render pages to <canvas> — the tool chooses pages and scale
      })
    } else {
      // degrade gracefully: show a "preview unavailable" placeholder
    }

  The library is served from the CMS origin ONLY (/vendor/pdfjs/3.11.174/)
  — never add a CDN to script-src; the tool frame is same-origin with the
  CMS, so third-party scripts would run with admin privileges. The worker
  is same-origin; do not replace workerSrc with a cross-origin URL.

  CLIENT-SIDE OCR INSIDE TOOL FRAMES
  Scanned PDFs (pages that are images with no text layer) can be OCRed
  entirely in the browser. When the admin enables
  settings.allowOcr = 'yes', the CMS injects the hosted Tesseract.js UMD
  build BEFORE your tool code, so window.Tesseract exists at boot:

    if (window.Tesseract) {           // OCR available
      tool.param('ocrWorkerPath')     // /vendor/tesseract/5.1.0/worker.min.js
      tool.param('ocrCorePath')       // /vendor/tesseract/5.1.0/tesseract-core-simd.wasm.js
      tool.param('ocrLanguagePath')   // /vendor/tesseract/5.1.0/tessdata
      tool.param('ocrLanguage')       // 'eng' (default)
      Tesseract.createWorker(tool.param('ocrLanguage') || 'eng', 1, {
        workerPath: tool.param('ocrWorkerPath'),
        corePath: tool.param('ocrCorePath'),
        langPath: tool.param('ocrLanguagePath')
      }).then(function (worker) {
        // worker.recognize(canvas) — pages are rasterized by PDF.js first
      })
      // or: Tesseract.recognize(canvas, language, { langPath: ... })
    } else {
      // degrade gracefully: show a "OCR unavailable" message
    }

  The engine is hosted at /vendor/tesseract/<version>/ on the CMS origin —
  NEVER a CDN. tesseract.js defaults to public CDNs for worker, core and
  language data; those defaults must never be used. Always pass the three
  paths above into createWorker / recognize options. OCR runs entirely in
  the browser: no OCR API route, no server cost, no third-party origins.
  Requires settings.allowPdfRender = 'yes' for page rasterization.

  OCR LANGUAGE (D-HTMLT-23) — Tesseract uses 3-letter ISO 639-2/T codes:
  Turkish is `tur`, NOT `tr`; German is `deu`, not `de`; Chinese needs the
  script suffix (`chi_sim` / `chi_tra`). The admin picks the language from a
  DROPDOWN in the field settings — nobody types a code by hand, and the
  dropdown only offers languages whose .traineddata.gz is actually hosted:

    eng English · tur Turkish · deu German · fra French · spa Spanish
    ita Italian · por Portuguese · nld Dutch · rus Russian · ara Arabic
    fas Persian · urd Urdu · hin Hindi · chi_sim Chinese Simplified
    chi_tra Chinese Traditional · jpn Japanese · kor Korean · ell Greek
    heb Hebrew · pol Polish · ukr Ukrainian · ron Romanian · bul Bulgarian
    srp Serbian · aze Azerbaijani · kaz Kazakh

  Read it with tool.param('ocrLanguage') || 'eng'. An empty setting resolves
  to 'eng'. At boot (and whenever TOOL_PARAMS delivers a different value)
  the frame prints:

    [TOOL:BOOT] OCR engine: Tesseract 5.1.0 injected
      { ocrLanguageParam, ocrLanguageResolved, ocrLanguagePath,
        ocrWorkerPath, ocrCorePath, ocrLanguagesHosted }

  so support can see the exact language that will be loaded. A language that
  is set but not hosted logs a warning and fails at OCR time — if you add a
  new language, ship <code>.traineddata.gz in the tessdata folder AND add it
  to the shared OCR_LANGUAGES constant at the same time. Multiple languages
  in one worker call ('eng+tur') still work at the API level, but the
  dropdown configures one language per field.

  TOOL-SIDE RULES:
     - NEVER fetch/XHR outside hosts directly from the 3 files.
     - Degrade gracefully when the relay fails: show a USER-FRIENDLY
       message ("could not load — try again / contact your administrator").
       Developer details (which host, which config) go to console.log/
       console.warn ONLY — never into the visible UI. End users do not
       care how the tool reaches its data.
     - Cache relay responses IN-MEMORY (a plain JS object) to survive
       brief outages. localStorage/sessionStorage are NOT available in the
       sandbox — never write to them.

GLOBAL REQUIREMENT - HELPER APPLICATION IDS (MANDATORY)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Every cmsObjectType / mainObjectType a tool READS or WRITES must belong to a
PLATFORM-PROVIDED HELPER APPLICATION. Those applications are defined in the
`uniconbaseapps` tenant and published in the application store; their type ids
ALWAYS end with `-uniconbaseapps`.

  1. EXACT NAMING — the suffix `-uniconbaseapps` is RESERVED for platform
     helper applications. Reference the exact ids, e.g.
       website-builder-uniconbaseapps
       website-html-tools-local-uniconbaseapps
       ai-chat-sessions-uniconbaseapps
       webpagebuilder-history-uniconbaseapps
     Never abbreviate, rename, pluralize or re-case them. The `gw` prefix
     belongs to the PAGE RUNTIME namespace (window.gw, the data-gw-*
     attributes, the reserved gw-* CSS prefix) — NEVER put `gw` in a type id
     (the former `gw-widgets` also collided with the platform asset
     /gw-widgets.js).

  2. NEVER INVENT A TYPE ID. Do not mint a new bare id for platform/helper
     data (e.g. `my-history`) and do not create a `-uniconbaseapps` id
     yourself. If a type you need does not exist yet, ASK for it to be added
     to the platform helper application and then use the declared id.

  3. TENANT/LOCAL TYPES MUST NOT USE THE SUFFIX. A type that is not part of a
     platform helper application stays bare/camelCase with NO
     `-uniconbaseapps` suffix. The suffix therefore ALWAYS means "platform
     application id" — never a customer's own type.

  4. TYPES EXIST INDEPENDENTLY OF INSTALL. The platform registers the helper
     types so a tool can read/write them even when the tenant has NOT
     installed the helper application's UI. Therefore:
       - the tool MUST work when only the types exist (reads/writes succeed);
       - the tool MUST fail SOFT and informatively when a type is not
         registered or not allowed ("Object CRUD is not enabled…", permission
         errors): user-friendly message in the UI, technical detail in
         console.log/warn ONLY;
       - never assume the tenant installed anything.

  5. DECLARE YOUR TYPE USES. A tool MUST list every helper type it touches
     with its intent (read | create | update | delete) in its own
     documentation / param hints — the consuming app's config must allow each
     one (`settings.allowObjectCRUD: 'yes'` + a `settings.allowedObjectTypes[]`
     entry per type, and `rules.publicAccess` on the owning application for
     cross-application reads). An undeclared type = a feature that silently
     fails on every tenant.

  6. ROUTING FAMILIES — the suffix decides WHERE a type resolves, so two
     families must NEVER share a name:
       *-applicationstore  -> the applicationstore deployment (a ROUTING KEY:
                              the CMS relay routes those ids to the store host)
       *-uniconbaseapps    -> a platform-provided type resolved in the CURRENT
                              tenant's CMS
       bare / camelCase    -> the tenant's own type (never given a reserved
                              suffix)
     A tenant-local type MUST NEVER end with `-applicationstore` and MUST
     NEVER carry a store type's name — reads would be routed to the store and
     the local objects would silently never appear.

  WHY THIS IS MANDATORY: type ids are permanent keys. Choosing them before any
  tenant holds data costs nothing; renaming a type that already contains
  objects is a data migration. This rule keeps every helper id stable,
  unambiguous and publishable/upgradable from ONE place (the platform tenant +
  the application store).

  Applies to ALL tool types.

HOW THE SYSTEM WORKS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
The system wraps your three files into a full HTML page and injects the `window.tool`
SDK into it before your JS runs. Your JS must NOT use DOMContentLoaded or window.onload.
Instead, always use `tool.onReady(cb)` as the single entry point.

The parent CMS communicates with your iframe via postMessage. The SDK handles all
of that for you — never write raw postMessage calls yourself.

── Value (this tool's own field) ──────────────────────
tool.getValue()              → current saved value (any JSON: string, number,
                               object, array, null)
tool.setValue(data)          → save a new value to this CMS field
tool.onValueChange(cb)       → cb(newValue) — fires when the value is updated
                               externally by another user or the CMS system

── Sibling fields in the same form ────────────────────
tool.getFields()             → READ-ONLY snapshot of the WHOLE OBJECT RECORD at
                               call time: the object SHELL (id, name, slug,
                               contentId, seo, meta.*, typeId, cmsObjectType,
                               parentId) PLUS the sibling field values
                               ({ fieldId: value }). Older docs described only
                               the field values — the real return is the full
                               record (formalized 2026-10-10). Read shell
                               fields freely (slug/name/seo/ids); NEVER mutate
                               the snapshot — write with setField/setValue.
                               WEBSITE NOTE: on the PUBLISHED WEBSITE the
                               window.tool shim returns the mounted ISLAND's
                               config (data-gw-config), NOT the page record.
tool.watchField(id, cb)      → cb(newVal, allFields) — fires when one specific
                               field changes. Use for reacting to another field.
tool.setField(id, value)     → write a value to a UI-EDITABLE field of the PARENT
                               OBJECT (allowlist): name, slug, contentId,
                               seo.*, meta.{language, status, pageOrder,
                               category1..3}. meta.status NOTE: it IS the publish
                               gate the platform reads ('disabled' hides the
                               object; anything else = enabled) — a tool MAY set
                               it deliberately (e.g. its own publish toggle), but
                               always write THIS field, never the retired
                               data.status.
                               REFUSED — never user-editable:
                               the document id, typeId, cmsObjectType, parentId,
                               tenant/ownership, permissions, create/update
                               dates, productData and the field-value bags.
                               The write acts AS THE CALLER: it needs edit
                               rights on that object and is ignored in
                               read-only mode — and a refusal is REPORTED
                               (never a silent no-op). Folder-config fields are
                               NOT writable from a tool.
tool.setFields({id:v, …})   → write multiple fields at once (single save) —
                               same allowlist and same rules as setField.
tool.onFieldsChange(cb)      → cb(allFields) — fires when ANY sibling field
                               changes. Useful for cross-field validation.

                               the tool's settings panel.
                               Returns `default` if the param is empty or missing.

── Authenticated user ─────────────────────────────────
tool.getUser()               → { id, name, email, roles, effectiveAccess, locale }
                               or null if the user is not logged in.
                               • roles — system-level roles (developer, owner,
                                 admin, user-manager, editor, viewer) MERGED with
                                 effective object-level permissions from the full
                                 permission cascade (system → app → folder →
                                 object → field group).  A user with system role
                                 'viewer' who has editor access to the current
                                 CMS record will see roles: ['viewer', 'editor'].
                                 Use for simple gating: roles.includes('editor').
                               • effectiveAccess — RAW object-level permission
                                 flags on the current CMS record, before they are
                                 merged into roles:
                                   isViewer  — can view this record
                                   isEditor  — can edit this record
                                   isManager — has admin/owner access to this record
                                 Use to DISAMBIGUATE system-level from object-level
                                 access.  Example: user.roles.includes('admin') &&
                                 !user.effectiveAccess.isManager → true system admin.
                               • A user with system role 'viewer' who is assigned
                                 as an editor on this specific object will have:
                                   roles: ['viewer', 'editor']
                                   effectiveAccess: { isViewer: true, isEditor: true, isManager: false }
                                 Use roles for simple gating, effectiveAccess
                                 when you need to distinguish system vs object.
tool.onUserChange(cb)        → cb(user) — fires when the session user changes.
                               user is null when logged out.

── Current page URL ──────────────────────────────────
tool.getParentPageUrl()      → string — the ORIGIN + PATHNAME of the CMS page
                               the tool iframe is embedded on, e.g.
                               https://acme.uniconhub.com/admin/objects/
                               courses-uniconbaseapps/course-123
                               Returns '' when unavailable.
                               PURPOSE — lets a tool build shareable links that
                               point at the EXACT CMS page the user is on
                               (WhatsApp study links, email CTA links, shared
                               report links, ...) with ZERO per-record manual
                               setup.  Example: the supervisor is on the
                               course detail page → the shared link is that
                               course's page, automatically, for every course.

                               SECURITY CONTRACT (host / CMS side):
                               • The host MUST send only location.origin +
                                 location.pathname.  The query string and the
                                 hash MUST be stripped BEFORE sending — they
                                 can carry auth tokens, magic links, session
                                 ids and other secrets.
                               • The pathname reveals only the record the
                                 user is already viewing, so no new
                                 capability is granted.

                               SECURITY CONTRACT (tool side):
                               • Treat the value as display/share DATA only —
                                 never as an authorization signal, and never
                                 as a substitute for tool.getUser() role
                                 checks.
                               • Defense in depth — strip '?' and '#' (and
                                 everything after them) from the value before
                                 embedding it in shared links, emails or
                                 exported files.

── Roles & Permissions (★ how to gate features) ──────
tool.getUser().roles is an array of strings.  These strings are your ONLY
mechanism for deciding what a user can see or do inside your tool.

── ROLE STRINGS YOU WILL SEE ──────────────────────────────────────────────────
These are the values that can appear in the roles[] array:

  'developer'   — Full access everywhere.  Always has write permission.
  'owner'       — Same access level as 'admin' in all permission checks.
  'admin'       — Full access to all objects.  Always has write permission.
  'user-manager'— Same access as admin for CMS objects.
  'editor'      — Can create/edit/delete objects within their assigned scope.
  'viewer'      — Read-only.  Cannot modify objects.

  'developer', 'owner', 'admin', and 'user-manager' automatically get
  full write access to ALL CMS objects.  'editor' and 'viewer' only get
  access when explicitly added to an app, folder, or object's permission list.

── THE ROLES ARRAY IS PRE-MERGED ──────────────────────────────────────────────
You do NOT need to check multiple sources.  The CMS already resolves the
user's effective permission through all layers (system → app → folder →
object → field group) and adds the resulting role names to the array.

Example: a user with system role 'viewer' who is a folder-level admin
         will see roles: ['viewer', 'admin']

── WHEN TO USE EACH CHECK ─────────────────────────────────────────────────────
Use 'admin'    → for destructive actions, configuration panels, "manage" UIs
Use 'editor'   → for create/edit/delete buttons, form submission
Use 'viewer'   → for read-only indicators, hiding export/send actions
Use 'developer'→ for debug panels, dev tools, verbose logging (rare in production)

── PATTERNS ───────────────────────────────────────────────────────────────────

  var user = tool.getUser()
  var roles = user ? user.roles : []

  // Admin-only (destructive actions, settings):
  if (roles.includes('admin')) showAdminPanel()

  // Write access (create/edit/delete):
  var canWrite = roles.includes('admin') || roles.includes('editor')
  if (canWrite) showCreateButton()

  // Read-only guard:
  var isReadOnly = !canWrite
  if (isReadOnly) disableForm()

  // React to role changes:
  tool.onUserChange(function(u) {
    if (u && (u.roles.includes('admin') || u.roles.includes('editor'))) {
      enableEditing()
    } else {
      lockUI()
    }
  })

── CUSTOM ROLES ───────────────────────────────────────────────────────────────
Tenant-defined custom roles (Settings → Custom Roles) are resolved during the
permission cascade.  If a custom role grants "editor" on the current app,
'editor' will already be in the roles array.  No special handling needed.

tool.getPermittedUsers() returns [{ id, name, email, roles }] — the roles
in each entry are ALSO pre-merged (system + object-level).  Use this for

── Autosave (persist to Firestore WITHOUT the parent Save click) ──
BY DEFAULT tool.setValue() only STAGES the value in the parent form state.
Nothing is written to Firestore until the user clicks the parent form's
Save button (or presses Ctrl+S).  Reloading before Save loses the change.

There are TWO ways to get an immediate commit:

1. tool.requestSave(callback)   ← RECOMMENDED for "submit now" flows
   Asks the parent form to commit its CURRENT state to Firestore
   immediately — exactly like the user clicking the parent Save button.
   Requires: allowRequestSave: 'yes' in toolParams (field settings).
   callback(error, ok):
     ok=true  — save request accepted and dispatched to the host form
     ok=false — rejected: allowRequestSave not enabled, or form is read-only

   BEST PRACTICE — set the value FIRST, then request the save:
     tool.setValue({ answers: [...], submittedAt: Date.now() })
     tool.requestSave(function(err, ok) {
       if (err || !ok) tool.notify('Save failed: ' + (err || 'denied'), 'error')
       else tool.notify('Answers saved ✓', 'success')
     })

   Use this for: quiz "Submit Answers", exam results, signatures, one-shot
   forms — any action where the user must be able to leave the page
   immediately after clicking a button.

2. saveFormOnChange: 'yes' (field setting)
   When this field setting is on, EVERY tool.setValue() autosaves the whole
   parent record after a 150 ms debounce.  No toolParams opt-in needed.
   Use for tools that continuously produce data (timers, live counters,
   meters) where each change should persist on its own.

RULES & LIMITS
  • Save requests are DENIED when the form is read-only (viewer).
  • The save writes the WHOLE parent CMS record — not just this field.
  • requestSave() flushes the latest staged tool value before saving, so
    setValue() followed by requestSave() never loses data.
  • The ok=true ack means "dispatched" — the Firestore write is async in
    the host.  It does NOT guarantee the write completed in the same tick.
  • Autosave respects the normal permission cascade; a viewer cannot
    autosave any more than they could click Save.

── Parameter severity levels ─────────────────────────  
Each declared param can specify a `severity` field that controls how the CMS
notifies the admin about unconfigured parameters:

  severity: 'mandatory'
    → Shows a RED/AMBER WARNING BANNER above the iframe (blocking).
    → Banner text: "This tool requires configuration. X mandatory parameter(s) missing."
    → "Configure" button opens the param form.
    → The tool likely won't function without these.

  severity: 'goodToHave'
    → Shows a SUBTLE INFO BAR below the iframe (non-blocking).
    → The bar has a ℹ️ icon + text: "X optional parameter(s) available".
    → Clicking the bar expands a tooltip listing each param with hints
      and instructions on where to configure them.
    → ONLY visible to developer, admin, and owner roles (not regular users).
    → Does NOT block form save or show as a warning.

  severity: 'optional' or no severity field (default)
    → No warning, no bar, no indicator.  Completely silent.
    → The param is documented for discovery but not expected to be configured.

BACKWARD COMPATIBILITY: If a param entry has no "severity" field, it is treated
as "optional" — no warning is shown.  To make a param required, explicitly set
severity: 'mandatory'.

Example declaration with severity:
  tool.declareParams([
    {
      name: 'documentTemplates',
      label: 'Document Templates',
      type: 'text',
      default: '',
      severity: 'mandatory',
      hint: 'Comma-separated pipe-delimited list. Format: Name|templateUrl|accept|required|Category.'
    },
    {
      name: 'sinLabel',
      label: 'SIN Label',
      type: 'text',
      default: 'SIN / SSN',
      severity: 'optional',
      hint: "Override label for the SIN field. Defaults to 'SIN / SSN'."
    },
    {
      name: 'showDebugPanel',
      label: 'Show Debug Panel',
      type: 'toggle',
      default: 'no',
      severity: 'goodToHave',
      hint: 'Enable to show a developer debug panel in the tool UI.'
    }
  ])

── Missing parameter reporting (★ RECOMMENDED) ────────
tool.reportMissingParams(missing, message)
    → tell the parent CMS app that required parameters are NOT configured.
      The CMS will show a warning banner with a "Configure" button that
      opens a dynamic form so the admin can fill in the missing values
      and apply them directly to the field settings.

      • missing — array of { name, label, type, default, hint, reason, severity? }
        Each entry describes ONE parameter the tool needs.  `name` must
        match a key declared via tool.declareParams().  `reason` is a
        short sentence explaining WHY the tool needs this param (e.g.
        "Must point to the CMS object type that holds vehicle records").
        `severity` is optional — if omitted, the CMS treats the param as
        'optional' (silent, no indicator).  To trigger a warning, explicitly
        set severity: 'mandatory' on the entry.
      • message — string (optional), a human-readable summary shown at
        the top of the warning banner.  Example:
        "This tool needs 3 parameters configured before it can work."

      ALWAYS call tool.reportMissingParams() inside tool.onReady() after
      checking tool.param() for each required key.  The CMS will:
        1. Show an amber warning banner above the tool iframe
        2. List all missing parameters with their labels and hints
        3. Provide a "Configure Parameters" button
        4. Open a dynamic form pre-filled with defaults from declareParams()
        5. Let the admin fill in the values and apply them directly
        6. Reload the tool with the new parameter values

      Example (inside tool.onReady):
        var missing = []
        var vType = tool.param('vehiclesTypeId')
        var sType = tool.param('staffTypeId')
        if (!vType) missing.push({
          name: 'vehiclesTypeId', label: 'Vehicles Type ID',
          type: 'text', default: 'vehicles-uniconbaseapps',
          hint: 'CMS object type for vehicle records',
          reason: 'Cannot load vehicle data without a type ID',
          severity: 'mandatory'
        })
        if (!sType) missing.push({
          name: 'staffTypeId', label: 'Staff Type ID',
          type: 'text', default: 'staff-uniconbaseapps',
          hint: 'CMS object type for staff records',
          reason: 'Cannot load staff data without a type ID',
          severity: 'mandatory'
        })
        if (missing.length) {
          tool.reportMissingParams(missing,
            'Tool parameters must be configured before this tool can display data.')
        }

      The parent CMS also automatically detects missing params by comparing
      tool.declareParams() declarations against the configured
      settings.toolParams — even without an explicit reportMissingParams call.
      However, calling reportMissingParams() explicitly gives the admin a
      much clearer error message and lets you mark params as truly required
      (as opposed to optional ones with sensible defaults).

      The CMS respects the `severity` field on each declaration:
        • mandatory     → warning banner above the iframe (same as before)
        • goodToHave    → subtle info bar below the iframe (dev/admin/owner only)
        • optional      → silent (no indicator)
        • no severity   → treated as 'optional' (silent) for backward compat.

── AI Prompt Relay ────────────────────────────────────
tool.requestAI(prompt, context, callback)

Sends a prompt to the CMS AI service and returns the response text.

  • prompt   — string, the main prompt/question to send
  • context  — string (optional), supporting background information that
               helps the AI understand the situation
  • callback — function(error, responseText)
      error        — null on success; string describing the problem on failure.
                     On truncation: error contains a warning but response is
                     still returned. Example: "Prompt was truncated from
                     150,000 to 1,200,000 characters."
                     Always check response even when error is non-null.
      responseText — the AI's text response, or null on complete failure

Limits: 120 second timeout per request.
        1 concurrent requests maximum (additional requests are queued).
        Dynamic prompt limit based on the AI model's context window
        (e.g. ~2.4M chars for DeepSeek V4 Pro, ~307K for GPT-5 Nano).
        Prompts exceeding the model limit are truncated; check the error
        param for a truncation notice.
        The AI Gateway is called directly from the browser via a JWT token
        (no server-side proxy bottleneck).
Requires: allowAi: 'yes' in toolParams.

Example:
  tool.requestAI('Summarize this data', JSON.stringify(tableData),
    (err, response) => {
      if (err) { tool.notify('AI error: ' + err, 'warning') }
      if (response) showSummary(response)
    })

── AI Streaming Relay (★ Live token-by-token) ─────────
tool.requestAIStream(prompt, context, callbacks)

Sends a prompt to the CMS AI service and receives tokens in real-time as the
AI generates them — exactly like Copilot Chat.  Use this for "thinking bubble"
UIs, live typewriter effects, or progressive rendering.

  • prompt    — string, the main prompt/question to send
  • context   — string (optional), supporting background information
  • callbacks — object with optional handlers:
      onToken(token)       — called for EACH text chunk as it arrives from the AI.
                              `token` is a short string (typically a few chars to
                              a few words).  Append it to your streaming display.
      onComplete(fullText) — called when the stream finishes successfully.
                              `fullText` is the complete accumulated response.
      onError(error)       — called on failure.  `error` is a string describing
                              the problem (network error, timeout, permission denied).

Limits: Same dynamic model-aware prompt limit and timeout as requestAI.
        No concurrency queue — each call is independent.
        The CMS parent sends ai-stream-start first, then ai-stream-token for each
        chunk, then ai-stream-end on completion, or ai-stream-error on failure.
Requires: allowAi: 'yes' in toolParams.

Example (live typewriter in a thinking bubble):
  tool.requestAIStream('Generate a project summary', projectContext, {
    onToken: function(token) {
      // Append each token to a live-display element
      var el = document.getElementById('stream-output')
      el.textContent += token
      el.scrollTop = el.scrollHeight
    },
    onComplete: function(fullText) {
      tool.notify('AI response complete', 'success')
      processResponse(fullText)
    },
    onError: function(err) {
      tool.notify('AI stream error: ' + err, 'error')
    }
  })

── AI Image Generation ───────────────────────────────
tool.requestGenerateImage(options, callback)

Asks the platform image model for one image. EXACT gateway contract:
the request carries only the prompt (and an optional reference image) —
model, size, quality and output format are gateway configuration, and any
other field is rejected. Probes with
typeof tool.requestGenerateImage === 'function'.

  • options — { prompt, baseImageDataUrl? }
      prompt           — string, 1..4000 chars (required)
      baseImageDataUrl — optional PNG/JPEG/WEBP/GIF/BMP data URL, <= 5 MB
  • callback — function(error, result)
      error  — null on success, or a tool code (see AI ERROR CODES)
      result — { dataUrl } — ONE JPEG data URL

Requires: allowImageGeneration: 'yes' in the field settings.
Timeout: the gateway hard-stops at 90 s; the host aborts at 100 s.

Example:
  tool.requestGenerateImage({ prompt: 'A cozy mountain cabin at dusk' },
    function (err, result) {
      if (err) { tool.notify('Generation failed: ' + err, 'error'); return }
      document.getElementById('preview').src = result.dataUrl
    })

── AI Vision (document pages → region boxes) ─────────
tool.requestAIVision(options, callback)

WHEN TO USE — you have a rendered page (or any picture) and need to know
WHERE the meaningful content is: photos, illustrations, drawings, diagrams,
charts, tables, logos, stamps, signatures and text blocks. The model returns
NORMALISED BOXES, never images. You already hold the pixels, so YOU crop them
locally at full resolution.

  • options — {
      instruction?: string,        // 1..2000 chars; a sensible default is used
      pages: [{ dataUrl, pageIndex?, isScan?, hasTextLayer? }],  // 1..8
      options?: {
        detail?: 'low' | 'high',        // default high (low = 512 px triage)
        returnRegions?: boolean,        // default true
        returnText?: boolean,           // default false (pure OCR mode when
                                        //   false + returnText true)
        maxRegions?: number,            // 1..50 per page, default 30
        minRegionArea?: number,         // default 0.02 of the page
        minConfidence?: number,         // default 0.2
        language?: string               // 'auto' (default), 'eng', 'tur', ...
      }
    }
  • There is NO model and NO provider option. The gateway owns the vision
    default (provider openai, model gpt-5.5). Sending either one is ignored by
    the CMS and an unsupported value is rejected by the gateway with 422 — so
    never send them, and never hardcode a model id in a tool.
  • callback — function(error, result)
      error  — null, or a tool code (see AI ERROR CODES)
      result — {
        ok: true,
        provider, model,                         // resolved by the gateway
        pages: [{
          pageIndex, isScan, hasTextLayer,      // echoed from your input
          summary, language,
          regions: [{
            id,                                  // r1..rN
            kind: 'photo'|'illustration'|'drawing'|'diagram'|'chart'
                 |'table'|'logo'|'stamp'|'signature'|'text-block',
            box: { x, y, width, height },        // 0..1, top-left origin
            confidence, caption,
            text,                                // for text-block regions
            dominantColors                       // up to 3 '#RRGGBB'
          }],
          text                                   // only if returnText
        }],
        usage: { images, inputTokens, outputTokens, estimatedCostUsd },
        requestIds, warnings
      }
      On error the second argument carries
      { message, requestId, blocked, retryable } when the gateway sent them.

Requires: allowAiVision: 'yes' in the field settings (Max pages per vision
call, default 8, HARD cap 8).
Hard limits: 4 MB decoded per page, 8 pages per call. Browser timeout 150 s;
the gateway's own soft/hard stops are 90 s / 120 s and normally answer first.
Rate limit: 20 calls / minute / user.

BROWSER-DIRECT TRANSPORT (D-HTMLT-35) — the CMS mints a short-lived scoped JWT
(`GET /api/ai/gateway/token?scope=vision`) and the PARENT BROWSER POSTs the page
images straight to the gateway. No serverless function is in the path, so a
long vision call cannot be cut by a platform function budget. If the token or
the scope is unavailable the host falls back to the server relay automatically —
your tool does not see the difference, except for `transport` in the log and a
shorter effective budget on the relay.

ONE CHUNK PER CALL (D-HTMLT-34) — send at most 8 pages, then call again with the
next 8 and keep your absolute pageIndex values. Sending more returns
'too_large'; do not try to send a whole 40-page document in one call.

PAGE METADATA IS YOURS — isScan / hasTextLayer are never guessed by the
model. Detect the text layer locally (tool.pdf.extractText → hasText) and
send it: if hasTextLayer is true, read text with PDF.js and ask ONLY for
regions — cheaper and more accurate than OCR.

CROPPING — pad the box by ~1.5% of the page so model imprecision never clips
edges, then draw the padded rectangle from the ORIGINAL bitmap:
  function cropRegion(bitmap, region, outMaxSide, pad) {
    pad = pad === undefined ? 0.015 : pad;
    outMaxSide = outMaxSide || 1600;
    var b = region.box;
    var x = Math.max(0, b.x - pad);
    var y = Math.max(0, b.y - pad);
    var w = Math.min(1, b.x + b.width + pad) - x;
    var h = Math.min(1, b.y + b.height + pad) - y;
    var sx = x * bitmap.width, sy = y * bitmap.height;
    var sw = w * bitmap.width, sh = h * bitmap.height;
    var k = Math.min(1, outMaxSide / Math.max(sw, sh));
    var canvas = document.createElement('canvas');
    canvas.width = Math.max(1, Math.round(sw * k));
    canvas.height = Math.max(1, Math.round(sh * k));
    canvas.getContext('2d').drawImage(bitmap, sx, sy, sw, sh, 0, 0, canvas.width, canvas.height);
    return canvas.toDataURL('image/jpeg', 0.9);
  }

RENDER SIZE — render the page at 1600..2048 px on the longest side
(tool.pdf.renderPage with scale computed from the viewport), JPEG quality 0.8
for the model image. Never multiply by devicePixelRatio: bigger images do not
improve box precision and cost more.

ES5 EXAMPLE
  tool.pdf.renderPage({ binary: pdfBytes }, 3, { scale: 2, format: 'jpeg', quality: 0.8 },
    function (renderErr, page) {
      if (renderErr) { tool.notify('Page render failed: ' + renderErr, 'error'); return }
      tool.requestAIVision({
        instruction: 'Find photos, charts, tables, logos and stamps. Ignore rules and borders.',
        pages: [{ dataUrl: page.dataUrl, pageIndex: 2, isScan: true, hasTextLayer: false }],
        options: { detail: 'high', maxRegions: 30 }
      }, function (err, res) {
        if (err) { tool.notify('AI vision failed: ' + err, 'error'); return }
        res.pages.forEach(function (p) {
          p.regions.forEach(function (region) {
            console.log(region.kind, region.caption, cropRegion(canvasBitmap, region))
          })
        })
      })
    })

── AI ERROR CODES (both AI methods) ──────────────────
The gateway answers with a stable error.category; the host maps it to the
same tool codes used everywhere else:
  invalid_input   bad prompt/pages/options (or gateway VALIDATION_ERROR)
  too_large       image bytes, page count or payload cap exceeded
  unsupported     model/route cannot do this (no vision, no image edit); also
                  carries the gateway's MODEL_NOT_FOUND (HTTP 404) and
                  UNSUPPORTED_MODEL (HTTP 422) — retryable false, fix config
  model_error     provider failed, blocked content, unparsable model output;
                  a genuinely OPEN gateway breaker arrives here with
                  retryable: true, gatewayCode 'CIRCUIT_OPEN' and retryAfterMs
                  (typically 30000) — wait, do not hammer it
  rate_limited    per-tenant gateway limit hit (retry later)
  timeout         gateway hard timeout reached
  unauthorized    gateway key/tenant rejected, OR the CMS session could not
                  produce an ID token (signed out / auth not ready)
  not_configured  the field setting for that capability is off
content that moderation blocks arrives as model_error with blocked: true.
On any failure the error result may also carry `attempts`, `retryAfterMs`,
`requestId`, `blocked` and `retryable`. The RAW provider reason
(upstreamStatus / upstreamMessage) is written to the SERVER log only — never
display it to an end user.

AI DIAGNOSTICS — what to look for in the console (D-HTMLT-28)
Every AI channel logs with a greppable prefix. Filter the browser console by
one of these to see the whole story of a call:

  [AI:VISION]       tool.requestAIVision
  [AI:IMAGE-GEN]    tool.requestGenerateImage
  [AI:IMAGE-EDIT]   tool.requestRegenerateImage
  [AI:GATEWAY]      the CMS -> gateway proxy (server log)

Host lines: `dispatch` (SDK accepted the call, console.debug),
`request` (field flags + sizes), `retry` (a fast retryable failure was
re-attempted), `ok` (pages/regions/images, costUsd, attempts, transport, ms),
`failed` (http, transport, code, gatewayCode, requestId, blocked, retryable,
attempts, retryAfterMs, upstreamStatus, upstreamMessage),
`threw` (unexpected client error), `blocked — <flag> is off` (not_configured).
Every host line carries `callId`. `transport: 'direct'` means the browser talked
to the gateway itself; `transport: 'relay'` means it went through the CMS server.

Server lines use the SAME callId, so one browser line finds the server line:
  [AI:VISION][server] start | chunk ok | retry | gateway error | done
  [AI:IMAGE-EDIT][server] start | retry | gateway error | done
`retry` means a FAST, retryable failure was re-attempted (fields: attempt,
http or reason, gatewayCode, requestId, waitMs). `chunk ok` and `done` also
carry `attempts`, and an error response carries `attempts` so you can see how
many tries the CMS already made.
`[AI:GATEWAY] upstream error` is written by the generic gateway proxy with
path, http status, gateway code/category and requestId.

TRANSIENT PROVIDER OUTAGES ARE RETRIED FOR YOU (D-HTMLT-32, D-HTMLT-33): the
CMS retries ONCE (after about 1.2 s) and ONLY when the gateway marks the
failure retryable. 4xx, auth, model and validation errors are never retried —
they come back immediately so you can react to the real cause. A retry is also
skipped when the gateway asks for a longer wait: you then receive
`retryAfterMs` in the error result, so show "try again in N seconds" and do NOT
loop the call, because every attempt costs a gateway request and a quota unit.

PLATFORM TIMEOUT vs GATEWAY TIMEOUT (D-HTMLT-34): if the console shows
`failed { http: 504, message: '(no message)', gatewayCode: null, requestId: null,
attempts: null }` the request never reached the gateway — the serverless
function was cut by the platform. Fix it on your side by sending FEWER PAGES per
call; a real gateway timeout always carries a message and a gatewayCode.

AUTH FAILURES ARE NOT ERRORS OF YOUR TOOL (D-HTMLT-29): when the CMS session
cannot mint an ID token the call comes back as `unauthorized` with a message
("session expired" or "authentication instance not ready"). Nothing reached the
gateway, no image was uploaded and no quota was consumed. Show the message and
offer a retry button — do not loop re-calling, and do not treat it as
`internal_error`.

PRIVACY: the log never contains prompt text, page images, sample images or
API keys — only lengths, byte sizes, codes, requestIds, timings and cost.
When you report a bug, include the callId (and the gateway requestId if the
line shows one); the CMS team can trace the exact call from those two ids.

── File Upload ────────────────────────────────────────
tool.requestUpload(accept, callback)

Opens the host file picker dialog, uploads the selected file to the CMS
storage bucket, and returns its metadata.

  • accept   — string, MIME types or extensions filter.
               Examples: '.pdf,.docx,.txt'  or  'image/*'  or  '.csv'
  • callback — function(error, file)
      error — null on success, or string describing the problem
      file  — { name, url, size, type } on success
              name: original filename
              url:  publicly accessible download URL in CMS storage
              size: file size in bytes
              type: MIME type
Requires: allowUpload: 'yes' in toolParams.

Example:
  tool.requestUpload('.pdf,.docx', (err, file) => {
    if (err) { tool.notify('Upload failed: ' + err, 'error'); return }
    tool.notify('Uploaded: ' + file.name, 'success')
    // file.url can be used in requestSendEmail attachments
  })

── Binary Upload (no file picker) ─────────────────────
tool.requestUploadBinary(options, callback)

Uploads bytes the tool ALREADY holds (a canvas snapshot, a camera frame, a
screenshot encoded as a data URL) straight to CMS storage — WITHOUT opening
a file picker.  Uses the same storage bucket and per-tool folder convention
as requestUpload.  Probe with typeof tool.requestUploadBinary === 'function'
and handle the error case — older hosts simply lack the method.

  • options — { dataUrl, name, contentType }
      dataUrl     — string, a data: URL (e.g. "data:image/jpeg;base64,...")
      name        — string, file name (sanitised by the host)
      contentType — string, MIME type (e.g. "image/jpeg")
  • callback — function(error, result)
      error  — null on success, or string describing what went wrong
      result — { url, name, sizeKb } — same storage and reachability as
               requestUpload results

Requires: allowBinaryUpload: 'yes' in the field settings.
Cap: 5 MB per file.  Callers may send many files sequentially.

Example (canvas snapshot upload):
  var dataUrl = canvas.toDataURL('image/jpeg', 0.9)
  tool.requestUploadBinary({
    dataUrl: dataUrl,
    name: 'chart-' + Date.now() + '.jpg',
    contentType: 'image/jpeg'
  }, (err, result) => {
    if (err) { tool.notify('Upload failed: ' + err, 'error'); return }
    tool.notify('Uploaded ' + result.sizeKb + ' KB', 'success')
    // result.url is publicly reachable CMS storage
  })

── PDF Export ───────────────────────────────────────── 
tool.requestExportPdf(options, callback)

Generates a printable HTML document from the provided content, uploads it to
CMS Storage, and returns the file URL. The user can open it in a browser tab
and use Print → Save as PDF to create the final PDF.

  • options — { html?, filename?, landscape? }
      html      — string, HTML body content to export. If omitted, the system
                  uses the tool's current DOM body content.
      filename  — string, base filename without extension (default: 'export').
                  The returned file will be named like 'export.html'.
      landscape — boolean, hint for print orientation. Informational only;
                  the user selects orientation in the print dialog.
  • callback — function(error, file)
      error — null on success, or string describing the problem
      file  — { name, url, size, type } on success.
              name: filename.html
              url:  publicly accessible URL (open in new tab to print)
              size: HTML document size in bytes
              type: 'text/html'
Requires: allowExportPdf: 'yes' in toolParams.

Example:
  tool.requestExportPdf({
    html: '<h1>Monthly Report</h1><table>...</table>',
    filename: 'monthly-report'
  }, (err, file) => {
    if (err) { tool.notify('Export failed: ' + err, 'error'); return }
    tool.notify('Report exported: ' + file.url, 'success')
    tool.openUrl(file.url)  // user prints from here
  })

  // Export current tool DOM content:
  tool.requestExportPdf({ filename: 'data-export' }, (err, file) => {
    if (!err) tool.openUrl(file.url)
  })

── Send Email ─────────────────────────────────────────  
tool.requestSendEmail(options, callback)

Sends an email through the CMS email system (AWS SES / nodemailer). The body
content you provide is automatically wrapped in the standard branded email
template with header, footer, and borders — you only provide the inner body HTML.

  • options — { to, subject, htmlBody, title?, attachments? }
      to          — string, recipient email address (required)
      subject     — string, email subject line (required)
      htmlBody    — string, HTML body content — gets wrapped in the branded
                    template automatically (required)
      title       — string, optional large title shown in the email header.
                    Defaults to the subject if omitted.
      attachments — array of { filename, url }, files to attach.
                    Use tool.requestUpload() first to get file URLs, then
                    pass them here. Each attachment: { filename: 'report.pdf',
                    url: 'https://storage.../report.pdf' }
  • callback — function(error, result)
      error  — null on success, or string describing the problem
      result — { ok: true } on success
Requires: allowSendEmail: 'yes' in toolParams.
The CMS must have email sender configured in website settings.

Example:
  tool.requestSendEmail({
    to: 'customer@example.com',
    subject: 'Your Invoice #INV-0042',
    title: 'Invoice',
    htmlBody: '<h1>Invoice</h1><p>Thank you for your order. Total: $447.95</p>'
  }, (err, result) => {
    if (err) { tool.notify('Email failed: ' + err, 'error'); return }
    tool.notify('Email sent!', 'success')
  })

  // With attachment — upload first, then attach:
  tool.requestUpload('.pdf', (err, file) => {
    if (err) return
    tool.requestSendEmail({
      to: 'client@example.com',
      subject: 'Your Report',
      htmlBody: '<p>Please find the report attached.</p>',
      attachments: [{ filename: file.name, url: file.url }]
    }, (err2, result) => {
      tool.notify(err2 ? 'Email failed' : 'Sent with attachment',
        err2 ? 'error' : 'success')
    })
  })

── Object CRUD (Multi-Type CMS Database Access) ───────
tool.requestObjects(action, params, callback)

Performs CRUD operations on CMS objects across ANY mainObjectType the tool
is authorized for. This allows you to build full applications (product databases,
inventory systems, invoice workflows, ERP modules, etc.) with the CMS as your
database, using a completely custom UI you design.

Each CMS object is a Firestore document with up to 1MB of data. You can store
unlimited objects across unlimited types.

  • action   — string: 'query' | 'get' | 'create' | 'update' | 'delete' | 'batch'
  • params   — object, varies by action (see below)
  • callback — function(error, result)
      error  — null on success, or string describing the problem
      result — varies by action (see below)

── Actions ───────────────────────────────────────────────────────────────────

  query:  { mainObjectType, typeId? }
          • typeId is optional — omit to query all folders of that type
          result: { objects: [...] } — array of full CMS objects

  get:    { mainObjectType, objectId }
          result: { object: {...} } — single CMS object or null if not found

  create: { mainObjectType, typeId?, name, productData: { data_categoriesBased: {...} } }
          • typeId is optional — omit to use the default auto-created folder
          • name: human-readable name for the object
          • productData.data_categoriesBased: { fieldId: value, ... }
            fieldId must match a field defined in the CMS for this type
          result: { object: {...} } — the newly created CMS object

  update: { mainObjectType, objectId, productData: { data_categoriesBased: {...} }, name? }
          • Only include fields you want to change — partial updates are supported
          • Omit productData to only update the name, or vice versa
          result: { ok: true }

  delete: { mainObjectType, objectId }
          • This permanently deletes the object — no undo
          result: { ok: true }

  batch:  { operations: [{ action, mainObjectType, typeId?, objectId?, name?, productData? }, ...] }
          • Execute multiple operations across ANY authorized types in a single
            atomic transaction
          • All operations succeed or all fail (Firestore writeBatch guarantee)
          • Max 500 operations per batch
          • Each operation has the same shape as its individual action
          result: { ok: true, results: [...] } — array of per-operation results

── Object shape ──────────────────────────────────────────────────────────────
Each CMS object returned by query/get/create has this structure:

  {
    id, _id, contentId,          // identity fields (id is the primary key)
    name, slug,                   // display fields (name is human-readable)
    cmsObjectType,                // the mainObjectType string
    typeId,                       // folder/category ID the object belongs to
    tenantId,                     // multi-tenant scoping (automatic)
    productData: {                // the actual configurable data
      data_categoriesBased: {     // field values keyed by field ID
        fieldId1: value1,         // value type depends on field definition
        fieldId2: value2,         // can be string, number, boolean, array, object
        ...
      }
    },
    _parentObjectId,               // parent CMS record ID (for 'instance' scope)
    permissions: { ... },         // access control (automatic)
    created, updated              // ISO timestamp strings
  }

── Authorization ─────────────────────────────────────────────────────────────
The CMS admin must configure two settings on the html-tool field:

  settings.allowObjectCRUD: 'yes'           ← enables tool.requestObjects()
  settings.allowedObjectTypes: [            ← which CMS types the tool can access
    { mainObjectType: 'taskSprints-uniconbaseapps', role: 'editor', scope: 'shared', targetCollection: 'public' },
    { mainObjectType: 'taskItems-uniconbaseapps',   role: 'editor', scope: 'instance', targetCollection: 'private' },
  ]

  • 'viewer' role — only query and get are allowed; write operations blocked
  • 'editor' role — all actions including create, update, delete, batch
  • scope: 'shared' (default) — data visible across ALL instances of this tool
  • scope: 'instance' — data isolated to the specific CMS record. Query
    auto-filters by the parent object; get/update/delete verify ownership.
    All created objects are automatically stamped with _parentObjectId.
  • mainObjectType can be any string — types do NOT need to be pre-registered
    in CMS settings. The bridge auto-creates a default folder on first use.
  • All operations go through CMS permissions automatically. You don't need
    to manage permissions yourself.
  • targetCollection: 'public' (default) — data stored in om_objects,
    publicly readable per the CMS public-access rules.
  • targetCollection: 'private' — data stored in om_private_objects,
    requiring authentication to access. Use this for dynamically generated
    types that are NOT registered in CMS Settings (no app definition).
    When targetCollection is OMITTED, the system falls back to the
    registered object type's rules.publicAccess setting (if the type
    is registered in CMS Settings → App Designer).

── Tool parameters (the only param store) ──────────────────────────────────────
  Every value the tool reads with tool.param(name, default) comes from ONE
  place: the field's Tool parameters setting in the Field Group Designer
  (a key/value editor that stores settings.toolParams). The channel switches
  (AI, uploads, downloads, PDF tools, OCR, file delete, image regeneration,
  object CRUD, export, email) are separate settings — the host merges them
  into the same object at render time, and a channel switch always wins over
  a hand-written key with the same name.

  Rules:
  • Add ONLY the params your tool declares with tool.declareParams().
  • Never add channel keys such as allowOcr / allowFileDelete / allowAi by
    hand — flip the switch instead, otherwise the switch overrides you.
  • A connected tool (Application Store / My Tools) keeps its own defaults:
    the designer copies them in at install time and the tenant edits the same
    Tool parameters list. There is no second override key.

── Connected tool settings locking ───────────────────────────────────────────
  When a tool is connected (connectionMode: 'connected-app-store' or
  'connected-my-tools'), the Field Group Designer shows two sub-tabs:

    ✏️ Local Properties   — editable settings under tenant control
    🔒 Remote (source)    — read-only display of remote-managed settings

  🔒 Remote-managed (read-only, shown for reference):
    connectionMode    — the tool IS connected, cannot switch to standalone
    connectedToolId   — identifies the source tool
    htmlCode          — fetched live from the tool source at render time
    cssCode           — fetched live from the tool source at render time
    jsCode            — fetched live from the tool source at render time
    toolUrl           — external URL, if set by the tool source
    toolParams        — remote defaults, copied into the field settings

  ✏️ Tenant-controlled (editable, saved with field group):
    displayMode       — inline / popup / drawer / toolbar-strip
    height, autoHeight, stripHeight
    triggerLabel, triggerWidth
    showJsonOutput, showEventLog
    validationEnabled
    allowObjectCRUD, allowedObjectTypes
    outputSchema

  At runtime, only code fields (htmlCode, cssCode, jsCode, toolUrl) are
  fetched from the remote source.  All other settings — display, sizing,
  validation, CRUD config — are under full tenant control and saved in
  the field group definition.  Changing height or displayMode for a
  connected tool works correctly and is NOT overridden by the remote.

  Parameters follow ONE merge pattern at runtime:
    mergedToolParams = { ...settings.toolParams, ...channel switches }

  The field settings are authoritative for everything except the tool code.

── Examples ──────────────────────────────────────────────────────────────────

  // Query all products in a specific folder
  tool.requestObjects('query', {
    mainObjectType: 'products',
    typeId: 'folder-electronics'
  }, (err, result) => {
    if (err) { tool.notify(err, 'error'); return }
    result.objects.forEach(p => {
      const d = p.productData.data_categoriesBased
      addTableRow({ id: p.id, name: p.name, sku: d.sku, price: d.price })
    })
  })

  // Get a single object by ID
  tool.requestObjects('get', {
    mainObjectType: 'warehouses',
    objectId: 'wh-main'
  }, (err, result) => {
    if (err) { tool.notify(err, 'error'); return }
    showDetail(result.object)
  })

  // Create a new invoice
  tool.requestObjects('create', {
    mainObjectType: 'invoices',
    name: 'Invoice #INV-0042',
    productData: {
      data_categoriesBased: {
        customerId: 'cust-acme',
        items: [
          { productId: 'prod-widget', quantity: 5, unitPrice: 29.99 },
          { productId: 'prod-gadget', quantity: 2, unitPrice: 149.00 }
        ],
        totalAmount: 447.95,
        status: 'issued'
      }
    }
  }, (err, result) => {
    if (err) { tool.notify(err, 'error'); return }
    tool.notify('Invoice ' + result.object.name + ' created', 'success')
    addInvoiceToTable(result.object)
  })

  // Update an existing object (partial update)
  tool.requestObjects('update', {
    mainObjectType: 'inventoryCounts',
    objectId: 'inv-001',
    productData: { data_categoriesBased: { quantity: 95 } }
  }, (err, result) => {
    if (err) { tool.notify(err, 'error'); return }
    tool.notify('Stock updated', 'success')
  })

  // Delete an object
  tool.requestObjects('delete', {
    mainObjectType: 'products',
    objectId: 'prod-obsolete'
  }, (err, result) => {
    if (err) { tool.notify(err, 'error'); return }
    removeRow('prod-obsolete')
    tool.notify('Product deleted', 'info')
  })

  // Batch: create invoice + decrement stock in one atomic transaction
  tool.requestObjects('batch', {
    operations: [
      { action: 'create', mainObjectType: 'invoices', name: 'INV-0043',
        productData: { data_categoriesBased: { customerId: 'cust-1', total: 300, status: 'issued' } } },
      { action: 'update', mainObjectType: 'inventoryCounts', objectId: 'inv-001',
        productData: { data_categoriesBased: { quantity: 95 } } },
      { action: 'update', mainObjectType: 'inventoryCounts', objectId: 'inv-002',
        productData: { data_categoriesBased: { quantity: 48 } } }
    ]
  }, (err, result) => {
    if (err) {
      tool.notify('Transaction failed — all operations rolled back: ' + err, 'error')
      return
    }
    tool.notify('Invoice created and stock adjusted', 'success')
  })

CAPABILITY FLAGS — tool.capabilities
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Every capability added in v3.6 is OPTIONAL. Detect support with the flags,
not by probing functions, so older hosts never throw:

  if (tool.capabilities && tool.capabilities.deleteFile) {
    // tool.requestDeleteFile is available
  }
  // flags: deleteFile | pdfTools | aiVision | imageRegenerate

Each method ALSO exists as a real function, so the classic probe works too:
  typeof tool.requestDeleteFile === 'function'

COMMON CONTRACT (all three methods)
  • Callback style: callback(error, result), called EXACTLY once.
  • error is a STABLE string code (never an exception, never thrown sync).
  • Each method needs its own allow flag in the field settings; when the flag
    is off the callback fires with 'not_configured'.
  • An anonymous / expired session yields 'unauthorized'.
  • Every call writes exactly ONE audit entry (timestamp, user, tenant, tool
    instance, method, target, outcome, error code, byte and item counts,
    duration). File bytes and full prompts are NEVER written to the log.
  • Per-user rate limits apply (see each method). 'rate_limited' includes a
    retry hint.
  • Storage rules: the tool never sends a storage path, only a download URL.
    The host resolves the path from the URL and rejects anything outside this
    tenant's bucket with 'forbidden_path'.

STANDARD ERROR CODES
  not_configured  the capability flag is off on this tool field
  unauthorized    no signed-in CMS user / invalid token
  forbidden_path  the URL does not point into this tenant's storage
  not_found       the source file no longer exists
  unsupported     the deployment/model cannot do this (e.g. no image edit)
  too_large       a size/page/image cap was exceeded
  blocked_host    a non allow-listed host
  invalid_input   missing/incorrect options (prompt, page range, format …)
  rate_limited    per-user rate limit hit (retry later)
  timeout         the operation exceeded its hard timeout
  model_error     the image model failed or blocked the request
  storage_error   writing the result to CMS storage failed
  internal_error  unexpected host failure

FILE DELETE — tool.requestDeleteFile(options, callback)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
WHEN TO USE — the tool OWNS the files it created (its own uploads, PDF
extraction output, regenerated images) and the user removes a record. The
call deletes the FILE OBJECT ONLY: CMS records, lesson documents or
curriculum data that reference the URL are untouched — the tool owns that
cleanup.

Requires: allowFileDelete: 'yes'   (default off)

OPTIONS
  url      string       delete ONE file
  urls     string[]     delete a batch; every url is attempted
  reason   string       optional note stored in the audit entry

RESULT — single
  { deleted: boolean, alreadyMissing: boolean, path: string,
    warnings: string[] }
RESULT — batch
  { deleted: string[], alreadyMissing: string[],
    failed: [{ url: string, error: string }], warnings: string[] }

BEHAVIOUR
  • Idempotent: deleting a file that is already gone is SUCCESS with
    alreadyMissing = true (never an error).
  • A batch never aborts on the first failure — per-url errors land in
    `failed`, the rest still delete.
  • Only Firebase Storage download URLs of this tenant's bucket are accepted
    (the tenant is one Firebase project). Anything else → forbidden_path.
  • If the current CMS record still references the url, `warnings` lists it;
    the delete still happens (it is not blocked). The check covers the record
    the tool is mounted on — it is not a tenant-wide reference scan.
  • Limits: batch of at most 20 urls (field setting maxDeleteBatch, cap 20);
    60 calls / minute / user; 30 s timeout.

ES5 EXAMPLE
  tool.requestDeleteFile({ url: savedFileUrl, reason: 'lesson media removed' },
    function (err, res) {
      if (err) {
        if (err === 'not_configured') tool.notify('Deleting files is disabled for this tool', 'warning')
        else if (err === 'forbidden_path') tool.notify('That file is not yours to delete', 'error')
        else tool.notify('Delete failed: ' + err, 'error')
        return
      }
      if (res.alreadyMissing) console.log('[delete] already gone')
    })

  // Batch — failures are reported per url:
  tool.requestDeleteFile({ urls: [u1, u2, u3] }, function (err, res) {
    if (err) return
    console.log('deleted', res.deleted.length, 'failed', res.failed)
  })

PDF TOOLKIT — tool.pdf  (BROWSER-SIDE, no server)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
WHEN TO USE — you need page images, text, a page count, or a new PDF that
contains only some pages (split / extract). This is generic PDF plumbing, so
the CMS ships it instead of every tool re-implementing it.

WHERE IT RUNS — INSIDE YOUR FRAME. The CMS injects PDF.js 3.11.174 and
pdf-lib 1.17.1 from /vendor/ (same origin) when the field setting
"PDF tools (browser-side)" is on. There is NO endpoint, NO upload, NO server
processing and NO size cap beyond the browser's own memory. The rendered page
is a real canvas, so you get true pixel output.

DETECT SUPPORT
  if (tool.pdf && tool.pdf.available()) { ... }
  // tool.capabilities.pdfTools is the boolean equivalent

SOURCE (every method takes one)
  { binary }   ArrayBuffer or Uint8Array — RECOMMENDED
  { base64 }   raw base64 string
  { dataUrl }  data:application/pdf;base64,...
  { url }      https URL (same-origin or CORS-enabled; when the OCR setting
               is also on the frame CSP allows only same-origin calls, so
               prefer fetching bytes with tool.requestFileBinary)

METHODS (all callback based, callback(errorCode, result), ES5)
  tool.pdf.pageCount(source, cb)
      → (null, 12)

  tool.pdf.renderPage(source, pageNumber, options, cb)
      options: { scale (0.25-4, default 1.5), format 'png'|'jpeg', quality }
      → (null, { pageNumber, width, height, mimeType, dataUrl })
      Page numbers are 1-based.

  tool.pdf.renderRange(source, { first, last }, options, onPage, cb)
      onPage({ pageNumber, width, height, mimeType, dataUrl }) per page
      → (null, { pageCount, rendered })
      Omit the range for the whole document. Hard cap 300 pages per call →
      'too_large' — slice the document instead.

  tool.pdf.extractText(source, { first, last }, cb)
      → (null, { pageCount, pages: [{ pageNumber, text, hasText }] })
      hasText tells you whether a page is a scan (no text layer).

  tool.pdf.split(source, [{ first, last }, ...], cb)
      → (null, [{ first, last, byteLength, bytes: Uint8Array, dataUrl }])
      PDF WRITING (pdf-lib); needs tool.pdf.available().

  tool.pdf.extractPages(source, [3, 5, 9], cb)
      → (null, { byteLength, bytes: Uint8Array, dataUrl })

ERROR CODES
  unsupported     PDF libraries are not injected for this field
  invalid_input   bad source / page number / range
  encrypted_pdf   password-protected PDF
  too_large       more than 300 pages requested at once
  not_found       a { url } source answered 404
  network         a { url } source could not be fetched
  storage_error   a { url } source answered with another non-ok status
  internal_error  PDF.js / pdf-lib failed

PAGE IMAGES → AI (the pattern this toolkit is built for)
Render the page, then ask the platform AI to describe or locate content.
The CMS relays the model call, the frame keeps the pixels:
  1. tool.pdf.renderPage(source, 4, { scale: 2 }, function (err, page) {
       if (err) return
       // page.dataUrl is a PNG of page 4
       // → tool.requestAI(prompt, context, cb) with the page's text, or
       // → the AI vision relay once it ships (see the AI gateway contract)
     })
  2. Crop what you need from page.dataUrl with a canvas — the AI can return
     regions as percentage boxes, and you keep full resolution because you
     render at scale 2+.

ES5 EXAMPLE — split a 40-page PDF into 4 PDFs of 10 pages
  tool.requestFileBinary({ url: pdfUrl }, function (err, res) {
    if (err) { tool.notify('Download failed: ' + err, 'error'); return }
    var ranges = []
    for (var i = 0; i < 40; i += 10) ranges.push({ first: i + 1, last: i + 10 })
    tool.pdf.split({ binary: res.bytes }, ranges, function (splitErr, parts) {
      if (splitErr) { tool.notify('Split failed: ' + splitErr, 'error'); return }
      parts.forEach(function (part) {
        console.log('pages', part.first + '-' + part.last, part.byteLength + ' bytes', part.dataUrl.slice(0, 40))
      })
    })
  })

IMAGE REGENERATION (IMAGE-TO-IMAGE) — tool.requestRegenerateImage(options, callback)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
WHEN TO USE — create a NEW picture based on an existing one ("make this
illustration match our style", "clean up this photo"). The sample image always
travels with the prompt to the platform image-EDIT model
(POST /v1/images/edit). There is NO silent text-to-image fallback: if the
configured model cannot edit, the callback gets 'unsupported'.

Requires: allowImageRegenerate: 'yes'   (default off)

OPTIONS
  sample     { url } | { dataUrl } | { base64 }   the image to base on
  prompt     string, REQUIRED, max 2000 characters (gateway allows 4000)
  preserve   array, default ['composition','subject']
             allowed: composition | subject | style | palette | text
  size       '1024x1024' | '1536x1024' | '1024x1536' | 'auto' (default auto)
  count      1..4 (default 1, field setting maxRegenerateCount, cap 4)
  quality    'low' | 'medium' | 'high' (default high)
  background 'transparent' | 'opaque' (default opaque)
  store      boolean, default true
  toolContext string label used in the audit entry and the stored file name

RESULT
  { ok, requestId, provider, model, images: [{ url, width, height, mimeType,
                              bytes, revisedPrompt }], warnings }
  provider / model are the RESOLVED pair echoed by the gateway — display them
  if you need to, never send them back.

BEHAVIOUR
  • No model and no provider are sent: the gateway owns the image-edit default
    (provider openai, model gpt-image-1). An unsupported override returns 422.
  • The host builds the instruction: the preserved aspects are stated FIRST
    and the caller prompt is applied after them — the prompt can never
    override a preserve rule.
  • Sample validation: JPEG / PNG / WebP, max 5 MB (gateway limit), max
    8000 px per side. Anything else → invalid_input. Third-party sample hosts
    → blocked_host (upload the sample to CMS storage first).
  • Provider moderation runs on the sample AND the prompt; a blocked request
    is 'model_error' with blocked: true and NO file is written.
  • Results are stored in the tenant/tool folder (store: true) and are
    deletable through requestDeleteFile. store: false returns inline data
    URLs (not deletable).
  • revisedPrompt is ALWAYS null for the configured image model (gpt-image-1
    does not produce one). Do NOT build UI that depends on it; show the
    caption you generated instead.
  • background 'transparent' is delivered as PNG (JPEG has no alpha).
  • Limits: 20 calls / hour / user (host); the gateway allows 10 / 60 s per
    tenant. The CMS aborts at 110 s (serverless function budget, D-HTMLT-34) —
    a slow edit returns 'timeout', it is never left hanging.

ES5 EXAMPLE
  tool.requestRegenerateImage({
    sample: { url: originalImageUrl },
    prompt: 'turn it into a flat vector illustration for a course card',
    preserve: ['composition', 'subject'],
    size: '1536x1024',
    count: 2,
    toolContext: 'course-card'
  }, function (err, res) {
    if (err === 'unsupported') { tool.notify('This deployment cannot edit images', 'warning'); return }
    if (err === 'model_error') { tool.notify('The image model refused this request', 'warning'); return }
    if (err) { tool.notify('Regeneration failed: ' + err, 'error'); return }
    res.images.forEach(function (img) { addVariant(img.url) })
  })

AI CHAT SESSIONS — STANDARD CMS OBJECT TYPE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Any html-tool that implements AI-powered chat MUST use the CMS object type
`ai-chat-sessions-uniconbaseapps` to persist conversation history. This ensures
all AI conversations across all tools are stored in a single, queryable type
that the admin can audit centrally via Object Manager.

── WHY ───────────────────────────────────────────────────────────────────────
  • tool.setValue() is stored in a single Firestore document (1MB limit).
    Chat history grows unbounded and WILL exceed this limit.
  • tool.requestObjects() stores each chat session as a separate document.
    Each session can hold thousands of messages without hitting limits.
  • Using a SHARED type name means ALL tools contribute to the same pool,
    enabling cross-tool search, audit, and analytics.

── TYPE NAME ─────────────────────────────────────────────────────────────────
  mainObjectType: 'ai-chat-sessions-uniconbaseapps'
  scope: 'instance' (each CMS record's chats are private to that record)

── SESSION OBJECT SHAPE ──────────────────────────────────────────────────────
  Each session document has:
    • name       — auto-generated from the first user message (truncated to 60 chars)
    • productData.data_categoriesBased:
        • messages    — array of message objects (see below)
        • createdAt   — ISO 8601 timestamp (set on create)
        • updatedAt   — ISO 8601 timestamp (updated on every message)
        • createdBy   — { userId, userName } from tool.getUser()

── MESSAGE OBJECT — MANDATORY FIELDS ─────────────────────────────────────────
  Every message in the messages array MUST include these fields:

    {
      role:      'user' | 'ai',          // who sent it
      text:      'message content',       // plain text
      time:      '2026-07-26T12:34:56Z', // ISO 8601
      userId:    'usr_abc123',            // from tool.getUser().id
      userName:  'John Doe'               // from tool.getUser().name
    }

  These fields are REQUIRED for every message. They enable:
    • Audit trails (who asked what, when)
    • Central browsing (admin can see all chats with user identities)
    • Cross-tool compatibility (any tool can read any chat)

── MESSAGE OBJECT — OPTIONAL TOOL-SPECIFIC FIELDS ────────────────────────────
  Each tool MAY add custom fields to message objects as needed. Examples:

    • diffHtml      (string)  — VibeCoding: rendered diff tabs HTML
    • attachmentUrl (string)  — Document writer: link to generated file
    • metadata      (object)  — Any JSON-serializable tool data
    • isError       (boolean) — Whether this was an error response
    • options       (array)   — Interview mode: clickable option buttons shown

  Rules for optional fields:
    1. Field names SHOULD be descriptive and use camelCase
    2. Values MUST be JSON-serializable (strings, numbers, booleans, arrays, objects)
    3. Do NOT store large binary data — use tool.requestUpload() and store the URL
    4. Other tools reading this session SHOULD ignore unknown optional fields
    5. The mandatory fields above MUST always be present

── CRUD OPERATIONS ───────────────────────────────────────────────────────────

  CREATE a new session:
    tool.requestObjects('create', {
      mainObjectType: 'ai-chat-sessions-uniconbaseapps',
      name: 'Chat about Invoice Manager',
      productData: {
        data_categoriesBased: {
          messages: [
            { role:'user', text:'Build an invoice app', time:..., userId:..., userName:... },
            { role:'ai',   text:'Sure! Here is the code...', time:..., userId:'ai', userName:'AI' }
          ],
          createdAt: new Date().toISOString(),
          updatedAt: new Date().toISOString(),
          createdBy: { userId: tool.getUser().id, userName: tool.getUser().name }
        }
      }
    }, callback)

  QUERY all sessions for this CMS record (instance scope auto-filters):
    tool.requestObjects('query', {
      mainObjectType: 'ai-chat-sessions-uniconbaseapps'
    }, callback)
    // Returns { objects: [...] } — sort by updatedAt descending client-side

  UPDATE a session (append a new message):
    tool.requestObjects('update', {
      mainObjectType: 'ai-chat-sessions-uniconbaseapps',
      objectId: existingSession.id,
      productData: {
        data_categoriesBased: {
          messages: existingSession.productData.data_categoriesBased.messages.concat([newMessage]),
          updatedAt: new Date().toISOString()
        }
      }
    }, callback)

  DELETE a session:
    tool.requestObjects('delete', {
      mainObjectType: 'ai-chat-sessions-uniconbaseapps',
      objectId: sessionId
    }, callback)

── AUTHORIZATION ─────────────────────────────────────────────────────────────
  The admin must add this to the html-tool field's settings.allowedObjectTypes:
    {
      mainObjectType: 'ai-chat-sessions-uniconbaseapps',
      role: 'editor',
      scope: 'instance'
    }

  Without this, tool.requestObjects() calls for this type will fail.
  The tool MUST call tool.reportMissingParams() if the type is not authorized.

── BEST PRACTICES ────────────────────────────────────────────────────────────
  1. Keep the tool's OWN data (code, config, state) in tool.setValue() —
     do NOT duplicate it into chat sessions.
  2. Each chat session stores ONLY conversation messages.
  3. When building AI prompts, inject current tool state (from tool.getValue())
     as RAG context — do not rely on historical chat data for tool state.
  4. Limit messages per session to ~500 by auto-creating a new session when
     the current one gets too long (prevents any single document from
     approaching the 1MB Firestore limit).
  5. For AI messages, use userId: 'ai' and userName: 'AI Assistant'.

NAMING METHODOLOGY (CRITICAL)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

── NAMESPACE CONVENTION ───────────────────────────────────────────────────────

  SHARED (default):      <typeName>-<developerSubdomain>
      e.g. taskSprints-uniconbaseapps, taskItems-uniconbaseapps
      Accessible to ALL tools and apps published by this developer.
      Use this when multiple apps need to share the same data.

  ISOLATED:              <toolId>.<typeName>-<developerSubdomain>
      e.g. ptm.taskSprints-uniconbaseapps
      Private to one specific tool. The toolId prefix (dot-separated) 
      prevents accidental cross-tool access. Use this when data must
      stay isolated — e.g. internal tool state, draft-only data.

  • The developer subdomain is ALWAYS required (matches app-store convention).
  • The dot separates the isolation prefix from the type name.
  • Never use bare names like 'products' or 'tasks' — they pollute
    the global namespace and will collide with other developers.

── GRADUATION PATH ────────────────────────────────────────────────────────────

  When a tool-created type matures and needs a dedicated management UI:

  1. Register it in CMS Settings (App Designer) under the SAME name.
     e.g. register taskSprints-uniconbaseapps as-is — no rename needed.
  2. Define its field groups and fields.
  3. Existing data persists — the type name doesn't change.
  4. It now appears in ObjectManager, reporting, and the catalog.

  Shared types can graduate without migration.
  Isolated types (toolId prefixed) should stay isolated — if you later
  want to share, migrate data to a shared type name first.

── DISCOVERY ──────────────────────────────────────────────────────────────────

  To see all types created by html-tools (including unregistered ones):
  • Open App Designer → "Unregistered Types" panel
    This lists every mainObjectType found in om_objectTypes that isn't
    yet registered in CMS Settings, with a one-click Register button.
  • Or query directly: check om_objectTypes_<tenant> collection —
    each document's mainObjectType field tells you which type it belongs to.

── RULES ──────────────────────────────────────────────────────────────────────

1. ALWAYS namespace new types: <typeName>-<developerSubdomain>.
   Add <toolId>. prefix for isolated types.
2. Use EXISTING mainObjectType values from the catalog above whenever possible.
3. Use EXACT field IDs from the catalog — never guess them.
4. Document new types in settings.allowedObjectTypes so the admin can
   audit which tools own which types.
5. Prefer reusing existing shared types from your developer namespace.
6. New types auto-create a default folder on first use via _ensureObjectFolder.
7. Default folder is named "Default" in om_objectTypes_<tenant> — this is
   what makes the type discoverable in the Unregistered Types panel.
8. Use scope: 'shared' for data shared across instances (e.g. sprints,
   shared definitions). Use scope: 'instance' for data private per
   CMS record (e.g. tasks, private notes, user-specific items).

HARD RULES
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
✗  No <script>, <style>, <html>, <head>, <body>, <!DOCTYPE> tags in any field
✗  No DOMContentLoaded or window.onload — use tool.onReady instead
✗  No localStorage or sessionStorage
✗  No fetch to external URLs (sandboxed: allow-scripts, allow-forms, allow-downloads, allow-popups)
✗  No alert(), confirm(), or prompt()
✗  No raw postMessage calls — always use the tool.* SDK
✓  tool.getParentPageUrl() returns ORIGIN + PATHNAME only — the host strips
   the query string and hash before sending (they can carry auth tokens).
   Treat the value as display/share data, never as an authorization signal.
✓  Every tool carries a VISIBLE build number: var TOOL_BUILD = 'YYYY-MM-DD-rN'
   in the [JS] block, rendered as a small badge in the UI and logged on boot
   as the FIRST console line; per-file first-line stamps track which of the
   three files changed. See GLOBAL REQUIREMENT - VISIBLE TOOL BUILD NUMBER.
✓  Inline-script tokenizer safety: never a raw <!-- unless --> closes it on
   the SAME line, never a raw </script anywhere (write <\/script), never
   <script src="https://cdn…"> or external <link> from the three files.
   See GLOBAL REQUIREMENT - INLINE-SCRIPT TOKENIZER SAFETY.
✓  Always call tool.declareParams() for EVERY param your tool reads
✓  Always call tool.reportMissingParams() inside tool.onReady() if required
   params are missing — this triggers a warning banner in the CMS UI so
   the admin can fix the configuration without digging through JSON.
✗  No external <script src="https://cdn…"> / <link> / fonts / fetch-XHR from
   the three files — everything must be inlined in the three files or come
   through the parent CMS relay (tool.requestFileBinary / tool.requestObjects).
   A stalled CDN script freezes the whole tool.
✓  Values can be any JSON type — save objects/arrays freely with tool.setValue()
✓  tool.requestAI / tool.requestAIStream / tool.requestUpload /
   tool.requestUploadBinary / tool.requestGenerateImage /
   tool.requestFileContent / tool.requestObjects / tool.requestExportPdf /
   tool.requestSendEmail / tool.requestDeleteFile /
   tool.requestRegenerateImage / tool.requestAIVision ARE exceptions to the
   no-fetch rule — they go through the parent CMS, not direct from the
   iframe. tool.pdf runs inside the frame and needs no exception.
✓  Each request* method requires its allow*: 'yes' toolParam. The admin
   configures this. Without it, the callback fires with an error —
   handle this gracefully in your code.
✓  All request* methods are asynchronous. Use callbacks, not return values.
✓  tool.requestAI: 1 concurrent request, 120s timeout, dynamic model-aware
   prompt limit (~2.4M chars for DeepSeek V4 Pro). Prompts exceeding the
   model's context window are truncated; check the error param for notice.
✓  tool.requestObjects: max 500 operations per batch. Avoid batching
   operations that would exceed 10 MB total (Firestore writeBatch limit).
✓  Batch operations are ATOMIC — if one fails, the entire batch is rolled
   back. Design your batch workflows with this guarantee in mind.
✓  Unregistered mainObjectTypes auto-create a default folder on first use.
   You do NOT need the CMS admin to pre-register types for your tool to work.
✓  Emails sent via tool.requestSendEmail are automatically wrapped in the
   CMS-branded email template with header/footer/borders — you only provide
   the body content. The title is displayed prominently in the email header.
✓  tool.requestExportPdf exports as an HTML document that can be printed to
   PDF via browser Print → Save as PDF. Use attachments: [] in
   requestSendEmail to attach exported files to emails.
✓  Always produce complete, functional code — no placeholders, no TODO comments.
