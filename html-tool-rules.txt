── Parameter severity levels ─────────────────────────  
Each declared param can specify a `severity` field that controls how the CMS
notifies the admin about unconfigured parameters:

  severity: 'mandatory'
    → Shows a RED/AMBER WARNING BANNER above the iframe (blocking).
    → Banner text: "This tool requires configuration. X mandatory parameter(s) missing."
    → "Configure" button opens the param form.
    → The tool likely won't function without these.

  severity: 'goodToHave'
    → Shows a SUBTLE INFO BAR below the iframe (non-blocking).
    → The bar has a ℹ️ icon + text: "X optional parameter(s) available".
    → Clicking the bar expands a tooltip listing each param with hints
      and instructions on where to configure them.
    → ONLY visible to developer, admin, and owner roles (not regular users).
    → Does NOT block form save or show as a warning.

  severity: 'optional' or no severity field (default)
    → No warning, no bar, no indicator.  Completely silent.
    → The param is documented for discovery but not expected to be configured.

BACKWARD COMPATIBILITY: If a param entry has no "severity" field, it is treated
as "optional" — no warning is shown.  To make a param required, explicitly set
severity: 'mandatory'.

Example declaration with severity:
  tool.declareParams([
    {
      name: 'documentTemplates',
      label: 'Document Templates',
      type: 'text',
      default: '',
      severity: 'mandatory',
      hint: 'Comma-separated pipe-delimited list. Format: Name|templateUrl|accept|required|Category.'
    },
    {
      name: 'sinLabel',
      label: 'SIN Label',
      type: 'text',
      default: 'SIN / SSN',
      severity: 'optional',
      hint: "Override label for the SIN field. Defaults to 'SIN / SSN'."
    },
    {
      name: 'showDebugPanel',
      label: 'Show Debug Panel',
      type: 'toggle',
      default: 'no',
      severity: 'goodToHave',
      hint: 'Enable to show a developer debug panel in the tool UI.'
    }
  ])

── Missing parameter reporting (★ RECOMMENDED) ────────
tool.reportMissingParams(missing, message)
    → tell the parent CMS app that required parameters are NOT configured.
      The CMS will show a warning banner with a "Configure" button that
      opens a dynamic form so the admin can fill in the missing values
      and apply them directly to the field settings.

      • missing — array of { name, label, type, default, hint, reason, severity? }
        Each entry describes ONE parameter the tool needs.  `name` must
        match a key declared via tool.declareParams().  `reason` is a
        short sentence explaining WHY the tool needs this param (e.g.
        "Must point to the CMS object type that holds vehicle records").
        `severity` is optional — if omitted, the CMS treats the param as
        'optional' (silent, no indicator).  To trigger a warning, explicitly
        set severity: 'mandatory' on the entry.
      • message — string (optional), a human-readable summary shown at
        the top of the warning banner.  Example:
        "This tool needs 3 parameters configured before it can work."

      ALWAYS call tool.reportMissingParams() inside tool.onReady() after
      checking tool.param() for each required key.  The CMS will:
        1. Show an amber warning banner above the tool iframe
        2. List all missing parameters with their labels and hints
        3. Provide a "Configure Parameters" button
        4. Open a dynamic form pre-filled with defaults from declareParams()
        5. Let the admin fill in the values and apply them directly
        6. Reload the tool with the new parameter values

      Example (inside tool.onReady):
        var missing = []
        var vType = tool.param('vehiclesTypeId')
        var sType = tool.param('staffTypeId')
        if (!vType) missing.push({
          name: 'vehiclesTypeId', label: 'Vehicles Type ID',
          type: 'text', default: 'vehicles-uniconbaseapps',
          hint: 'CMS object type for vehicle records',
          reason: 'Cannot load vehicle data without a type ID',
          severity: 'mandatory'
        })
        if (!sType) missing.push({
          name: 'staffTypeId', label: 'Staff Type ID',
          type: 'text', default: 'staff-uniconbaseapps',
          hint: 'CMS object type for staff records',
          reason: 'Cannot load staff data without a type ID',
          severity: 'mandatory'
        })
        if (missing.length) {
          tool.reportMissingParams(missing,
            'Tool parameters must be configured before this tool can display data.')
        }

      The parent CMS also automatically detects missing params by comparing
      tool.declareParams() declarations against the configured
      settings.toolParams — even without an explicit reportMissingParams call.
      However, calling reportMissingParams() explicitly gives the admin a
      much clearer error message and lets you mark params as truly required
      (as opposed to optional ones with sensible defaults).

      The CMS respects the `severity` field on each declaration:
        • mandatory     → warning banner above the iframe (same as before)
        • goodToHave    → subtle info bar below the iframe (dev/admin/owner only)
        • optional      → silent (no indicator)
        • no severity   → treated as 'optional' (silent) for backward compat.

── AI Prompt Relay ────────────────────────────────────
tool.requestAI(prompt, context, callback)

Sends a prompt to the CMS AI service and returns the response text.

  • prompt   — string, the main prompt/question to send
  • context  — string (optional), supporting background information that
               helps the AI understand the situation
  • callback — function(error, responseText)
      error        — null on success; string describing the problem on failure.
                     On truncation: error contains a warning but response is
                     still returned. Example: "Prompt was truncated from
                     150,000 to 1,200,000 characters."
                     Always check response even when error is non-null.
      responseText — the AI's text response, or null on complete failure

Limits: 120 second timeout per request.
        1 concurrent requests maximum (additional requests are queued).
        Dynamic prompt limit based on the AI model's context window
        (e.g. ~2.4M chars for DeepSeek V4 Pro, ~307K for GPT-5 Nano).
        Prompts exceeding the model limit are truncated; check the error
        param for a truncation notice.
        The AI Gateway is called directly from the browser via a JWT token
        (no server-side proxy bottleneck).
Requires: allowAi: 'yes' in toolParams.

Example:
  tool.requestAI('Summarize this data', JSON.stringify(tableData),
    (err, response) => {
      if (err) { tool.notify('AI error: ' + err, 'warning') }
      if (response) showSummary(response)
    })

── AI Streaming Relay (★ Live token-by-token) ─────────
tool.requestAIStream(prompt, context, callbacks)

Sends a prompt to the CMS AI service and receives tokens in real-time as the
AI generates them — exactly like Copilot Chat.  Use this for "thinking bubble"
UIs, live typewriter effects, or progressive rendering.

  • prompt    — string, the main prompt/question to send
  • context   — string (optional), supporting background information
  • callbacks — object with optional handlers:
      onToken(token)       — called for EACH text chunk as it arrives from the AI.
                              `token` is a short string (typically a few chars to
                              a few words).  Append it to your streaming display.
      onComplete(fullText) — called when the stream finishes successfully.
                              `fullText` is the complete accumulated response.
      onError(error)       — called on failure.  `error` is a string describing
                              the problem (network error, timeout, permission denied).

Limits: Same dynamic model-aware prompt limit and timeout as requestAI.
        No concurrency queue — each call is independent.
        The CMS parent sends ai-stream-start first, then ai-stream-token for each
        chunk, then ai-stream-end on completion, or ai-stream-error on failure.
Requires: allowAi: 'yes' in toolParams.

Example (live typewriter in a thinking bubble):
  tool.requestAIStream('Generate a project summary', projectContext, {
    onToken: function(token) {
      // Append each token to a live-display element
      var el = document.getElementById('stream-output')
      el.textContent += token
      el.scrollTop = el.scrollHeight
    },
    onComplete: function(fullText) {
      tool.notify('AI response complete', 'success')
      processResponse(fullText)
    },
    onError: function(err) {
      tool.notify('AI stream error: ' + err, 'error')
    }
  })

── PDF Export ───────────────────────────────────────── 
tool.requestExportPdf(options, callback)

Generates a printable HTML document from the provided content, uploads it to
CMS Storage, and returns the file URL. The user can open it in a browser tab
and use Print → Save as PDF to create the final PDF.

  • options — { html?, filename?, landscape? }
      html      — string, HTML body content to export. If omitted, the system
                  uses the tool's current DOM body content.
      filename  — string, base filename without extension (default: 'export').
                  The returned file will be named like 'export.html'.
      landscape — boolean, hint for print orientation. Informational only;
                  the user selects orientation in the print dialog.
  • callback — function(error, file)
      error — null on success, or string describing the problem
      file  — { name, url, size, type } on success.
              name: filename.html
              url:  publicly accessible URL (open in new tab to print)
              size: HTML document size in bytes
              type: 'text/html'
Requires: allowExportPdf: 'yes' in toolParams.

Example:
  tool.requestExportPdf({
    html: '<h1>Monthly Report</h1><table>...</table>',
    filename: 'monthly-report'
  }, (err, file) => {
    if (err) { tool.notify('Export failed: ' + err, 'error'); return }
    tool.notify('Report exported: ' + file.url, 'success')
    tool.openUrl(file.url)  // user prints from here
  })

  // Export current tool DOM content:
  tool.requestExportPdf({ filename: 'data-export' }, (err, file) => {
    if (!err) tool.openUrl(file.url)

── Send Email ─────────────────────────────────────────  
tool.requestSendEmail(options, callback)

Sends an email through the CMS email system (AWS SES / nodemailer). The body
content you provide is automatically wrapped in the standard branded email
template with header, footer, and borders — you only provide the inner body HTML.

  • options — { to, subject, htmlBody, title?, attachments? }
      to          — string, recipient email address (required)
      subject     — string, email subject line (required)
      htmlBody    — string, HTML body content — gets wrapped in the branded
                    template automatically (required)
      title       — string, optional large title shown in the email header.
                    Defaults to the subject if omitted.
      attachments — array of { filename, url }, files to attach.
                    Use tool.requestUpload() first to get file URLs, then
                    pass them here. Each attachment: { filename: 'report.pdf',
                    url: 'https://storage.../report.pdf' }
  • callback — function(error, result)
      error  — null on success, or string describing the problem
      result — { ok: true } on success
Requires: allowSendEmail: 'yes' in toolParams.
The CMS must have email sender configured in website settings.

Example:
  tool.requestSendEmail({
    to: 'customer@example.com',
    subject: 'Your Invoice #INV-0042',
    title: 'Invoice',
    htmlBody: '<h1>Invoice</h1><p>Thank you for your order. Total: $447.95</p>'
  }, (err, result) => {
    if (err) { tool.notify('Email failed: ' + err, 'error'); return }
    tool.notify('Email sent!', 'success')
  })

  // With attachment — upload first, then attach:
  tool.requestUpload('.pdf', (err, file) => {
    if (err) return
    tool.requestSendEmail({
      to: 'client@example.com',
      subject: 'Your Report',
      htmlBody: '<p>Please find the report attached.</p>',
      attachments: [{ filename: file.name, url: file.url }]
    }, (err2, result) => {
      tool.notify(err2 ? 'Email failed' : 'Sent with attachment',
        err2 ? 'error' : 'success')
    })
  })

── Object CRUD (Multi-Type CMS Database Access) ───────
tool.requestObjects(action, params, callback)

Performs CRUD operations on CMS objects across ANY mainObjectType the tool
is authorized for. This allows you to build full applications (product databases,
inventory systems, invoice workflows, ERP modules, etc.) with the CMS as your
database, using a completely custom UI you design.

Each CMS object is a Firestore document with up to 1MB of data. You can store
unlimited objects across unlimited types.

  • action   — string: 'query' | 'get' | 'create' | 'update' | 'delete' | 'batch'
  • params   — object, varies by action (see below)
  • callback — function(error, result)
      error  — null on success, or string describing the problem
      result — varies by action (see below)

── Actions ───────────────────────────────────────────────────────────────────

  query:  { mainObjectType, typeId? }
          • typeId is optional — omit to query all folders of that type
          result: { objects: [...] } — array of full CMS objects

  get:    { mainObjectType, objectId }
          result: { object: {...} } — single CMS object or null if not found

  create: { mainObjectType, typeId?, name, productData: { data_categoriesBased: {...} } }
          • typeId is optional — omit to use the default auto-created folder
          • name: human-readable name for the object
          • productData.data_categoriesBased: { fieldId: value, ... }
            fieldId must match a field defined in the CMS for this type
          result: { object: {...} } — the newly created CMS object

  update: { mainObjectType, objectId, productData: { data_categoriesBased: {...} }, name? }
          • Only include fields you want to change — partial updates are supported
          • Omit productData to only update the name, or vice versa
          result: { ok: true }

  delete: { mainObjectType, objectId }
          • This permanently deletes the object — no undo
          result: { ok: true }

  batch:  { operations: [{ action, mainObjectType, typeId?, objectId?, name?, productData? }, ...] }
          • Execute multiple operations across ANY authorized types in a single
            atomic transaction
          • All operations succeed or all fail (Firestore writeBatch guarantee)
          • Max 500 operations per batch
          • Each operation has the same shape as its individual action
          result: { ok: true, results: [...] } — array of per-operation results

── Object shape ──────────────────────────────────────────────────────────────
Each CMS object returned by query/get/create has this structure:

  {
    id, _id, contentId,          // identity fields (id is the primary key)
    name, slug,                   // display fields (name is human-readable)
    cmsObjectType,                // the mainObjectType string
    typeId,                       // folder/category ID the object belongs to
    tenantId,                     // multi-tenant scoping (automatic)
    productData: {                // the actual configurable data
      data_categoriesBased: {     // field values keyed by field ID
        fieldId1: value1,         // value type depends on field definition
        fieldId2: value2,         // can be string, number, boolean, array, object
        ...
      }
    },
    _parentObjectId,               // parent CMS record ID (for 'instance' scope)
    permissions: { ... },         // access control (automatic)
    created, updated              // ISO timestamp strings
  }

── Authorization ─────────────────────────────────────────────────────────────
The CMS admin must configure two settings on the html-tool field:

  settings.allowObjectCRUD: 'yes'           ← enables tool.requestObjects()
  settings.allowedObjectTypes: [            ← which CMS types the tool can access
    { mainObjectType: 'taskSprints-uniconbaseapps', role: 'editor', scope: 'shared' },
    { mainObjectType: 'taskItems-uniconbaseapps',   role: 'editor', scope: 'instance' },
  ]

  • 'viewer' role — only query and get are allowed; write operations blocked
  • 'editor' role — all actions including create, update, delete, batch
  • scope: 'shared' (default) — data visible across ALL instances of this tool
  • scope: 'instance' — data isolated to the specific CMS record. Query
    auto-filters by the parent object; get/update/delete verify ownership.
    All created objects are automatically stamped with _parentObjectId.
  • mainObjectType can be any string — types do NOT need to be pre-registered
    in CMS settings. The bridge auto-creates a default folder on first use.
  • All operations go through CMS permissions automatically. You don't need
    to manage permissions yourself.
  • Data is stored in om_private_objects and is visible in the
    standard ObjectManager UI if the type is registered in CMS Settings.

── Tenant-level parameter overrides ──────────────────────────────────────────
  For connected tools (from Application Store or My Tools), the tool's
  built-in toolParams serve as remote defaults.  Tenants can override
  individual parameters without modifying the upstream definition by
  setting settings.localToolParams in the Field Group Designer:

    settings.toolParams      = { "currency": "USD", "max": 100 }    ← remote
    settings.localToolParams = { "currency": "EUR" }                ← tenant override

  Effective params at runtime: { "currency": "EUR", "max": 100 }
  Local overrides always win.  This is the same pattern as
  TenantProfileCustomizer for cmsObjectType remote apps.

  • Use settings.toolParams for the tool's default configuration
    (set at install time from the tool source).
  • Use settings.localToolParams for tenant-specific overrides
    (e.g. pointing to a different CMS object type, changing currency).
  • When the tool source is updated, the remote toolParams may change,
    but localToolParams always take precedence for the keys they define.
  • Leave localToolParams empty to use remote defaults as-is.

── Connected tool settings locking ───────────────────────────────────────────
  When a tool is connected (connectionMode: 'connected-app-store' or
  'connected-my-tools'), the Field Group Designer shows two sub-tabs:

    ✏️ Local Properties   — editable settings under tenant control
    🔒 Remote (source)    — read-only display of remote-managed settings

  🔒 Remote-managed (read-only, shown for reference):
    connectionMode    — the tool IS connected, cannot switch to standalone
    connectedToolId   — identifies the source tool
    htmlCode          — fetched live from the tool source at render time
    cssCode           — fetched live from the tool source at render time
    jsCode            — fetched live from the tool source at render time
    toolUrl           — external URL, if set by the tool source
    toolParams        — remote defaults; use localToolParams to override

  ✏️ Tenant-controlled (editable, saved with field group):
    localToolParams   — overrides specific remote toolParams keys
    displayMode       — inline / popup / drawer / toolbar-strip
    height, autoHeight, stripHeight
    triggerLabel, triggerWidth
    showJsonOutput, showEventLog
    validationEnabled
    allowObjectCRUD, allowedObjectTypes
    outputSchema

  At runtime, only code fields (htmlCode, cssCode, jsCode, toolUrl) are
  fetched from the remote source.  All other settings — display, sizing,
  validation, CRUD config — are under full tenant control and saved in
  the field group definition.  Changing height or displayMode for a
  connected tool works correctly and is NOT overridden by the remote.

  Parameter overrides follow the merge pattern:
    mergedToolParams = { ...remoteToolParams, ...localToolParams }

  Local wins where both define the same key.  Leave localToolParams
  empty to use the remote defaults as-is.

AI CHAT SESSIONS — STANDARD CMS OBJECT TYPE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Any html-tool that implements AI-powered chat MUST use the CMS object type
`ai-chat-sessions-uniconbaseapps` to persist conversation history. This ensures
all AI conversations across all tools are stored in a single, queryable type
that the admin can audit centrally via Object Manager.

── WHY ───────────────────────────────────────────────────────────────────────
  • tool.setValue() is stored in a single Firestore document (1MB limit).
    Chat history grows unbounded and WILL exceed this limit.
  • tool.requestObjects() stores each chat session as a separate document.
    Each session can hold thousands of messages without hitting limits.
  • Using a SHARED type name means ALL tools contribute to the same pool,
    enabling cross-tool search, audit, and analytics.

── TYPE NAME ─────────────────────────────────────────────────────────────────
  mainObjectType: 'ai-chat-sessions-uniconbaseapps'
  scope: 'instance' (each CMS record's chats are private to that record)

── SESSION OBJECT SHAPE ──────────────────────────────────────────────────────
  Each session document has:
    • name       — auto-generated from the first user message (truncated to 60 chars)
    • productData.data_categoriesBased:
        • messages    — array of message objects (see below)
        • createdAt   — ISO 8601 timestamp (set on create)
        • updatedAt   — ISO 8601 timestamp (updated on every message)
        • createdBy   — { userId, userName } from tool.getUser()

── MESSAGE OBJECT — MANDATORY FIELDS ─────────────────────────────────────────
  Every message in the messages array MUST include these fields:

    {
      role:      'user' | 'ai',          // who sent it
      text:      'message content',       // plain text
      time:      '2026-07-26T12:34:56Z', // ISO 8601
      userId:    'usr_abc123',            // from tool.getUser().id
      userName:  'John Doe'               // from tool.getUser().name
    }

  These fields are REQUIRED for every message. They enable:
    • Audit trails (who asked what, when)
    • Central browsing (admin can see all chats with user identities)
    • Cross-tool compatibility (any tool can read any chat)

── MESSAGE OBJECT — OPTIONAL TOOL-SPECIFIC FIELDS ────────────────────────────
  Each tool MAY add custom fields to message objects as needed. Examples:

    • diffHtml      (string)  — VibeCoding: rendered diff tabs HTML
    • attachmentUrl (string)  — Document writer: link to generated file
    • metadata      (object)  — Any JSON-serializable tool data
    • isError       (boolean) — Whether this was an error response
    • options       (array)   — Interview mode: clickable option buttons shown

  Rules for optional fields:
    1. Field names SHOULD be descriptive and use camelCase
    2. Values MUST be JSON-serializable (strings, numbers, booleans, arrays, objects)
    3. Do NOT store large binary data — use tool.requestUpload() and store the URL
    4. Other tools reading this session SHOULD ignore unknown optional fields
    5. The mandatory fields above MUST always be present

── CRUD OPERATIONS ───────────────────────────────────────────────────────────

  CREATE a new session:
    tool.requestObjects('create', {
      mainObjectType: 'ai-chat-sessions-uniconbaseapps',
      name: 'Chat about Invoice Manager',
      productData: {
        data_categoriesBased: {
          messages: [
            { role:'user', text:'Build an invoice app', time:..., userId:..., userName:... },
            { role:'ai',   text:'Sure! Here is the code...', time:..., userId:'ai', userName:'AI' }
          ],
          createdAt: new Date().toISOString(),
          updatedAt: new Date().toISOString(),
          createdBy: { userId: tool.getUser().id, userName: tool.getUser().name }
        }
      }
    }, callback)

  QUERY all sessions for this CMS record (instance scope auto-filters):
    tool.requestObjects('query', {
      mainObjectType: 'ai-chat-sessions-uniconbaseapps'
    }, callback)
    // Returns { objects: [...] } — sort by updatedAt descending client-side

  UPDATE a session (append a new message):
    tool.requestObjects('update', {
      mainObjectType: 'ai-chat-sessions-uniconbaseapps',
      objectId: existingSession.id,
      productData: {
        data_categoriesBased: {
          messages: existingSession.productData.data_categoriesBased.messages.concat([newMessage]),
          updatedAt: new Date().toISOString()
        }
      }
    }, callback)

  DELETE a session:
    tool.requestObjects('delete', {
      mainObjectType: 'ai-chat-sessions-uniconbaseapps',
      objectId: sessionId
    }, callback)

── AUTHORIZATION ─────────────────────────────────────────────────────────────
  The admin must add this to the html-tool field's settings.allowedObjectTypes:
    {
      mainObjectType: 'ai-chat-sessions-uniconbaseapps',
      role: 'editor',
      scope: 'instance'
    }

  Without this, tool.requestObjects() calls for this type will fail.
  The tool MUST call tool.reportMissingParams() if the type is not authorized.

── BEST PRACTICES ────────────────────────────────────────────────────────────
  1. Keep the tool's OWN data (code, config, state) in tool.setValue() —
     do NOT duplicate it into chat sessions.
  2. Each chat session stores ONLY conversation messages.
  3. When building AI prompts, inject current tool state (from tool.getValue())
     as RAG context — do not rely on historical chat data for tool state.
  4. Limit messages per session to ~500 by auto-creating a new session when
     the current one gets too long (prevents any single document from
     approaching the 1MB Firestore limit).
  5. For AI messages, use userId: 'ai' and userName: 'AI Assistant'.

NAMING METHODOLOGY (CRITICAL)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

── NAMESPACE CONVENTION ───────────────────────────────────────────────────────

  SHARED (default):      <typeName>-<developerSubdomain>
      e.g. taskSprints-uniconbaseapps, taskItems-uniconbaseapps
      Accessible to ALL tools and apps published by this developer.
      Use this when multiple apps need to share the same data.

  ISOLATED:              <toolId>.<typeName>-<developerSubdomain>
      e.g. ptm.taskSprints-uniconbaseapps
      Private to one specific tool. The toolId prefix (dot-separated) 
      prevents accidental cross-tool access. Use this when data must
      stay isolated — e.g. internal tool state, draft-only data.

  • The developer subdomain is ALWAYS required (matches app-store convention).
  • The dot separates the isolation prefix from the type name.
  • Never use bare names like 'products' or 'tasks' — they pollute
    the global namespace and will collide with other developers.

── GRADUATION PATH ────────────────────────────────────────────────────────────

  When a tool-created type matures and needs a dedicated management UI:

  1. Register it in CMS Settings (App Designer) under the SAME name.
     e.g. register taskSprints-uniconbaseapps as-is — no rename needed.
  2. Define its field groups and fields.
  3. Existing data persists — the type name doesn't change.
  4. It now appears in ObjectManager, reporting, and the catalog.

  Shared types can graduate without migration.
  Isolated types (toolId prefixed) should stay isolated — if you later
  want to share, migrate data to a shared type name first.

── DISCOVERY ──────────────────────────────────────────────────────────────────

  To see all types created by html-tools (including unregistered ones):
  • Open App Designer → "Unregistered Types" panel
    This lists every mainObjectType found in om_objectTypes that isn't
    yet registered in CMS Settings, with a one-click Register button.
  • Or query directly: check om_objectTypes_<tenant> collection —
    each document's mainObjectType field tells you which type it belongs to.

── RULES ──────────────────────────────────────────────────────────────────────

1. ALWAYS namespace new types: <typeName>-<developerSubdomain>.
   Add <toolId>. prefix for isolated types.
2. Use EXISTING mainObjectType values from the catalog above whenever possible.
3. Use EXACT field IDs from the catalog — never guess them.
4. Document new types in settings.allowedObjectTypes so the admin can
   audit which tools own which types.
5. Prefer reusing existing shared types from your developer namespace.
6. New types auto-create a default folder on first use via _ensureObjectFolder.
7. Default folder is named "Default" in om_objectTypes_<tenant> — this is
   what makes the type discoverable in the Unregistered Types panel.
8. Use scope: 'shared' for data shared across instances (e.g. sprints,
   shared definitions). Use scope: 'instance' for data private per
   CMS record (e.g. tasks, private notes, user-specific items).

tool.onReady((val, fields) => {
  render(val, fields)               // initial draw — value + all sibling fields
  if (tool.isReadOnly()) lockUI()   // read-only may be active on first load

  tool.onValueChange(v  => render(v))
  tool.onFieldsChange(f => syncFields(f))
  tool.onReadonlyChange(ro => lockUI(ro))
})

Replace render / syncFields / lockUI with your actual functions.
Never skip isReadOnly() inside onReady — the form can be in read-only
mode on the very first load.
Always define tool.onReady as your single entry point — never use
DOMContentLoaded, window.onload, or inline onload attributes.

HARD RULES
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
✗  No <script>, <style>, <html>, <head>, <body>, <!DOCTYPE> tags in any field
✗  No DOMContentLoaded or window.onload — use tool.onReady instead
✗  No localStorage or sessionStorage
✗  No fetch to external URLs (sandboxed: allow-scripts, allow-forms, allow-downloads, allow-popups)
✗  No alert(), confirm(), or prompt()
✗  No raw postMessage calls — always use the tool.* SDK
✓  Always call tool.declareParams() for EVERY param your tool reads
✓  Always call tool.reportMissingParams() inside tool.onReady() if required
   params are missing — this triggers a warning banner in the CMS UI so
   the admin can fix the configuration without digging through JSON.
✓  External CDN <script> tags ARE allowed inside the HTML field
   (e.g. Chart.js, Sortable, DataTables, SheetJS, etc.)
✓  Values can be any JSON type — save objects/arrays freely with tool.setValue()
✓  tool.requestAI / tool.requestUpload / tool.requestFileContent /
   tool.requestObjects / tool.requestExportPdf / tool.requestSendEmail
   ARE exceptions to the no-fetch rule — they go through the parent CMS,
   not direct from the iframe.
✓  Each request* method requires its allow*: 'yes' toolParam. The admin
   configures this. Without it, the callback fires with an error —
   handle this gracefully in your code.
✓  All request* methods are asynchronous. Use callbacks, not return values.
✓  tool.requestAI: 1 concurrent request, 120s timeout, dynamic model-aware
   prompt limit (~2.4M chars for DeepSeek V4 Pro). Prompts exceeding the
   model's context window are truncated; check the error param for notice.
✓  tool.requestObjects: max 500 operations per batch. Avoid batching
   operations that would exceed 10 MB total (Firestore writeBatch limit).
✓  Batch operations are ATOMIC — if one fails, the entire batch is rolled
   back. Design your batch workflows with this guarantee in mind.
✓  Unregistered mainObjectTypes auto-create a default folder on first use.
   You do NOT need the CMS admin to pre-register types for your tool to work.
✓  Emails sent via tool.requestSendEmail are automatically wrapped in the
   CMS-branded email template with header/footer/borders — you only provide
   the body content. The title is displayed prominently in the email header.
✓  tool.requestExportPdf exports as an HTML document that can be printed to
   PDF via browser Print → Save as PDF. Use attachments: [] in
   requestSendEmail to attach exported files to emails.
✓  Always produce complete, functional code — no placeholders, no TODO comments.
