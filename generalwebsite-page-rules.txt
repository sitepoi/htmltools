WHY v1.2 REPLACES v1.1
──────────────────────
v1.1 described an idealized architecture: a `window.gw` SDK, [METADATA]/[HTML]/
[CSS]/[JS] output blocks, auto-scoped CSS, gw.db()/gw.service()/gw.api(),
partials and page gating — NONE of which exist in the codebase yet.

v1.2 describes what the GeneralWebsite platform ACTUALLY ingests today,
grounded in the real implementation (verified against the code):

  • Content is stored as CMS content records with `blocks[]` (Firestore
    `sp_contents`), rendered by Next.js SSR (pages/[...param].js →
    PageBlocks/dynamicPages/PageSSR/MainPageSSR → PageJSX/MainPageJSX →
    FlatContent).
  • `html-code` blocks DO execute custom JavaScript and hoist <style>/<link>
    into <head>.  `html` blocks render raw markup but do NOT execute scripts.
  • Metadata comes from the content's `seo` field (metaTitle/metaDesc/metaImage).
  • There is NO window.gw SDK yet.  CMS JavaScript runs unsandboxed with full
    DOM access (Section 15).

Every capability that the platform does NOT support yet is marked [PLANNED]
and itemized in the companion document:
    zHTMLDOCS/generalwebsite-roadmap/generalwebsite-capability-roadmap.html   (how to build them)

1. WHAT GENERALWEBSITE IS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

GeneralWebsite (GW) is the Uniconhub system that publishes public websites
from CMS content.  You generate the INNER CONTENT of a page, stored as a
content record (or you configure reusable pieces of it), and the platform
renders it inside a live public website.

  • Runs NATIVELY in the host page DOM — NEVER inside an iframe.
  • Inherits the website's theme, global CSS/JS, SEO shell, navigation, footer.
  • Full SEO — content is SSR-rendered into the page HTML and is indexable.
  • Server-side Nunjucks templating on all text/html block values.
  • Custom JavaScript CAN run (via `html-code` blocks) with full DOM access.
  • Target audience: the general public.
  • Mobile-responsive is MANDATORY (Section 11).

You NEVER write <html>, <head>, or <body> tags.  Your output is only inner
content embedded into an already running page.  [METADATA]/[HTML]/[CSS]/[JS]
block syntax from v1.1 is NOT supported — see Section 3 for the real format.

2. ONE PAGE MODEL — SEO CONTENT + EMBEDDED WEB APPS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

There is ONE kind of output: a page composed of CMS blocks.  A page can be
mostly informational, can contain interactive web applications (booking
forms, calculators, product catalogs, payment checkout), or can mix both.
Web apps are just ordinary `html-code` / `dynamic-form` / `object-query-list`
blocks on the same page.

Informational parts must follow Section 8 (SEO).  Interactive parts only need
the starred (★) SEO basics and mobile responsiveness.

For a shared/reusable piece use:

  <!-- GW-PARTIAL-ID: your-partial-name -->

3. WHAT YOU DELIVER — THE CMS CONTENT RECORD
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

── 3.1 CONTENT RECORD ANATOMY (sp_contents) ───────────────────────────────────

A page is one Firestore content record (collection `sp_contents`-<tenant>):

  {
    "contentId": "contact-us",          // stable ID = translation group id
    "slug": "contact-us",               // URL slug (per language)
    "tenantId": "...",                  // auto
    "typeId": "...",                    // content type
    "name": "Contact Us",
    "meta": {
      "language": "en",                 // en, es, fr, de, tr, it, pt, nl, pl, ru, sv
      "category1": "page",              // category1/2/3; category1 === 'blog' ⇒ BlogPosting JSON-LD
      "category2": "",
      "category3": "",
      "status": "enabled",              // 'enabled' | ...
      "pageOrder": 1,
      "isVisible": ""                   // 'no' hides the whole content
    },
    "seo": {                            // ← this is the [METADATA] of v1.1
      "metaTitle": "Contact Us | Your Company",        // ≤ 60 chars (company name auto-appended)
      "metaDesc": "Talk to our team. We reply within one business day.",  // ≤ 160 chars
      "metaImage": "https://cdn.example.com/og/contact.jpg"               // og:image / featured image
    },
    "blocks": [ ... ]                   // Section 3.2
  }

Translation variants share the same `contentId` and differ in `slug` +
`meta.language`.  The platform builds hreflang tags and the language switcher
from these siblings automatically.

── 3.2 BLOCK ANATOMY ──────────────────────────────────────────────────────────

Each block:

  {
    "type": "html-code",                // 'html' | 'html-code' | 'text' | 'image' | 'json' | 'faq-item'
    "value": "<section>...</section>",  // depends on type (see Section 5)
    "meta": {
      "slug": "hero",                   // becomes the DOM id of the block wrapper
      "name": "Hero",
      "isVisible": "",                  // 'no' hides the block
      "mobileDesktopVisibility": "",    // hide on mobile/desktop (component-specific)
      "cssClassNames": "my-hero",       // extra className on html-code wrapper
      "altText": "", "width": 600, "height": 300,   // image blocks
      "groupId": ""
    },
    "css": "{\"paddingTop\":\"24px\"}",         // JSON string of React inline styles for the wrapper
    "settingsJSON": "{}",                       // JSON string passed to the block component
    "fullWidthBlockCss": "{}"                   // JSON string of styles for the full-width wrapper
  }

IMPORTANT: `css`, `settingsJSON`, `fullWidthBlockCss` must be JSON STRINGS of
React inline-style objects (camelCase keys), NOT CSS text.

── 3.3 MAPPING FROM THE v1.1 FORMAT TO THE REAL FORMAT ────────────────────────

  v1.1                            →  REAL PLATFORM
  ──────────────────────────────     ──────────────────────────────────────────
  [METADATA] title                →  seo.metaTitle
  [METADATA] description          →  seo.metaDesc
  [METADATA] og:image             →  seo.metaImage
  [METADATA] canonical            →  auto-generated from slug (Section 10);
                                     override: seo.canonicalUrl  [PLANNED]
  [METADATA] robots noindex       →  seo.noIndex            [PLANNED]
  [METADATA] keywords             →  seo.keywords           [PLANNED]
  [METADATA] schema               →  auto JSON-LD (Section 9);
                                     arbitrary passthrough: seo.structuredDataJson [PLANNED]
  [HTML] (markup only)            →  block { type: 'html', value: '...' }
  [HTML] + [JS] + <style>         →  block { type: 'html-code', value: '<style>…</style>
                                     <div>…</div><script>…</script>' }
  [CSS]                           →  block.css (JSON inline styles) and/or a <style>
                                     tag inside the html-code value (hoisted to <head>)
  [JS]                            →  <script>…</script> at the end of an html-code
                                     block value (executed after the DOM is ready)
  gw.onReady(cb)                  →  NO SDK YET — see Section 4 (script timing) and
                                     Appendix A (planned SDK)

── 3.4 REUSABLE PIECES THAT EXIST TODAY ───────────────────────────────────────

  • shared-content — a json block with meta.slug === 'shared-content' and
    value { "sharedContentId": "<contentId>" } splices another content's
    blocks into the current page at that position.
  • settings-items — site-wide content whose `css-variables` / `css-classes`
    blocks are applied to every page (and compiled into /api/css/[host].css).
  • additions-inside-head / additions-after-body-start /
    additions-before-body-end — three fixed contentIds whose html/html-code
    blocks are injected into the document <head> / after <body> start /
    before </body> (site-wide scripts, pixels, cookie banners).
  • default-header / default-footer — site chrome contents; overridable per
    page with `page-header` / `page-footer` blocks (meta.slug set, isVisible ≠ 'no').
  • Partial WITH PARAMETERS ({% include 'x' with {...} %} style) is [PLANNED]
    — see roadmap P6.

── 3.5 HTML/CSS/JS WRITING RULES FOR GENERATED CODE ────────────────────────────

  ✓ Never emit <html>, <head>, <body>, <style> or <script> outside a block.
    <style>/<script> are allowed INSIDE an html-code block value only.
  ✓ Prefix ALL your class names (e.g. `gw-` or page-specific prefix).  CSS
    injected from html-code is global to the page — there is NO automatic
    scoping in the platform today.
  ✓ Block meta.slug becomes the DOM id — keep it unique within the page.
  ✓ Nunjucks runs over html/html-code/text/markdown values with autoescape
    OFF.  If your generated markup contains literal `{{ }}` or `{% %}` (e.g.
    a client-side templating library), wrap it in {% raw %} ... {% endraw %}.
  ✓ Escape user data yourself — no sanitizer runs anywhere (Section 15).

4. HOW YOUR PAGE IS RENDERED (REAL PIPELINE — NO IFRAME)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  1. Request → pages/index.js (home) or pages/[...param].js (everything else).
     Both call shouldBlockRequest() (bot/traffic filtering), then MainPageSSR.
  2. MainPageSSR resolves:
       • language: context.locale, else env <HOSTNAME_WITH_UNDERSCORES>_default_language, else 'en'
       • route → page id (Section 10)
       • content by slug (getContentBySlug) → contentId + translation siblings
       • fetch ids: ['default-header', <pageId>, 'settings-items', 'default-footer']
         via getModifiedContentsByIds (data/utils/contentUtils.js)
  3. getModifiedContentsByIds applies the pipeline:
       • Nunjucks rendering of block values (Section 6)
       • shared-content splicing
       • object-query-list expansion (Section 7.1)
       • i18n block variables
       • css-classes / css-variables collection and substitution
       • productData.data_categoriesBased → content.data
  4. SSR returns props (ssr_contents, ssr_seoMeta, ssr_canonicalUrl,
     ssr_hreflangTags, ssr_pageMainStructuredData, ssr_variablesForContent, ...).
  5. MainPageJSX renders MainAppView → Layout1 → for each content → FlatContent,
     which dispatches each block by `type` (Section 5).
  6. html-code blocks: InjectedContent (PageBlocks/web/content-components/
     InjectedContent.js) injects the HTML, hoists <style>/<link rel="stylesheet">
     into <head> (deduped), and executes <script> tags sequentially after a
     double requestAnimationFrame — i.e. after the DOM is ready.  Inline
     scripts run inside an IIFE (Blob URL) with error-swallowing timers, and
     top-level named functions are hoisted to window so inline onclick
     handlers work.  You do NOT need DOMContentLoaded — scripts already run
     after render.  For SPA navigation re-inits, CMS chrome scripts are
     re-run via a reinit registry.

  SCRIPT TIMING RULE FOR GENERATED CODE:
  Put everything in one <script> at the end of the html-code value.  Wrap
  your code in an IIFE and namespace globals under one window object, e.g.
  window.MyPage = { init: function(){ ... } }.  There is no gw.onReady yet.

  YOU DO NOT CONTROL:
  • <title>/<meta>/JSON-LD — they come from the content's seo field + the
    platform's HeadAndMetaData component (Sections 8–9).
  • The document shell, site header/footer (unless you use page-header /
    page-footer / additions-*).

5. BLOCK TYPE REFERENCE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  TYPE           VALUE                        RENDERING
  ──────────     ──────────────────────────   ─────────────────────────────────
  html           raw HTML string              dangerouslySetInnerHTML.
                                              Nunjucks-rendered.
                                              ✗ <script> inside will NOT run.
                                              ✗ <style> inside will NOT be hoisted.
                                              Use for static markup only.

  html-code      raw HTML string              InjectedContent: HTML injected,
                                              <style>/<link> hoisted to <head>,
                                              <script> executed (sequential).
                                              Nunjucks-rendered.
                                              Use when the page needs CSS or JS.

  text           plain text                   rendered as escaped-ish text node.

  image          { url, thumb_url }           next/image; alt/title/width/height
                                              from meta.altText/meta.width/meta.height.

  json           depends on meta.slug         dispatched to ContentComponentIncluder:
    meta.slug === 'dynamic-form'                → DynamicForm (Section 7.2)
    meta.slug === 'enduser-registration-form'   → EndUserRegistration
    meta.slug === 'object-query-list'           → QueryList (Section 7.1)
    meta.slug === 'new-uniconhub-company-account' → NewCompanySubDomain
    meta.slug === 'flexbox-content'             → legacy layout (deprecated)
    meta.slug === 'shared-content'              → content splicing (Section 3.4)
    meta.slug === 'i18n'                        → translation variables (Section 6)
    meta.slug === 'css-variables' / 'css-classes' / 'css-classes-sync-with-components'
                                                → theme pipeline (Section 3.4)
    meta.slug === 'page-header' / 'page-footer' → replaces default chrome
    meta.slug === 'product-listing-component'   → LEGACY, do not use
                                              (replaced by object-query-list)

  faq-item       { question, answer }         visual rendering TEMPORARILY DISABLED;
                                              FAQPage JSON-LD is still auto-generated
                                              from these blocks (Section 9).

  markdown       markdown text                Nunjucks-rendered but NOT displayed by
                                              FlatContent today — avoid.

  image-gallery  { imageList: [...] }         TEMPORARILY DISABLED — avoid.

  Block meta controls (all types):
    meta.isVisible === 'no'            → block hidden
    meta.mobileDesktopVisibility       → hide per device class
    meta.cssClassNames                 → extra className (html-code)
    css / fullWidthBlockCss / settingsJSON → see 3.2

  Every page automatically runs the hooks useScrollAnimation, useParallax and
  useStickyHeader (FlatContent).  Generated code can use the classes they
  watch: .block-effect-50 / -100 / -150 / -200 (scroll reveal) etc.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  CONTEXT = whole content record + variablesFromParams + i18n block vars:

    endswith  nl2brSentences  bulletEachSentence  formatDate  linkify

    {% for day in nextDays(7) %}

7. DATA CONNECTIVITY
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

── 7.1 OBJECT LISTS — object-query-list (READ) ────────────────────────────────

  json block, meta.slug 'object-query-list', value:

    {
      "objectQueries": [
        {
          "cmsObjectType": "products-uniconbaseapps",
          "folders": [ { "slug": "summer-collection", "maxCount": 8 } ],
          "itemTemplateId": "product-card-template"
        }
      ],
      "itemTemplateId": "default-product-card"
    }

  The platform loads the objects (om_objects / om_private_objects, respecting
  the object type's publicAccess + parentTenants) and renders each item with
  the Nunjucks template stored in the referenced `system-items` object.
  Inside the item template the item's data is available; the object's
  productData.data_categoriesBased is copied to `data`.

  Object type visibility: rules.publicAccess === 'no' moves objects to a
  private collection; per-user permissions.{email}.hasPermission further
  filter reads.

── 7.2 FORMS — dynamic-form (WRITE, no login needed) ──────────────────────────

  json block, meta.slug 'dynamic-form'; the block VALUE is a JSON string with
  the key `form-type-id` pointing to the form definition:

    { "form-type-id": "quote-request-form" }

  Form definition = a `system-items` object whose config json block describes:
    dataDefinitions[]  (field types, validationRules, formulas)
    destinationTable   (default 'forms'; 'users' stores roles:['customer'])
    saveType           ('cmsObject' → saves as a CMS object instead)
    afterSaveApiHooks  (e.g. call /api/email/sendEmail)

  Capabilities: validation rules, cross-field formulas (moment, axios, xlsx,
  fuse, context functions), dependent chaining, file upload (react-dropzone →
  Firebase Storage folder from cmsParams.onlineStorageFolder), multilingual
  labels.  NO captcha yet [PLANNED].  Form submissions land in the tenant's
  Firestore `forms` collection (or destinationTable).

── 7.3 PAYMENTS (Stripe) ──────────────────────────────────────────────────────

  Existing API route: /api/pay/stripe/[...param]  (API-key gated)
    mp  / str-002 → charge via stripe tokens
    mpfi / str-003 → pay an invoice object (updates paymentStatus)
  Client: PaymentSelection / PaymentCreditOnline (@stripe/react-stripe-js).
  The v1.1 gw.service('createPayment') abstraction does NOT exist [PLANNED].

── 7.4 EMAIL (AWS SES) ────────────────────────────────────────────────────────

  /api/email/sendEmail — nodemailer + AWS SES.  Types: end-user-register,
  new-form-submitted, your-form-submitted.  Trigger from form hooks.

── 7.5 FILE UPLOAD ────────────────────────────────────────────────────────────

  Via form upload fields (Section 7.2) — there is no standalone gw.service
  ('upload') yet [PLANNED].

── 7.6 [PLANNED] — NOT BUILT YET ──────────────────────────────────────────────

  gw.service('search') (full-text) — fuse.js exists as a dependency; today
    filtering is only via object-query-list folders/filters.
  gw.service('exportPdf') — @react-pdf/renderer dependency exists; no route.
  gw.service('ai') — no AI gateway wired.

15. SECURITY MODEL
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

The REAL model today (differs from v1.1):

  • CMS content is written by trusted tenant admins/tools.  html-code blocks
    execute arbitrary JavaScript with FULL page privileges (no sandbox).
    Form formulas are evaluated with new Function().  InjectedContent
    neutralizes inline onerror handlers and suppresses CMS-script errors,
    but this is noise control, NOT a security boundary.
  • There is NO HTML sanitization anywhere.  Generated pages MUST escape
    user-generated data themselves (Nunjucks autoescape is OFF).  Sanitizing
    object-list item templates is [PLANNED] (roadmap P3).
  • Secrets must NEVER be placed in content — API keys live server-side in
    env vars (Stripe, SES, IndexNow, revalidate secret).  There is no
    per-page key storage.
  • State-changing API routes are key-gated (checkAPIKey) and form writes go
    through Firestore rules.
  • If a page collects personal data, include a privacy notice / link.
  • Known hardening backlog (fixes, not features): hardcoded AWS SES
    credentials in /api/email/sendEmail, hardcoded Stripe fallback key line
    in /api/pay/stripe, hardcoded API keys in data/utils/apiUtils.js,
    base64 password in localStorage (see roadmap "housekeeping").
