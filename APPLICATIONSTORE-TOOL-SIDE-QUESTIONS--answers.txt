Q1. Record shape — one ObjectRecord JSON (canonical)
--------------------------------------------------------------
Field values live under productData.data_categoriesBased.{fieldId}.
v2 ObjectRecord anatomy (CMS Application System Reference §11.3).

{
  "id": "lib-food-ordering-cart",
  "name": "Food Ordering Cart",
  "slug": "food-ordering-cart",
  "cmsObjectType": "website-html-tool-library-applicationstore",
  "productData": {
    "data_categoriesBased": {
      "gwAppName": "Food Ordering Cart",
      "title": "Food Ordering Cart",
      "description": "Customer-facing food ordering UI with cart and checkout.",
      "category": "food",
      "configSchema": {
        "type": "object",
        "properties": {
          "limit": { "type": "number", "default": 12 }
        }
      },
      "ssrHtml": "<div class=\"foc-ssr\"><div class=\"foc-ssr-head\">Menu loading…</div></div>",
      "ssrEnabled": true,
      "code": {
        "html": "<div class=\"foc-app\"><!-- widget template --></div>",
        "css": ".foc-app { font-family: inherit; }",
        "js": "(function(){ if(!window.gw) return; gw.apps.register('Food Ordering Cart', function(ctx){ /* render ctx.el from ctx.config */ }); })();"
      }
    }
  }
}

Type map (EXACT):
  STRINGS      : gwAppName, title, description, category, ssrHtml
  NESTED OBJECT: configSchema, code { html, css, js }
  BOOLEAN      : ssrEnabled (optional; client-only opt-in when false)

  - data-gw-app value == gwAppName EXACTLY (case- and space-sensitive).
  - configSchema and code are EMITTED as nested objects. The reference
    consumer (WebpageBuilder) also ACCEPTS them as JSON strings for
    robustness (legacy records), but the canonical publish contract is
    nested objects.
  - The consumer also tolerates alternative/legacy field names
    (gwApp/widgetName/name for the island name; htmlCode/cssCode/jsCode,
    toolHtml/toolCss/toolJs, or a code triple anywhere in the record),
    but ONLY gwAppName/title/description/category/configSchema/ssrHtml/
    code are contractual — do not rely on the tolerances.

Q2. configSchema — draft + defaults
--------------------------------------------------------------
  - JSON Schema keywords: draft-07 compatible SUBSET (type, properties,
    required, default, enum, minimum/maximum, items). We do NOT emit a
    "$schema" declaration in catalog records.
  - Page builders ALREADY bake defaults: WebpageBuilder generates
    data-gw-config from configSchema at insert time — every
    properties[].default is materialized (recursively for nested
    objects; arrays → []; strings/numbers → the default or '').
    A freshly authored page therefore carries a complete config.
  - STILL REQUIRED PLATFORM-SIDE: apply properties[].default for
    missing keys at mount time (PUBLICWEBSITE-REQUEST §3 Step B.2:
    "config = JSON.parse(data-gw-config), with configSchema defaults
    applied for missing keys"). Reason: hand-edited pages, older saved
    values, and third-party builders can produce partial configs.

Q3. ssrHtml — guarantees + size
--------------------------------------------------------------
  - NO <script>: guaranteed-by-convention; the widget hydrates
    client-side via code.js, so ssrHtml MUST NOT contain <script>.
    (Scripts injected via innerHTML never execute anyway — they would
    only bloat the SSR payload and confuse hydration.)
  - <style>: discouraged. Widget styling belongs in code.css (appended
    to <head> after page css). If a record ships <style> inside ssrHtml,
    the platform SHOULD hoist it like page embedded styles, but the
    canonical contract is: no <style> in ssrHtml.
  - Determinism: ssrHtml must be static/deterministic (Redis/CDN cache
    keyed by page version) — no Math.random/time dependence.
  - Size: no tool-side hard cap beyond Firestore's 1 MiB/document. The
    fetch relay caps responses at 500 KB (PLATFORM-REQUEST §1).
    PRACTICAL GUIDANCE: keep ssrHtml ≤ ~50 KB and code.css/js in the
    low tens of KB (public-website-page-rules §16). If the catalog LIST
    carries full code for many widgets it gets heavy — the contract
    already allows a lean list + detail fetch:
    tool.requestObjects('get', { mainObjectType, objectId }) -> { object }.

Q4. Runtime SDK — widget code.js on the published page
--------------------------------------------------------------
  YES — published page context = window.gw (gw.db, gw.apps, gw.forms,
  gw.navigate, gw.formatCurrency, gw.sanitize…). NO window.tool there.
  (html-tool-rules.txt: the widget/page runtime is "(window.gw, no
  window.tool)"; window.tool exists ONLY inside the CMS tool iframe.)

  Module rules (exact, from public-website-page-rules §3.2/§3.3):
    - Plain vanilla scripts ONLY — NOT ES modules. No import/export.
    - Page js is wrapped in an IIFE executed via a Blob URL.
    - NO top-level await (scripts run in a non-async wrapper).
    - Idempotent: the code re-runs on every visit AND every SPA
      navigation. Guard window/document listeners (window.__xInit).
    - Attach helpers to gw.ns; never rely on hoisted window functions.
    - Widget code.js MUST call gw.apps.register(name, factory) once;
      factory receives { el, config, gw } and may return a cleanup fn.
      It REPLACES or hydrates the SSR markup found inside el.

  The CMS iframe runtime is a DIFFERENT world: the three files are
  INLINED into one <script> (not modules), and the SDK is window.tool
  (tool.onReady, tool.requestObjects, tool.requestAI…). A library tool
  that is ALSO usable as an island must branch: tool.onReady → tool UI;
  gw context → gw.apps.register (see the Food Ordering Cart source).

Q5. CSS scoping — wrapper-class convention
--------------------------------------------------------------
  code.css MUST be scoped under the widget's OWN unique wrapper class
  (same rule as pages, §3.4): never bare html/body/*/a/button/h1; the
  gw- prefix is RESERVED — the widget may USE --gw-color-* variables and
  gw-shared-* classes but must NEVER define gw-* rules.
  Convention: the FIRST element of code.html carries a single unique
  kebab-case wrapper class named after the widget, e.g.
      <div class="foc-app">…</div>   →  .foc-app { … }
  The platform appends code.css to <head> AFTER page css (SSR spec
  Step A.5), so equal-specificity widget rules win. The page builder
  does NOT rewrite widget css — it injects it verbatim.

Q6. Fallback marker — exact contract
--------------------------------------------------------------
  From PUBLICWEBSITE-REQUEST--widget-island-ssr.txt Step A/B/C:
    record found + has ssrHtml          → inject ssrHtml INSIDE the
                                           island; data-gw-ssr="1"
    record found + NO ssrHtml           → island left EMPTY server-side;
                                           data-gw-ssr="none" (no error,
                                           no crash)
    record found + ssrEnabled:false     → NO server markup;
                                           data-gw-ssr="client"
    island name UNKNOWN / store down /
    record missing                       → render NOTHING (empty div),
                                           log a server warning, never
                                           break the page. (In the
                                           BUILDER's preview only, an
                                           inert placeholder chip is
                                           shown — never on publish.)
  NOTE for the platform team: the spec text says ssrEnabled:false uses
  "data-gw-ssr='client' or 'none'" — we standardize on EXACTLY
  "client" for opt-out records and "none" for unknown/missing records
  (three values total: "1" | "client" | "none"). Page builders do NOT
  emit data-gw-ssr in their preview (client-side only); this attribute
  is publish-side only.

Q7. Publish invalidation
--------------------------------------------------------------
  Tool-side: the WebpageBuilder saves only the page value
  (tool.setValue → data.htmlPage.code); it does NOT call any
  revalidation endpoint, and it must not. Store publish is
  platform-owned.
  Recommendation: WIRE IT. TTL-only (5 min) is NOT acceptable on its
  own, because:
    - the PublicWebsite cache key is site + page identity + language +
      data.version (page version) — a WIDGET update does NOT bump page
      version, so stale SSR output could survive beyond TTL;
    - the gw-widgets registry is a MANDATORY site-wide shared source —
      updating it must invalidate the whole site.
  Wire: store/library publish → CMS triggerRevalidate →
  POST /api/cms/revalidate-trigger (server-side, REVALIDATE_SECRET) →
  PublicWebsite POST /api/revalidate.

Q8. Dev/staging store
--------------------------------------------------------------
  No platform-wide dev/staging Application Store base URL exists in the
  tool contract. PROD (https://applicationstore.uniconhub.com) is the
  default for every environment:
    apiV2BaseUrl default = https://applicationstore.uniconhub.com/api/v2
  The tool DOES support per-instance overrides for testing:
    - apiV2BaseUrl          (API v2 base)
    - applicationStoreHost  (legacy host)
    - widgetCatalogUrl      (full catalog list override)
  Because the catalog is fetched through the parent-CMS relay
  (tool.requestObjects / tool.requestFetch), the CMS host can also map
  the store host per environment server-side (recommended if a staging
  store is provisioned). The CMS team should confirm whether a staging
  store exists; if not, PROD is used everywhere.
