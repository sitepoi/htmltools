1. Purpose and governance

This document defines one tool and one set of invariants around MapleBooks Tax Prep BC - loading the taxpayer's documents (bank statements, invoices paid, invoices sent, other supporting files), extracting income and expense transactions with AI, hunting missed deductions, and preparing tax + GST/PST summaries - and it is the single source of truth for every decision we make about this tool, now and in the future. No decision is considered made until it is written here. Rules of use:

  • Every decision is logged here. Before or together with any change to this tool, the decision is added to section 11 with a date, and the affected section is updated in the same change.
  • The register is append-only. Decision rows are never deleted. A reversed decision is marked "Reversed (date)" with a reason - the original row stays for history.
  • This document wins ties. If this document or the code disagree, the discrepancy is resolved in this document first (with a dated decision), then applied to the code - never the other way around, and never silently left divergent.
  • Check before changing. Before changing any behavior covered here, read the relevant section and the register; after the change, update this document in the same change as the code.
  • Names must be self-explanatory. Every variable, function, and code snippet in any update uses understandable names. No cryptic abbreviations. Short names are allowed only for loop indexes and universally known abbreviations (id, url, api).
  • Acronyms are always expanded next to every use - in prose, tables, and headings. Literal identifiers stay as they are.

Core guarantees. (1) A document uploaded under one kind tab (bank statement, invoice paid, invoice sent, receipt, T4 slip, other) keeps that kind, its bank/period/vendor metadata and its income/expense direction for its whole life; legacy documents migrate automatically. (2) Every number shown anywhere in the tool - dashboard, GST, tax estimate, reports - is computed from the transaction ledger and nothing else. (3) All tax figures are planning estimates and are always labelled as such; final filing numbers are the accountant's call.

5. Verified problem and root cause

5.1 Verified evidence

  • 2026-09-27: the user could not tell which menu items were reports, tools or data entry, and could not see how much tax was actually owed (feature requests 2 and 3 in the tax-at-a-glance round).
  • 2026-09-27: the user wanted accepted deductions without receipts (home office, vehicle use) and a way to simulate savings vehicles (RRSP, TFSA).
  • 2026-09-28: the user wanted documents grouped per kind with per-kind details (bank, month) instead of one mixed list.

5.2 Current implementation (verified in code)

// Before this round: one documents list + kind filter; no tax total; no simulator
renderDocuments() // single table filtered by a select
emailAccountant() // email button that required an accountant email field

5.3 Structural flaws

  1. One list for different document types. Bank statements, invoices and receipts are different inputs with different details (bank, month, vendor); one list hid those details.
  2. No payable number. Tax, GST and PST existed in separate pages; the user could not see the total owed in one place.
  3. No what-if tool. There was no way to test the effect of RRSP/FHSA/donations on the tax bill.

Root cause: the tool was organized around data structures (documents, transactions, GST) instead of around the taxpayer's journey (gather, review, save tax, see what I owe).

6. Requirements

  1. Documents are grouped in six tabs; each tab has its own add popup capturing kind-specific details; the list shows the Date/Period column.
  2. Bank-statement popup asks bank, account type, statement month and year; the AI prompt receives these details.
  3. The dashboard shows one glance card: revenue, expenses, net profit, income/corporate tax, GST, PST and the total to CRA.
  4. A Tax Saver page simulates RRSP, FHSA, TFSA, donations and medical expenses and shows the tax saved.
  5. All numbers stay planning estimates, labelled as such; nothing is ever sent to CRA.
  6. Works without AI (manual + CSV entry) and degrades gracefully when any allow* channel is off.

8. Solution design

8.1 Core invariants

Invariant DOC-KIND. A document's kind is set once at upload (normalizeDocKind) and never changes; its transactions inherit the direction expectation of that kind.

Invariant LEDGER-ONLY. Every displayed total (dashboard, GST, tax estimate, saver, reports) is derived from DB.transactions via ledgerTotals / gstTotals / computeTaxEstimate - no display path reads documents directly.

Invariant ESTIMATE. Any monetary result presented as tax carries the word estimate and the note 'verify with an accountant'. Nothing is submitted to CRA.

8.2 Document pipeline

// app/PersonalTaxPreparation.js - upload path
openUploadDocModal(kind) -> collectUploadMeta(kind) -> uploadDocWithMeta(kind, meta)
  -> extractDoc (requestFileContent) -> parseCsvDoc | analyzeDoc (requestAI, chunked)
  -> addTransactions (dedupe by date|amount|description key) -> ledger
  • CSV files parse locally first (findCsvColumns, normDate, parseMoney).
  • Non-CSV files are chunked (50,000 chars) and analyzed sequentially with the kind-aware prompt.
  • Duplicates are skipped by the txKey dedupe key, so re-uploading a statement adds nothing twice.

8.3 Tax Saver math

// saverBase(): taxable = business net (personal side) + employment + other income
// computeSaver(): newTaxable = taxable - RRSP - FHSA;
//   newTax = personalTaxOn(newTaxable);
//   credits = min(newTax, donationCredit + medicalCredit);
//   finalTax = newTax - credits; saving = personalTax - finalTax
  • Corporate tax (11% small business / 27% general, BC combined) is shown but never reduced by the personal savers.
  • CPP self-employed is computed on business income and is unchanged by RRSP.

12. Maintenance rules

  1. This document is the single source of truth for every decision about this tool. Every decision is recorded in section 11 with a date, and the affected section is updated in the same change as the code. A decision that is not in the register did not happen.
  2. Rollback of a decision = mark it "Reversed (date)" with reason; never delete rows.
  3. Tool-specific rule: a document's kind and meta are immutable after upload - review every new code path against invariant DOC-KIND (section 8.1).
  4. Never introduce a display path that computes a total outside the ledger - review against invariant LEDGER-ONLY.
  5. Never present a tax number without the estimate wording - review against invariant ESTIMATE.
  6. Global naming rule: any update - code or documentation - MUST use understandable, self-explanatory names. No cryptic abbreviations. Existing misleading names are renamed when their code is touched.
