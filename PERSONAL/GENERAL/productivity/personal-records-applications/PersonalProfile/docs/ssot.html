1. Purpose and governance

This document defines one tool and one set of invariants around a reusable personal profile that changes shape for the application in front of the person - and it is the single source of truth for every decision we make about this tool, now and in the future. No decision is considered made until it is written here. Rules of use:

  • Every decision is logged here. Before or together with any change to this tool, the decision is added to section 11 with a date, and the affected section is updated in the same change.
  • The register is append-only. Decision rows are never deleted. A reversed decision is marked "Reversed (date)" with a reason - the original row stays for history.
  • This document wins ties. If this document or the code disagree, the discrepancy is resolved in this document first (with a dated decision), then applied to the code - never the other way around, and never silently left divergent.
  • Check before changing. Before changing any behavior covered here, read the relevant section and the register; after the change, update this document in the same change as the code.
  • Names must be self-explanatory. Every variable, function, and code snippet in any update uses understandable names. No cryptic abbreviations. Short names are allowed only for loop indexes and universally known abbreviations (id, url, api).
  • Acronyms are always expanded next to every use - in prose, tables, and headings. Literal identifiers stay as they are.

Core guarantee. Changing the profile use changes ONLY which sections the sidebar shows. A saved answer can never be deleted, rewritten or hidden from the record by switching the profile use, toggling focus areas, or turning sections off.

5. Verified problem and root cause

5.1 Verified evidence

  • 2026-11-05, request. The user asked for a personal profile tool built on the Company Profile pattern: a basic generic profile that asks for more data when the person is building a resume, applying to university, or filling some other application, with those profile scenarios added to the tool.
  • 2026-11-05, workspace review. The Company Profile tool already proves the adaptive pattern: an industry selection plus focus areas hide sections, and customs fields/sections absorb extra data. No personal equivalent existed; the closest tools are single-purpose (StudentFileBuilderForApplications holds one student's application file, VolunteerProfile holds one volunteer's portal).
  • 2026-11-05, data duplication. A person applying to a university, a scholarship and a job re-types the same identity, education, work and reference data into three separate tools because each tool owns a narrow slice.

5.2 Root cause

The tool library models company data once and reuses it, but personal data has no shared record. Without one record, every application form becomes the source of truth and the answers drift apart.

  • Every existing tool owns one narrow slice (student file, volunteer profile), so an application form outside that slice starts from an empty page.
  • The first screen asked for private data (date of birth, nationality, marital status, gender, pronouns) even when the chosen application never uses it.
  • Share and export were modelled as one more section in the sidebar, mixing "data about the person" with "actions on the record".

5.2 Current implementation (verified in code)

The first build stored private details inside basicInfo and rendered Share & Export as a section:

// app/PersonalProfile.js - emptyDB() before 2026-11-05
basicInfo: { legalName, preferredName, pronouns, dateOfBirth, placeOfBirth,
             gender, maritalStatus, nationality, citizenship, photoUrl }
// SECTIONS
{ id: 'share', group: 'Output', title: 'Share & Export' }

5.3 Structural flaws

  1. Private fields were unconditional. Nothing tied date of birth, nationality, marital status, gender or pronouns to a profile need, so the tool collected sensitive data by default.
  2. Contact details were split. Email and phone sat in Contact while the name sat in Basic Information, so the top-of-application block was spread over two screens.
  3. Tool actions lived in the data tree. Share & Export was a section in SECTIONS, counted in the pager and the completion logic, which mixed navigation with actions.

Root cause: the original model treated every field and feature as a section, with no notion of "only ask when a profile needs it" and no place for tool-level actions.

6. Requirements

  1. One record, many applications. A single record holds the answers reused by resumes, university applications, scholarships, immigration forms, volunteer applications, portfolios and care forms.
  2. Adaptive, never destructive. Changing the profile use or focus areas may hide sections but must never delete, rewrite or hide saved values from the record.
  3. No admin configuration required. The tool works with zero CMS parameters; every param is optional and only seeds or narrows behavior.
  4. Sensitive data is opt-in for export. Identity, health, funding and documents are excluded from exports until the user explicitly includes them; the summary text never contains them.
  5. Record size stays small. Files are linked by URL, never embedded; essays are plain text. The record must stay far below the 1MB CMS document limit.
  6. Fails soft. Missing upload support, missing user identity, copy denial and read-only hosts all degrade to a visible message, never to a broken screen or silent data loss.
  7. Multi-tenant safe. No tenant name, email, domain or organisation fact is baked into the tool or its sample data.
  8. Deterministic saving. Every edit is written to tool.setValue on a short debounce; structural changes save immediately. No unsaved state survives a section switch.
  9. Private by default. Date of birth, place of birth, nationality, citizenship, marital status, gender and pronouns appear only when a selected profile need requires them. The default birth detail is the year, not the day.
  10. Actions are not sections. Share and export live in a tool-level menu and drawer, never in the profile section list.

8. Solution design

8.1 Core invariants

Invariant PP-1. Visibility is computed, never stored per field. A section is shown when one of its needs matches an enabled focus area (or when nothing is configured yet). No code path deletes a value because a section became hidden.

Invariant PP-2. The saved record is the only source. readAllFromDOM runs before every export and before every structural change, so an export can never be built from stale in-memory data.

Invariant PP-3. Sensitive sections leave the tool only through the explicit opt-in in Share & Export. The summary text is always built from non-sensitive sections.

8.2 Data model

{
  schemaVersion: 1,
  basicInfo: { legalName, preferredName, photoUrl, photoName },
  personal: { birthYear, dateOfBirth, placeOfBirth, nationality,
              citizenship, maritalStatus, gender, pronouns },
  summary, contact, identity, health,
  documents[], education[], testScores[], certifications[],
  workExperience[], skills[], projects[], publications[],
  achievements[], volunteer[], extracurricular[], references[],
  essays[], languages[], preferences, funding,
  profile: { kind, kindChosen, focus[], presetFocus[], showAllSections,
             initialized, prefilledFromAccount, exportIncludeSensitive,
             customFields{}, customSections[] }
}
  • Every list is an array of flat records with a stable id, normalised on load.
  • customFields is keyed by section id or custom:<sectionId>; a custom field is {id, label, type, value}.
  • No file bytes: documents store fileUrl and fileName only.

8.3 Section registry and repeatable fields

var SECTIONS = [
  { id: 'education', group: 'Education', icon: 'book',
    title: 'Education', desc: '...',
    count: function () { return DB.education.length; } },
  { id: 'essays', group: 'Applications', icon: 'pen',
    title: 'Essays & Statements', needs: ['university', 'scholarship', 'research'], ... }
];

var ARRAY_LISTS = {
  education: {
    containerId: 'pp-education-container',
    get: function () { return DB.education; },
    rows: [[{ field: 'institution', label: 'Institution' }, ...], ...]
  }
};
  • A new field is one entry in rows; a new list is one entry in ARRAY_LISTS.
  • renderArrayList renders, readArrayFields reads through data-list, data-idx and data-field, so add/remove and saving stay in one place.

8.4 Saving and external changes

  • Text edits debounce 400ms, then readAllFromDOM and tool.setValue.
  • Add, remove, profile-use change, focus toggle and custom-section edits save immediately.
  • selfSaving prevents the tool from re-rendering its own echo through onValueChange; a real external change reloads the record and re-renders.
  • Every structural change updates header name, completion, badges, pager and the share preview in one pass.

8.5 Export contract

OutputContainsSensitive data
Summary text (copy)Name, headline, contact, links, summary, objectives, experience, education, skills, certifications, languages, projects, volunteering, achievements, referencesNever - personal details, identity, health, funding and documents are excluded
JSON (copy or download)The whole normalised record plus exportedAt, exportedFrom, exportedSensitiveOnly with the opt-in checkbox; personal, identity, health, funding and documents are blank when off
Readiness listUp to six focus-aware checks, missing items firstNever

8.6 Read-first forms

  • Profile Summary is five cards: headline, profile summary, objectives, values and interests. Only the edited card becomes an input or textarea with a word count, Cancel and Save; Escape cancels. The other cards stay readable.
  • Examples sit inside each summary editor: one realistic sentence or paragraph plus a "Use this example" button that fills the field so the user can edit rather than invent from a blank box. Ambiguous list fields carry an inline help sample.
  • List items are collapsed cards showing a title, a subtitle and meta chips (dates, levels, expiry, hours, word count). Edit opens the fields, Done closes them, opening another item closes the previous one, and a new item opens automatically.
  • Read-only hosts expand every list item and hide the Edit controls; the data stays readable but not editable.

8.7 Privacy-first personal details

  • Private fields live in DB.personal, not in basicInfo; old records are migrated once in normalizeDB and the legacy keys are deleted.
  • The Personal Details section declares needs: ['immigration', 'government', 'health']. It is hidden for general, résumé, university, scholarship, research, volunteer and portfolio profiles, and for an unconfigured record.
  • The default birth question is year only (four digits, sanitised on input). The full date stays in the same section with the help text "Only when an official form demands the exact day".
  • The section is optional in completion: it never counts toward the profile percentage, so the tool does not push users to fill private data.
  • personal is treated as sensitive: it is blanked in JSON export unless the opt-in is on, and it never enters the summary text.

8.8 Photo card and header avatar

  • Basic Information step 1 opens with a photo card: an 84px avatar, a short hint, Upload photo, Paste link and Remove. The URL field is collapsed behind Paste link so the default path is an upload.
  • The same image renders as a 32px avatar in the header and a 40px avatar in the menu, with initials from the legal or preferred name as the fallback.
  • Email and phone sit beside the name in the same block; Contact keeps alternate phone, address, time zone and the web links.

8.9 Header menu and share drawer

  • The header account control is the avatar plus name and profile use; it opens a menu with Edit basic information, Share & export, Copy summary, Copy JSON and Download JSON.
  • Share & export opens a right-hand drawer with the readiness list, the sensitive opt-in, the three export actions and the summary preview.
  • The drawer is not part of SECTIONS: it never appears in the sidebar, the pager, the completion count or the section visibility rules. Escape or a click on the overlay closes it.

12. Maintenance rules

  1. This document is the single source of truth for every decision about this tool. Every decision is recorded in section 11 with a date, and the affected section is updated in the same change as the code. A decision that is not in the register did not happen.
  2. Rollback of a decision = mark it "Reversed (date)" with reason; never delete rows.
  3. Section visibility is computed in one place. Add a section with its needs list; never hard-code a hidden section with inline styles or a conditional render list.
  4. No new list code. A new repeatable list or field goes into ARRAY_LISTS. Hand-written read/render loops are not allowed.
  5. Never introduce an export path that bypasses buildExportData or a summary path that bypasses buildProfileSummaryText.
  6. Global naming rule: any update - code or documentation - MUST use understandable, self-explanatory names. No cryptic abbreviations. Existing misleading names are renamed when their code is touched.

14. Open questions

Decision points we resolve together before or during implementation. Every answer becomes a dated row in section 11.

  1. Should the record link to other tools? A Company Profile record links to invoices already. A personal profile could feed StudentFileBuilderForApplications, VolunteerProfile and future resume tools through a param holding the record id. Not built yet because it needs a CMS-side contract.
  2. Should an application target list live in the profile? A list of programs or jobs with deadlines and status would turn the profile into a tracker. It overlaps with idea I-01 and is deliberately out of scope for 0.1.
  3. How long should essays be capped? Essays are plain text today with no limit. A per-essay character cap (for example 20,000) would protect the record size; no cap was chosen because competition essays can be long.
  4. Should sensitive sections be locked behind a reveal action? Identity and health are visible whenever their section is visible. A reveal toggle would add friction but reduce shoulder-surfing risk.
  5. Which profile use should be the default in a new record? Today the select starts empty and only the basic sections show (D-PP-16). Once real usage exists, a most-used default can be seeded through the defaultKind param.
  6. Should Personal Details be reachable from the basic sections on demand? Today it appears only for immigration, government and health. A "needs this form" link on Basic Information could reveal it for one profile without changing the focus set; not built yet because it adds a second visibility rule.

Before every push re-evaluate every OPEN risk of the groups being pushed: solve them one by one (tick the checkbox), or mark the risk Accepted (data-risk-status="accepted") with a reason and the date, and update the Last re-evaluation line inside the risk. A group is push-ready when its tasks are done AND it has no OPEN risks - the task panel shows a PUSH READY badge per group and the open-risk count.

Risks: 0 open - 0 solved - 0 accepted (0% solved)
R-01Sensitive data is visible to anyone who can open the record

Applies to: whole group PP-1.

What can go wrong: identity numbers, medical details and funding data sit in a CMS record, and the CMS permissions decide who reads them.

Likelihood / impact: medium likelihood, high impact.

Mitigation: sensitive sections sit behind their own section with an explicit note, are excluded from every export by default (D-PP-09), and never enter the summary text. Record access stays a CMS permission decision.

Last re-evaluation: 2026-11-05 - accepted with the export default and the section notes; record sharing remains an owner/CMS decision.

R-02Essays and long notes grow the record

Applies to: T-03 and T-06.

What can go wrong: a record with dozens of long essays approaches the 1MB CMS document limit.

Likelihood / impact: low likelihood, medium impact.

Mitigation: no file bytes are stored, only links; essays are plain text. Section 14 question 3 covers an optional per-essay cap.

Last re-evaluation: 2026-11-05 - accepted; revisit if a real record crosses 700KB.

R-03Clipboard or download blocked by the host frame

Applies to: T-06.

What can go wrong: a sandboxed CMS iframe denies navigator.clipboard or blob downloads, so Copy and Download appear to do nothing.

Likelihood / impact: medium likelihood, low impact.

Mitigation: clipboard falls back to execCommand and then to a visible warning that asks the user to select the preview text; the preview is always on screen.

Last re-evaluation: 2026-11-05 - accepted; preview text is the guaranteed fallback.

R-04A hidden section looks missing on first load

Applies to: T-01.

What can go wrong: an unconfigured record shows only five sections, so someone looking for Work Experience may think it is missing.

Likelihood / impact: medium likelihood, low impact.

Mitigation: the sidebar always shows "N sections hidden by this profile" next to the Show all sections toggle, and the setup note explains the rule (D-PP-16).

Last re-evaluation: 2026-11-05 - accepted; the toggle sits above the fold in the sidebar foot.

R-05Account prefill fills the wrong person on a shared device

Applies to: T-07.

What can go wrong: the signed-in user's name is written into a record that belongs to someone else.

Likelihood / impact: low likelihood, medium impact.

Mitigation: prefill only writes into empty fields, runs once per record, and the user can edit every value; nothing is sent anywhere.

Last re-evaluation: 2026-11-05 - accepted.
