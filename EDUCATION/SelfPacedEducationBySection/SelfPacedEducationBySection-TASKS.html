T1 Stable tab rail — no up/down jumping when switching tabs UXDONE
ProblemClicking a tab restored an absolute scroll offset saved on a different tab. Because tabs have very different content heights, the restored position got clamped to the new content's bottom — the page visibly jumped up and down with each click.
Why it mattersNavigation felt broken and disorienting; students lost their place and trust in the tool.
BenefitEvery tab switch now lands in the same deterministic position (study content top, right under the sticky header). The rail and content stay visually stable no matter how tall each tab is.
SolutionRemoved per-tab scroll memory; activateTab always calls alignScrollToStudyFlow(). Same-lesson re-renders (countdown refresh, quiz submit) restore the exact previous reading position instead of re-aligning.
LocationactivateTab / alignScrollToStudyFlow in SelfPacedEducationBySection.js (~line 1150)

ProblemThe quiz rail tab showed "(15 questions)" but the student only sees 5 questions per attempt (sets of 5). Misleading information.
Why it mattersStudents expected 15 questions and were confused when only 5 appeared.
BenefitHonest, calm labeling: the tab now reads "Test your knowledge".
SolutionSubtitle changed to 'Test your knowledge'.
Locationsteps tab-subtitle builder in renderLessonDetail (~line 980)
T3 Mark Complete checks only the current 5-question set — passing any ONE set (≥60%) is enough BUGDONE
ProblemmarkComplete() checked the FULL quiz (e.g. all 15 questions) before allowing completion — but the quiz is intentionally a 3-set retry pool and the student only ever sees the current 5-question set. The requirement was impossible to satisfy.
Design ruleAny set can be answered. Passing ONE set with ≥60% is enough to complete the lesson — the other sets exist only as retry opportunities. There is no need to answer all 15 questions.
BenefitThe completion gate now matches exactly what the student sees; no dead ends and no impossible requirement.
SolutionThe completeness check now loops only over the CURRENT set (same setStart .. setEnd range as submitQuiz). If the set is answered, the quiz is submitted and — when that set passes — the lesson completes in the SAME click. When it fails, the student gets the normal study guidance.
LocationmarkComplete() — the hasQuiz && !quizSubmitted branch
Acceptance15-question quiz: answer the visible 5, click Mark Complete → the set is submitted; ≥60% completes the lesson immediately, <60% starts study time. The "answer all questions" error is gone.

🔴 P0 — Bugs that block students (develop first)

T4 Guard empty quiz sets for short quizzes (the 3×5 retry-pool design is intentional) BUGP0
Design noteThe retry-pool design is intentional: the student may answer ANY set, and passing one set at ≥60% is enough (see T3). There is no requirement to answer all questions. The pool layout now adapts to the content — 15 questions still gives the classic 3 × 5.
ProblemThe set count was hardcoded, so a lesson with fewer than 15 questions produced partial or empty sets ("Set 3 of 3" with 0 questions). An empty active set could trap a student in study mode, and the retry button could disappear on the last set.
Why it mattersShort quizzes are common, and an empty set silently traps a student.
BenefitAny quiz length works correctly, every set is non-empty, and every question in the content is used.
SolutiongetQuizSetLayout(n): sets = min(3, max(1, ceil(n/5))), perSet = ceil(n/sets). Clamp currentSet/setIndex everywhere, guard submitQuiz against empty sets, always show Retry on fail, and adapt the supervisor view to the real set count. ✅ DONE
LocationrenderQuizInFlow, submitQuiz, getQuizPassedSetIndex, renderQuizSetsTabs, renderQuizSetHtml, markComplete
Acceptance15 questions → 3 × 5 (unchanged). 6 questions → 2 sets of 3. 7 questions → 2 sets (4 + 3). 20 questions → 3 sets (7 + 7 + 6). No empty set can ever be rendered or scored; failing always moves to a valid set.
T5 Study countdown re-renders the whole lesson every 30 seconds BUGP0
ProblemWhile a student is in "study time", renderQuizInFlow calls setTimeout(renderLessonDetail, 30000). Each re-render rebuilds every tab, re-fetches every PDF/HTML doc, and resets in-tab state (flipped flashcards, zoom levels). Scroll position is now preserved (fixed this session) but the rebuild itself is still heavy and causes flicker.
Why it mattersBandwidth waste on mobile, visible flicker every 30 s, loss of in-tab UI state, and repeated network load for every PDF in the lesson.
BenefitStudying becomes smooth and cheap; the countdown still updates live.
SolutionReplace the full re-render with a live countdown: update the "⏳ ~N min remaining" text in place via a 1-minute interval. Re-render only when the state actually changes (timer expired, answers submitted).
LocationrenderQuizInFlow — isStudying && studyRemaining > 0 branch
AcceptanceDuring study time, the countdown text updates with no re-fetch (DevTools network tab stays quiet) and no scroll/flicker change.

🟠 P1 — High-value UX & correctness

T6 PDFs render eagerly for ALL tabs and re-fetch on every re-render PERFP1
ProblemrenderLessonDetail queues every PDF in every tab for immediate rendering — even tabs the student never opens — and the bytes are fetched again on every re-render.
Why it mattersLesson open is slow and data-heavy; on weak connections PDFs may never finish, and every internal re-render multiplies the cost.
BenefitFast lesson open, far less bandwidth, same experience once a tab is opened.
SolutionLazy-render PDFs on first activation of their tab, and cache fetched buffers / PDF.js documents per URL in memory (invalidate when the URL list changes).
LocationrenderPdfIntoContainer + the window._pdfRenderQueue flow

T13 Stale-echo protection can swallow a supervisor's save (no optimistic concurrency) RISKP1
ProblemonValueChange ignores any parent value that differs from our last save within a 3-second window. If a supervisor approves/rejects a lesson in that window (or the student and supervisor are on the record simultaneously), the newer supervisor data can be overwritten by the stale-echo rule.
Why it mattersSupervisor decisions are the highest-value data on the record — silently losing one erodes trust.
BenefitStudent saves and supervisor actions can never silently clobber each other.
SolutionAdd a lightweight baseVersion (or updatedAt) to the stored progress. Accept incoming parent data when it is newer than our own; reject-and-re-stage only when it is provably older. (Topic was parked in an earlier session — revisit with this design.)
LocationonValueChange stale-echo block + saveProgress()
