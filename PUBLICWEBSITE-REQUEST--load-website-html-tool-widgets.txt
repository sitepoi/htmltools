PUBLICWEBSITE — LOADING A WEBSITE-HTML-TOOL AS A PAGE WIDGET
Complete publish-side contract: what a website-html-tool is, where
the publishing app gets its code, and how to render it on the page
(SSR + hydration). Hand this to the PublicWebsite codebase that
publishes the content generated by the WebpageBuilder tool.
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

0. WHY THIS DOCUMENT EXISTS

The WebpageBuilder tool lets users search the application-store
library and insert tools as WIDGETS into a page. The tool emits only
the island markup below. The PUBLISHING APP is responsible for turning
that markup into a working widget: on the server (SSR) and in the
browser (hydration). Today the published page shows nothing because
the publishing app does not yet load website-html-tool widgets at all.
This document is the binding contract to implement that.

1. WHAT A WEBSITE-HTML-TOOL IS

A library item in the application store
(cmsObjectType: website-html-tool-library-applicationstore) is a
self-contained html tool — exactly the same shape as a CMS html tool:

    code.html   the widget's markup (body fragment, NO document tags)
    code.css    the widget's stylesheet
    code.js     the widget's behavior

The JS is written for the CMS tool runtime: it boots through
window.tool.onReady(cb) (the same SDK contract CMS tools use) and/or
registers itself with gw.apps.register(name, factory). It may use
tool.getUser(), tool.param(), tool.notify(), tool.resize(),
tool.isReadOnly(), tool.requestObjects(...) for read-only data, and
window.gw for db/forms/services. It must NEVER use tool.requestAI or
any write/upload API on the publish side.

2. THE ISLAND MARKUP (what page builders emit — already the binding
   contract, do not change it)

     <div data-gw-app="Food Ordering Cart" data-gw-config='{}'></div>

   - data-gw-app       = the widget NAME as published in the library
                         catalog (gwAppName field).
   - data-gw-config    = VALID JSON (double-quoted). The builder
                         generates it from the widget's configSchema;
                         it may be '{}' when the schema has no fields.
   - Convention: single-quoted attribute holding double-quoted JSON
     (if the JSON must contain apostrophes, double-quote the attribute
     and &amp;-escape inner quotes).
   - The island sits INSIDE the page's composed html fragment
     (data.htmlPage.code.html), possibly inside a section. The page
     itself may carry several islands of different widget names.

3. WHERE THE PUBLISHING APP GETS THE WIDGET CODE (SSR-side, server-only)

   The store host is platform-owned: applicationstore.uniconhub.com.
   Public API v2 (x-api-key header; the publishing app authenticates
   server-side, never the browser):

     Catalog list:
       GET {base}/api/v2/objects/website-html-tool-library-applicationstore
       -> array | { items: [ObjectRecord...] } | { objects: [...] }

     Record detail (when the list omits code — REQUIRED capability):
       GET {base}/api/v2/objects/website-html-tool-library-applicationstore/{objectId}
       -> { object: ObjectRecord }

   ObjectRecord anatomy (v2): field values live in
   productData.data_categoriesBased.{fieldId}:

     gwAppName      string    island name (== data-gw-app value)
     title          string
     description    string
     category       string
     configSchema   object?   JSON schema for config defaults
     ssrHtml        string?   SERVER-RENDERED markup for the widget
                              (optional but STRONGLY recommended for
                              SEO-critical widgets)
     code           object    { html, css, js } — the widget's own
                              three blocks (REQUIRED for hydration)

   RULES:
   - The publishing app must resolve each island's record from a
     SERVER-SIDE cache of the catalog (refreshed on a schedule,
     optionally pinned per page by an optional data-gw-app-version
     attribute). Never fetch from the browser.
   - The catalog LIST SHOULD include the `code` block for every record
     so one fetch serves everything. If the list stays lean, the
     DETAIL endpoint above is mandatory and the app must fetch missing
     code by objectId at render time.
   - If a widget is NOT in the catalog: render nothing (or an inert
     placeholder only in preview mode), log a server warning — never
     break the page.

4. HOW TO LOAD IT ON THE PAGE — THE FULL PIPELINE

   STEP A — SSR (server render, before caching):
     1. Scan the composed page HTML for [data-gw-app] islands and
        resolve each unique widget name to its catalog record (step 3).
     2. Widget markup inside the island, in priority order:
          a. If record.ssrHtml exists: inject it INSIDE the island div
             and mark data-gw-ssr="1".
          b. Else if record.code.html exists: inject it INSIDE the
             island div and mark data-gw-ssr="template".
          c. Else: leave the island empty, mark data-gw-ssr="none"
             (no error, no crash).
        Output must stay DETERMINISTIC (Redis/CDN cache keyed by page
        version) — no Math.random/time in SSR output.
     3. Widget CSS: append record.code.css to the page <head> AFTER
        page CSS, ONCE per unique widget (dedupe across islands).
     4. Widget JS: emit record.code.js ONCE per unique widget, after
        the page's own JS, before the auto-mount script (Step B).
     5. Provide the TOOL SHIM before any widget JS runs (widgets are
        html tools — they boot through window.tool):

          window.tool = {
            onReady:        fn => queue/fire fn({ fields: {...} }),
            onValueChange:  fn => no-op registration,
            onReadonlyChange: fn => no-op registration,
            onUserChange:   fn => no-op registration,
            getUser:        () => { id, name, roles } | null,
            param:          (name, def) => widget config value with
                                        that key, else def,
            getFields:      () => ({ ... }),
            notify:         () => {},
            resize:         () => {},
            isReadOnly:     () => true,
            requestObjects: (action, params, cb) => READ-ONLY relay to
                            the CMS objects API (query/get only),
            requestAI:      undefined (must not exist on publish side)
          };

   STEP B — HYDRATION (after page scripts, before auto-mount completes):
     1. The widget's code.js runs exactly like page js: idempotent,
        no top-level await. Widgets that follow the registry contract
        call gw.apps.register(name, factory) — factory receives
        { el, config, gw } and may return a cleanup function.
     2. The platform auto-mounts every [data-gw-app] island
        (idempotent — mark data-gw-mounted="1", never double-mount):
          - config = JSON.parse(data-gw-config) with configSchema
            defaults applied for missing keys;
          - if a registered factory exists, call it with
            { el, config, gw };
          - the factory hydrates/replaces the SSR markup inside el
            (SSR is a progressive-enhancement first paint — the client
            render wins after hydration).
     3. A failing island is isolated (gw:app-error event, console
        warning) and never breaks the app shell.
     4. SPA navigation: unmount on page unmount (call returned cleanup
        functions, remove data-gw-mounted), then re-run Steps B.1-B.3
        for the new page. Tool-style widgets boot again via onReady.

   STEP C — CLIENT-ONLY MODE (opt-in, NOT the default):
     A catalog record may set ssrEnabled:false. Then: no server markup
     (data-gw-ssr="client"), and the island renders fully client-side
     in Step B. Use ONLY for widgets needing browser-only APIs,
     auth/session state, or non-deterministic content. SSR stays the
     default (better SEO/first paint/caching) — it is safe because the
     island code is platform/admin-authored library code (trusted),
     config values are DATA (widgets must render values with
     textContent / gw.sanitize), and raw client writes are banned.

5. SECURITY / CONSISTENCY NOTES
   - Island code is library code, not tenant content: trusted at build
     time; config values are data — escape on render.
   - Determinism: SSR output must not depend on Math.random/time.
   - The WebpageBuilder tool's own PREVIEW is client-side-only: it
     runs record.code.{html,css,js} via the tool-shim + gw.apps
     auto-mount; if the catalog list omits code it asks the parent CMS
     for the record detail (requestObjects 'get') and re-renders;
     unknown widgets get a clearly-marked placeholder chip.

6. ACCEPTANCE TESTS
   A. A page containing
      <div data-gw-app="Food Ordering Cart" data-gw-config='{}'></div>
      renders in the SSR HTML the widget's ssrHtml (or code.html)
      inside the island with data-gw-ssr set; after hydration the
      island shows the client render and data-gw-mounted="1".
   B. Same page cached: SSR output identical across two renders.
   C. Widget with ssrEnabled:false → empty island server-side,
      rendered client-side after hydration.
   D. A tool-style widget (boots via window.tool.onReady, no
      gw.apps.register call) boots once per page via the shim and
      renders inside its island; it never receives requestAI.
   E. Unknown island name → page still renders, warning logged, no
      runtime error.
   F. Invalid data-gw-config JSON → island mounts with {} and a
      warning (page unaffected).
   G. Two islands of the SAME widget → css/js emitted once, both
      islands mounted independently.
   H. SPA navigation away and back → islands unmount cleanly and
      re-mount without duplicates (no leaked listeners).
