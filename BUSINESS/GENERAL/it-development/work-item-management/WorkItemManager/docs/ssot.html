1. Purpose and governance

This document defines one tool and one set of invariants around the Work Item Manager - and it is the single source of truth for every decision we make about this tool, now and in the future. No decision is considered made until it is written here. Rules of use:

  • Every decision is logged here. Before or together with any change to this tool, the decision is added to section 11 with a date, and the affected section is updated in the same change.
  • The register is append-only. Decision rows are never deleted. A reversed decision is marked "Reversed (date)" with a reason - the original row stays for history.
  • This document wins ties. If this document or the code disagree, the discrepancy is resolved in this document first (with a dated decision), then applied to the code - never the other way around, and never silently left divergent.
  • Check before changing. Before changing any behavior covered here, read the relevant section and the register; after the change, update this document in the same change as the code.
  • Names must be self-explanatory. Every variable, function, and code snippet in any update uses understandable names. No cryptic abbreviations. Short names are allowed only for loop indexes and universally known abbreviations (id, url, api).
  • Acronyms are always expanded next to every use - in prose, tables, and headings. Literal identifiers stay as they are.

Core guarantee. One item, one screen: the form shows the item, Save writes only the fields that changed, the progress rail and the close checks follow what is typed, and the prompt never contains an unresolved double-brace placeholder, undefined or null.

5. Verified problem and root cause

5.1 Verified evidence

  • 2026-11-04 - the first build of this tool was a prompt screen with a summary card. The fields that decide the work (status, owner, reported build, tool library build, checker) were only listed as labels, so the developer still worked from the CMS form above it.
  • 2026-11-04 - the lifecycle had no representation. Nothing on the screen said what the next step of the item was.
  • 2026-11-04 - the two closing rules of the Hub (a newer tool library build, and a recorded checker) existed only in the Hub document. The tool never checked them.
  • 2026-11-04 - the harness asked for a file when it was opened from disk, while every other harness in the repository mounted straight away.

5.2 Current implementation (verified in code)

The close checks are computed from the record on every render, so the screen can never claim the item is closable when it is not:

// app/WorkItemManager.js - buildCloseChecks, the two hard rules of the Hub
var buildComparison = isBuildNewer(record.toolLibraryBuild, record.reportedBuild);
checkList.push({ label: 'Tool library build is newer than the reported build', state: comparisonState, note: comparisonNote });
checkList.push({ label: 'Checked by is recorded', state: record.checkedBy ? 'pass' : 'fail', note: checkedByNote });

5.3 Structural flaws

  1. The screen was organised around the output, not the work. The prompt sat on the right and took most of the space, so the tool read as a prompt generator that happens to sit on a record.
  2. The item state was a card of labels, not a lifecycle. No step, no next action, no sense of where the item is.
  3. The closing rules were documentation only. The two hard rules of the Hub were never checked against the record.
  4. The harness depended on reading a neighbouring file. Under file:// that read is blocked, so the harness asked for a file that every other tool loads by itself.

Root cause: the tool was designed as a prompt generator mounted on a record, instead of a work item page whose last step produces a prompt.

6. Requirements

  1. The tool opens on the item: key, kind, status and severity chips, then a form with every editable field. One screen, no scrolling to find the item.
  2. The item can be entered and changed in the tool: Save item writes only the changed fields, a record without an id is created with a key, and a refused write says what the administrator must enable.
  3. Nothing is lost by accident: an unsaved-change marker, a Discard changes button, and a title is required before a save.
  4. The lifecycle new, accepted, working, done is shown as a rail, with rejected as a branch, and the next step is one plain sentence.
  5. The close checks are computed on every keystroke: owner, reported build, proof, tool library build, the build comparison and the checker, with the self-check labelled.
  6. Working notes are append only, carry author and time and stay in the tool value, because the item timeline belongs to the CMS.
  7. The prompt tab is read-only and builds the change-existing prompt from the item data alone, with no input fields and no unresolved placeholder.
  8. Four tabs, no long page: Item, Progress, Notes, Prompt.
  9. The tool looks like the documentation: Inter with the system fallback, the SSOT colour tokens, pill tabs, one accent colour, one-line UI copy.
  10. No horizontal scroll at 390 px and at 1280 px.
  11. The harness opens from disk without a file picker and still loads the real file when served over http.
  12. Screenshots are added in the tool, stored as a list of URLs in the tool value, and carried into the prompt.
  13. The tool always opens and stays on the Item tab.

8. Solution design

8.1 Core invariant

Invariant P1. The form is a draft of the record: the screen renders the draft, the progress rail and the close checks follow the draft, and the record changes only when Save item sends the fields that actually changed. The prompt is a pure function of the draft, the attached screenshots and the active template, and it never contains a double-brace placeholder, undefined or null - and never a section with no content.

8.2 Rendering the item and its position

// app/WorkItemManager.js - renderLifecycle, one rail, one current step
var currentStepIndex = LIFECYCLE_STEPS.indexOf(record.status);
var isRejected = record.status === 'rejected';
var isPastStep = !isRejected && currentStepIndex > -1 && stepPosition < currentStepIndex;
var isCurrentStep = !isRejected && stepPosition === currentStepIndex;
  • Every value is normalised by toDisplayText before it reaches the screen: a person object becomes a name, a select object becomes its label, an array becomes a comma list, and the strings undefined, null and NaN are treated as empty.
  • The status is lower-cased once, so a CMS value of Working still matches the rail.
  • Build stamps are parsed as YYYY-MM-DD-N and compared by date first, then revision. A value that is not a build stamp makes the comparison say so instead of guessing.
  • The notes are capped at 200 entries, newest last in storage and newest first on screen.
  • Prompt inputs save after a 400 ms pause; adding a note and generating the prompt save immediately.

12. Maintenance rules

  1. This document is the single source of truth for every decision about this tool. Every decision is recorded in section 11 with a date, and the affected section is updated in the same change as the code. A decision that is not in the register did not happen.
  2. Rollback of a decision = mark it "Reversed (date)" with reason; never delete rows.
  3. Invariant P1 (section 8.1) is reviewed against every new call site: the screen renders the draft, and the record changes only through Save item.
  4. Save item sends only the fields that changed. A whole-record write from the tool is forbidden: it would overwrite the form silently.
  5. When section 19 of the Hub SSOT changes, the built-in prompt array in app/WorkItemManager.js is updated in the same change, and the build stamp moves.
  6. When the app markup changes, the embedded copy inside app/test-harness.html is re-pasted in the same change. The harness reports a mismatch when served over http.
  7. The JS keeps the two tokenizer hazards escaped: the html comment opener as \u003C!-- and the closing script tag as <\/script>.
  8. Global naming rule: any update - code or documentation - MUST use understandable, self-explanatory names. No cryptic abbreviations. Existing misleading names are renamed when their code is touched.

14. Open questions

Decision points we resolve together before or during implementation. Every answer becomes a dated row in section 11.

  1. Should the notes survive a tool uninstall? They live in the tool value, so a removed field would take them along. Moving them to the item timeline would need a write, which D-WIM-09 forbids.
  2. Should the close checks block a status change? They are computed and shown, but the status is set in the CMS form, which this tool does not validate.
  3. Should the tool show the parent finding of a task? The Hub has a one-level parentId link. It would help a chat that continues a converted finding, and it is not read by this build.
  4. Should line 7 of the report be pre-filled with the next build number? The tool knows the reported build, not the next one, and a wrong prediction is worse than the placeholder.
