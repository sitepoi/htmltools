1. Purpose and governance

This document defines one tool and one set of invariants around [what the tool does] - and it is the single source of truth for every decision we make about this tool, now and in the future. No decision is considered made until it is written here. Rules of use:

  • Every decision is logged here. Before or together with any change to this tool, the decision is added to section 11 with a date, and the affected section is updated in the same change.
  • The register is append-only. Decision rows are never deleted. A reversed decision is marked "Reversed (date)" with a reason - the original row stays for history.
  • This document wins ties. If this document or the code disagree, the discrepancy is resolved in this document first (with a dated decision), then applied to the code - never the other way around, and never silently left divergent.
  • Check before changing. Before changing any behavior covered here, read the relevant section and the register; after the change, update this document in the same change as the code.
  • Names must be self-explanatory. Every variable, function, and code snippet in any update uses understandable names. No cryptic abbreviations. Short names are allowed only for loop indexes and universally known abbreviations (id, url, api).
  • Acronyms are always expanded next to every use - in prose, tables, and headings. Literal identifiers stay as they are.

4. Glossary

Terms used in this document, with the exact meaning used here. Add a row whenever a discussion introduces a term - one meaning per term, so every reader and every AI sees the same definition.

TermMeaning
Question setA request or application pack: a named group of sections and fields selected for a record independently of the customer's identity type. Stored in profileKeys.
Profile configurationThe full app-level JSON stored in the CMS profileConfig parameter. When it defines segments, it takes precedence over applicationType.
Application typeA built-in shortcut stored in applicationType that selects a named question-set catalog, app title, labels and default keys. It never filters by customer type; the question-set library can still select any set.
SegmentAn app-defined customer or profile type, such as Student, Guardian, Client or Supplier. Stored in segmentKey.
Base typeThe core identity layout a segment uses: person or company.
Fixed formA segment with allowProfileSelection: false; the app decides the form and hides selection controls.
Selectable profileA segment with allowProfileSelection: true; the user selects from allowedProfileKeys.
Segment keyThe stable identifier written to the record. It must not be renamed after records exist.
PresetA complete profileConfig JSON file in profiles/, ready to copy into the CMS.

T-ACP-02Remove customer-type filtering and make type identity-onlyMandatory

Problem: An appliesTo or vertical filter hides question sets that do not match the customer type, so a software seller cannot profile an arbitrary customer.

Approach: The identity type now only chooses the person/company basic fields. Every question set is available to either type, selecting one never changes the type, and the library reports all 12 built-in sets without vertical tags. QA asserts the combination and type-switch behavior.

Files: app/CustomerProfile.js, app/qa-cdp.js, app/qa-datapacks.js

T-ACP-03Add the catalog picker with an all-question-sets library escape hatchMandatory

Problem: A small application catalog keeps the common flow short, but it can hide the question set the user actually needs.

Approach: In application mode the picker uses the catalog keys, Select all is scoped to the catalog, and the count reports selections outside the catalog. All question sets opens the existing library with every profile; choosing an outside set keeps it and renders its sections.

Files: app/CustomerProfile.js, app/qa-appcontext.js

T-ACP-04Migrate legacy company-vertical profile keysMandatory
