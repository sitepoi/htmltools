1. Purpose and governance

This document defines one tool and one set of invariants around browsing and managing a CMS asset library that is stored entirely in this field's value - and it is the single source of truth for every decision we make about this tool, now and in the future. No decision is considered made until it is written here. Rules of use:

  • Every decision is logged here. Before or together with any change to this tool, the decision is added to section 11 with a date, and the affected section is updated in the same change.
  • The register is append-only. Decision rows are never deleted. A reversed decision is marked "Reversed (date)" with a reason - the original row stays for history.
  • This document wins ties. If this document or the code disagree, the discrepancy is resolved in this document first (with a dated decision), then applied to the code - never the other way around, and never silently left divergent.
  • Check before changing. Before changing any behavior covered here, read the relevant section and the register; after the change, update this document in the same change as the code.
  • Names must be self-explanatory. Every variable, function, and code snippet in any update uses understandable names. No cryptic abbreviations. Short names are allowed only for loop indexes and universally known abbreviations (id, url, api).
  • Acronyms are always expanded next to every use - in prose, tables, and headings. Literal identifiers stay as they are.

Core guarantee. A drive record is always read back into a normalised shape, and the browser never invents a folder record: folders exist only because a file path or an explicitly created empty folder says so, so the tree, the breadcrumb and the file list can never disagree.

5. Verified problem and root cause

5.1 Verified evidence

  • 2026-11-17: the CMS had no generic in-field asset browser; media URLs were copied from raw records or from an external drive.
  • The owner asked for a tool that behaves like the existing Asset Drive (FolderManager): folders from file paths, image previews, URL lists, downloads and basic file management.
  • Users need one place to browse, preview, copy URL lists and download files without leaving the CMS record, while the tool stores no binary data of its own.

5.2 Current implementation (verified in code)

// app/AssetDrive.js - the normalized field value (authoritative shape)
{
  folderId: string,
  name: string,
  files: [{
    id: string, name: string, displayName: string, path: string,
    url: string, thumb_url: string, cdnUrl: string, contentType: string,
    size: number, updatedAt: number, firstUploadedAt: number,
    starred: boolean, locked: boolean, tags: string[],
    colorLabel: 'red' | 'orange' | 'yellow' | 'green' | 'blue' | 'purple' | '',
    versions: [{ url: string, size: number, updatedAt: number }]
  }],
  emptyFolders: [string]
}

5.3 Structural flaws

  1. No folder records. A folder only exists while a path or an empty-folder entry references it, so a naive folder table would drift from the files.
  2. Opaque URLs. Effective and thumbnail URLs follow a fallback chain; any code path that reads url directly would miss a CDN override or a thumbnail.
  3. Sandbox limits. No direct fetch, no storage APIs and no browser dialogs; every outside action must go through the tool SDK.

Root cause: the asset index must be one normalised metadata value whose folders are a pure function of the file paths, with a single URL rule shared by every action. A second folder table or a direct-URL shortcut would immediately create two disagreeing views of the same drive.

6. Requirements

  1. R-01 Field-value only. The drive lives entirely in this field's value; no Firestore call and no requestObjects is made.
  2. R-02 Folder consistency. The tree, the breadcrumb and the file list are all derived from the same path model and must always agree.
  3. R-03 URL rule. Copy, open, share and download use cdnUrl || url; previews use thumb_url || cdnUrl || url.
  4. R-04 Safe rendering. Every file and folder name is escaped before it enters markup; no HTML from a record is executed.
  5. R-05 Read-only. tool.isReadOnly() and a viewer-only identity hide every mutation, while browsing, copy and download stay fully available.
  6. R-06 Malformed values. A null, JSON-string or incomplete value renders an empty drive instead of throwing.
  7. R-07 Size discipline. Only metadata is saved; a warning appears when the value approaches 900 KB.
  8. R-08 No browser dialogs. New folder, rename, move and delete use the in-tool modal; feedback uses tool.notify.
  9. R-09 Upload contract. Uploads use tool.requestUpload, respect the MB limit and turn the same path into an overwrite with at most three versions.
  10. R-10 Build freshness. The visible build badge, the boot log and the first-line stamps identify the running build.

8. Solution design

8.1 Core invariant

Invariant AD-INV-1. The tree, breadcrumb and file list are pure functions of value.files[].path plus value.emptyFolders. No UI action may create a folder that is not backed by one of those two sources.

8.2 Folder and record model

// app/AssetDrive.js - source of truth for folders
function buildFolderTree() {
  const root = { path: '', name: 'Root', children: [], direct: 0, total: 0 }
  files.forEach(file => ensure(dirNameOf(file.path)).direct += 1)
  emptyFolders.forEach(folder => ensure(folder))
  computeTotals(root) // recursive total = direct + children totals
  return { root, map }
}
  • Every navigation targets a path from that model; an unknown path is ignored.
  • Creating a folder only appends to emptyFolders; uploading into it removes that entry.
  • Moving or deleting the last file in a folder calls preserveEmptyChain so the folder stays visible.

8.3 Caller contract table

9. Failure matrix - deterministic outcomes

ScenarioOutcome
Value is null, a JSON string, or has no files arrayThe drive renders empty (Root) with no console error; the field is saved only after a user action.
Upload channel unavailable (allowUpload off)Warning toast; no record is created; the rest of the tool keeps working.
Upload larger than maxUploadSizeMbError toast naming the file and limit; no record is created.
Upload to an existing exact pathThe record is overwritten, its id stays, the old URL enters versions (max three), all other flags survive.
Upload with a similar name in another folderBoth records exist; a dismissible warning banner names the existing folder.
Move or delete a locked recordThe record is skipped and a warning reports the locked count; nothing changes for it.
Clipboard API rejectedThe hidden-textarea fallback is used; if both fail an error toast is shown and no copied state is applied.
Image URL fails to loadThe image is removed and the coloured type icon is shown instead; the card keeps its layout.
External value change while a detail or selection existsThe view re-renders, unknown paths fall back to Root, deleted selections and detail are pruned.
Value grows beyond 900 KBA one-time warning toast appears; the save still goes through; the warning resets below the threshold.

12. Maintenance rules

  1. This document is the single source of truth for every decision about this tool. Every decision is recorded in section 11 with a date, and the affected section is updated in the same change as the code. A decision that is not in the register did not happen.
  2. Rollback of a decision = mark it "Reversed (date)" with reason; never delete rows.
  3. Folder invariant. Every folder shown by the UI must come from a file path or emptyFolders; a new folder UI must never create a third source.
  4. URL invariant. Every consumer of a file URL uses effectiveUrl() or thumbnailUrl(); no direct file.url read is allowed in a new feature.
  5. Read-only invariant. canWrite() is the only mutation gate; a new mutation path must call it and must be re-evaluated by onReadonlyChange.
  6. Global naming rule: any update - code or documentation - MUST use understandable, self-explanatory names. No cryptic abbreviations. Existing misleading names are renamed when their code is touched.

14. Open questions

Decision points we resolve together before or during implementation. Every answer becomes a dated row in section 11.

  1. ZIP downloads. Which approach should replace the deferred ZIP feature: a small built-in STORE-only ZIP writer, the parent CMS relay, or no ZIP at all? The current build offers one-by-one downloads only.
  2. Placeholder records. Should .gitkeep records stay visible as tiny files, or be hidden from the grid while remaining in the value?
  3. Folder deletion semantics. Deleting a folder currently removes its empty-folder entries; should a different behaviour preserve the folder while deleting its records?
  4. Empty folders after a move. Moving the last file out of a folder keeps that folder as an empty folder. Is that the desired drive behaviour?
  5. Bulk and drag-drop upload. Should a later version accept multiple files or drag-and-drop into the grid? The current host channel uploads one file at a time.
  6. Automatic thumbnails. Should the tool generate a thumbnail URL on upload (I-06), or is a record-level thumb_url always supplied by the host?

I-01 ZIP downloads with a built-in STORE writer

Idea: pack the current folder, a recursive folder or a selection into one archive, with progress and skipped-file reporting.

Why: one download is easier than many browser download prompts, especially for large folders.

Idea: remove the binary as well as the record.

Discussion / outcome: Ignored - the tool SDK exposes no storage-delete channel and the host keeps the real security boundary. Record-level removal is the contract (D-AD-05).

Why: faster for a new folder with many assets.

Discussion / outcome: The host channel currently returns one file per picker call. Needs a host capability or a sequential upload loop (Q5).

I-05 Folder rename

Discussion / outcome: needs a host capability; the current fallback chain already supports a supplied thumbnail.

17.1 Scenarios

  1. AD-T-01 - first load. Open the harness with no value. PASS if the Root view renders with the empty state and no console error.

  4. AD-T-04 - search and filter. Search catalogue and apply each type filter. PASS if the results show their source folder and clearing restores the current folder.
  5. AD-T-05 - selection. Use Select, Ctrl/Cmd click, Shift click, All and None. PASS if the bulk count matches and navigation clears the selection.
  6. AD-T-06 - copy. Copy a single URL, this folder, this folder plus subfolders, image URLs and image thumbnails. PASS if every list is newline-separated, skips .gitkeep and shows the copied label.
  7. AD-T-07 - downloads. Download a folder one by one. PASS if one host URL call per file is started and the final notice counts them.
  8. AD-T-08 - upload. Upload a new file, then upload the same name again. PASS if the second upload keeps the record id and adds one version; an oversized file must be rejected with a toast.
  9. AD-T-09 - records. Rename, move, duplicate, star, lock, colour, tag and delete. PASS if each change survives a reload and locked records cannot be moved or deleted.
  10. AD-T-10 - folder lifecycle. Create an empty folder, upload into it, move out and delete the folder. PASS if the tree and record list stay consistent.
  11. AD-T-11 - read-only. Switch to a viewer or enable isReadOnly. PASS if upload, new folder and all mutations disappear while browse, copy and download remain.
  12. AD-T-12 - narrow layout. Load the harness at 420 px. PASS if there is no horizontal overflow, the tree opens as an off-canvas drawer and the grid uses two columns.

R-01 1 MB field-value limit

Applies to: T-AD-01, T-AD-08

What can go wrong: a drive with thousands of records and long URLs approaches the Firestore limit and the save can fail host-side.

Likelihood / impact: Low for normal drives, high for large media libraries.

Mitigation: metadata only; 900 KB warning; no binary or base64 in the value. Monitor the field size before the first large import.

Last re-evaluation: 2026-11-17 - warning implemented, risk accepted as a documented limitation (L-03).

R-02 Deleting a record leaves the stored file and its URL alive

Applies to: T-AD-10

What can go wrong: a shared URL keeps working after the record is removed, so the drive no longer reflects every live asset.

Likelihood / impact: Expected behaviour; medium impact on governance.

Mitigation: the delete confirmation says explicitly that the stored URL becomes unmanaged; the tool never claims to delete storage.

Last re-evaluation: 2026-11-17 - accepted by D-AD-05 (no storage-delete channel exists).

R-03 Read-only gating relies on the host identity

Applies to: T-AD-12

What can go wrong: a missing getUser API falls back to a no-identity mode; a UI-level user could attempt edits the host would normally reject.

Likelihood / impact: Low - the host enforces storage permissions and isReadOnly stays authoritative.

Mitigation: both tool.isReadOnly() and merged roles are checked; no write is attempted when the host is read-only.

Last re-evaluation: 2026-11-17 - accepted by D-AD-08.

R-04 Locked is only a record flag

Applies to: T-AD-10

What can go wrong: another tool or a direct record edit can change a locked record.

Likelihood / impact: Low inside this drive; medium if other tools share the field.

Mitigation: the UI blocks move/delete for locked records and reports the skipped count; the limitation is documented (L-05).

Last re-evaluation: 2026-11-17 - accepted.

R-05 Similar-name uploads create two records

Applies to: T-AD-08

What can go wrong: the same asset exists in two folders under slightly different names.

Mitigation: a dismissible warning banner names the other folder; both records are intentionally kept (D-AD-12).

Last re-evaluation: 2026-11-17 - accepted.

R-06 Stale CMS upload shows an old build

Applies to: the whole group

What can go wrong: the CMS serves an older JS file, so fixes appear missing.

Mitigation: the visible build badge, the boot log and per-file stamps; re-upload only the files whose stamp changed.

Last re-evaluation: 2026-11-17 - accepted (D-AD-11).

R-07 ZIP downloads are absent from the first release

Applies to: the whole core group

What can go wrong: users expecting a single archive must download files one by one and may face browser download prompts.

Mitigation: the download menu carries the one-file-at-a-time hint; ZIP is tracked as I-01 / T-AD-20.

Last re-evaluation: 2026-11-17 - accepted by D-AD-06.
