1. Purpose and governance

This document defines one tool and one set of invariants around collecting and maintaining one company profile - and it is the single source of truth for every decision we make about this tool, now and in the future. No decision is considered made until it is written here. Rules of use:

  • Every decision is logged here. Before or together with any change to this tool, the decision is added to section 11 with a date, and the affected section is updated in the same change.
  • The register is append-only. Decision rows are never deleted. A reversed decision is marked "Reversed (date)" with a reason - the original row stays for history.
  • This document wins ties. If this document or the code disagree, the discrepancy is resolved in this document first (with a dated decision), then applied to the code - never the other way around, and never silently left divergent.
  • Check before changing. Before changing any behavior covered here, read the relevant section and the register; after the change, update this document in the same change as the code.
  • Names must be self-explanatory. Every variable, function, and code snippet in any update uses understandable names. No cryptic abbreviations. Short names are allowed only for loop indexes and universally known abbreviations (id, url, api).
  • Acronyms are always expanded next to every use - in prose, tables, and headings. Literal identifiers stay as they are.

8.4 Saved value shape - invoicing (schema version 3)

{
  schemaVersion: 3,
  ...
  invoicing: {
    paymentInstructions: '',   // free text, printed as written
    invoiceFooterNote: '',     // max 160 characters, one line
    logoUrl: '',               // CMS upload link or external image URL
    logoName: ''               // file name for display, never a path
  }
}
  • normalizeDB creates the four keys when a record predates schema version 3, so old records open unchanged.
  • The summary reads basicInfo.legalName, billingAddress.email (or headquarters.email) and salesTaxDefinitions; it never writes them.
  • The logo field shows Upload, Replace and Remove when tool.requestUpload exists, and a logo URL input when it does not; both paths save only logoUrl and logoName.
  • sectionProgress returns no criteria for invoicing, so updateCompletion prints Optional and leaves the section out of the completion ring.

8.5 Record card contract

  • Data model unchanged: cards read and write the same arrays (salesTaxDefinitions, otherOffices, contacts.others, industryOps.capabilities, documents.certificates, referenceLetters, assets.owned, assets.partnerAccessible, humanResources.staffCapabilities, financials.annualRevenues, referenceProjects). A new list is one entry in RECORD_VIEWS with a list accessor, a create factory and field definitions.
  • Only one record editor exists at a time (openRecordViewId, openRecordIndex, recordEditorDraft). Opening another card saves the open card first, so no draft is lost silently.
  • Card editors are excluded from the debounced auto-save: inputs inside [data-record-editor] and [data-group-editor] use data-record-field and data-group-field, never data-section or data-field, so readAllFromDOM cannot half-read a draft.
  • Cancel and Escape drop the draft without writing. The Remove button arms on the first click and deletes on the second.
  • Field group editors write into the existing object on Save (industryOps, contacts.primary, financials, geographicCoverage). The matching read functions guard on element existence so a record is never wiped when the old inputs are gone.
  • Read-only mode hides Edit and Add actions and keeps every card readable.

8.6 Basic Information order

  • Step 1 is the company identity card (legal name, trade name, company type, year established, employees, registration number). Step 2 is the profile setup block with templates, the primary industry select and the coverage chips.
  • The identity card writes DB.basicInfo through the shared field group engine and runs afterSave, which adds the grants area once when the company type becomes non-profit or registered charity.
  • readBasicInfo only reads an identity input when it exists, so the card markup cannot blank a saved record during the debounced auto-save.
  • The industry select stays in the profile setup block because it drives section visibility, and Template chips still set industry plus coverage in one click.

8.7 Additional details on every section

  • Each built-in section ends with an Additional details area. With fields it lists the rows and offers a "+ Add another detail" button; without fields it shows a compact "+ Add a custom detail" link, so the add action sits where the result appears.
  • The section header + remains a shortcut. After adding, the new row is scrolled into view and its field name is focused.
  • Read-only mode hides both add actions while keeping existing custom values readable.

8.8 Brand images

{
  brandAssets: [
    {
      id: 'bi_xxx',              // stable id for edit and remove
      kind: 'Company logo',      // one of BRAND_IMAGE_KINDS
      name: 'ApexCon logo',      // display name, defaults to the file name
      url: 'https://...',        // CMS upload link or public image URL
      caption: 'Used on invoices' // optional, max 160 characters
    }
  ]
}
  • The gallery follows the card contract: one editor at a time, Save applies, Cancel and Escape discard, Remove needs a second click.
  • Uploads accept PNG, JPG, SVG and WebP up to 5 MB. Only the link and the name are stored, never the binary.
  • normalizeDB keeps only entries with a URL, so a record saved without an image cannot create an empty gallery card.
  • An image that fails to load shows a preview fallback on the card instead of a broken icon.

8.9 First-load visibility

  • profileIsConfigured() is true when a coverage area is selected, a template is stored, or the selected industry has a preset. It never changes data, only which sections the sidebar shows.
  • sectionHiddenByProfile() returns true for every section outside BASIC_SECTION_IDS while unconfigured, and falls back to the normal needs matching afterwards.
  • The sidebar note reads "N sections appear once you choose an industry, template or area" in that state, and "Show all sections" still reveals everything without configuring anything.
  • Custom sections are user-created and always visible, so nothing the user added disappears.

14. Open questions

Decision points we resolve together before or during implementation. Every answer becomes a dated row in section 11.

  1. Tender-specific data as its own section? Bonding and surety capacity, insurance limits, prequalification registrations and vendor numbers currently have no dedicated home - they would sit in Documents or Reference Projects. Should they become a "Tender & Procurement" section, shown only for the tender focus?
  2. Per-tenant presets? The industry presets are built in. Should a CMS application be able to supply its own preset (for example a tenant that always works with grants) through a tool parameter?
  3. Profile PDF export? Should a completed profile be exportable as a tender-ready PDF (cover, company identity, certificates, references, capacity), and is that a tool or a listing-tool feature?
