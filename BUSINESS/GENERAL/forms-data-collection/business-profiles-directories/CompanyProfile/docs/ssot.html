1. Purpose and governance

This document defines one tool and one set of invariants around collecting and maintaining one company profile - and it is the single source of truth for every decision we make about this tool, now and in the future. No decision is considered made until it is written here. Rules of use:

  • Every decision is logged here. Before or together with any change to this tool, the decision is added to section 11 with a date, and the affected section is updated in the same change.
  • The register is append-only. Decision rows are never deleted. A reversed decision is marked "Reversed (date)" with a reason - the original row stays for history.
  • This document wins ties. If this document or the code disagree, the discrepancy is resolved in this document first (with a dated decision), then applied to the code - never the other way around, and never silently left divergent.
  • Check before changing. Before changing any behavior covered here, read the relevant section and the register; after the change, update this document in the same change as the code.
  • Names must be self-explanatory. Every variable, function, and code snippet in any update uses understandable names. No cryptic abbreviations. Short names are allowed only for loop indexes and universally known abbreviations (id, url, api).
  • Acronyms are always expanded next to every use - in prose, tables, and headings. Literal identifiers stay as they are.

11. Decision register

IDDateDecisionRationale / riskStatus
D-CP-012026-11-04 Sections are shown or hidden by the profile setup in Basic Information (industry + coverage areas). Hiding is a navigation decision only: no data is deleted, hidden sections keep their saved values, and "Show all sections" restores every section. One tool must serve a construction company bidding on tenders and an IT company with no tender work. A single fixed 17-section form made both profiles noisy. The trade-off is that the sidebar can hide data the user forgot about; the hidden-sections note and the Show all toggle mitigate it. Adopted
D-CP-022026-11-04 Choosing an industry applies that industry's suggested coverage set only while the current selection is still the previous suggestion. Manual selections are never overwritten; the setup offers "Use the suggested set" instead. Prevents losing a hand-picked scope when the industry changes (common when a company is reclassified), while keeping the one-click preset benefit for new records. Adopted
D-CP-032026-11-04 The shell is modernised: grouped navigation, inline SVG line icons instead of emoji, section pager, completion ring, light/dark themes, responsive horizontal navigation below 820px. A profile used for tenders and contracts must look professional. Inline icons avoid an external icon library in the tool sandbox, and token-based theming keeps every component readable in both modes. Adopted
D-CP-042026-11-04 The saved value becomes schema version 2 with three extension points: profile.customFields (extra fields attached to any built-in section), profile.customSections (user-defined sections with their own field list) and industry-based starting templates. normalizeDB guarantees the structures and never removes unknown keys; adding a new field type or template is a data change, not a migration. New profile requirements must not force a rewrite of the tool or a migration of existing records. Custom fields and sections cover tenant-specific data; templates cover new scenarios (tenders, grants, vendor onboarding). The trade-off is that custom data has no typed validation beyond the chosen field type, which is acceptable because the tool is a data collector, not a validator. Adopted
D-CP-052026-11-04 Long statements are edited one card at a time: the Brand & Positioning section renders five read-only statement cards; Edit opens that card's textarea with a word count and Save / Cancel, and opening another card saves the current one first. Five stacked textareas looked like a draft form and made the section hard to scan. Cards keep the written profile readable while editing stays deliberate. The trade-off is that typing is not auto-saved until Save, which is why Cancel and Save are explicit. Adopted

14. Open questions

Decision points we resolve together before or during implementation. Every answer becomes a dated row in section 11.

  1. Tender-specific data as its own section? Bonding and surety capacity, insurance limits, prequalification registrations and vendor numbers currently have no dedicated home - they would sit in Documents or Reference Projects. Should they become a "Tender & Procurement" section, shown only for the tender focus?
  2. Per-tenant presets? The industry presets are built in. Should a CMS application be able to supply its own preset (for example a tenant that always works with grants) through a tool parameter?
  3. Profile PDF export? Should a completed profile be exportable as a tender-ready PDF (cover, company identity, certificates, references, capacity), and is that a tool or a listing-tool feature?

I-01 Tender readiness score

Idea: a score card for the tender focus that checks the evidence a submission usually needs: legal identity, tax number, insurance, safety certificate, three references, bonding capacity, financial statements.

Why: the completion ring counts sections, but a tender reviewer looks for specific evidence. A readiness score would tell the user what to collect next.

Discussion / outcome: new - depends on the Tender & Procurement section (T-05).

I-02 Per-tenant industry presets

Idea: let a CMS application pass its own coverage preset through a tool parameter instead of relying on the built-in industry list.

Why: a tenant that only works with grants, or only with municipal tenders, would start from an exact scope instead of an approximation.

Discussion / outcome: open question 2 in section 14.

I-03 Tender-ready profile PDF

Idea: export the profile as a formatted PDF: identity page, certificates with expiry status, reference projects, references and capacity.

Why: tender packages ask for a company profile document, and re-typing the same data into Word is where most of the time goes.

Discussion / outcome: open question 3 in section 14 - tool feature or listing-tool feature.
