1. Purpose and governance

This document defines one tool and one set of invariants around capturing a board meeting end to end - agenda subjects, notes, action items and time tracking - and it is the single source of truth for every decision we make about this tool, now and in the future. No decision is considered made until it is written here. Rules of use:

  • Every decision is logged here. Before or together with any change to this tool, the decision is added to section 11 with a date, and the affected section is updated in the same change.
  • The register is append-only. Decision rows are never deleted. A reversed decision is marked "Reversed (date)" with a reason - the original row stays for history.
  • This document wins ties. If this document or the code disagree, the discrepancy is resolved in this document first (with a dated decision), then applied to the code - never the other way around, and never silently left divergent.
  • Check before changing. Before changing any behavior covered here, read the relevant section and the register; after the change, update this document in the same change as the code.
  • Names must be self-explanatory. Every variable, function, and code snippet in any update uses understandable names. No cryptic abbreviations. Short names are allowed only for loop indexes and universally known abbreviations (id, url, api).
  • Acronyms are always expanded next to every use - in prose, tables, and headings. Literal identifiers stay as they are.

Core guarantee. A meeting record - subjects, tasks, notes, and the tracked times - is always written through the same normalized, debounced autosave pipeline, so a viewer can never alter data, an older save can never silently overwrite newer edits, and a page reload can never lose the last typed change. Everything below serves this one sentence.

5. Verified problem and root cause

5.1 Verified evidence

  • Board meetings run without a shared record: notes end up in personal notebooks, action items are assigned verbally and forgotten, and nobody knows how long each agenda item really took (observed in the tool ideas catalog entry that this tool implements, 2026-09).
  • Minutes written after the meeting from scattered notes take hours and miss follow-ups (same source).
  • Result for the user: meetings feel unstructured, follow-ups slip, and there is no projector view with a per-subject timer.

5.2 Current implementation (verified in code)

This document is written at the first ship of the tool, so there is no "before" implementation to quote. The baseline is the shipped code in app/MeetingNotes.js with the data model described in section 8.2.

5.3 Structural flaws addressed by the design

  1. No single source of truth for the meeting. Notes and tasks were separate artifacts; the tool keeps them in one normalized document that autosaves.
  2. No time pressure visibility. Agenda items had no countdown; the tool gives every subject a planned duration with a visible countdown, overrun and spent-time tracking.
  3. Minutes are tedious. Writing minutes by hand is slow; the AI Assistant drafts them from the subjects and raw notes.

Root cause: the meeting workflow was never supported by one structured, time-aware document - the tool replaces the notebook with a single autosaved record that drives the meeting itself.

6. Requirements

  1. The tool runs as a TYPE 1 html-tool inside the CMS sandbox iframe and talks to the host ONLY through the tool SDK - never through custom storage, servers or network calls.
  2. Every edit is saved through the debounced autosave pipeline; a page hide or reload must never lose the last change.
  3. Viewers can read everything but can never edit; write access follows the host role list plus the effective access flags.
  4. Stored data is normalized on load: unknown or malformed fields are clamped or dropped, so an old object version opens cleanly.
  5. Meeting Mode shows one subject at a time with a planned duration, a live countdown, overrun, and spent-time that keeps counting while the subject is on screen.
  6. Action items can be assigned only to people the CMS says are permitted on this object; if the host cannot provide the list, a plain text field is used instead.
  7. AI features degrade gracefully: when allowAi is off or the host has no requestAI, the tab shows a clear notice and nothing breaks.
  8. Exports are produced without third-party libraries; PDF goes through the CMS print pipeline when allowExportPdf is yes, otherwise an HTML download that the user prints.
  9. The output contract (declareOutput) always matches the normalized data model, including spentMs and meeting.waitingMs.
  10. No polling loops except the 500 ms Meeting Mode tick; no unbounded growth; the timer interval is the only recurring work.

8. Solution design

8.1 Core invariant

Invariant MN-1. Every mutation of the meeting document goes through a handler that updates the DB object and calls persistSoon(); every write path is gated by canWrite(); every read path renders from DB only. No code path writes the tool value directly.

8.2 Data model

// app/MeetingNotes.js - the persisted document (normalized)
{
  version: '1.1.0',
  meeting: { title, date, timestart, timeend, location, chair,
             minutetaker, attendees, waitingMs },
  subjects: [{ id, title, notes, notesHtml, status: 'open'|'done',
               durationMinutes (default 15), spentMs }],
  tasks: [{ id, text, assignee, dueDate, priority, status, source,
            subjectId }],
  rawnotes: '',
  ai: { summary, minutesDraft }
}
  • normalizeSubject() clamps durationMinutes to 1-480 (default 15) and spentMs to 0-86400000.
  • normalizeDatabase() migrates legacy subject.items into tasks with subjectId, and clamps meeting.waitingMs.
  • declareOutput lists the full shape including spentMs and meeting.waitingMs, so the CMS stores every tracked field.

8.3 Autosave pipeline

  • persistSoon() debounces 400 ms, then stages the normalized JSON.
  • The staged value is pushed via tool.setValue() and tool.requestSave(); a once-per-session warning appears if the host denies saving.
  • flushPendingSave() runs on pagehide and visibilitychange (hidden), so a close never loses the last edit.
  • _lastStagedJson is the echo guard: a value that round-trips equal to the staged JSON is not pushed again.
  • reportValid(false) fires while the meeting title is empty, so the CMS can show the object as incomplete.

8.4 Meeting Mode time engine

  • The timer strip lives in the RIGHT-SIDE panel above the tasks card, so the center column shows only the subject title and the notes page.
  • One 500 ms tick drives everything; _lastTickAt stores the previous wall-clock sample, so a sleeping tab never earns free time.
  • tickTimer() banks the elapsed wall time into the active target: subject.spentMs always, plus remainingMs decrement when running.
  • settleProjectionTime() banks the residual on switch / close / break and KEEPS state.running, so a started countdown resumes when the subject is shown again.
  • Overrun keeps the countdown negative (fmtClockSigned renders -0:05) and paints the timer red; quick buttons ADD minutes while running.
  • The waiting slot banks into meeting.waitingMs and pauses subject time; choosing a subject ends the break.

8.5 Assignee pickers from the CMS permission list

  • loadPermittedUsers() reads tool.getPermittedUsers() once on ready; onPermittedUsersChange re-applies the pickers and re-renders.
  • assigneeFieldHtml() renders a select with a "- No assignee -" first option plus the permitted names, and falls back to the old text input when the list is empty.
  • Used in the Tasks tab cards, the new-task form, the Meeting Mode panel rows and its quick-add; the change listener routes data-field="task.assignee" to handleFieldEdit().

8.6 Role gating

  • canWrite() is true for the roles admin, editor, owner, developer, user-manager, or when the effective access flags are editor/manager, or when no identity is available (_noIdentity).
  • Viewers get disabled inputs, hidden edit buttons, no toolbar and a read-only Meeting Mode; the identity is polled until the host answers.

12. Maintenance rules

  1. This document is the single source of truth for every decision about this tool. Every decision is recorded in section 11 with a date, and the affected section is updated in the same change as the code. A decision that is not in the register did not happen.
  2. Rollback of a decision = mark it "Reversed (date)" with reason; never delete rows.
