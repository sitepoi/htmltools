1. Purpose and governance

The flow touches three systems and three codebases, and today no single document describes it end to end:

  1. CMS webpage builder (cms.uniconhub.com) - authors webpages and embeds website-html-tools as widget islands.
  2. Application store (applicationstore.uniconhub.com) - hosts the published website-html-tool catalog.
  3. publicwebsite renderer (www.uniconhub.com) - fetches pages from the CMS, renders them, discovers widget islands, fetches the tool code from the store and embeds it in the generated page.

Each project owns its section here and fills it in the same change as any code that alters its side of the contract. The renderer-side sections were verified from the publicwebsite code on 2026-10-09. The CMS builder side (this document's 8.1, 8.2, 8.4 write view, 8.7 authoring side, the CMS publish facts in 8.3 and D-WFLOW-09..13) was verified from the sitepoicms code on 2026-10-09. The WebpageBuilder TOOL side (the 8.1/8.2 tool-internals blocks, the tool rows of sections 2/3/9, the 8.4 note and D-WFLOW-14..16) was verified from the HTMLBasedTools repo code (app/WebpageBuilder.js build 2026-10-09-3) on 2026-10-09. The application store DEPLOYMENT internals (ssrHtml generation, versioning, SHELL markers, the revalidate webhook) remain explicit TO FILL blocks with questions, owned by the store deployment.

5. Verified problem and root cause

The knowledge of how a webpage with widgets travels from the CMS builder through the application store to www.uniconhub.com is scattered across three codebases. Each side knows its own half; the shared contract (field names, island markup, catalog endpoints, ssr markers, invalidation) has no single home.

Evidence: the publicwebsite AGENTS.md sync table already lists a page-rendering SSOT document that does not exist in the workspace; the builder-side and store-side behavior exists only as assumptions inside the renderer code (tolerated field aliases, envelope shapes, marker semantics).

Root cause: the three systems were built against each other's outputs without one shared design document, so the contract drifted (example: pages store webpageContentWithBuilder.code while the renderer's fixed field is htmlPage.code - the renderer reads both as aliases).

8.1 Phase A - webpage creation in the CMS webpage builder VERIFIED (CMS side, sitepoicms code, 2026-10-09)

VERIFIED - what the renderer READS from a created page (the builder must produce exactly this):
  • The page is an object in the site app's folder tree (section 8.4).
  • Content contract: data.htmlPage.code.{html,css,js} is the fixed html-tool field; webpageContentWithBuilder.code.{html,css,js} is read as an alias; field lookup order is data first, then productData.data_categoriesBased.
  • SEO precedence (builder-first): webpageContentWithBuilder.seo → data.seo → record.seo; language: webpageContentWithBuilder.meta.language → record.meta.language.
  • data.css / data.js are tolerated as embedded style/script blocks, but the canonical fields are code.css / code.js.
  • The page html must be a pure body fragment - never <!DOCTYPE>, <html>, <head>, <body>.
  • Optional data.sections references reusable section objects (max 20, each with own html/css/js).
  • Draft pages are hidden unless preview is requested (404 otherwise).
VERIFIED - how the CMS writes pages (the builder side of the read contract above). The CMS (sitepoicms) is a GENERIC object engine - the webpage builder is not a hardcoded editor in this codebase. Its facts:
  • The website publishing app is an app definition (website-builder-uniconbaseapps, observed in the dev trace .next/dev/trace as /objects/website-builder-uniconbaseapps and /manage/settings/app-designer/website-builder-uniconbaseapps), configured in App Designer and stored in cms-settings.objectTypes[] (Firestore) - not in code. Its field groups define the page fields.
  • Page objects live in om_objects (or om_private_objects when the type has rules.publicAccess === 'no'), routed by getObjectTableName(mainObjectType) in utils/appUtils.js. Folders live in om_object_types.
  • Field data envelope: every field value is stored as productData.data_categoriesBased.{fieldId: value, objectStatus: ''} (data/firebase/objects.js lines ~474-477; PageBlocks/object-manager/ObjectManager.js maps this to objectData in the UI and back on save - the comment reads "Will be productData in db, due to legacy reasons"). The page content fields (htmlPage, webpageContentWithBuilder) are therefore FIELD IDS defined in the app's field groups in Firestore - the ids appear in ZERO code files in this repo (only in this document). Which one is written when is app-config data; both field names are read by the renderer as aliases (D-WFLOW-04).
  • The builder UI is an html-tool. Page authoring runs inside a html-tool field rendered by components/families/display/HtmlToolViewer/FormHtmlToolItem.js (sandboxed iframe, postMessage SDK). The builder tool's own code lives in Firestore html_tools or the app store - outside this repo. The tool saves its result with tool.setValue(...), which lands in the field value (the same envelope above).
  • Object shell fields (Settings tab, PageBlocks/object-manager/ObjectSettings.js): top-level slug and contentId; meta.language, meta.status ('enabled' | 'disabled'), meta.pageOrder, meta.category1..3, meta.relatedBaseProduct/relatedObjectType/relatedObjectIds; folder selector built from the parentId tree.
