1. Purpose and governance

This document defines one tool and one set of invariants around how the Webpage Builder generates, stores, updates, versions and exports single-page website code - and it is the single source of truth for every decision we make about this tool, now and in the future. No decision is considered made until it is written here. Rules of use:

  • Every decision is logged here. Before or together with any change to this tool, the decision is added to section 11 with a date, and the affected section is updated in the same change.
  • The register is append-only. Decision rows are never deleted. A reversed decision is marked "Reversed (date)" with a reason - the original row stays for history.
  • This document wins ties. If this document or the code disagree, the discrepancy is resolved in this document first (with a dated decision), then applied to the code - never the other way around, and never silently left divergent.
  • Check before changing. Before changing any behavior covered here, read the relevant section and the register; after the change, update this document in the same change as the code.
  • Names must be self-explanatory. Every variable, function, and code snippet in any update uses understandable names. No cryptic abbreviations. Short names are allowed only for loop indexes and universally known abbreviations (id, url, api).
  • Acronyms are always expanded next to every use - in prose, tables, and headings. Literal identifiers stay as they are.

Core guarantee. The page code the AI produces is always stored, versioned and exported as the SAME three separate blocks (html, css, js) that the PublicWebsite platform expects (data.htmlPage.code.{html,css,js}), so anything generated in this tool works in the platform without manual conversion. Everything below serves this one sentence.

5. Verified problem and root cause

5.1 Verified evidence

  • 2026-10-02: the user shared a REAL old-CMS page object ("Home Page", typeId 101-general-pages-MPT62Q-wwwuniconhobcom, slug home-page) with an 8-entry blocks array: 7 blocks of type html-code (each = one section div + one inline <style>) and 1 block of type json with meta.slug: "dynamic-form" and value {"form-type-id":"request-demo-form"}.
  • The new platform has NO blocks and NO dynamic-form — so pasting this object as-is into the tool would store everything inside the HTML block, fail compliance (inline styles, no honeypot form), and bypass the platform contract.
  • Result: old pages cannot be migrated into the new tool/website without manual copy-paste surgery.

5.2 Current implementation (verified in code)

// WebpageBuilder.js - no importer exists today
parseGeneratedCode()        // only parses AI responses (=== sections / legacy [HTML])
_ensureImageSrcs(html)      // only fills image placeholders
// nothing reads obj.blocks, obj.typeId, or meta.slug === "dynamic-form"

5.3 Structural flaws

  1. No importer entry point. The tool can only receive page code from AI chat or direct editor edits — there is no path for pasted CMS objects or ready-made pages to be normalized into the three blocks.
  2. No shared-source storage. Site-wide CSS/JS have no home in the tool: the platform supports default-settings.sharedCss and header/footer js, but the tool cannot edit or preview them.
  3. Paste goes straight to one editor. A whole page pasted into the HTML editor stays one blob (see Q-03) instead of being split into html/css/js.
  4. No widget / shared-source surface. The tool cannot place library widgets (data-gw-app islands) or reference shared sources (data.sections) - there is no picker for either, so reusable content and the widget library cannot reach pages.

Root cause: the tool only understands the NEW three-block model; it has no import surface for the two real sources of ready-made code — outside-authored pages and old-CMS blocks objects.

6. Requirements

  1. REQ-01 (Shared sources). The tool must let the user maintain site-wide CSS and site-wide JS, preview them together with any page, and export them in the platform-accepted form (default-settings.sharedCss for CSS; header/footer objects' htmlPage.code.js for JS).
  2. REQ-02 (Paste ready-made pages). The tool must accept a page prepared outside as three separate parts (HTML / CSS / JS) in one paste action, and also accept a whole page and AUTO-SPLIT it into the three blocks (deterministic splitter; AI only as a fallback).
  3. REQ-03 (CMS blocks import). The tool must accept a pasted old-CMS object (with blocks), convert every html-code block (strip inline <style>), convert dynamic-form json blocks into data-gw-form fragments, map name/slug/language/status into === PAGE META ===, and produce the three blocks + SEO + CMS CONFIG NEEDED notes.
  4. REQ-04 (Predictability). Import is deterministic and reversible: the user sees exactly what was extracted (per-block summary) before the result replaces the current page; history snapshot is taken before import so one click restores the previous state.
  5. REQ-05 (No data loss). Unrecognized block types or unparseable parts are preserved and REPORTED (never silently dropped).
  6. REQ-06 (Shared source objects). Shared content is stored as separate CMS objects with the SAME code.{html,css,js} shape as a page ("another instance of this tool in another object"). Two types: MANDATORY - injected directly into every page of the website; OPTIONAL - pages opt in by adding the shared source in this tool's config (data.sections, composed before the page's own content).
  7. REQ-07 (Widget library). The tool must let the user select any tool/widget from the website html tool library at applicationstore.uniconhub.com and add it to the page at the correct place as a widget island (data-gw-app + data-gw-config), with a valid generated config.
  8. REQ-08 (SSR + cache). Every generated page must be SSR-renderable and cacheable in Redis and Vercel CDN (and others if needed). Tool-side obligation: output stays pure static three-block code (no document tags, idempotent JS, deterministic, version-stamped). Rendering and caching themselves are platform-side (informational).

I-06 Shared source objects + companion builder

I-08 Outside sources policy (analytics / embeds / CDN)

Why: One auditable policy for everything outside the platform; pages stay clean, secure and cacheable.

Discussion / outcome: Scheduled: tasks T-11..T-12 (group g4-outside-sources). Open: CDN allowlist vs vendoring only.

I-09 SSR + cache-ready pages (Redis / Vercel CDN)

Why: Performance and SEO at the platform level; the tool must never block it (REQ-08, D-WB-03).

Discussion / outcome: Scheduled: tasks T-13..T-14 (group g5-ssr-cache). Open: widget SSR behavior (Q-09, platform-side).
