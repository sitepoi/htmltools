The whole platform in five boxes

Three rules that prevent 90% of the confusion

1 · One folder = one website

Two domains on one folder = one site answering on both. Two different headers/footers = two folders (two sites).

2 · Settings live on the folder, code lives in objects

Domain, language, theme, shared CSS, head/body code → folder. Page content, header/footer, widgets → objects. A page builder tool can never write folder settings.

3 · Reserved slugs are not pages

home-page, default-header, default-footer, default-settings are looked up by slug by the platform. Never use them for a normal page.

Connect a folder to a domain

Two halves: DNS (done once, at your domain registrar) and binding the hostname to the folder (done in the CMS, per site).

  1. Point the domain at the platform

    At your registrar, add the DNS records the platform gave you for the public website deployment (typically an A/ALIAS record for the bare domain and a CNAME for www). This step never happens inside the CMS.

  2. Open the site folder in the CMS

    Folders live in the app’s folder tree. The site folder is the one that owns the site (its descendants are its pages).

    Folder list → Edit on the site folder

  3. Fill the “Website / Domain” section

    This is the folder config section the website app declares (storage key websiteConfig). It is the only place the renderer reads the domain from.

  4. Add every hostname, then choose the canonical one

    hostNames = all hosts this site answers on. primaryHost = the one used for canonical URLs, sitemap and hreflang.

  5. Save, then open the domain in a browser

    The platform resolves host → tenant → site folder whose hostNames contains it, then renders the page whose slug matches the path.

  6. Create the home page

    A page object with slug home-page renders at /. Without it the domain resolves but shows “no page”.

Two sites, one domain? A hostname may belong to only one site folder. If a domain “jumps” to the wrong site, check that it is not still listed in another folder’s hostNames.
Preview secret is not optional. Draft pages are reachable only with ?gw-preview=<previewSecret>. No secret = no way to look at a draft before publishing.

Share a header and footer across pages

The header and footer are site chrome: two reserved-slug objects in the site folder, rendered by the platform around every page of that site. There is no per-page switch — and no need for one.

default-header

Rendered above every page of the site. Same code contract as a page: data.htmlPage.code.html (one self-contained fragment, optional inline style/script).

default-footer

Rendered below every page of the site. Keep it light — it runs site-wide, on every navigation.

Chrome rules (or the site breaks)

MustWhy
Fragment only — no <html>/<head>/<body>It is injected inside the page shell, not loaded as a document.
Wrap everything in your own class (.site-chrome-header) and prefix every CSS rule with itYour CSS shares the document with every page, so unscoped rules leak into pages.
Nav links: <a data-ic-nav-href="/shop" href="/shop">Keeps in-app navigation client-side; the plain href stays for SEO and fallback.
JS idempotent and guarded, no top-level awaitScripts re-run on every SPA navigation.
Never define gw-* classesThe gw- prefix belongs to the platform shell and built-in widgets.
Stay lightChrome is on every page: no big images, no heavy libraries.

“I want it on some pages, not all”

You wantDo this
Same header/footer on every page of the sitedefault-header / default-footer in the site folder — the only supported “default”.
A different header/footer for a group of pagesMake a second site folder (own domain or subdomain, own chrome + own settings).
A block on one page onlyPut it inside the page fragment itself.
A reusable block on several pages, configured per pageUse a widget / island (data-gw-app + per-page config).
Translated chromeSibling chrome objects sharing one contentId, each with its own meta.language.
Where do I edit them? In the site folder’s object list — the objects whose slug is default-header / default-footer. Author them with the code-object builder tool (WebsiteSharedSourceBuilder), or paste the same object shape from any other tool.
Retired concept: there is no “optional shared block” list inside a page any more (data.sections is ignored). Per-page shared blocks = widgets; site-wide shared blocks = chrome.

All of these live in data.websiteConfig on the site folder. They are folder fields — no object, no page and no builder tool can write them; only the folder editor can.

Minimal working site config 
{
  "hostNames": ["example.com", "www.example.com"],
  "primaryHost": "example.com",
  "defaultLanguage": "en",
  "previewSecret": "long-random-string",
  "currency": "EUR",
  "theme": { "colors": { "primary": "#4f46e5" } }
}
Why can’t a page tool change this? The domain must be known before any object is looked up, so site identity has to sit on the folder. Tools write their own value (and, where the CMS allows it, a few declared fields of their parent object) — never folder config.

Pages, slugs and publishing

A page is an object inside the site folder tree. Its slug decides the URL; its status decides whether anyone can see it.

Slug / routeURL
home-page/
about/about
object of a registered type/<type>/<id> (object detail page)
template page tours/t/tours/<contentId>
app-<appId>/app/<appId>/… (app capability page)
Not pages: default-settings, default-header, default-footer

Publishing a page

  1. Generate or paste the page code

    One self-contained fragment: markup + at most one scoped <style> + at most one <script>, no document tags.

  2. Save the tool value

    The builder stores the page inside its own field value — that is normal and expected.

  3. Check the object status in the CMS list

    That status is the publish gate: a disabled/hidden record is not rendered on the live site.

  4. Look at it on the real domain

    Drafts only render with ?gw-preview=<previewSecret>. Publish the record, then open https://<host>/<slug>.

  5. Add it to navigation

    Links are plain <a data-ic-nav-href="/about" href="/about"> — in the page, or in default-header if it belongs in the site menu.

Nothing appears on the domain? In this order: (1) is the hostname in hostNames? (2) does the object live in that folder tree? (3) is the record enabled? (4) is the slug right (home-page for /)? (5) DNS still propagating?

Widgets (islands)

Widgets are the reusable building blocks inside a page: a menu, a cart, a slot picker, a photo gallery. A page embeds a reference; it never contains the widget’s code.

How a page embeds a widget 
<div data-gw-app="menu"
     data-gw-config='{"cmsObjectType":"menu-items","folder":"menu","priceField":"price"}'></div>

① Shared catalog

The application store catalog (website-html-tool-library-applicationstore) — the same widgets for every tenant.

② This site’s own widgets

Objects of type website-html-tools-local-uniconbaseapps. Your own widgets, only for this site. On a name clash the site-local widget wins.

Never copy widget code into a page. Embed the island and let the platform mount it; config must be valid JSON (data-gw-config) and islands are never nested.

FAQ — the settings nobody remembers

How do I connect a domain to a folder?

Add the domain to the site folder’s “Website / Domain” section, field hostNames (hostname only, no https://, no path). Set primaryHost to the canonical one. That is the whole binding — the platform resolves host → tenant → the folder whose hostNames contains it.

Do I also have to touch DNS?

Yes, once: at the registrar, point the domain at the public website deployment (A/ALIAS for the bare domain, CNAME for www). Without DNS the folder binding exists but the domain never reaches the platform.

Where exactly is the “Website / Domain” section defined?

The website app declares it in App Designer as its folder config section (storage key websiteConfig). The folder editor renders those fields. If the section is missing in the folder editor, the app declaration is missing — that is an app-configuration problem, not a folder problem.

Why does my domain show the wrong website?

The same hostname is listed in more than one folder’s hostNames. Keep each host in exactly one site folder, and make sure the folder you expect is the one that owns it.

Where do I set the header and footer for all pages?

Two objects in the site folder: default-header and default-footer. The platform renders them around every page of that site automatically. There is no per-page switch.

Can I use a header on only some pages?

Not through chrome. Options: (a) put it in the page fragment for a one-off page; (b) use a widget for a block that repeats with per-page config; (c) create a second site folder with its own chrome when a whole group of pages needs a different shell.

Header shows up but the links do a full page reload — why?

The links are missing data-ic-nav-href. Write them as <a data-ic-nav-href="/shop" href="/shop"> so the router intercepts the click; keep the plain href for SEO and fallback.

My page CSS is leaking into other pages / the header — what happened?

Page and chrome CSS share one document. Give the root fragment a unique class and prefix every rule with it; never style bare html, body, *, a, h1. And never define gw-* classes — that prefix is the platform’s.

How do I preview a draft before publishing?

Open the URL with the site’s preview secret: https://<host>/<slug>?gw-preview=<previewSecret>. If drafts still 404, previewSecret is empty on the folder.

What is primaryHost for?

Canonical URLs, sitemap entries and hreflang. It should be the host you want indexed — pick one and stick to it (usually the non-www form).

How do I make a second site (different domain, different chrome)?

Create another site folder with its own websiteConfig (its own hostNames, theme, chrome objects). Pages of the two sites never mix: a folder tree is a site.

Where do analytics scripts go?

In the folder’s headCode / bodyStartCode / bodyEndCode (or the platform plugin settings). Never inside page or chrome code, and never as an external <script src> inside a page.

Why is my page not at /?

Only the object with slug home-page renders at /. Any other slug becomes /<slug>. Check for a second home-page in the same tree as well.

How do translations work?

One object per language, all sharing the same contentId, each with its own meta.language and its own slug. An empty language falls back to the folder’s defaultLanguage. There are no /en/ prefixes.

Can a page tool change the folder settings for me?

No. A tool writes its own value (and, where the CMS allows, a few declared fields of its parent object). Folder settings such as hostNames, theme or previewSecret are folder-only by design — the domain has to be known before any object is loaded.

I changed the domain but the site kept the old one — where is it cached?

Check, in order: the folder’s hostNames (old value still listed?), primaryHost, and any other folder that still claims the old host. Then reload with a hard refresh — pages are server-rendered and cached by host.

Widget appears as an empty box — why?

Usually one of: the island name does not match a catalog/site-local widget, data-gw-config is not valid JSON, or the widget object is disabled. Spacing/sizing can also come from the page CSS overriding the wrapper.

What should never be in a page or chrome?

Secrets and keys, <html>/<head>/<body> tags, external script libraries, unscoped CSS, gw-* class definitions, and analytics snippets (those belong to the folder).
