Volunteer Profile & Hour Portal

SINGLE SOURCE OF TRUTH for the Volunteer Profile & Hour Portal html tool. One tool instance is attached to one volunteer profile and holds everything that volunteer owns: the applications to events, the work assigned, the hours submitted, the messages received, the certificate and the profile details. Event side data - the event definition, the roster, the task list, the approvals - belongs to the Event Volunteer Manager. Every decision made for this tool is logged in section 11 and this document is updated in the same change as the code. When this document or the code disagree, this document is the tiebreaker - it is updated to capture the final decision, never silently left divergent.

1. Purpose and governance

This document defines one tool and one set of invariants around a single volunteer's own record - and it is the single source of truth for every decision we make about this tool, now and in the future. No decision is considered made until it is written here. Rules of use:

  • Every decision is logged here. Before or together with any change to this tool, the decision is added to section 11 with a date, and the affected section is updated in the same change.
  • The register is append-only. Decision rows are never deleted. A reversed decision is marked "Reversed (date)" with a reason - the original row stays for history.
  • This document wins ties. If this document or the code disagree, the discrepancy is resolved in this document first, then applied to the code - never the other way around.
  • Check before changing. Read the relevant section and the register before changing behavior, and update this document in the same change as the code.
  • Names must be self-explanatory. Every variable, function and snippet uses understandable names. No cryptic abbreviations. Short names only for loop indexes and universally known abbreviations (id, url, api).
  • Acronyms are always expanded next to every use.

Core guarantee. The volunteer sees their own record and only their own record. They can ask to join an event, report work and submit hours. They can never decide an application, approve an hour line or edit an event. Everything below serves those two sentences.

5. Verified problem and root cause

5.1 Verified evidence

  • 2026-10-21: in the previous single tool a volunteer could edit event data and approved totals because every screen trusted the page, not the role.
  • The volunteer had no single place for their own history: applications, tasks, hours and messages were spread across shared documents that also carried other people's records.
  • A volunteer could not see why an hour line was rejected, and could not see their own certificate at all.

5.2 Current implementation (verified in code)

5.3 Structural decisions that follow

  1. One instance per profile. The profile is the unit of identity and of permission.
  2. Read for context, write for self. Events, tasks and messages are read; placements and own details are written.
  3. Hours are submitted, not recorded. The volunteer proposes, the manager approves into the ledger.

Root cause of the old design: a shared page with write access to shared documents gave every volunteer the manager's pen.

6. Requirements

  1. The tool shows exactly ONE volunteer: the host profile, the session user's own profile, or the personId param.
  2. A volunteer writes only their own placement and their own profile details. Every other write is refused.
  3. Every record is its own CMS object via tool.requestObjects(). tool.setValue() holds UI preferences only.
  4. Applications are placements with requested status; only the manager changes the status.
  5. Task progress is written on the placement task row only.
  6. Submitting hours writes a pending line that is not counted anywhere until approved.
  7. Approved hours are read from the ledger, never recomputed from pending lines.
  8. Messages are filtered to approved events and read state is remembered per profile.
  9. Every screen states its purpose in one line, and every empty state names the next action.
  10. Graceful degradation: a missing object type produces a clear empty state and a report, never a broken page.
  11. The catalog serves every volunteering type. A record declares opportunityType; when the field is missing the type is derived from the record, so older records keep working.
  12. An application always names the position. An opportunity without positions offers one general position instead of blocking the volunteer.
  13. Requesting a second role of an opportunity the volunteer already belongs to adds a role request; it never creates a second membership.
  14. Places filled are counted from approved roles only. A request is not a place.

7. Option evaluation and decision

OptionDescriptionFixes the problem?ChurnVerdict
A. One tool per profile, read only context Attached to the volunteer profile; writes placements and own details, reads events, tasks and messages. Yes - identity drives permission, and the volunteer can never reach another person's record. Medium - new folder and a new model ADOPTED
B. One portal for every volunteer One tool lists all volunteers and lets each one open their page. No - the list itself exposes the whole network, and permissions become a screen concern. Low REJECTED (privacy)
C. Volunteer edits the shared task document Progress written directly into the event task list. No - two volunteers writing one large document overwrite each other. Low REJECTED (data loss risk)
D. Volunteer records their own approved hours The volunteer writes the ledger directly, with no approval step. No - approved hours feed the certificate and recognition; without a gate the number means nothing. Low REJECTED (trust)

Decision: option A. The volunteer owns their record and their submissions; the manager owns the decisions.

8. Solution design

8.1 Core invariants

Invariant ONE-VOLUNTEER. An instance resolves to exactly one profile and never lists other volunteers.
Invariant SELF-WRITE. Only the profile owner can write; a different session user gets a read only view.
Invariant SUBMIT-NOT-APPROVE. Hours are proposed here and approved by the manager. No approval logic exists in this tool.

Soft budget 400 KB, hard budget 600 KB, measured before every write. Above the hard budget the write is blocked with an explanation instead of being sent to fail. The yearly collapse writes a summary line with the line count so totals and the certificate stay correct.

  • Approved totals come from the ledger, so a rejected or removed pending line can never inflate them.

8.8 Volunteering types and the position model

One list serves every kind of volunteering. The record declares its type; when the field is absent the type is derived, so a record written before this model existed still lands in the right group.

TypeDeclared asDerived whenWhat the catalog shows
EventopportunityType: "event"startDate or endDate existsThe date range and the time window
Task basedopportunityType: "task"A task document exists for the recordThe commitment, or the deadline
RecurringopportunityType: "recurring"recurrence, recurringSchedule or recurrenceText exists"Every Saturday, 10:00 to 12:00"
Self pacedopportunityType: "self-paced"No date, no tasks and a commitment is set"About 2 hours per article" and "Online"

Any other declared string is accepted and displayed with its own chip, so a new type needs no code change to appear; it only gets a dedicated colour when it is added to the type list.

position: { id, name, slots, description, skills, timeCommitment }

recurrence: { weekdays: [6], timeFrom: '10:00', timeTo: '12:00', frequency: 'weekly' }

requested role on a membership:
  { positionId, name, status: 'requested', requestedAt }

Position rules. One application names exactly one position. A position with slots is full when the number of approved roles reaches that number. An opportunity without positions offers one row called "General volunteer" that creates a requested role with an empty positionId.

12. Maintenance rules

  1. Every decision is recorded in section 11 with a date, and the affected section changes in the same commit as the code.
  2. Rollback of a decision = mark it "Reversed (date)" with a reason; never delete rows.
  3. Before adding a field to the placement, ask whether the volunteer should be able to change it. If not, it belongs to the manager side.
  4. Never write records through tool.setValue(); it is reserved for UI preferences.
  5. Never add approval logic here. Approval lives in the manager tool and its SSOT.
  6. Keep the five type names identical to the paired tool's SSOT. A rename must change both documents in one change.
  7. After any change, re-run the checks in section 17 and update the capability table in section 3.
  8. Keep the visual language identical to the documentation (Inter, slate ink, indigo accent, white cards, the shared chip palette). A new colour or font is a decision row, not a local tweak.

    Every risk or side effect of a change that is not pushed yet lives here, linked to its release group.     Risks: 0 open - 0 solved - 0 accepted (0% solved)
    R-01 A profile owner can write fields the manager owns

    Applies to: T-01, T-03 (g1-portal)

    What can go wrong: a volunteer who can update their own placement could set status to approved or edit hoursApprovedTotal.

    Likelihood / impact: low likelihood, high impact.

    Mitigation: the tool always writes an explicit field set; approved totals are taken from the ledger, so a forged total cannot create hours; field level protection is tracked in the manager register as R-01 too.

    Last re-evaluation: 2026-10-22 - open, waiting for the platform answer.

    R-02 Two parts of the portal write one placement at the same time

    Applies to: T-04, T-05

    What can go wrong: a task update and an hour submission started from two tabs; the last write wins.

    Likelihood / impact: low likelihood, medium impact - a lost pending line rather than lost hours.

    Mitigation: the screen reloads after every write, and each write re-reads the placement before merging its change.

    Last re-evaluation: 2026-10-22 - open, accepted unless it appears in practice.

    R-03 Self registration creates duplicate profiles

    Applies to: T-10

    What can go wrong: the same person signs in twice and two profiles hold different hours.

    Likelihood / impact: medium likelihood, medium impact.

    Mitigation: look up by userId before creating; a manager merge step is planned before the feature ships.

    Last re-evaluation: 2026-10-22 - open, must be designed with T-10.

    R-04 The volunteer ledger grows past the document limit
    4

    Applies to: T-05

    What can go wrong: years of approved lines push the profile document toward 1 MB.

    Likelihood / impact: low in the first years, high once it happens - a blocked write.

    Mitigation: above 500 lines the oldest year collapses into one summary line that keeps the count, so totals and the certificate stay exact.

    Last re-evaluation: 2026-10-21 - solved by D-VP-07.

    R-05 The profile object is deleted in the CMS

    Applies to: all groups

    What can go wrong: the instance has nothing to show.

    Likelihood / impact: low likelihood, low impact - the empty state explains it.

    Mitigation: placements remain, so hours are not lost if the profile is recreated with the same id.

    Last re-evaluation: 2026-10-22 - accepted, documented in the failure matrix.
