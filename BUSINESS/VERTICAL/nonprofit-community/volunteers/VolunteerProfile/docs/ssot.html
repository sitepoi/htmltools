1. Purpose and governance

This document defines one tool and one set of invariants around a single volunteer's own record - and it is the single source of truth for every decision we make about this tool, now and in the future. No decision is considered made until it is written here. Rules of use:

  • Every decision is logged here. Before or together with any change to this tool, the decision is added to section 11 with a date, and the affected section is updated in the same change.
  • The register is append-only. Decision rows are never deleted. A reversed decision is marked "Reversed (date)" with a reason - the original row stays for history.
  • This document wins ties. If this document or the code disagree, the discrepancy is resolved in this document first, then applied to the code - never the other way around.
  • Check before changing. Read the relevant section and the register before changing behavior, and update this document in the same change as the code.
  • Names must be self-explanatory. Every variable, function and snippet uses understandable names. No cryptic abbreviations. Short names only for loop indexes and universally known abbreviations (id, url, api).
  • Acronyms are always expanded next to every use.

Core guarantee. The volunteer sees their own record and only their own record. They can ask to join an event, report work and submit hours. They can never decide an application, approve an hour line or edit an event. Everything below serves those two sentences.

5. Verified problem and root cause

5.1 Verified evidence

  • 2026-10-21: in the previous single tool a volunteer could edit event data and approved totals because every screen trusted the page, not the role.
  • The volunteer had no single place for their own history: applications, tasks, hours and messages were spread across shared documents that also carried other people's records.
  • A volunteer could not see why an hour line was rejected, and could not see their own certificate at all.

5.3 Structural decisions that follow

  1. One instance per profile. The profile is the unit of identity and of permission.
  2. Read for context, write for self. Events, tasks and messages are read; placements and own details are written.
  3. Hours are submitted, not recorded. The volunteer proposes, the manager approves into the ledger.

Root cause of the old design: a shared page with write access to shared documents gave every volunteer the manager's pen.

6. Requirements

  1. The tool shows exactly ONE volunteer: the host profile, the session user's own profile, or the personId param.
  2. A volunteer writes only their own placement and their own profile details. Every other write is refused.
  3. Every record is its own CMS object via tool.requestObjects(). tool.setValue() holds UI preferences only.
  4. Applications are placements with requested status; only the manager changes the status.
  5. Task progress is written on the placement task row only.
  6. Submitting hours writes a pending line that is not counted anywhere until approved.
  7. Approved hours are read from the ledger, never recomputed from pending lines.
  8. Messages are filtered to approved events and read state is remembered per profile.
  9. Every screen states its purpose in one line, and every empty state names the next action.
  10. Graceful degradation: a missing object type produces a clear empty state and a report, never a broken page.
  11. The catalog serves every volunteering type. A record declares opportunityType; when the field is missing the type is derived from the record, so older records keep working.
  12. An application always names the position. An opportunity without positions offers one general position instead of blocking the volunteer.
  13. Requesting a second role of an opportunity the volunteer already belongs to adds a role request; it never creates a second membership.
  14. Places filled are counted from approved roles only. A request is not a place.
  15. A time session stores timestamps, never a running counter. Delivered hours are computed from startedAt and stoppedAt.
  16. A session can never end later than its type boundary: the event window plus grace, the recurring occurrence window plus grace, or a hard session cap.
  17. Only an approved membership can clock in, and only one session runs per volunteer at any time.
  18. A stopped session becomes a pending hour line with source: 'timer'. The manager still approves it.
  19. Every opportunity resolves to a monitoring profile: window clock, project log, duty roster, or a burst cycle made of a project log plus a window clock.
  20. Each profile has a visible cap, and a claim can never exceed it.
  21. Preparation and delivery of one cycle are recorded separately and summed once; they never share one timer.
  22. A duty shift claims the availability block, never the response time of the messages answered inside it.
  23. Travel time is never counted as volunteer time.
  24. A certificate covers exactly one closed period and is an immutable snapshot with a verification id. The statement of hours is the live report for any range.
  25. By default one certificate is issued per volunteer per period, with every role as a line. A standalone event or role certificate is an excerpt issued on request.
  26. No certificate is issued while any hour of the period is still pending.
  27. A certificate never contains a third-party name, a pending hour or a quality claim.
  28. A correction after issue creates a replacement certificate and marks the previous one superseded; an issued document is never silently rewritten.

8.9 Clock in and clock out (time sessions)

The hard constraint that shapes the whole design. This tool is a browser page inside an iframe. A counter that runs in JavaScript stops the moment the tab is closed, the laptop sleeps or the phone is locked. A server job cannot be added here. So the timer is never a counter: a session stores a startedAt and a stoppedAt timestamp, and the minutes are computed from those two values. That is what makes "it counted for three days" impossible.

Automatic stop is a computation, not a background job. The event already carries the window we need (startDate, endDate in vm.events-uniconbaseapps). A recurring opportunity carries recurrence.weekdays, timeFrom and timeTo. The stop time is the earlier of: what the volunteer pressed, the window end plus a grace period, or a hard session cap. Every load re-evaluates that rule, so a session that was left running is closed correctly whenever the volunteer comes back.

8.9.1 Which volunteering types suit a clock

TypeClock in / outBoundary used for the automatic stopBehaviour
Event Yes - the main case startDate + startTime until endDate + endTime The clock opens 15 minutes before the start. It stops itself at the end plus 15 minutes of grace. A session cannot exceed the window.
Recurring Yes, one session per occurrence That occurrence: the weekday plus timeFrom to timeTo The same rule as an event, applied to the occurrence that contains the clock-in time. Two sessions for the same day are refused.
Task based Optional No window. The deadline is a due date, not a work window. Only a session cap applies (240 minutes per session, 480 per day). Manual "Log hours" stays the recommended path.
Self paced Discouraged No window at all No automatic stop is possible, so the clock would only measure how long a tab stayed open. Offer a short focus session capped at 120 minutes, or manual logging.

8.9.2 Forget-to-stop protection - four layers

  1. A ceiling on every session. A session can never end later than the type boundary above. For an event that means the window end plus grace; for a recurring role the occurrence end plus grace; for task based and self paced work the session cap. Nothing can run "forever" because no counter is used.
  2. A heartbeat while the page is open. Every 60 seconds the running session writes lastSeenAt. A closed tab stops sending heartbeats, which is exactly the evidence we need for the next layer.
  3. A stale session close on the next load. If a session is still running when the volunteer comes back, it is closed at the earliest of: the window end plus grace, or lastSeenAt plus two heartbeat intervals. It is marked autoStopped and verified: false, and the volunteer is asked to confirm the real end time. We never silently award hours for time nobody can evidence.
  4. Visible reminder while it runs. A running strip at the top of every screen shows the elapsed time and the start time, with a Stop button. Leaving the page with a running clock warns once.

8.9.3 Rules with one owner each

  • Only an approved membership can clock in. A requested role cannot.
  • One session per volunteer at a time, across all opportunities. Starting another asks to stop the first, so no hour is counted twice.
  • Clock-in is refused before window start - earlyGraceMinutes and after window end. The message names the time the clock opens.
  • A stopped session becomes a pending hour line immediately, with source: 'timer', startTime, endTime and the exact minutes. The session keeps the pendingId; hours can never live only in a session.
  • Rounding happens at conversion, not while running. roundingMinutes (default 5) rounds the pending line; the raw minutes stay on the session for the manager.
  • The manager still approves. A clocked line is a submission like any other, and can be approved, corrected or rejected.
  • A session under one minute, an overlap, a negative duration or a duration over 24 hours is rejected as invalid; the volunteer logs the time manually instead.
  • If the event window is edited while a session runs, the session is recomputed against the new window, clamped, and marked recomputed: true.

8.10.2 Physical event rules (on site)

  • Arrival and leave. The window opens 15 minutes before the published start, so arriving early is counted inside the early grace and nothing before it is.
  • Setup and cleanup belong to the window. They are inside the event window, so they need no separate rule; the 15 minute closing grace covers a late pack-up.
  • One session per day. A session never crosses midnight. A two-day event is two sessions, and a long day with a real break is clock-out then clock-in.
  • Split shifts are separate sessions, and only the time inside each shift counts. Waiting between shifts is not work.
  • Travel time is not counted (D-VP-22). It is not work for the organisation, and counting it would reward distance instead of contribution.
  • No signal or a dead phone. The volunteer logs the time manually; the manager confirms it from the sign-in sheet or the team record. Both paths end in the same approval step.
  • Venue sign-in is evidence, not a second ledger. If a QR or sheet check-in is added later, it compares against the clock and creates a flag; it never creates hours on its own.

8.10.4 What we deliberately do not measure

  • Travel time, for the reason above.
  • Response latency in chat: answering "in 4 minutes" is not four minutes of work, and measuring it rewards being glued to a phone.
  • Unengaged availability: an on-call block with no call is not work unless the policy says it is paid time, and this tool has no such policy.
  • Thinking time between sessions: it cannot be evidenced, so it must not be claimed.

8.10.5 Fairness and anti-gaming

  • Each primitive has a cap the volunteer can see before starting, so nobody is surprised by a rejection.
  • One session per volunteer at a time, even across primitives: a chat shift and a lesson cannot run together.
  • Prep and delivery of the same cycle never share a timer; they are two logs that are summed once, at the cycle level (D-VP-21).
  • The estimate on a task is there to calibrate the next estimate, not to police the volunteer. A large gap is a conversation, not an accusation.
  • Every claim still passes manager approval. The timer is a convenience that produces evidence, not a payment system.

8.11 Certificates - what we issue, when, and what we combine

The problem with the current certificate. Today the tool prints one certificate from the whole ledger: total approved hours and a count of events. That has three faults. It has no period, so a 2024 hour and a 2026 hour sit on the same page. It has no roles, so a weekly reading buddy and a one-off coat sort look the same. And it changes every time another hour is approved, so a PDF already emailed to a school can disagree with the next download of "the same" certificate.

8.11.1 Two documents instead of one

DocumentWhat it isPeriodChanges over time?Used for
Statement of hours The running service record: approved hours per opportunity, per volunteering type and per month. Any range the volunteer picks, including everything to date. Yes - it is a live report, always regenerated. A current total, an internal check, or a request that does not need a sealed document.
Certificate A sealed snapshot of one period with roles, hours, attendance and a verification id. One closed period: calendar year, academic term or programme cycle. No - issued once and never recalculated. School, employer, scholarship or reference use.

Most confusion disappears with this split: the statement answers "how many hours do I have right now", the certificate answers "what did I do in that period, and can you prove it".

8.11.2 Combine or separate - the rule

  • Default: one certificate per volunteer per period, listing every role held inside it. Not one certificate per event, and never one per weekly session.
  • A one-time event is a line, not a document. A food drive or a coat sort appears inside the period certificate. A standalone event certificate exists on request only and is labelled as an excerpt of the period record.
  • A recurring weekly role is one line per period, with sessions attended against sessions expected. Twelve weekly lessons are not twelve certificates.
  • A year-long role uses the period that matches reporting. If the academy reports by academic term, the term certificate is the unit and the annual one is a roll-up.
  • Burst cycles are grouped by series within the period: "five mock exams organised in 2026" is one line, not five documents.
  • Never a certificate while hours are pending. Pending work is visible in the statement, never on a sealed document.

8.11.4 The certificate is a snapshot, not a view

At issue time the tool stores a snapshot: period, volunteer name, organisation, totals by type, role lines, issue date, a certificateId such as FBA-2026-000123, the template version, and a check code derived from those values. Re-downloading returns the same snapshot, so two copies of one certificate always agree.

8.11.5 What a certificate may never contain

  • No third-party names. A coaching or writing role says "12 one-to-one sessions", never a student's name. Student privacy outranks detail.
  • No other volunteer's data, and no totals for the organisation as a whole.
  • No pending or rejected hours, and no estimate presented as fact.
  • No claim about quality of work ("excellent", "outstanding"). The certificate states what was done, not how well.

8.11.6 Verification

Every certificate carries a verification id and a short check code. Without a public endpoint the check is manual: a manager opens the tool, enters the id and sees the snapshot it belongs to. The wording on the document states that plainly instead of implying a public verification service that does not exist. A public verification page on the academy website is an idea (I-09), not a promise.

14. Open questions

  1. Real per-object size limit. The whole budget assumes 1 MiB; if the store is smaller only the caps in section 8.5 scale.
  2. Can a profile be created from the volunteer side? Blocks self registration (T-10).
  3. Can the session user be resolved to a profile automatically? Today the personId param or getUser() is used.
  4. Should a declined volunteer see the manager note? A declined line today has no note to show.
  5. Is the certificate a printed page or a file? Blocks the email certificate (T-11).
  6. Do we ever count travel time? Currently no (D-VP-22). A volunteer who drives two hours for a three hour shift may disagree, and that is a reimbursement conversation, not a timer.
  7. Is a chat duty shift measurable at all? The design claims the shift plus a manager sample. If a manager will not sample, the duty should be recognised another way instead of guessed.
  8. Should the volunteer see the cap before starting? The design says yes. Confirm the wording, because a cap that appears only at rejection feels like a trap.
  9. What happens to a cycle cap when an exam is postponed? The prep is already logged; the cycle either moves with the date or closes and a new cycle opens.
  10. What exactly is the academic term? The default period is the calendar year. If the academy reports by term, the term dates must be confirmed once (for example September to June) and stored as a setting.
  11. Who signs a certificate? The design prints the programme lead name and the issue date. A named signer per programme needs a decision, and an e-signature is out of scope.
  12. Should an open period ever produce a document? The current answer is no: the statement covers a running total. Confirm that a mid-year "proof of hours so far" is acceptable as a statement and not a certificate.
  13. May a recipient see the volunteer's contact details? The design says no: name, period and work only. Confirm that a school asking for a contact route is handled outside the document.
