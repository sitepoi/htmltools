Volunteer Platform - Three-Object Architecture

Volunteer Profile, Volunteer Event, and a Member-Membership relation that links them.

DRAFT v3 - for approval Status: planning only. No application code, data or configuration is changed. 2026-10-21

v3 answers the four open questions. The model changes from two objects to three: the membership relation becomes its own object again, because the platform may not support array-contains, and because a separate relation removes the dual writes, the roster exposure and the 1 MiB risk in one move.

1. Verdict: three objects, not two

Yes - make the relation a separate object. I changed my recommendation.

In v2 I accepted the two-object model on the condition that the platform can do array-contains queries and a two-object batch write. You just told me neither is confirmed, and a standard JSON object system may support neither. That condition is not met, so the model has to change - and the change is for the better anyway.

No special query features
Every lookup becomes an equality filter on one field: personId, eventId or status. Nothing exotic is required from the object store.
No duplicated state
The relation is the single source of truth for "person X in event Y". No mirrors, no reconcile action, no drift between two documents.
Nothing shared gets rewritten
A volunteer writes one small relation, not the event. The event document is only touched by managers, for definitions and tasks.
Privacy by shape
The event document holds no roster at all, so a volunteer reading an event cannot see other volunteers. Their own data lives in their own relation.
The 1 MiB question disappears
Memberships, tasks, hours and messages never pile up in one document. Every document stays small for the life of the system.

What you give up: the event page needs two reads instead of one (event plus its relations), and the volunteer's page needs two reads instead of one (profile plus their relations). In exchange, no document ever carries a list of people, so no write is ever amplified and no document grows with participation.

Bonus: the relation type already exists in your data. Today's vm.eventApplications-uniconbaseapps is exactly a person-event relation with a status. This is an additive upgrade of an existing object rather than a new concept, which keeps migration cheap.

2. Your questions, answered

D1 - Would a separate event-person relation object type be better?

Yes. With two objects, the relation has to be duplicated (an array in the event plus an array in the person) and the platform has to support array-contains to find it from both sides. With three objects, the relation is stored once, and both sides find it with a plain equality filter. It also removes the only place where two documents had to be written together.

Cost check, same event as before (250 members, 100 tasks): reading the event team costs 1 event read plus 250 small relation reads. That is more operations than one embedded read, but about the same bytes, and it is the only shape that works without special query support.

D2 - Where exactly would we have used array-contains?

In v2, in five places. All five disappear with the relation object:

#Needv2 query (needs array-contains)v3 query
1 Event tool: who is in this event events.where(memberProfileIds, array-contains, me) relations.where(eventId == X)
2 Volunteer tool: the events I belong to persons.where(memberEventIds, array-contains, eventId) relations.where(personId == me)
3 Event tool: pending join requests persons.where(requestEventIds, array-contains, eventId) relations.where(eventId == X) then keep status = requested
4 Event tool: pending hours to approve persons.where(pendingEventIds, array-contains, eventId) relations.where(eventId == X) then keep rows with pending hours
5 Volunteer tool: my open tasks events.where(memberProfileIds, array-contains, me) then filter tasks relations.where(personId == me) then read the task rows

Rows 3 and 4 need no second query at all: the event tool already loads the relations of its event, so requests and pending hours are filtered in memory. v3 uses zero array-contains queries.

D3 - Do we still need a batched write across two objects?

For membership decisions: no. Approving, declining or removing a person is one write to one relation. That was the main reason v2 needed a batch, and it is gone.

For hours there is still one two-step case: the approved line goes on the person (permanent record) and the pending line is cleared from the relation. Recommended handling without a batch:

  1. Give every pending hour line an id. The ledger line id is deterministic: relationId + ':' + pendingHourId.
  2. Write the person ledger first - if it fails, nothing changed.
  3. Then clear the pending entry from the relation.
  4. If the second write fails, the pending line stays. A re-approval would try to add the same ledger id, which the tool skips, so the worst case is a stale "pending" row, not double hours.
  5. The relation keeps approvedLedgerIds[] (ids only, capped) so a repair action can detect and fix a mismatch.

If a batch does exist, use it - it turns this into one atomic step. If not, the deterministic id makes the flow idempotent and safe.

D4 - Pending hours collect and get approved on the same object?

Yes, that is the idea, with one refinement: they live on the relation, not on the person document. The relation is exactly "this person in this event", which is the scope of an hour line. The flow:

  1. Volunteer adds pendingHours[] to their own relation (temporary, private, only they and the event managers see it).
  2. Event tool lists the relations of its event and shows every pending line, grouped by volunteer.
  3. Manager approves: a permanent line is appended to the person's hoursLedger[], and the pending entry is removed from the relation.
  4. The person's certificate and totals read the ledger only, so pending hours never count.

Nothing is ever written into the event document for hours.

D5 - Volunteer marks a task done, manager confirms later

Agreed, and it fits the object model cleanly: the task definition and its confirmation live on the event; the volunteer's progress lives on their relation.

Statuses: open (no assignee) - assigned - in-progress - reported-done (volunteer) - completed (manager confirmed) - cancelled.

The event tool reads relations anyway, so it shows "Reported done, waiting for confirmation" without any extra read. Confirming writes the event task to completed and marks the relation row confirmed.

D6 - What did "roster name" mean? Volunteers need their info, nothing unrelated

"Roster name" was my shorthand for a name snapshot stored in the event document so the manager list renders without reading person documents. My concern was that whoever can read the event document can read that list. Your rule resolves it: the event document should carry no roster at all.

With the relation object this is automatic. A volunteer can read:

  • the event definition (name, dates, venue, contact, description, positions),
  • their own relation (their status, their positions, their tasks, their pending hours),
  • their own person document (profile, ledger, certificate).

They cannot see other volunteers' names, statuses, task assignments or hours, because that data is not in any document they can read. The manager roster comes from the relations query, which is a manager-side permission.

Is the plan fully applicable, and does it never hit 1 MiB? Are all questions answered?

Never 1 MiB: not by count caps alone - my v3 draft had two holes (an 8,000-character message body, and unbounded free text in task descriptions and notes). They are closed in section 8: field length limits, array caps, and a measured pre-write check against a 600 KB hard budget. With those in place the worst case is 390 KB (event), 335 KB (person) and 60 KB (relation), so a single write can never reach the store limit - it is blocked in the UI first.

Fully applicable: yes for the model; not yet for the platform. Five behaviours must be confirmed before the volunteer flow is buildable: equality filters (P1), volunteers writing only their own relation (P2), read scope (P4), chosen document ids (P5), and whether an update replaces or merges the object (P6 - this one matters because a relation has two writers). If P2 or P4 fails, the volunteer side needs a different route.

All questions answered: the six product questions are closed (D1, D2, D3, D4, D5, D6). What is left is platform verification plus three product decisions: whether old ledger detail may be collapsed into yearly summary lines, whether a 2,000-character message limit is acceptable, and what the real per-object size limit is.

3. The objects (split by write frequency)

One change from the previous draft. Tasks and team messages moved out of the event document into their own document per event (sections 3.4 and 3.5). The rule behind the split: one document per write rhythm. The event definition changes a few times in its life, tasks change a few times a week, messages change every day and grow forever. Keeping them in one document meant every chat message rewrote the whole event, and a runaway message list could damage the event record itself.

3.4 Event Tasks - vm.eventTasks-uniconbaseapps

Document id: eventId + '__tasks'. One task list per event, always the same id, so the event tool reads it with a direct get - no query, no index.

Why not keep tasks on the event? Three reasons:

  1. A task can be archived, bulk-cleared or rebuilt without touching the event definition (dates, venue, capacity).
  2. Task writes stop competing with event edits for the same ~1 write/second document limit.
  3. The volunteer-facing task list can be fetched without loading the whole event, if that ever matters.

The cost, stated honestly: a task status change rewrites the whole task document. At 200 tasks (about 120 KB of JSON) that is a real write, so the tool must not write on every keystroke or checkbox click. The lifecycle is designed for it: volunteers report progress on their relation (small document, one writer), and only the manager's confirm/cancel touches the task document. A confirmed task is written once.

Hard rule: volunteer progress never writes the task document. If it did, ten volunteers clicking "done" in the same minute would rewrite a 120 KB document ten times, and some writes would be lost.

Document id: eventId + '__messages' for volume 1, then eventId + '__messages#2', #3, and so on.

Why a document, not per-message documents? A typical event produces tens of messages from one or two managers. One document means one read for the whole conversation, one write per message, and no pagination plumbing. Per-message documents would triple the document count and the read cost for the same conversation.

When it turns into a problem, and the fix: two-way chat between many volunteers would serialise writes on one document (the 1 write/second rule), and the document grows forever. Both are handled by rotation:

  1. Before writing, check messages.length >= 150 or lastSentAt older than the retention window, or an estimated size above 250 KB.
  2. If any is true, mark the current volume closed = true and write the new message into volume n + 1.
  3. Closed volumes are read-only. The event tool shows the newest open volume by default and offers "older messages" (volume list, still one get each).
  4. A closed volume can be deleted as a whole when it is no longer relevant. Deleting it can never damage the event, the tasks, the hours or the person records.

"Remove by relevance" therefore has a safe unit: a volume, not a message. That is the property the previous design could not offer - a message list lived inside the event, so deleting old chatter meant rewriting the event's core record, and any size accident damaged the event itself.

If two-way volunteer chat becomes a requirement (not just manager announcements), move that one feature to per-message documents (eventId + '__msg__' + timestamp) and keep this document for announcements. The tool can show both merged by sentAt. Do not do this before it is asked for: it multiplies reads by a factor of 10 - 50 for the same screen.

The one platform rule this depends on: a volunteer must be allowed to write their own relation and nowhere else. If the object store only grants write access per type (all relations or none), then a volunteer could alter someone else's membership. That must be verified in phase 1 - see section 9.

5. The four flows in detail

5.1 Apply to an event or a position

  1. Volunteer opens their profile tool, sees the events they may join (open events, paged).
  2. They pick an event and optionally a position. The tool creates the relation with status = requested, the requested position, and appliedAt.
  3. Event tool loads its relations and shows the requested ones in "Requests to decide".
  4. Manager approves: one write, status = approved, decidedAt/By, positions confirmed. Declining is the same write with declined.

5.2 Log hours, then approve them

  1. Volunteer adds a pending line to their relation: date, task (optional), hours, note.
  2. Event tool shows it under Hours for that volunteer; the person tool shows it as "pending, waiting for the event manager".
  3. Manager approves: append to the person ledger with id relationId + ':' + pendingId, remove the pending line, increase hoursApprovedTotal.
  4. Reject: remove the pending line and record the rejection on the relation (hoursHistory[], capped) without touching the person ledger.
  5. Certificate and totals read the person ledger only.

5.3 Task lifecycle

event.tasks[]                         relation.taskLinks[]

  | manager assigns

  | volunteer starts                    |

The event document stays the source of truth for the task itself; the relation is the source of truth for what this person did. The event tool joins them in memory because it already has both.

5.4 Network approval (stage one)

Unchanged and unrelated to events: the manager flips the person's network status from candidate to active. One write, one document.

Worst case is now 335 KB on the largest document, against a hard budget of 600 KB and a store limit of 1,048,576 bytes. Splitting tasks and messages also lowered the event document from about 390 KB to about 12 KB, so an event edit is a cheap write that can never be blocked by chatter or task volume. The gap is deliberate: it absorbs platform metadata, future fields and non-ASCII text that costs more than one byte per character.

8.4 Enforcement in the tool (this is the actual guarantee)

  1. Measure before writing. Every write path computes the serialized byte size of the document it is about to write (UTF-8, plus a 1 KB platform overhead allowance).
  2. Soft budget 400 KB. Above it the tool runs the prune rule for that document type, then re-measures.
  3. Hard budget 600 KB. If the document is still above it, the write is blocked with a clear message and an action, instead of being sent and failing at the store. A failed write at the limit looks like data loss to a user; a blocked write with an explanation does not.
  4. Pruning must not change totals. When the ledger exceeds 500 lines, the oldest year is collapsed into one line: { id: "summary-2025", summary: true, year: 2025, hours: 118.5, events: 14 }. The certificate and the totals add summary lines exactly like detail lines, so the number never drops.
  5. Every new array needs a cap and a length limit in the same change. A field added without a budget is how a document quietly grows past the limit.

If the store limit is not 1 MiB (P7), set the hard budget to 60% of the real limit and scale the caps: 600 KB assumes 1 MiB. The rule stays the same, only the numbers move.

The rule in words, to hand to the platform owner:

allow update, delete on relation:
    resource.data.personUserId == request.auth.uid        // own record only
    AND protected fields unchanged                         // see below

allow create on relation:
    request.resource.data.personUserId == request.auth.uid
    AND request.resource.data.status == "requested"        // cannot self-approve

    resource.data.personUserId == request.auth.uid  OR  isManager()

protected fields (a volunteer may never change them):
    status after creation, decidedAt, decidedBy, hoursApprovedTotal,
    approvedLedgerIds, positions[].status, notes

What the rule must prevent, explicitly: a volunteer setting status = approved, awarding themselves hours by writing hoursApprovedTotal, or editing positions[].status. If the store cannot compare individual fields on update, then the volunteer-writable part must move into its own field group that the manager's screen never trusts until a manager confirms it - which is what pendingHours[] and taskLinks[].status already are. That is the fallback, and it is why those two arrays are named "pending" and "reported", not "approved".

Merge (P6). Updates merge field by field, so the volunteer writing pendingHours[] cannot erase status that the manager just changed. Two limits still apply, and the tool handles them:

  1. Arrays are written as a whole value. Merge does not merge array entries. Two writers editing the same array at the same time means the last one wins.
  2. Protocol for array edits: read the relation, keep its updatedAt, change the array, write with a check that updatedAt is unchanged. On mismatch: re-read, re-apply the change to the fresh array, retry once. If it fails again, tell the user instead of overwriting.

Because the two sides normally write different arrays (volunteer: pendingHours, taskLinks; manager: status, positions, hoursApprovedTotal), collisions are rare in practice - the protocol is the safety net, not the normal path.

DynamoDB400 KBCaps shrink: 500 ledger lines becomes about 200, message volume about 60
MongoDB / SQL JSON column16 MB or moreNothing to change; the budget becomes a performance rule, not a safety rule

Why it matters even when the limit is large: the same number decides write cost and read cost. A record is written and read as a whole, so a 300 KB record is a 300 KB write on every message. The budget in section 8 keeps the everyday records small on purpose - not only to avoid the hard limit.

What is needed from the platform owner: one sentence - "the per-object limit is X". If the answer is Firestore, nothing changes. If it is smaller, the hard budget becomes 60% of X and the caps in 8.2 scale down proportionally. No design decision in this document depends on the answer; only the numbers in 8.2 and 8.3 do.10. 10.2 What each audience sees

Volunteer

own data only
  • Profile and network status.
  • Events joined: status, positions, dates.
  • Tasks: my progress, report done.
  • Hours: pending (waiting) and approved (ledger).
  • Certificate from approved hours only.
  • Open events they may apply to.

Event manager

their event only
  • Event definition and positions.
  • Team: requests to decide, approved members.
  • Tasks: create, assign, confirm reported work.
  • Hours: pending approvals, approved totals.
  • Report and team messages.

10.3 Interaction rules

  • The volunteer's pending rows are visibly pending and never counted in totals.
  • "Report done" is a volunteer button; "Confirm" is a manager button. Two words, two owners.
  • A rejected hour line disappears from the volunteer's pending list; the reason stays with the manager.
  • No screen ever lists other volunteers inside the volunteer's tool.
  • Caps surface at 70% with a one-click archive action.

11. Migration plan

Phase 0 - Decisions

  • Approve the three-object model.
  • Answer P1, P2 and P4 (query filters, volunteer write scope, read scope).
  • Confirm the volume assumptions.

Phase 1 - Platform check (no UI work)

  • Prove an equality filter on eventId and on personId.
  • Prove a volunteer can write their own relation and cannot write another person's.
  • Prove a chosen document id is accepted (deterministic relation id).

Phase 2 - Extend the relation type

  • Reuse today's vm.eventApplications records as relations; add taskLinks, pendingHours, positions, hoursApprovedTotal, approvedLedgerIds, schemaVersion.
  • Rename the display label to "Membership"; keep the type id to avoid config churn.
  • Backfill personId from registryProfileId or resolve by volunteerUserId.

Phase 3 - Extend person and event

  • Person: add hoursLedger (aggregated from approved hour records) and totals.
  • Event: add positions and keep tasks as an array, imported from vm.eventTasks.
  • Fold approved hours into the person ledger; move pending hours into their relations; keep vm.eventHours read-only.

Phase 4 - Event Team tool

  • Dashboard, Team, Tasks, Hours, Report, Messages against event plus relations.
  • Approve, confirm, approve hours - one write per decision where possible.
  • Exit criterion: one event runs end to end, and the report matches the old numbers.

Phase 5 - Volunteer Profile tool

  • Own profile, events, tasks, hours, certificate, messages.
  • Manager variant on the same tool: network approval, edit, ledger verification.

Phase 6 - Hygiene and retirement

  • Merge duplicate persons by normalized email.
  • Archive vm.eventTasks, vm.eventHours, vm.eventMessages after two clean releases.

12. Risks

RiskImpactMitigation
Volunteers cannot write their own relation (P2) No volunteer-initiated apply, hours or task progress Resolve in phase 1 before building; fallback options in section 9
Volunteers can read the whole relation type Roster exposure Restrict reads by person (P4); if impossible, accept "names only, no contact data" as policy
Duplicate relations for one pair Double membership, double hours Deterministic id, or check-then-create in one tool action
Hours approval half-completed Ledger written but pending row left, or the reverse Deterministic ledger ids and approvedLedgerIds; repair action re-runs safely
Event tool loads a very large team Slow event page Page the relations list (50 at a time); totals come from aggregation or a capped scan
Task progress split between event and relation Confusing status One lifecycle with a single derivation rule: the relation says what the volunteer did, the event says what the manager confirmed
Two writers on one relation (volunteer and manager) One side's change is lost: a new pending hour line disappears, or an approved line comes back Answer P6; re-read before write with an updatedAt check; retry once; show "this record changed, refresh" instead of overwriting silently
Pruning silently lowers a certificate total The volunteer's lifetime hours appear to drop Collapse old ledger lines into a summary line that keeps the hours; totals are recomputed from detail plus summary lines
A new field or array is added later without a budget The document grows past the limit again Rule in section 8.4: every new array needs a cap and a length limit in the same change, reviewed
