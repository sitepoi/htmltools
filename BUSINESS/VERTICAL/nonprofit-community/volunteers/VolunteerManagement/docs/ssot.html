1. Purpose and governance

This document defines one tool and one set of invariants around volunteer administration for events - and it is the single source of truth for every decision we make about this tool, now and in the future. No decision is considered made until it is written here. Rules of use:

  • Every decision is logged here. Before or together with any change to this tool, the decision is added to section 11 with a date, and the affected section is updated in the same change.
  • The register is append-only. Decision rows are never deleted. A reversed decision is marked "Reversed (date)" with a reason - the original row stays for history.
  • This document wins ties. If this document or the code disagree, the discrepancy is resolved in this document first (with a dated decision), then applied to the code - never the other way around, and never silently left divergent.
  • Check before changing. Before changing any behavior covered here, read the relevant section and the register; after the change, update this document in the same change as the code.
  • Names must be self-explanatory. Every variable, function, and code snippet in any update uses understandable names. No cryptic abbreviations. Short names are allowed only for loop indexes and universally known abbreviations (id, url, api).
  • Acronyms are always expanded next to every use - in prose, tables, and headings. Literal identifiers stay as they are.

Core guarantee. Volunteer master data exists exactly once - in the shared registry. Event instances never store a copy of a volunteer profile; they store only event-scoped records that reference the registry. Everything below serves this one sentence.

5. Verified problem and root cause

5.1 Verified evidence

  • 2026-09-29: the type constants in app/VolunteerManagement.js define TYPE_VOLUNTEERS = 'vm.volunteers-uniconbaseapps' (instance-scoped) and store name, email and skills inside it - no shared registry exists.
  • The same person volunteering for two events gets two separate profiles; skills and contact data are re-entered per event.
  • A future public registration app has no type it can write that this admin tool reads - the two apps cannot share a volunteer list today.

5.2 Current implementation (verified in code)

// app/VolunteerManagement.js - type constants, current logic
var TYPE_VOLUNTEERS = 'vm.volunteers-uniconbaseapps'; // profile + membership mixed
var TYPE_TASKS      = 'vm.tasks-uniconbaseapps';
var TYPE_HOURS      = 'vm.hours-uniconbaseapps';
var TYPE_MESSAGES   = 'vm.messages-uniconbaseapps';

5.3 Structural flaws

  1. No SSOT for volunteer identity. Profiles live inside event-scoped documents, so the same human is a different record in every event.
  2. No cross-app contract. Nothing defines which shared type the public registration app writes and the admin tool reads.
  3. 1 MB risk is undecided. It is not documented where bulk data may and may not go; tool.setValue() (one Firestore document) could be misused for records.

Root cause: the data model was designed without separating volunteer identity (global, shared) from event membership and operations (per event), and without a documented storage budget.

6. Requirements

  1. The tool manages exactly ONE event: it is hosted on an event object; all event data is instance-scoped.
  2. Volunteer master data lives in one shared registry type read and written by this tool and by the future public registration app (SSOT).
  3. Event membership is a separate record that references a registry profile by id - profiles are never duplicated into event data.
  4. Every record (profile, application, task, hour log, message) is its own Firestore document via tool.requestObjects(); tool.setValue() stores only UI preferences.
  5. Estimated size budget per document: profile ≤ 2 KB, application ≤ 1 KB, task ≤ 2 KB, hour log ≤ 1 KB, message ≤ 10 KB - all far below the 1 MB per-document limit, so no single record can hit the cap.
  6. Type names follow the CMS naming rules: shared = volunteerRegistry-uniconbaseapps; isolated = vm.*-uniconbaseapps.
  7. Role gating: managers write everything; volunteers only apply, update their own task status, log their own hours, and message managers.
  8. Graceful degradation when a CRUD channel is not configured: notify + missing-parameter report, never a broken page.
