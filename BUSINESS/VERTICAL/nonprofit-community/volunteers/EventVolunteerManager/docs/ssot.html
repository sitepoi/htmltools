One tool instance is attached to one event CMS object and manages everything that happens around that event: the volunteers linked to it, their roles, the work, the hours, the messages, the report and the event information itself. The event object is created in the CMS; this tool never creates or deletes it. Every decision made for this tool is logged in section 11 and this document is updated in the same change as the code. 1. Purpose and governance

This document defines one tool and one set of invariants around running a single event with volunteers - and it is the single source of truth for every decision we make about this tool, now and in the future. No decision is considered made until it is written here. Rules of use:

  • Every decision is logged here. Before or together with any change to this tool, the decision is added to section 11 with a date, and the affected section is updated in the same change.
  • The register is append-only. Decision rows are never deleted. A reversed decision is marked "Reversed (date)" with a reason - the original row stays for history.
  • This document wins ties. If this document or the code disagree, the discrepancy is resolved in this document first, then applied to the code - never the other way around.
  • Check before changing. Read the relevant section and the register before changing behavior, and update this document in the same change as the code.
  • Names must be self-explanatory. Every variable, function and snippet uses understandable names. No cryptic abbreviations. Short names only for loop indexes and universally known abbreviations (id, url, api).
  • Acronyms are always expanded next to every use.

Core guarantee. The event object holds the event. The membership object holds the connection between one volunteer and that event. This tool never copies a volunteer profile into event data and never stores records in tool.setValue(). Everything below serves those two sentences.

5. Verified problem and root cause

5.1 Verified evidence

  • 2026-10-21: the previous single tool mixed event management, volunteer master data and cross event reporting in one screen, and stored tasks, hours and messages as separate documents stamped with eventId.
  • The event record itself lived inside the same tool as the volunteer roster, so a message flood or a long task list increased the event document and slowed event edits.
  • An event could not have its own manager workspace: every manager saw every event and every person in one page.

5.2 Current implementation (verified in code)

// app/EventVolunteerManager.js - five types, one document per write rhythm
var DEFAULT_TYPES = {
  event: 'vm.events-uniconbaseapps',              // host object
  relation: 'vm.eventMemberships-uniconbaseapps', // personId + '__' + eventId
  person: 'volunteerRegistry-uniconbaseapps',     // names + permanent ledger
  tasks: 'vm.eventTasks-uniconbaseapps',          // eventId + '__tasks'
  messages: 'vm.eventMessages-uniconbaseapps'     // eventId + '__messages', then '#2', '#3'
};

5.3 Structural decisions that follow

  1. One instance per event. The event is the unit of work and of permission.
  2. Three write rhythms, three documents. Event information, task list and message volumes are separate so a busy conversation cannot touch the event record.
  3. The volunteer owns one record. This tool reads the profile and only writes the ledger line when approving hours.

Root cause of the old design: one document carried the event definition, the roster, the tasks and the messages, and one tool carried every event of the organization.

6. Requirements

  1. The tool manages exactly ONE event: it is attached to an event object; all operational data is scoped to that event.
  2. The event object is created, named and deleted in the CMS. This tool only reads and updates its fields.
  3. Every record (placement, task document, message volume, ledger line) is its own CMS object via tool.requestObjects(). tool.setValue() holds UI preferences only.
  4. Task definitions live in one document per event; volunteer progress lives on the placement and never writes the task document.
  5. Hours approval writes the volunteer ledger first, then clears the pending line, and is idempotent.
  6. Assignments are limited to volunteers approved for this event.
  7. Messages rotate by volume so no volume approaches the document budget.
  8. Role gating: managers write everything; a volunteer opening the tool sees a read only view.
  9. Every screen states its purpose in one line, and every empty state names the next action.
  10. Graceful degradation: a missing object type produces a clear empty state and a report, never a broken page.

7. Option evaluation and decision

OptionDescriptionFixes the problem?ChurnVerdict
A. One tool per event object One instance per event; tasks and messages in their own documents; volunteer master data in the shared registry. Yes - matches the CMS object model, isolates permissions, keeps every document small. Medium - new folder and a new model ADOPTED
B. Keep one organization-wide console One tool lists every event and opens each one inside itself. No - one document would grow with the whole program, and permission per event becomes a screen concern instead of a store rule. Low REJECTED (budget and permissions)
C. Keep tasks and messages inside the event document One event document holds definition, roster, tasks and messages. No - every message rewrites the event and a long task list slows every event edit. Low REJECTED (write amplification)
D. Let volunteers manage the event too One tool for both sides, with the volunteer editing tasks and hours directly. No - decisions need one owner, and a volunteer writing the task document loses concurrent updates. Medium REJECTED (data loss risk)

Decision: option A. The event is a CMS object, the tool is attached to it, and the volunteer side is a separate tool with its own SSOT.

8. Solution design

8.1 Core invariants

Invariant EVENT-HOST. An instance is bound to exactly one event object. It cannot list, create or delete events.
Invariant PLACEMENT-ONLY. Anything that connects a volunteer to this event lives in the placement record, never inside the event document.
Invariant ONE-APPROVER. A manager decides requests, hours and task confirmation. A volunteer never decides.

12. Maintenance rules

  1. Every decision is recorded in section 11 with a date, and the affected section changes in the same commit as the code.
  2. Rollback of a decision = mark it "Reversed (date)" with a reason; never delete rows.
  3. Before adding a field to the event document, ask whether it belongs to the event or to a placement. Event = the same for everybody; placement = one person.
  4. Never write records through tool.setValue(); it is reserved for UI preferences.
  5. Never let a volunteer write the task document or the ledger.
  6. Keep the five type names identical to the paired tool's SSOT. A rename must change both documents in one change.
  7. After any change, re-run the checks in section 17 and update the capability table in section 3.
  8. Keep the visual language identical to the documentation (Inter, slate ink, indigo accent, white cards, the shared chip palette). A new colour or font is a decision row, not a local tweak.

14. Open questions

  1. Real per-object size limit. The whole budget assumes 1 MiB; if the store is smaller only the caps in section 8.5 scale.
  2. Can a document be created with a chosen id? If not, the query-then-create fallback stays.
  3. Can individual fields be protected on update? If not, manager approval remains the effective gate.
  4. Should a decline be reversible without a new request? Today a declined person must ask again from the volunteer tool.
  5. Should a full role block approval or allow an override? Blocks the capacity warning in T-16.

R-01 The store cannot protect individual fields on update

Applies to: T-03, T-06 (g1-event-workspace)

What can go wrong: a volunteer who can update their own placement might try to set status approved or write the approved total.

Likelihood / impact: low likelihood, high impact.

Mitigation: the tool never trusts volunteer-written totals; the ledger is written only by manager approval; if field rules are impossible, the approval step stays the effective gate.

Last re-evaluation: 2026-10-22 - open, waiting for the platform answer.

R-02 Two managers write the task document at the same time

Applies to: T-05

What can go wrong: the last write wins and one change disappears.

Likelihood / impact: low for a single event manager, medium if two people run one event.

Mitigation: the screen reloads after every write, so stale data is visible quickly; task lists are small; a future change can compare updatedAt before writing.

Last re-evaluation: 2026-10-22 - open, accepted until a second manager appears in practice.

R-03 Manager-recorded hours double count with a volunteer submission

Applies to: T-14

What can go wrong: a manager records hours the volunteer already submitted, and both lines land in the ledger.

Likelihood / impact: medium likelihood, medium impact.

Mitigation: the form shows the waiting lines of that volunteer first and warns when a line exists on the same date; the id rule stays deterministic per source line.

Last re-evaluation: 2026-10-22 - open, must be designed with T-14.

R-04 A message flood grows the event document

Applies to: T-07

What can go wrong: messages inside the event would grow it without limit.

Likelihood / impact: certain with conversations, high impact before the split.

Mitigation: messages live in their own type, rotate at 150 per volume, and the event document stays around 12 KB.

Last re-evaluation: 2026-10-21 - solved by D-EVM-03 and D-EVM-08.
