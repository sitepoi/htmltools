1. Purpose and governance

This document defines one tool and one set of invariants around [what the tool does] - and it is the single source of truth for every decision we make about this tool, now and in the future. No decision is considered made until it is written here. Rules of use:

  • Every decision is logged here. Before or together with any change to this tool, the decision is added to section 11 with a date, and the affected section is updated in the same change.
  • The register is append-only. Decision rows are never deleted. A reversed decision is marked "Reversed (date)" with a reason - the original row stays for history.
  • This document wins ties. If this document or the code disagree, the discrepancy is resolved in this document first (with a dated decision), then applied to the code - never the other way around, and never silently left divergent.
  • Check before changing. Before changing any behavior covered here, read the relevant section and the register; after the change, update this document in the same change as the code.
  • Names must be self-explanatory. Every variable, function, and code snippet in any update uses understandable names. No cryptic abbreviations. Short names are allowed only for loop indexes and universally known abbreviations (id, url, api).
  • Acronyms are always expanded next to every use - in prose, tables, and headings. Literal identifiers stay as they are.

Core guarantee. Two or more users can complete the same CSJ application at the same time without silently losing each other's work. Every saved unit is its own CMS document, every update writes only the changed keys against a revision check, a dirty editor is never replaced by a remote value, and a submitted application is frozen as a separate snapshot. No entry is ever allowed to approach the 1 MiB Firestore document limit.

5. Verified problem and root cause

5.1 Verified evidence

  • The existing process uses four CMS field groups: CSJ - Job Descriptions - Base, Funding - CSJ - Required Information, CSJ - Jobs In Application, Funding - CSJ Application Required Documents and Funding - Conditional Requirements.
  • The CSJ - Jobs In Application table references job descriptions through cmsObjectType: canada-summer-jobs-grant-job-definitions-uniconbaseapps, so the two applications are coupled and both must be maintained.
  • The field-group model has one data record per application. Two users editing different jobs, contacts or documents in the same record write the same document, so the last save wins and the other edits can disappear.
  • All data lives inside one Firestore document. A large application with many jobs and long descriptions moves toward the 1 MiB per-document limit with no guard.
  • There is no readiness check, no status lock, no frozen submission and no audit trail per entry.

5.2 Current implementation (verified from the supplied field definitions)

// Old model, summarised
// One record = organization + contacts + addresses + every job + documents.
// Job rows reference a separate job-description application by object id.
// No per-entry concurrency boundary, no revision, no freeze, no size guard.

5.3 Structural flaws

  1. One record is the concurrency boundary. Two people editing different jobs still write the same document, so one save can replace the other.
  2. The job description is a separate application. The application cannot be copied or frozen as one unit, and an edit to a shared job description can change a submitted application.
  3. No submission freeze. A submitted application can still be edited, so the version sent to the funder is not reconstructable.
  4. No size guard. The 1 MiB Firestore limit is discovered only when a save fails.
  5. No readiness model. Missing fields and documents are found at submission time, not while the team works.

Root cause: the field-group model assumes one editor and one record. A team application needs a per-entity concurrency boundary, a frozen submission, and an explicit document-size budget.

6. Requirements

  1. R-01 One central application tool. One tool instance prepares one Canada Summer Jobs application for one organization and one program year.
  2. R-02 CSJ-specific job descriptions. Each job holds the CSJ description, wage, language, skill development plan, employment terms, supervision, mentorship, recruitment plan and national/local priorities.
  3. R-03 Multi-user safety. Two users editing two different jobs, contacts, addresses, documents or the organization must not lose each other's work. A same-entry simultaneous edit must produce an explicit conflict, never a silent overwrite.
  4. R-04 No approach to 1 MiB. File binaries never enter a tool entry. Every entry is measured, warned at 200 KB, and blocked at 400 KB. Snapshots are separate entries and are capped at 400 KB.
  5. R-05 Readiness before submission. The tool lists blocking items and warnings across the organization, contacts, addresses, jobs and documents, and refuses submission while blockers remain.
  6. R-06 Frozen submission. Submitting writes a frozen snapshot and locks all entries. Only an administrator can reopen the application.
  7. R-07 Fail soft. If object storage or a type is not available, the tool explains the configuration problem, keeps editing in memory, and offers a JSON backup. It never fails silently.
  8. R-08 No legacy baggage. The old field groups are reference material only. There is no migration, no compatibility layer and no reuse of the old type.
  9. R-09 English only. Every label, message and exported document is English.
  10. R-10 Sandbox compliance. No localStorage, no fetch, no external scripts, no raw postMessage, no alert/confirm/prompt. All outside content and files go through the CMS SDK.
  11. R-11 Role gating. Viewers read only. Editors edit entries. Administrators also delete entries, change terminal status, submit and delete snapshots.
  12. R-12 Export. The application can be downloaded as JSON and exported as a print-ready A4 package, independent of the entries.
  13. R-13 AI assistance is optional and user-controlled. When the AI channel is enabled, the assistant drafts or revises only the tasks and responsibilities, only after an explicit request. It never changes another field and never saves the job; the user applies the draft and still presses Save job.
  14. R-14 AI chat is separate from application data. Conversation history lives in the shared AI chat session type, never in an application entry, so the entry size guard is unaffected.
  15. R-15 Per-user job ownership. An editor creates and edits only their own job descriptions. Other editors' jobs are visible read-only as samples and can be duplicated. An administrator edits every job and every organization setting.
  16. R-16 Administrator-managed priority definitions. National priorities are maintained once per application by an administrator. Every branch has its own local priorities, maintained by an administrator. Both lists use a guided item editor with Title, Keywords and Description fields. Job editors select from these lists and cannot invent entries in them.
  17. R-17 Branches and constituencies. The application holds any number of branches. Each branch names a province and one federal constituency from the embedded 343 district list.
  18. R-18 Regular scoring. Every job gets a deterministic alignment score from its selected priorities and its description text. The score updates without AI and without a save.
  19. R-19 Optional AI second opinion. When AI is enabled, the user can request an AI review of one job against its priorities. The AI score is displayed next to the regular score and is never saved automatically.
  20. R-20 Overall score. The dashboard shows an overall application score that combines readiness and the average job alignment score, with the component values visible.
  21. R-21 Priority lists are edited as items, not syntax. An administrator adds, edits and removes a priority as a card with separate Title, Keywords and Description fields. No pipe or comma parsing instructions are required.
  22. R-22 Writing workspace. The task editor and the AI assistant are visible at the same time on a dedicated Job description tab. The Job details tab stays compact: the Job title is always visible and the NOC search expands only when requested.

8. Solution design

8.1 Core invariant

Invariant CSJG-1. A save writes exactly one entry document. The application is never written as a whole. A submitted application is frozen as a separate snapshot entry. No entry may exceed 400 KB, and file binaries never enter an entry.

8.2 Entry model and CMS storage

All entries use one type:

canada-summer-jobs-grant-application-entry-uniconbaseapps

data_categoriesBased = {
  entryType: "application" | "job" | "contact" | "address" | "document" | "snapshot" | "branch",
  schemaVersion: 1,
  revision: 1,
  updatedAt: ISO timestamp,
  updatedByUserId, updatedByName, updatedByEmail,
  ownerUserId, ownerUserName, ownerUserEmail,   // jobs only
  ...entity fields
}
  • The object name is a human label: the job title, the contact name, the file name, the branch name or "CSJ application YEAR".
  • A job entry stores jobTitle, nocCode, nocTitle (the official class title), jobDescriptionHtml, ownerUserId, branchObjectId, supportedNationalPriorities, supportedLocalPriorities and the rest of the CSJ job answers. nocTitle is additive; older entries normalize it to an empty string. Older jobs without an owner are adopted by an administrator on the next admin save.
  • A branch entry stores branchName, province, constituency and its own localPriorities list. The national priorities are stored on the application header.
  • The tool value stores only { schemaVersion, applicationEntryId, ui.section }. It is a pointer, never the application data.
  • The field settings must include { mainObjectType: "canada-summer-jobs-grant-application-entry-uniconbaseapps", role: "editor", scope: "instance", targetCollection: "public" or "private" }.
  • Instance scope binds every entry to the record that hosts the tool. The CMS filters queries by the parent automatically.

8.3 Save algorithm

saveEntry(record, options):
  changed = keys where record differs from record._baseline
  if changed is empty: return no-op
  if size(record) > 400 KB: block with a message
  if record has no objectId: create entry, revision 1
  else:
    fresh = get(record.objectId)          // read before write
    if fresh.revision > record.revision and not overwrite:
      conflicts = keys changed by both fresh and record
      if conflicts: return "conflict" with the fresh entry
    merged = fresh + changed
    merged.revision = max(fresh.revision, record.revision) + 1
    update(record.objectId, only changed keys + revision + stamps)
  • Queries are serialized per entry with an in-memory queue, so one user cannot start two overlapping saves on the same entry.
  • If the CMS rejects an update with a version error, the tool re-reads once and retries with a fresh merge.
  • A same-entry conflict never overwrites silently. The editor shows Reload or Keep mine. Keep mine performs an explicit overwrite save.
  • Entries created while storage is unavailable stay in memory and are marked local; they are never written to the CMS later by surprise.

8.4 Live refresh

  • One query returns every entry of the current application.
  • Refresh runs on window focus, after every successful save, and every 20 seconds while the tab is visible. The interval is configurable and has a 10 second floor.
  • The remote list is merged by object id. A newer revision replaces a clean local entry. A dirty editor or a dirty organization form is never replaced; it receives a remote-change banner instead.
  • Entries removed remotely are removed from the lists. Local-only entries are kept.
  • There is no push subscription. The live chip states that the tool is on a refresh cadence, not a real-time socket.

8.5 Size guard

  • Every entry is measured as UTF-8 JSON before create or update.
  • Above 200 KB: a warning toast. Above 400 KB: the save is blocked.
  • The job description is capped at 20,000 plain-text characters.
  • Documents store only name, storage URL, size, MIME type and upload metadata. The binary is in CMS storage.
  • Snapshots are JSON in their own entry, capped at 400 KB. If the snapshot would be larger, the tool refuses and recommends the JSON export.
  • The NOC 2021 title index is embedded in the tool JS and adds about 120 KB to that code file only. It is not an application entry and has no effect on the entry budget.
  • The dashboard shows the largest entry, total stored bytes, the 1 MiB limit and the 400 KB tool stop.

8.6 Readiness and status

  • Every check is either a blocker or a warning. Blockers stop submission; warnings are shown but do not.
  • A job whose nocCode is not exactly five digits produces a warning, not a blocker, so a missing NOC suggestion never stops a first draft.
  • The score is the percentage of checks that pass. It is a completeness score, not an eligibility decision.
  • Statuses: Draft, Internal review, Ready to submit, Submitted, Approved, Declined. The last three lock every entry. Only administrators submit, mark approved or declined, and reopen.
  • Submission first creates a snapshot entry, then sets the application status to Submitted. If the snapshot fails, the status is not changed.

8.7 Exports

  • JSON export contains the application and every non-snapshot entry, with a schema version and export timestamp.
  • The PDF package is a self-contained A4 HTML document with organization, contacts, addresses, branches with local priorities, documents and every job. Each job shows its branch, its selected national and local priorities and its alignment score. It is passed to tool.requestExportPdf; if that channel is unavailable, a print-ready HTML file is downloaded instead.

8.9 AI writing assistant for tasks and responsibilities

  • The Job description tab is a two-column workspace: the task editor on the left and the AI assistant on the right. On narrow screens the assistant moves below the editor, so both remain usable.
  • Quick actions fill the composer with a prepared request; the user edits or sends it. The editor and assistant scroll independently where space allows.
  • The prompt contains the job title, the selected NOC title and code, the current tasks (plain text) and the recent chat turns. It instructs the model to return only an HTML <ul> with 5 to 10 concrete tasks, to avoid inventing wages, hours, dates or benefits, and to treat the job data as data.
  • The response streams into the chat. The tool extracts the list items, caps them at 12 escaped bullets, and shows two actions: Replace tasks and Append. Applying changes only the editor and marks the drawer dirty; nothing is written until the user presses Save job.
  • Chat history is one CMS object per job of type ai-chat-sessions-uniconbaseapps, named CSJ JD chat - <jobObjectId>. Messages carry the mandatory role, text, time, userId and userName fields, plus optional jobObjectId, jobTitle, tasksHtml and isError.
  • The session is created after the first message. For a new unsaved job the conversation stays in memory until the job is created; the session is then created with the new id.
  • Caps: 120 messages and 300 KB per session; the oldest turns are trimmed. Each message text is capped at 4,000 characters and the prompt at 16,000 characters.
  • If the AI channel is off, the panel is disabled. If the chat session type is not authorized, drafting still works but the panel warns that chat is not saved and the tool calls reportMissingParams. A viewer sees the panel read-only.
  • The tool does not choose the model. The CMS field decides the AI model; the tool only sends prompt and context through requestAI or requestAIStream.

8.10 Job ownership

  • Every job stores ownerUserId, ownerUserName and ownerUserEmail from the CMS user at creation time. An editor who creates a job owns it.
  • canEditJob(job) is true for an administrator on every job and for an editor only when the owner id matches the current user id. A job without an owner is editable by an administrator only.
  • The job list shows an owner chip. Opening another editor's job shows an owner banner, disables every field, the Save button, the NOC picker, the AI composer and the priority checkboxes, and offers Duplicate. A viewer gets the same read-only view for every job.
  • The save guard runs again in saveEntry, not only in the UI. An editor save on a job they do not own is refused with a clear message.
  • Administrators retain organization settings, contacts, addresses, documents, branches, national priorities, status, snapshots and deletion.

8.11 Branches, constituencies and priorities

  • The Branches panel lists the application's branches. An administrator adds a branch with a name, a province and one federal constituency from the embedded 343 district list. The list is a snapshot of the 2023 Representation Order and is not fetched at runtime.
  • A branch owns a local priority list. The national priority list is owned by the application header and edited once per program year. Both lists use the same guided item editor: each priority is a card with separate Title, Keywords and Description fields.
  • The editor has an Add button and a Remove button per card. Keywords are typed as a comma-separated list inside their own field; no pipe syntax or line format is shown to the user.
  • Saving a priority list keeps the id of every existing priority, including when its title is edited, so jobs keep their selections. A new priority gets an id from its title at save time.
  • The national list requires at least one priority and every card must have a title before the save is accepted. A local list may be empty; a blank local card blocks the branch save until it is titled or removed.
  • A job selects one branch. Its local priority checkboxes come from that branch; its national priority checkboxes come from the application header. A job with no branch shows a warning and selects from the national list only.
  • An editor sees the branch and priority definitions read-only. Only an administrator can add, edit or delete a branch or change a priority definition.
  • A branch that is still referenced by a job cannot be deleted; the tool reports how many jobs use it.

8.12 Regular alignment scoring

  • The description text is the plain text of jobDescriptionHtml, lowercased. The selected priorities are the national ids stored on the job plus the local ids resolved from its branch.
  • Each priority has a keyword list. A keyword may be a phrase. The tool counts a keyword as found when it appears as a whole word or phrase.
  • The priority score is the percentage of its keywords found, plus a small phrase bonus when the full priority title appears. A priority with no keywords scores by its phrase only.
  • The job score is the rounded average of the selected priority scores. No selected priority gives 0% and the label "No priorities selected". The score updates immediately when a checkbox changes and does not require a save.
  • The job list, the dashboard and the exported package show the score. The score measures how well the description reflects the chosen priorities; it is not a grant eligibility assessment.

8.13 AI second opinion and overall score

  • When AI is enabled, the priorities tab offers "AI score this job". The tool sends the job description and the selected priority titles with their keywords and asks for strict JSON: {score, strengths, gaps}.
  • The AI score is parsed, clamped to 0-100 and displayed next to the regular score with strengths and gaps. It is a second opinion and is not saved to the job.
  • An unparseable answer shows a clear message and leaves the job unchanged. An AI failure never blocks the regular score or the save path.
  • The dashboard overall score is round(0.5 * readiness + 0.5 * averageJobPriorityScore). Jobs without a score are excluded from the job average; the note shows the readiness value, the job match value and how many jobs are scored.

8.14 Compact job details and the writing workspace

  • The Job details tab is deliberately small. The Job title input is always visible; the NOC search, NOC code and NOC site link live in a collapsible block controlled by one button.
  • The NOC block opens automatically for a new job or a job without a NOC code. It stays collapsed for a job that already has a title and a NOC code, leaving the title and the posting details as the main content.
  • Selecting a NOC result fills the title, the code and the class title in place. The search stays available so the user can try another result, and the compact status line shows the current code and class title.
  • The Job description tab holds the task editor and the AI assistant. Switching tabs syncs the rich-text editor into the drawer draft first, so no task text is lost.
  • The editor is a large workspace (520 px minimum on desktop) with the formatting toolbar, a live character count and the 20,000 character limit. The assistant panel is sticky beside it on wide screens.

14. Open questions

Decision points we resolve together before or during implementation. Every answer becomes a dated row in section 11.

  1. Public or private collection? The entry type needs a targetCollection. Public (om_objects) follows the public-access rules; private (om_private_objects) requires authentication. The tool behavior is identical; the field setting decides.
  2. Who may submit? The current build restricts submit, approve, decline, reopen and delete to administrators. Should an editor be allowed to submit a Ready application?
  3. Which documents are blockers? The current build blocks on proof of business registration, proof of address and the health and safety policy. Should the void cheque, hiring policy and discrimination policy also block submission?
  4. Minimum wage warning. The optional minimumWage parameter is not used yet. Should the tool warn when a job wage is below the provincial minimum?
  5. Shared job descriptions. Is there a real need to reuse the same job description across years or organizations, or is duplication inside the application enough?
  6. Snapshot retention. How many frozen snapshots should be kept? The current build never deletes them automatically.
  7. French interface. Is a French version of the tool and the exported package required in a later phase?
  8. Multi-organization instances. Should one tool instance hold one organization, or should a year instance hold several organizations?
  9. Attachment bundle. Should the PDF export include the uploaded documents, or only the application text and a document checklist?
  10. NOC index refresh. The tool embeds NOC 2021 Version 1.0. When should the index be regenerated for a new NOC release, and should the job form block a code that is absent from the embedded version?
  11. NOC as a blocker. A missing or malformed NOC code is currently a readiness warning. Should a Ready application require a 5-digit NOC code before it can be submitted?
  12. AI scope. The assistant currently edits only the tasks and responsibilities. Should it also rewrite the skill development plan, supervision text or the whole job description in a later phase?
  13. AI chat retention. Chat sessions are separate CMS objects with no automatic deletion. Should old sessions be deleted after the application is submitted, or kept for audit?
  14. Owner reassignment. When an editor leaves, should an administrator be able to move that editor's jobs to another owner? The current build leaves the jobs editable by administrators only.
  15. Score weight. The overall score is half readiness and half the average job alignment score. Is that the right weight, or should readiness dominate?
  16. Priority versioning. When the national priorities change for a new year, should old jobs keep the old priority ids for audit, or be remapped to the new list?

What can go wrong: the model produces duties that do not fit the placement, or invents equipment or benefits that were not in the context.

Likelihood / impact: possible with any model; medium impact if the user applies the draft without reading it.

Mitigation: the prompt forbids invented facts and asks for concrete verbs; the draft stays in the chat until the user presses Replace or Append; the editor is still editable; the job is not saved until the user presses Save job.

Last re-evaluation: 2026-11-28 - accepted with explicit apply and review.

R-CSJ-16AI chat history is not saved when its type is unauthorized

Applies to: T-CSJ-20.

What can go wrong: the field does not allow ai-chat-sessions-uniconbaseapps, so the conversation disappears on reload even though the assistant worked.

Likelihood / impact: likely until the field is configured; low to medium impact because the job data is unaffected.

Mitigation: the assistant still works in memory, the panel says the chat is not saved, and reportMissingParams asks the administrator to authorize the shared type. No application entry is touched by this failure.

Last re-evaluation: 2026-11-28 - accepted; configure the type before the pilot.

R-CSJ-17Ownership is not enforced by the CMS host

Applies to: T-CSJ-21.

What can go wrong: a user who calls the object SDK outside the tool can write another user's job, because the host grants write permission at the field level, not per entry owner.

Likelihood / impact: low for normal users; medium impact if a user is technical and deliberately bypasses the UI.

Mitigation: the tool disables every editor path and repeats the owner check in saveEntry. Administrators still see every job for review. Per-owner host rules would need a CMS capability that does not exist today.

Last re-evaluation: 2026-11-28 - open, accepted only if the deployment trusts its editors.

R-CSJ-18Keyword score rewards wording, not real fit

Applies to: T-CSJ-25.

What can go wrong: an editor adds priority words without real duties and the score rises; a good description in different words scores low.

Likelihood / impact: possible; medium impact if the score is read as an eligibility judgment.

Mitigation: the UI calls it an alignment indicator, shows the regular and AI values side by side, and the AI prompt asks for gaps rather than only a number. The readiness score remains separate.

Last re-evaluation: 2026-11-28 - open; watch the first real applications.

R-CSJ-19Renamed priority drops existing job selections

Applies to: T-CSJ-22, T-CSJ-24, T-CSJ-27.

What can go wrong: an earlier parser derived the priority id from its title, so renaming created a new id and jobs silently lost the selection.

Likelihood / impact: no longer applies when a card is edited; the item editor keeps the existing id. Replacing the annual list with new cards still creates new ids.

Mitigation: the guided item editor saves each card with its original id. The remaining yearly replacement case is documented in L-16 and the open question on priority versioning.

Last re-evaluation: 2026-11-28 - solved by D-CSJG-28; edit existing cards to keep ids.

R-CSJ-20Branch deletion leaves jobs without local priorities

Applies to: T-CSJ-23.

What can go wrong: an administrator deletes a branch that jobs still reference, so those jobs lose their local priorities and their score.

Likelihood / impact: low; deletion is blocked while any job references the branch, but a race between two sessions is possible.

Mitigation: the delete action counts references and refuses; a job with a missing branch shows a warning and still scores its national priorities. Recreating the branch restores resolution if the object id matches, which it normally does not.

Last re-evaluation: 2026-11-28 - open.

R-CSJ-21AI score is not saved and may vary between runs

Applies to: T-CSJ-26.

What can go wrong: the AI number is not persisted and can differ on a second request, so it cannot be used as an official score.

Likelihood / impact: certain; low impact because it is explicitly a second opinion.

Mitigation: the modal labels it as a second opinion and not saved, and the regular deterministic score is the value stored and exported.
