1. Purpose and governance

This document defines one tool and one set of invariants around the restaurant document the customer website reads - and it is the single source of truth for every decision we make about this tool, now and in the future. No decision is considered made until it is written here. Rules of use:

  • Every decision is logged here. Before or together with any change to this tool, the decision is added to section 11 with a date, and the affected section is updated in the same change.
  • The register is append-only. Decision rows are never deleted. A reversed decision is marked "Reversed (date)" with a reason - the original row stays for history.
  • This document wins ties. If this document or the code disagree, the discrepancy is resolved in this document first (with a dated decision), then applied to the code - never the other way around, and never silently left divergent.
  • Check before changing. Before changing any behavior covered here, read the relevant section and the register; after the change, update this document in the same change as the code.
  • Names must be self-explanatory. Every variable, function, and code snippet in any update uses understandable names. No cryptic abbreviations. Short names are allowed only for loop indexes and universally known abbreviations (id, url, api).
  • Acronyms are always expanded next to every use - in prose, tables, and headings. Literal identifiers stay as they are.

Core guarantee. No customer-facing deal, campaign, hero image or promotion reaches the website in a shape the contract does not define, and no save can silently break an existing menu reference. Everything below serves this one sentence.

5. Verified problem and root cause

5.1 Verified evidence

  • The customer contract (docs/client-data-contract.html, version 3.3, 2026-10-21, sections 21 and 23) defines hero, promotions, campaigns, deals and promo_codes as OPTIONAL top-level sections of the very document this tool publishes.
  • Verified 2026-10-21: app/RestaurantAndMenuManager.js contains zero occurrences of deals, promotions, campaigns or hero (grep count 0).
  • Verified 2026-10-21: the DEFAULTS object (line 5) defines ten top-level keys - general_info, service_settings, taxation_currency, payment_methods, delivery_zones, delivery_form_settings, menu, alert_settings, social_links, device_connections. No presentation key exists.
  • Result: no tenant document can contain deals, so the website Deals page and every deal card stay empty, and the only way to publish a deal today is to hand-edit the stored JSON document.

5.2 Current implementation (verified in code)

  • app/RestaurantAndMenuManager.js - DEFAULTS (line 5) is the whole document shape. Anything absent here never appears in a new record.
  • app/RestaurantAndMenuManager.js - scheduleSave() (line 565) debounces for 500 ms and calls tool.setValue(JSON.parse(JSON.stringify(data))) (line 568). Whatever is in data is published verbatim.
  • app/RestaurantAndMenuManager.js - deepMerge(DEFAULTS, incoming) (line 248) copies unknown incoming keys through untouched, so a hand-edited presentation key would survive a load - but nothing in the UI can create, validate or edit it.

5.3 Structural flaws

  1. No presentation authoring surface. The contract expects four optional sections; the tool has no control that can produce any of them.
  2. No shape validation. Any object placed in data is published, so a malformed deal would reach the website without a warning.
  3. No reference integrity. Deals point at categories, items and size labels; the menu editor can delete them without knowing a deal depends on them.
  4. No preview surface. The owner cannot see what the Deals page will render, so errors are only discovered on the live site.

Root cause: the tool was built as a menu authoring tool for one fixed document shape. The presentation sections were added to the customer contract later, so the document can describe them but the admin tool can never write them.

6. Requirements

  1. R-01 - Placement. Deal management is reachable from one top-level tab at the same level as Menu, without opening the Menu tab.
  2. R-02 - Contract shape. Every saved deal, campaign, hero object, promotion and promo code matches contract version 3.3 exactly: same key names, same value types, no unknown keys.
  3. R-03 - Rule types. Exactly four rule types can be authored today: bundle, min_quantity, tiered, two_for_one. The extended set in contract section 23.1 is authorable since 2026-10-21 (T-30 to T-42, D-RAMM-18). No UI path can produce any value outside the contract set.
  4. R-04 - References. Every category, item and size reference resolves to a current menu entry, and every picker offers only existing entries with their real names.
  5. R-05 - Save gate. A deal cannot be saved when its rule filters match zero menu items, or when a required key is missing or of the wrong type.
  6. R-06 - Pricing. Bundle price is a fixed total; min quantity price is per unit with min_quantity of at least 2; tiered and two-for-one carry price: null.
  7. R-07 - Images. A deal image is optional. An empty image_url is valid and the website shows its placeholder.
  8. R-08 - Sections and order. Deals carry an optional section label; the list groups by section and the array order is the display order. The owner reorders deals by drag and drop, both inside a section and across sections (D-RAMM-16).
  9. R-09 - Campaigns. The campaign editor can only write "pricing": "most_expensive", shown read-only.
  10. R-10 - Presentation. The hero supports a direct image plus a preset gallery; promotions are limited to four stored entries in the chosen order.
  11. R-11 - Persistence. Saving uses the existing debounced tool.setValue path. No direct database, REST or network call is introduced.
  12. R-12 - Regression. Existing menu, photo, visibility and import behavior keeps working unchanged, and no existing top-level key changes shape.
  13. R-13 - Legacy records. Records written before this feature (without presentation keys) load without error and are published unchanged until the owner edits them.
  14. R-14 - Lifecycle. A deal can be created, edited, duplicated and deleted; deleting a deal never alters menu data.
  15. R-15 - Governance. Every decision taken here is recorded in section 11 in the same change as the code.
  16. R-16 - Active flag. Every deal stores a boolean active flag (default true). The website honors it since 2026-10-21: a deal with active: false is hidden from the Deals page. The editor label states exactly that (D-RAMM-15, D-RAMM-19).
  17. R-17 - Safe delete. A category that still contains items cannot be deleted. Deleting an item or category used by a deal is blocked with a message naming the deals that use it (D-RAMM-17).
  18. R-18 - Extended rule types. The deal editor can author every rule type in contract section 23.1: percentage_discount, subtotal_threshold, free_delivery, free_item_with_purchase, buy_n_get_m, volume_pricing and free_modifier, plus the optional schedule block on any deal. The discount types (percentage_discount, subtotal_threshold, free_delivery, free_modifier) carry price: null - the website computes the discount line (D-RAMM-18).
  19. R-19 - Promo codes. The top-level promo_codes array is authorable: a normalized code string, a title, one of the three supported rule types (percentage_discount, subtotal_threshold, free_delivery) with its matching rule, and an optional max_uses (D-RAMM-18).

8. Solution design

8.1 Core invariant

Invariant DEAL-SHAPE. Every presentation value this tool writes matches the shape in docs/client-data-contract.html version 3.3, sections 21 and 23 - same key names, same value types, no extra keys. A field the website does not read is never written, and a field the contract requires is never omitted. The deal active flag started as an exception (D-RAMM-15); the contract documents it since version 3.1 and the website honors it since 2026-10-21, so the editor label now describes the real behavior (D-RAMM-19).

8.2 Document schema - the five optional sections

{
  "hero": { "image_url": "", "preset_images": [] },
  "promotions": [
    { "id": "promo-1", "title": "", "description": "", "image_url": "" }
  ],
  "campaigns": [
    { "id": "", "title": "", "description": "", "required_item_count": 2,
      "same_size": true, "category_ids": [], "item_ids": [],
      "pricing": "most_expensive" }
  ],
  "deals": [
    { "id": "", "section": "", "title": "", "description": "", "price": 0,
      "image_url": "", "active": true, "rule_type": "bundle", "rule": { } }
  ],
  "promo_codes": [
    { "code": "SAVE10", "title": "", "rule_type": "percentage_discount",
      "rule": { "percent": 10 }, "max_uses": null }

}
  • All five sections are optional. Omitted means absent, and the website renders nothing for it.
  • The deals array order is the display order; section groups the cards.
  • There is no schema_version key. Do not add one.
  • The website caches the document for one hour and refreshes on tool.onValueChange, so the next save is visible to an open page immediately.

8.6 Read, write and publish path

  1. Read. tool.onReady(value) merges the document with DEFAULTS through deepMerge, then normalizes the four presentation sections to the expected array or object types.
  2. Write. scheduleSave() debounces 500 ms and calls tool.setValue with a deep copy of data. No direct database or REST access.
  3. Publish. The CMS stores the document unchanged. The website reads it, caches for one hour and refreshes on tool.onValueChange.
  4. Order path. The website builds the order line fields; this tool never writes orders.

14. Open questions

Decision points we resolve together before or during implementation. Every answer becomes a dated row in section 11 and is removed from this list. Q-01, Q-03 and Q-05 were answered on 2026-10-21 (D-RAMM-15 to D-RAMM-17).

  1. Q-01 - Where do the hero preset images come from? A preset is a ready-made hosted image URL the owner can pick with one click, so no upload is needed. hero.image_url is the image shown; hero.preset_images is the list offered in the manager. Contract section 21.1 says the owner picks a preset in the manager tool and the widget falls back to the first preset_images entry, but it never says who supplies those URLs. Options: (a) one tab named Deals with four sub-tabs (Deals, Campaigns, Hero, Promotions), (b) the same four sub-tabs under the name Deals & Promotions, (c) two tabs, one for offers (Deals, Campaigns) and one for presentation (Hero, Promotions).
