Restaurant & Menu Manager — Client Data Contract

The complete data structure consumed and produced by the Restaurant & Menu Manager tool, for building the customer-facing (client-side) website around it.

1. Overview

The Restaurant & Menu Manager is a single-page management tool that a restaurant owner uses to configure everything the public website needs to operate online ordering:

  • Menu structure — categories, products (items), sizes, and modifier groups with options.
  • Visibility scheduling — products and categories can be always-visible, hidden, or shown only during time windows / date ranges.
  • Availability — items and individual modifier options can be marked out of stock (until tomorrow, a date, or indefinitely).
  • Channel filtering — each product declares on which service channels it appears (pickup, delivery, on-premise).
  • Taxation — tax categories with per-channel rates, referenced from categories, products, and modifier groups.
  • Rich content — photos (galleries on products/categories, single photos on modifier groups/options), dietary marks, allergens, ingredients, additives, and a full nutrition table.
  • Supporting config — opening hours, delivery zones (geofences), payment methods, reservation settings, and more.
One JSON document. The tool stores everything as a single JSON object — the same object is both the tool's input (loaded on start) and its output (saved on every edit, debounced by 500 ms). The client website reads this same object to render the public menu.

This document is organized top-down: the embedding contract (§2), the top-level shape (§3), every section in detail (§4–§10), then the interpretation rules the client must implement (§11–§16) and a complete example (§18).

2. Embedding & SDK Contract

The tool runs inside a sandboxed iframe. The host page must inject a single global object, window.tool, before the tool's scripts execute. The tool never calls any other browser/network API for data — all persistence and file uploads go through this object.

window.tool— the complete SDK surface used by the tool
Method Signature Used for
onReady tool.onReady(function(value) { … }) Fires once at startup with the currently stored document (the full JSON below, or {} if none). The host must call the callback — this is how the tool boots.
onValueChange tool.onValueChange(function(value) { … }) Fires whenever the document changes outside the tool (another admin tab, CMS sync). The tool re-renders from the new value. Optional but recommended for multi-tab consistency.
setValue tool.setValue(jsonObject) The tool's save path. Called on every edit, debounced 500 ms, always with a full deep-cloned copy of the document. The host persists this object verbatim and later returns it via onReady/onValueChange.
requestUpload tool.requestUpload('image/*', function(err, file) { … }) Opens the host's file picker for images. On success the callback receives file with at least { url, name }. file.url is the string the tool stores in every photos[] / photo_url field. On failure pass a non-null err.
notify tool.notify(message, type) Toast notifications. type is one of 'success', 'warning', 'error', 'info'.
resize tool.resize() Requests the host to re-measure the iframe (the tool's height changes constantly while editing).
isReadOnly tool.isReadOnly() → boolean If true, the tool disables every input on boot.
onReadonlyChange tool.onReadonlyChange(function(ro) { … }) Fires when the host toggles read-only mode; the tool locks/unlocks all inputs.
UniconHub platform mode. On the UniconHub publicwebsite renderer, tool.onReady delivers the island CONFIG ({cmsObjectType, filters, pageSize, channel, mode, themeToggle}) instead of the document. In that case the widget queries the platform's read-only data relay itself - tool.requestObjects('query', params), then tool.requestObjects(params), then window.gw.db.query(params) - using cmsObjectType, filters and pageSize from the config, unwraps whatever response shape comes back, and applies the config's channel / mode / themeToggle display hints. Every other embedding mode keeps the document-through-onReady contract described below.
Strict equality on save. The value your host receives from setValue is a complete document — always store and return it whole. The tool merges the stored value over its internal defaults (deepMerge(DEFAULTS, incoming)), so partial documents are tolerated on load, but missing arrays are re-created and default values are injected on the next save. Never hand-modify the stored JSON while the tool is open in another tab without broadcasting an onValueChange.

3. Top-Level Document Shape

{
  "general_info":         { … },   // §4  Restaurant identity, contact, legal
  "service_settings":     { … },   // §5  Channels, hours, reservations
  "taxation_currency":    { … },   // §6  Currency + tax categories
  "payment_methods":      { … },   // §7  Accepted payment methods per channel
  "delivery_zones":       { … },   // §8  Geofenced delivery zones
  "delivery_form_settings": { … }, // §9  Customer address form config
  "menu":                 { … },   // §10 THE MENU — categories, items, modifier groups
  "deals":                [ … ],   // §23 OPTIONAL — customer offers (bundle, min_quantity, tiered, two_for_one)
  "hero":                 { … },   // §21 OPTIONAL — hero image above the restaurant name
  "promotions":           [ … ],   // §21 OPTIONAL — at most 4 promo entries under the hero
  "campaigns":            [ … ],   // §21 OPTIONAL — legacy offers, surfaced as two_for_one deals
  "promo_codes":          [ … ],   // §23.1 OPTIONAL — checkout codes (percent off, subtotal discount, free delivery)
  "alert_settings":       { … },   // §17 Admin alerts (not customer-facing)
  "social_links":         { … },   // §17 Public links
  "device_connections":   [ … ]    // §17 Admin-only device registry
}
The five presentation keys are OPTIONAL. deals, hero, promotions, campaigns and promo_codes may be absent from older records - treat an absent key exactly like an empty one, and render nothing for that section. The manager tool writes all five on every new record and on every save after an edit.

Every string field that contains free text from the admin is plain UTF-8. All date-times the client needs are ISO-8601: either YYYY-MM-DDTHH:mm (local wall-clock, used in schedules and OOS "until" values) or full ISO strings. All currency amounts are decimals (floats) in the restaurant's chosen taxation_currency.currency.

5. service_settings

5.1 Service channels — service_settings.service_toggles

These three flags define the channel vocabulary used everywhere else in the menu (show_on_channels, tax rates, payment methods):

pickup_enabled
Channel id "pickup" is active.
delivery_enabled
Channel id "delivery" is active.
on_premise_enabled
Channel id "on_premise" is active (dine-in / counter).
anonymous_ordering_allowed
Guests may order without an account.
table_reservation_enabled
Table reservations are offered.
A product can be configured with channels that are currently disabled in service_toggles. The client should intersect the product's show_on_channels with the enabled channels before showing availability.

5.2 Opening hours — service_settings.opening_hours

"opening_hours": [
  { "day": 0, "ranges": [{ "open": "09:00", "close": "17:00" }], "is_closed": false },
  // day 1 … day 6
]
  • day: 0 = Monday … 6 = Sunday (Monday-first).
  • ranges[]: one or more open/close HH:mm windows per day (multi-shift supported).
  • is_closed: true = closed all day, ranges ignored.

5.3 Scheduled orders — service_settings.scheduled_orders

{ "enabled": false, "pickup_min_advance": 30, "pickup_max_advance": 1440,
  "delivery_min_advance": 45, "delivery_max_advance": 1440,
  "time_slot_interval": 15 }

Advance values are minutes. Clients offering pre-order pickers should clamp the selectable lead time to these bounds and round to time_slot_interval.

on_premise_settings

6. taxation_currency — Tax Categories

"taxation_currency": {
  "currency": "USD",
  "tax_mode": "exclusive",
  "tax_name": "Tax",
  "tax_categories": [
    { "name": "Standard", "pickup": 5.0, "delivery": 5.0, "in_restaurant": 8.875 },
    { "name": "Reduced", "pickup": 0.0, "delivery": 0.0, "in_restaurant": 0.0 }
  ],
  "delivery_fee_tax_rate": 0
}
tax_categories[].name
The reference key used by tax_category_id fields on categories, items, and modifier groups. Free text entered by the admin — treat as an opaque key.
tax_categories[].pickup / delivery / in_restaurant
Percentage rate (0–100, decimals allowed) per channel. Same channel ids as §5.1.

Currently always "exclusive" — rates are applied on top of menu prices. See §16.
delivery_fee_tax_rate
Extra tax % applied to the delivery fee.

7. payment_methods

Flat boolean flags. The naming pattern is <method>_<channel>:

  • Methods: cash, card, interac, plus online_payment (global).
  • Channels: delivery, pickup, on_premise, reservation.
  • Examples: cash_delivery: true, card_pickup: true, interac_on_premise: false.
  • call_for_card_<channel> — card details are taken by phone, not online.

The client shows/hides payment options at checkout based on these flags for the active channel.

10. menu — The Core Data

"menu": {
  "categories":      [ … ],   // §10.1 — flat list, ordered
  "items":           [ … ],   // §10.2 — flat list, each references a category by id

11. Visibility Rules (Show / Scheduled / Hide)

Both categories and items carry the same visibility system. The public widget enforces it on items; categories are always rendered and a category simply disappears when it has no visible items (D-EFOC-17 - live easyorder records mark every category hide or scheduled, which must not blank the whole menu). Compute "is this item visible right now?" as follows:

  1. visibility_mode: "show" → visible always.
  2. visibility_mode: "hide" → hidden. If hide_until_date is set, it becomes visible again after that datetime; otherwise hidden permanently.
  3. visibility_mode: "scheduled" → visible only during the configured schedule:
    • schedule_type: "time_windows" — schedule_time_windows is an array of { days: number[], start_time: "HH:mm", end_time: "HH:mm" }. days: 1 = Monday … 7 = Sunday (note: different convention than opening_hours!). Visible iff today's number is in days and the current time (restaurant timezone) is within start_time–end_time of any window.
    • schedule_type: "date_range" — schedule_from / schedule_until are ISO datetimes. Visible iff now is within the range.
Day-number conventions differ: opening_hours[].day is 0=Mon…6=Sun, but schedule_time_windows[].days is 1=Mon…7=Sun. Do not mix them.

Category-level visibility is not enforced on the public widget (D-EFOC-17): a category renders whenever at least one of its items is visible. A hidden item is hidden even in a visible category. Effective item visibility = item rule only; the category contributes its grouping, not its visibility.

12. Availability & Out-of-Stock Rules

Items and modifier options use the same three fields:

Field Values Meaning
availability "available" · "out_of_stock" Current availability state.
oos_type "tomorrow" · "date" · "undetermined" · null Only meaningful when out of stock: tomorrow = back after tonight; date = back at oos_until; undetermined = no return time known.
oos_until ISO datetime · null Return-to-stock time for oos_type:"date". For "tomorrow" the tool stores a computed midnight timestamp; clients may compute their own.
  • Show "Out of stock" on the card; allow no ordering of the item / selection of the option while availability === "out_of_stock".
  • Option-level OOS only disables that option — the rest of the group remains selectable.
  • oos_until in the past ⇒ treat as available again.

13. Channel Filtering

Every item declares show_on_channels — the subset of ["pickup","delivery","on_premise"] where the item may be ordered. Rules for the client:

  1. Determine the active channel of the current user session (pickup / delivery / dine-in).
  2. Only show/order items whose show_on_channels contains that channel.
  3. Intersect with service_settings.service_toggles — if the channel itself is disabled in settings, it is closed regardless of item config.

14. Client-Side Price Resolution

  1. No sizes: base price = item.price (guaranteed non-null). Display sale_price when present as the struck-through comparison price.
  2. With sizes: the customer must pick a size. Base price = selected size's price. item.price is null in this case.
  3. Modifiers: cart line total = base price + Σ selected option price_adjustment × quantity.
  4. All prices are in taxation_currency.currency and exclude tax (tax_mode:"exclusive") — add tax per §16.

15. Modifier Selection Logic (Validation Rules)

For each modifier group attached to an item or to the selected size, first resolve the effective settings: start from the group's own fields, then apply modifier_group_overrides[groupId] if present (overrides is_required and allow_duplicates). Then enforce:

Rule Enforcement
selection_type: "single" At most one option may be chosen. (Tool also sets force_min/force_max=1 for its own single groups, but do not rely on that — honor selection_type first.)
selection_type: "multi" Any number of options; same option repeatable only if effective allow_duplicates is true.
effective is_required At least one selection is mandatory before add-to-cart.
force_min > 0 Customer must select at least force_min options (count repeats as separate selections when duplicates allowed). Implies required.
force_max > 0 Customer may select at most force_max options. 0 = unlimited.
Option out-of-stock OOS options are displayed but disabled (per §12).
is_default Pre-check defaults on load; still let the customer change them.

16. Client-Side Tax Calculation

  1. For an item, find its tax category: item.tax_category_id → else category.tax_category_id → else no category (0% / default).
  2. Look up that name in taxation_currency.tax_categories. Take the rate for the active channel: pickup, delivery, or in_restaurant.
  3. tax = round(subtotal × rate / 100, currency) — rates are exclusive percentages.
  4. Modifier groups carry their own tax_category_id when their options must be taxed differently — apply it to the modifier line amounts.
  5. Delivery fee tax: fee × delivery_fee_tax_rate / 100.

17. alert_settings · social_links · device_connections

alert_settings
{ failed_push_alert: bool, sound: "default|bell|ding|buzz|silent", supervisor_phone: string } — admin operational alerts; not needed by the public site.
social_links
{ facebook_url, smart_menu_link, website_enabled, website_domain, ios_app_enabled, android_app_enabled } — render social/website links in the footer.

Admin-only array of connected POS/tablet/KDS devices. Ignore on the client.

19. Legacy & Migration Notes

The tool itself auto-migrates older stored documents on load. The client should defensively handle these legacy shapes:

  • category.visible (boolean) → normalized to visibility_mode by the tool; treat false as hidden if ever encountered.
  • item.is_available (boolean) → same; legacy availability flag, prefer visibility_mode + availability.
  • is_vegetarian / is_vegan / is_gluten_free → legacy dietary booleans, now mirrored from dietary_marks.
  • Delivery zones may historically be stored as a GeoJSON features[] array — the tool migrates these to zones[] on load.
  • option.price / option.name exist only in the Gloria import source; in UniconHub storage they are always price_adjustment / option_name.
  • tax_category_id values are category names (strings), not numeric ids.
Summary for the client developer: load the document once via tool.onReady, render menu.categories in array order, join menu.items on category_id, apply visibility (§11) + channel (§13) + OOS (§12) filters, resolve prices (§14), validate modifier selections (§15), and compute tax per channel (§16). Render the presentation sections when present: hero above the restaurant name (§21), at most the first four promotions under it, campaigns surfaced as two_for_one deal cards, and the deals array grouped by section (§23). Everything else is supporting configuration.

20. Platform Write-Back (Orders)

The widget's only write on the UniconHub platform is the placed ORDER (intent: create only - no update, no delete). It follows the website-html-tool write-back contract (html-website-tool-rules.txt section 14, SSOT section 8.9): gw.db.create → same-origin renderer relay → CMS v2 POST /api/v2/objects/{type} with Idempotency-Key and header x-unicon-write-source: public-website.

  • Written type: restaurant-order-manager-easyorder (intent: create).
  • Required key setup: the site's write relay key must carry scope objects:write and list the type in allowedObjectTypes - the key allowlist IS the write surface (no app-level opt-in field exists).
  • Idempotency: Idempotency-Key = 'order-' + orderNumber - retries never duplicate a create.
  • Payload: the full order object (orderNumber, placedAt, channel, customer, address, customAddressFields, tableNumber, deliveryZone, scheduledFor, paymentMethod, paymentDetails, lines, totals); identity/audit keys are stripped server-side and _writeSource: 'public-website' is stamped.
  • Errors: 403 OBJECT_TYPE_NOT_ALLOWED / MISSING_SCOPE (key gate), PUBLIC_WRITE_OWNERSHIP, PUBLIC_WRITE_DELETE_NOT_ALLOWED, 409 CAS_CONFLICT, 429 rate/quota - all surface as the order-failure toast.
  • Until the renderer relay ships (task T-43): the platform branch confirms locally with a console warning - nothing is stored.

21.3 campaigns

Legacy campaigns (e.g. 2x pizza) are surfaced on the Deals page as two_for_one deal cards (section 23). The customer picks the required products INSIDE the deal popup - the picker enforces the same-category / same-size rules slot by slot - and the deal is added as ONE cart line: the more expensive product's price is charged, the cheaper one is free (pairs sorted by unit price, cheapest free), shown with Paid/FREE rows and a Deal discount row in the totals. New campaign-style promotions should be created as DEALS of type two_for_one. 

"campaigns": [
  {
    "id": "camp-2xpizza",
    "title": "2x Pizza",
    "description": "Pick two pizzas - pay only for the more expensive one.",
    "required_item_count": 2,
    "same_size": true,
    "category_ids": ["cat-pizzas"],
    "item_ids": [],
    "pricing": "most_expensive"
  }
]
  • required_item_count - how many campaign products the order needs (default 2).
  • same_size - true = every further pick must match the first campaign line's size label.
  • category_ids / item_ids - optional restrictions; empty = every item is eligible.

21.4 Category and item photos on the menu (decided 2026-10-21)

Categories render ONE big photo banner under their title (primary_photo_url or the first photos[] entry - see section 10); items render a small circular thumbnail using the same fields. When a photo is missing the widget shows a placeholder pizza photo (no data change is required).

22. Local Menu Cache (decided 2026-10-14)

Menus change rarely, so the widget caches the last loaded restaurant document in localStorage (efoc-menu-cache-v1) for ONE HOUR and renders it immediately on the next load while refreshing in the background. Document updates delivered through tool.onValueChange still refresh instantly.

23. Deals (decided 2026-10-21, D-EFOC-26..28)

The document carries an optional top-level deals array. The widget shows a Menu | Deals page switch; every deal is a card with a photo, a price tag, a description and a CUSTOMIZE button. Legacy campaigns entries are surfaced as two_for_one deals, so the deals page is the single place for promotions. Deal management lives in the CMS (restaurant-order-manager-easyorder, task T-64); the widget only consumes this contract. 

"deals": [
  {
    "id": "deal-2medium",               // unique id
    "section": "Online Only Deals",     // optional group header on the deals page
    "title": "Any 2 Medium Pizzas + 2 Cans of Pop + 4 Dips",
    "description": "Two medium pizzas, two cans and four dips.",
    "price": 34.99,                     // bundle: fixed total; min_quantity: per-unit; tiered: null
    "image_url": "https://...",         // optional; placeholder shown when empty
    "active": true,                     // stored by the manager - NOT yet honored by the website (see note)
    "rule_type": "bundle",              // bundle | min_quantity | tiered | two_for_one
    "rule": { ... }                     // see the rule shapes below
  }
]
The active flag is honored since 2026-10-21. The manager writes active (boolean, default true) on every deal. active: false hides the deal from the website's Deals page; a missing flag means active (backward compatible). The website is the current release that reads it.

Rule shapes (one per rule_type):

// bundle - fixed groups + included extras, one fixed total price
// a group WITHOUT item_ids is an option group: the customer picks the
// required quantity from the matching products
"rule": {
  "groups": [
    { "group_id": "pizzas", "label": "2 Large Pizzas", "quantity": 2,
      "category_ids": ["cat-pizzas"], "size_label": "Large" },   // pick 2
    { "group_id": "pop", "label": "2L Bottle of Pop", "quantity": 1,
      "category_ids": ["cat-pops"], "name_filter": "2L" },       // pick 1 from 2L options
    { "group_id": "dips", "label": "4 Dips", "quantity": 4,
      "category_ids": ["cat-dips"] },                            // pick 4 from dip options
    { "group_id": "extra", "label": "Fries", "quantity": 1,
      "item_ids": ["item-fries"] }                               // fixed included extra
  ]
}

// min_quantity - one picked product, minimum N units, every unit = deal price
"rule": {
  "category_ids": ["cat-pizzas"],
  "size_label": "Medium",
  "min_quantity": 2
}

// tiered - pre-defined quantity tiers, each with its own total
"rule": {
  "item_ids": ["item-lahmacun", "item-cola-2l"],
  "tiers": [
    { "quantity": 5,  "price": 49.90, "label": "5 Lahmacuns + 2L Coca-Cola" },
    { "quantity": 10, "price": 89.90, "label": "10 Lahmacuns + 2L Coca-Cola" }
  ]
}

// two_for_one = "Buy 1 Get 1 Free": the customer picks TWO SEPARATE
// products INSIDE the deal popup; the more expensive pick's price is
// charged and the cheaper pick is free. Legacy campaigns are surfaced as
// this type automatically.
"rule": {
  "required_item_count": 2,
  "category_ids": ["cat-pizzas"],
  "same_size": true
}
  • size_label matches size labels by substring, so "Medium" matches "Medium (12\")". A sized group excludes items without a matching size.
  • name_filter (optional) matches the item name by substring, case-insensitive - use it to narrow an option group (e.g. "2L" for the 2-litre pop options, "Can" for cans).
  • Groups WITHOUT item_ids are option groups: the customer picks the required quantity from the eligible products (category + optional size_label/name_filter). Groups WITH item_ids are fixed extras that come with the deal and need no picking.
  • Rule enforcement happens at selection time: the deal's CUSTOMIZE modal keeps its "Add deal to order" button disabled until every required group is complete - an incomplete deal can never reach the cart.
  • two_for_one is Buy 1 Get 1 Free, picked entirely inside the deal popup (one slot per required product; when same_size is true later slots only offer the first pick's size) and added as ONE cart line: the line price is the most expensive pick, the full price is struck through on the line, Paid/FREE rows list the picks, and the totals show a "Deal discount" row under subtotal. Remove deletes the whole deal; Edit reopens the popup with both picks - the pair can never be broken apart.
  • Bundle, tiered and two_for_one lines are fixed compositions - no quantity stepper in the cart (remove and re-pick to change). min_quantity lines use a normal quantity stepper with the minimum as its floor.

Order payload for deal lines - the order's lines[] entries carry these extra fields for deal lines:

"rule": { "min_subtotal": 30, "always": false }

"schedule": { "date_from": "2026-11-01", "date_until": "2026-11-30",

// promo_codes - top-level array, codes typed at checkout (T-74); supported

    "rule_type": "percentage_discount", "rule": { "percent": 10 },

Discount-type deals (percentage_discount, subtotal_threshold, free_delivery, free_modifier) add a discount LINE to the customer's cart; the website's totals engine evaluates each applied rule against the rest of the order and shows a green "- amount" on the line plus the Deal discount row under subtotal. Free delivery shows "Delivery: Free" instead of the fee row. The order payload carries promoCode when a code is applied.
