1. Purpose and governance

This document defines one tool and one set of invariants around the active orders board - the application-level surface where restaurant staff watch today's orders and advance their statuses - and it is the single source of truth for every decision we make about this tool, now and in the future. No decision is considered made until it is written here. Rules of use:

  • Every decision is logged here. Before or together with any change to this tool, the decision is added to section 11 with a date, and the affected section is updated in the same change.
  • The register is append-only. Decision rows are never deleted. A reversed decision is marked "Reversed (date)" with a reason - the original row stays for history.
  • This document wins ties. If this document or the code disagree, the discrepancy is resolved in this document first (with a dated decision), then applied to the code - never the other way around, and never silently left divergent.
  • Check before changing. Before changing any behavior covered here, read the relevant section and the register; after the change, update this document in the same change as the code.
  • Names must be self-explanatory. Every variable, function, and code snippet in any update uses understandable names. No cryptic abbreviations. Short names are allowed only for loop indexes and universally known abbreviations (id, url, api).
  • Acronyms are always expanded next to every use - in prose, tables, and headings. Literal identifiers stay as they are.

Core guarantee. An order that is still active can NEVER disappear from the board, and no order status change is ever written to the CMS without a clear, visible outcome for the user. Everything below serves this one sentence.

4.1 Applications and their object relationships

The restaurant tool set spans three CMS applications. They are related through the restaurant slug - never through position, name or the order of the records.

ApplicationWhat one record isObject type used by the toolsCardinality

How the board learns which restaurant it serves

The tool definition is tenant wide. On the multi-restaurant tenant (easyorder) one definition serves every restaurant, so a tool parameter cannot name the restaurant per restaurant, and no per-restaurant value is kept in the parameters at all - not the slug, not the timezone, not the currency (D-ROTA-46, D-ROTA-49). One value on the definition would silently apply to every restaurant's board. The board therefore resolves it at runtime, strongest signal first:

  1. the board record the tool runs in - one restaurant-order-taking-app-easyorder record per restaurant. Two page shapes are read (D-ROTA-52): the record page (/objects/restaurant-order-taking-app-easyorder/<id>), where the tool reads the record by id, and the APPLICATION page (/objects/restaurant-order-taking-app-easyorder, no id in the address), where the tenant's board records are listed - exactly one record is then used, several records make the board refuse to guess and name them. The tool takes the record's own slug (and restaurantSlug / restaurantId when present). Give that record the same slug as the restaurant object - that single equality is the whole link. Reading the record needs that type in settings.allowedObjectTypes.
  2. the CMS page address - /admin/objects/restaurants-easyorder/<id> is the restaurant itself; a per-restaurant page such as /admin/restaurants/downtown contributes its last path segment as a weak candidate. When the page IS the board record its id is a record id and is skipped here.
  3. the only restaurant of the tenant, when there is exactly one - never a guess among several.

When none of these resolves, the board shows a banner naming the cause and stays closed; it never falls back to "the first restaurant".

Reading the board record is a CMS permission. The tool being the application's own tool does not grant access to that application's objects: restaurant-order-taking-app-easyorder must be listed in settings.allowedObjectTypes (read) or the host refuses the request and shows its own "type is not in the allowed object types list" warning. The parser reads that list from the allowedObjectTypes setting when the host exposes it and then does NOT send the request, so no warning appears (D-ROTA-53). A system admin who does not want the board to read its own type at all sets readBoardRecords = no; the board then relies on the record page or the restaurant page.

Console diagnostics. Every time the restaurant cannot be resolved the console prints a [ROTA-DIAG] block: page + parsed route, the parameters, and the first records of the three types with their top-level keys, data categories, slug, restaurant references and the order fields actually seen. One block is enough to tell whether the tool can reach the ids, the slugs and the order payload.

The board record is the only place, because it is per restaurant while the tool definition is not. There is no tool parameter for it (D-ROTA-49). Either of these works, and both are read the same way:

The board detects which one an order uses and patches a status change back into that same place - writing a flat patch onto a category order would put status one level above the fields the order app reads.

The slug is the identifier a restaurant admin can choose and correct freely; the object id never changes. Every order therefore stores the slug in restaurantSlug. The tool compares case-insensitively and also accepts restaurantId, restaurantKey, restaurant, siteId and cmsRestaurantId, so an older writer keeps working - but restaurantSlug is the documented contract and the value every writer should store.

Only ONE stored field is required: the kitchen status. Everything else the board shows about the preparation is a DEFAULT, not a demand on the order writer (D-ROTA-51). The board works with the order exactly as the website creates it:

5. Verified problem and root cause

5.1 Verified evidence

  • 2026-10-25, user request: the restaurant order application had RestaurantOrderManager, which is "like a history item of an order with all details" - a detail view of ONE record, opened from the CMS object manager.
  • No surface existed where staff could see ALL of the day's orders at once and act on them. Watching orders meant opening each order record in the CMS object manager one by one.
  • User asked for a kitchen-style active orders manager with the same look and feel as the Foodsoft Restaurant app (orders list with tabs, accept with an estimated time, one-tap status advances), working on the same CMS order objects with live data.
  • Result: staff cannot tell at a glance which orders are waiting, and advancing an order takes a record-open round trip per order.

5.2 Current implementation at request time (verified in code)

// RestaurantOrderManager/app/RestaurantOrderManager.js - one record only
tool.onReady(function (value, fields) {
  boot(value, fields);  // reads THE opened record via tool.getFields()
});
// It has no list view at all - the CMS object manager lists records.

5.3 Structural flaws

  1. No application-level surface. The only tool for orders was placed at OBJECT level, so the application had no board to watch the collection.
  2. No live behavior. A single-record detail view has no refresh loop and no new-order awareness, so staff had no way to notice a fresh order arriving.
  3. No fast status workflow. Changing a status requires opening the record; there is no one-tap accept with an estimated time anywhere.

Root cause: the order application was missing the TYPE 3 (application-level listing) tool of its tool set. The existing object-level tool was doing its own job well, but nothing presented the collection - which is exactly the listing tool's job.

6. Requirements

  1. One board shows the day's orders: every active order (no matter how old) plus today's terminal orders; yesterday's terminal orders do not appear.
  2. The status workflow is new -> accepted -> in-preparation -> ready -> completed, with decline (from new) and cancel (from accepted, in-preparation or ready); all transitions write status + statusChangedAt through the CMS object relay.
  3. Accepting offers an optional estimated time with quick chips and a live computed "ACCEPT (h:mm)" button.
  4. The board stays live without manual reloads: polling refresh, refresh on tab visibility, and a 1-second clock.
  5. All data flows through the CMS tool SDK only - no direct database, REST or external network calls from the sandbox.
  6. Writes are gated to editor+ roles and the read-only mode; viewers can watch and search but not change anything.
  7. The tool's own saved value stays light: UI state only, never cached order lists (listing-tool rule).
  8. No confirm() dialogs (forbidden in the sandbox) - destructive statuses use an armed two-step button.
  9. Failures stay user-friendly: a retry state for load errors, toasts for write errors, a configuration banner with the required CMS settings when object access is not configured.
  10. Multi-tenant safe and generic: no tenant names, no hardcoded restaurant identity anywhere.
  11. Multi-restaurant safe: the board resolves its restaurant at runtime from the page context (the board record first, whose slug equals the restaurant slug, then the page address), falls back to the only restaurant when the tenant has exactly one, and shows only that restaurant's orders - never another restaurant's data (section 4.1, D-ROTA-46, D-ROTA-49). No tool parameter carries a restaurant slug, timezone or currency: the tool definition is tenant wide, so such a value would apply to every board.

8. Solution design

8.1 Core invariant

Invariant ROTA-INV-1. Every status change is written as one core update - status + statusChangedAt - through tool.requestObjects('update'), and nothing else may be required for the status change to stand. A second, optional update may carry acceptedAt + estimatedReadyAt; if that second update fails, the status change still stands and the failure is logged to the console, never surfaced as an error toast.

Invariant ROTA-INV-2. The board can never hide an active order: onBoard = isActive OR isToday, where isToday compares the order placed date with the viewer's local calendar day. A stuck order from yesterday stays visible.

8.2 Loading pipeline

// RestaurantOrderTakingApp.js - loadOrders (simplified)
function loadOrders(silent) {
  if (_loading) return;                  // never two queries in flight
  _loading = true;
  tool.requestObjects('query', { mainObjectType: _cfg.ordersType },
    function (err, result) {
      _loading = false;
      if (err) { setError(err); return; }
      applyOrders((result && result.objects) || []);
      _firstLoadDone = true;
      renderAll();
    });
}
  • One query loads every object of the type; all tab, search and sort logic is client-side over the loaded day list (the SDK query has no server-side filters, L-01).
  • normalizeOrder reads fields tolerantly from productData.data_categoriesBased (or the flat bag / objectData / data), the same bag-scoring reader the sibling tool uses.
  • New ids arriving with status new fire a host toast and a card flash (applyOrders vs _knownIds).

8.5 Live refresh

  • Polling: autoRefreshSeconds (default 20, 0 disables).
  • Refresh on visibilitychange when the tab becomes visible again.
  • A 1-second timer updates only the waiting-clock spans (.roa-elapsed[data-id][data-ts]), never the whole board.
  • A manual Refresh button always available.

8.6 Permissions and read-only

  • Write roles: admin, owner, developer, user-manager, editor (pre-merged roles array); effectiveAccess flags are the fallback when roles are missing.
  • No-identity mode: when the host has no user API, write gating falls back to the host read-only flag.
  • Read-only mode hides every write button and shows a banner; search, tabs, sort and the detail view stay available.
  • Busy guard: one write per order at a time; buttons show "Saving..." while in flight.

8.7 Own value contract

{ "version": "1", "ui": { "tab": "all", "sort": "waiting", "search": "" } }
  • Persisted with a 300 ms debounce; own-save echoes are ignored via a staged JSON comparison.
  • Order lists are never stored in the value - every load refetches.

8.8 Theme contract

  • All colors read CSS custom properties with fallbacks (--primary, --surface, --text, --border, --radius, --font), so a hosting application theme re-skins the board.
  • Status colors are tool-owned and fixed (new amber, accepted blue, preparation orange, ready green, declined red, cancelled gray).
  • Color system (D-ROTA-15): every status owns a SOFT pastel background and its normal color as the card border; tabs carry the same soft identity with a currentColor ring when active. Time remaining overrides the status colors: long-waiting new orders and late orders go red-tinted, orders inside the last 5 minutes go amber.

Recommendation: keep the order status as the single source of truth for now; if item tracking is needed, do it first as a display-only per-line checklist in the detail popup (no CMS field), and add a real per-item status only if a pilot restaurant with dine-in courses asks for it.
