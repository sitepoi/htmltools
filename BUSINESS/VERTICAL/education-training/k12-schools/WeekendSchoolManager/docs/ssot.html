1. Purpose and governance

This document defines one tool and one set of invariants around keeping every record of a weekend school - and it is the single source of truth for every decision we make about this tool, now and in the future. No decision is considered made until it is written here. Rules of use:

  • Every decision is logged here. Before or together with any change to this tool, the decision is added to section 11 with a date, and the affected section is updated in the same change.
  • The register is append-only. Decision rows are never deleted. A reversed decision is marked "Reversed (date)" with a reason - the original row stays for history.
  • This document wins ties. If this document or the code disagree, the discrepancy is resolved in this document first (with a dated decision), then applied to the code - never the other way around, and never silently left divergent.
  • Check before changing. Before changing any behavior covered here, read the relevant section and the register; after the change, update this document in the same change as the code.
  • Names must be self-explanatory. Every variable, function, and code snippet in any update uses understandable names. No cryptic abbreviations. Short names are allowed only for loop indexes and universally known abbreviations (id, url, api).
  • Acronyms are always expanded next to every use - in prose, tables, and headings. Literal identifiers stay as they are.

Core guarantee. Every student record of the weekend school - registration, attendance marks, payment entries, progress notes, Quran tracking and parent communication - lives in ONE structured document that autosaves after every change, so the school can run a whole week from one screen and never lose a record to paper or scattered chat messages. Everything below serves this one sentence.

4. Glossary

Terms used in this document, with the exact meaning used here. Add a row whenever a discussion introduces a term - one meaning per term, so every reader and every AI sees the same definition.

5. Verified problem and root cause

5.1 Verified evidence

  • Weekend schools keep each record in a different place: paper sign-in sheets, WhatsApp group messages, payment notebooks, and memory (observed during the 2026-09-30 design discussion).
  • Attendance marks are re-counted by hand for the monthly parent meeting, so reports are slow to assemble and easy to miscount.
  • Payment follow-ups are written per family from scratch every month; the school has no single list of who owes what.
  • There is no per-student file, so a parent asking "how is my child doing" gets an answer reconstructed from chat history.

5.2 Current implementation (verified in code)

There is no previous digital implementation - the school runs on paper and spreadsheets. This tool is the first implementation, built on the UniconHub html-tool SDK (one structured document per tool instance).

5.3 Structural flaws

  1. No single record. Because every domain lives in a different place, no one can see the whole picture of a student or a week.
  2. Reports are manual. Attendance rates and payment totals are recalculated by hand, which wastes time and risks errors.
  3. Follow-ups depend on memory. With no debt list and no absence-call log, late payments and absent students are forgotten.

Root cause: the school has no single structured record per student, so every workflow (attendance, payments, progress, communication, reporting) re-collects and re-enters the same data.

6. Requirements

  1. Every student record of the school lives in ONE structured document that fits the 1 megabyte Firestore limit and autosaves after every change.
  2. Attendance works per Sunday: marks per lesson per student, bulk buttons, and a week-completion action that flags entry made later than 24 hours after Sunday.
  3. Payments work per month per student with five statuses, a waiting (debt) list with due dates, and polite reminders in English and Turkish.
  4. Reports are generated as plain text (WhatsApp-ready) with copy, download and print / PDF export.
  5. Parent communication is archived: group messages, one-on-one feedback, same-day absence calls and suggestions, all searchable later.
  6. The tool runs inside the CMS html-tool SDK only - no server, no database calls, no polling loops; the only timer is the 300 millisecond save debounce.
  7. Roles and read-only mode are respected: viewers cannot edit, only administrators can delete students, group messages and suggestions.
  8. Failure paths degrade politely: missing upload, email or PDF support shows a clear message instead of failing silently.

7. Option evaluation and decision

OptionDescriptionFixes the problem?ChurnVerdict

B. One small tool per domain Separate tools for attendance, payments and progress. Partially - records stay split across tools and no combined report is possible. High - three tools to build, register and maintain. REJECTED (breaks the single-record guarantee)
C. Server-side database A backend with its own database and API. Yes, but outside the html-tool SDK contract. High - new infrastructure, security and cost. REJECTED (D-WSM-01 - the SDK single document is the constraint)

Decision: option A. One tool keeps every domain over one document, which makes the combined weekly and monthly reports possible. Option B is dropped; option C is out of scope for the SDK and the 1 megabyte budget stays managed inside the tool (see section 18).

8. Solution design

8.1 Core invariant

Invariant WSM-INV-1. Every mutation of a student record goes through persistSoon - the only path that marks the document dirty and schedules flushPendingSave - which calls tool.setValue with the WHOLE database object. No code path stores record data anywhere else, and the database object is the only place records live.

8.2 Data shape

// WeekendSchoolManager.js - defaultDatabase / normalizeDatabase, the stored document
{
  version: 1,
  school: { name, classGroups[], lessons[], paymentBrackets[{id,name,monthlyFee}],
            currency, paymentDueDay, requiredAttendanceChecksPerDay, seeded },
  students: [ { id, firstName, lastName, gender, dateOfBirth, classGroup,
                status, paymentBracketId, startDate, parent..., emergency...,
                health..., pickup..., photoConsent, paymentEntries[], documents[],
                progressNotes[], teacherContactLog[], quranReading,
                quranMemorization, parentCommunication, attendanceByDate } ],
  attendanceWeeks: { [sundayIso]: { completedAt, completedBy, completedByName } },
  schoolLogs: { groupMessages[], suggestionsComplaints[] },
  ui: { activePage }
}
  • Attendance marks live per student under attendanceByDate[sundayKey].lessons[lessonName]; week completion lives school-wide under attendanceWeeks.
  • Payment entries act as a debt list: an entry is created only when something changes, and the expected amount is the bracket fee when no explicit amount is stored.
  • Old shapes (for example paymentsByMonth) are migrated by normalizeStudent into paymentEntries so stored data stays readable.

8.3 Caller contract table

CallerRequired change
app/WeekendSchoolManager.js (persistence) Calls tool.setValue with the whole document, then tool.requestSave; on rejection warns once and retries after 10 seconds.
app/WeekendSchoolManager.js (documents) Calls tool.requestUpload for PDF, image and Word files; shows a warning when the CMS field setting allowUpload is not yes.
app/WeekendSchoolManager.js (messaging) Calls tool.requestSendEmail with to, subject and html body; shows a warning when the field setting allowSendEmail is not yes.
app/WeekendSchoolManager.js (reports) Calls tool.requestExportPdf; falls back to a message pointing to Download .txt when unavailable.
app/WeekendSchoolManager.js (boot) Declares the output schema and the parameters schoolName, currency, paymentDueDay, defaultLanguage, allowUpload, allowFileContent, allowSendEmail.

9. Failure matrix - deterministic outcomes

ScenarioOutcome
Saved document is missing or invalidnormalizeDatabase rebuilds a default database and the tool boots with the empty state.
Stored document uses the older paymentsByMonth shapenormalizeStudent migrates each month into a payment entry; no data is dropped.
Upload support is missing (allowUpload not yes)A warning notification explains the missing field setting; no file is lost.
Parent has no email on file and Send Email is clickedA warning notification says to add an email in Edit Info; the message text stays available to copy.
PDF export is not availableA warning notification points to Download .txt instead; the report text is not lost.
Automatic save is rejected by the CMSOne warning appears, then a retry after 10 seconds; the document stays dirty until a save succeeds.
Stored data approaches the 1 megabyte limitThe size meter turns amber above 800 kilobytes and red above 950; a warning notification appears on save; the data panel shows the remaining capacity.
User has no write role or the field is read-onlyThe app gets the read-only class: editing controls are hidden and changes are not saved.

12. Maintenance rules

  1. This document is the single source of truth for every decision about this tool. Every decision is recorded in section 11 with a date, and the affected section is updated in the same change as the code. A decision that is not in the register did not happen.
  2. Rollback of a decision = mark it "Reversed (date)" with reason; never delete rows.
  3. Review every new mutation path against WSM-INV-1: it must call persistSoon and never write records outside the document.
  4. Never introduce a path that bypasses normalizeDatabase on boot - stored data of any older shape must still load.
  5. Every new field on the student object goes through newStudent and normalizeStudent together, so the default and the migration always match.
  6. Global naming rule: any update - code or documentation - MUST use understandable, self-explanatory names. No cryptic abbreviations. Existing misleading names are renamed when their code is touched.

14. Open questions

Decision points we resolve together before or during implementation. Every answer becomes a dated row in section 11.

  1. Should the defaultLanguage parameter set the starting language of every message builder at boot? The parameter is declared for the CMS form but the builders always start in English. Answer: deferred - wire it when a school asks for a Turkish default (2026-09-30).

R-01 1 megabyte document limit reached by a large history

Applies to: the whole group

What can go wrong: a school with many students and long attendance histories could approach the Firestore limit and saves could fail.

Likelihood / impact: unlikely in the first year at average sizes; high impact if reached.

Mitigation: the size meter, the warning thresholds and the JSON export let the school trim or archive history before the limit.

Last re-evaluation: 2026-09-30 - open, watched by the meter; export path verified in the harness.

R-02 Automatic save depends on the CMS field setting allowRequestSave

Applies to: T-01 persistence

What can go wrong: if the CMS field setting is not yes, automatic saves are rejected until the form saves manually.

Likelihood / impact: possible at first deployment; low impact because the tool warns and retries.

Mitigation: one warning with the exact setting name, a 10 second retry, and manual form save as the fallback.

Last re-evaluation: 2026-09-30 - open; resolved when the CMS field settings are configured at installation.
