4. Glossary

TermMeaning
ProspectA family that may enroll; not yet a student.
ConvertThe one-click action that creates the student and all supporting objects.
StatusPipeline stage of a prospect: new, contacted, interested, enrolled, inactive.
Follow-up taskOne reach action for one prospect: channel (call / email / whatsapp), assignee, due date, status (open / done / skipped), outcome note.
Reach managementThe team queue: distributing follow-up tasks across principal, teachers and volunteers and tracking every contact.
Call roundOne iteration of the calling loop. A round assigns only the families without a decision; every new round gets smaller.
DecisionThe latest solid answer of a family: none (still undecided), positive (interested) or negative (not interested).

6. Requirements

  1. Conversion is atomic: all four objects are created in one batch call.
  2. Folder ids come from the school settings object; the tool never asks the user for folder ids beyond a fallback paste in the convert dialog.
  3. Every button carries data-act (D-PRB-01 - the New prospect button was dead until wired).
  4. Prospects live only in the prospect board value - no separate objects until conversion.
  5. Calls run in rounds: a round assigns only the families with no decision; logging a call records an outcome (none / positive / negative) that updates the family's decision and status.
  6. Every family's reach history stays visible: how many times it was assigned, how many calls were logged, and its latest decision (rounds report).

17. Test plan - step by step

All tests run in the local test harness (app/test-harness.html) served with python -m http.server 8765 and driven by headless Edge. The harness supports ?sample=1 (fresh sample data), ?tab=<pane> and ?actions=<list> (runs clicks after 500 ms; sub-actions set-input:<id>:<value>, clear-folder:<key>, check:<id>, set-select:<id>:<value>).

17.1 Scenarios

  1. H-01 - renders with sample data. Steps: open the harness with ?sample=1 and each ?tab=. PASS if: every pane renders data without console errors.
  2. H-02 - every button reacts. Steps: run the recorded ?actions= sequences for each button. PASS if: the expected dialog opens / row appears / cell toggles.
  3. H-03 - persistence. Steps: edit a field, wait 500 ms, press "Show log". PASS if: requestSave was accepted and the value survives a reload.
  4. H-04 - role cycle. Steps: switch role to editor / viewer / none. PASS if: write controls disable for read-only roles and nothing throws.
  5. H-05 - call rounds. Steps: open Distribution, press Start call round, then Log call with an outcome on a prospect. PASS if: the round number increases, only undecided prospects get tasks, leftover open tasks turn skipped, the outcome updates the decision + status, and the report rows show assignment counts and decisions.

18. Risk and side-effect register - push gate

Risks: 0 open - 0 solved - 0 accepted
R-01 Convert batch partially fails in the real CMS

Applies to: batch create of 4 objects

What can go wrong: Partial objects would look like a broken conversion

Likelihood / impact: Low / Medium - batch is atomic in the CMS contract

Mitigation: Rely on CMS batch atomicity; verify once in the real CMS

Last re-evaluation: ${DATE} - open; verify on first real CMS run

R-02 Round history grows the saved value over many rounds

Applies to: one task per prospect per round (tasks array in the prospectBoard value)

What can go wrong: Dozens of rounds × many prospects could approach the 1 MB Firestore limit

Likelihood / impact: Low / Medium - a school year rarely exceeds 4-6 rounds, tasks are tiny

Mitigation: Skipped tasks older than N rounds can be pruned later; watch the value size after a real year of use

Last re-evaluation: ${DATE} - open; re-check when a real school year of data exists

Overall verdict. The current build was verified in the harness (renders, buttons, persistence, call rounds). Before a real publish, resolve the open risks above and run the 17.1 scenarios once more.
