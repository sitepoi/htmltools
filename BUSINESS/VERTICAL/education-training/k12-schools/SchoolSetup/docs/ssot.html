School Setup - school year definition (weekend school application)

SINGLE SOURCE OF TRUTH for the school year definition of the weekend school application (mainObjectType weekendSchool). One School Setup object per school year holds the school profile, payment settings and brackets, lessons (subjects with levels), classes (student groups), teachers, the school calendar and the folder ids that connect every other school tool. Every decision made for this tool is logged in section 11 and this document is updated in the same change as the code. When this document and the code disagree, this document is the tiebreaker. Companion documents: WEEKEND-SCHOOL-APP-PLAN.md (architecture of the whole application) and WEEKEND-SCHOOL-BUILD-REPORT.md (build report) in the WeekendSchoolManager folder.

1. Purpose and governance

This document defines the school year setup tool and is the single source of truth for every decision about it. Rules of use:

  • Every decision is logged here in section 11 with a date; the affected section is updated in the same change as the code.
  • The register is append-only. Reversed decisions are marked "Reversed (date)", never deleted.
  • This document wins ties. Resolve discrepancies here first, then change the code.
  • Names must be self-explanatory. No cryptic abbreviations anywhere in code or documents.

Core guarantee. The school year definition (settings, classes, teachers, lessons, payments, calendar, folder ids) lives in exactly ONE settings object per school year, and every other school tool reads it from there - the definition is never duplicated anywhere else.

4. Glossary

TermMeaning
LessonA subject taught at the school (e.g. Quran), stored as one lesson object with levels, teacher, schedule, checklist, subfolders and attendance flag.
LevelA subdivision of a lesson (Level 1, Level 2). Students enroll in a lesson level.
ClassThe group a student belongs to (Grade 1-A, Grade 3-4). Separate from lessons; a student sits in one class and attends several lessons.
TeacherA real application user; stored here as name + email. The email is the CMS login identity.
Payment bracketA pricing plan for the school year: monthly fee + optional discounted monthly fee; assigned per student as the monthly installment.
Attendance ruleThe rule deciding which lessons need attendance checks: all, first lesson only, first + afternoon lessons, or custom per lesson.
School dayOne explicit date in the schoolDays[] list; attendance sheets use exactly this list.
Folder mapThe 9 folder ids of the application (settings, lessons, prospects, students, attendance, progress, payments, contacts, communication) stored in the settings object.
CASCompare-and-set update: a lesson object update carries the version it was read with; on conflict, reload and retry.

5. Verified problem and root cause

This tool replaces the settings page of the old all-in-one WeekendSchoolManager prototype. The prototype mixed settings, students, attendance and payments in one 2300-line tool with no per-year separation and no reusable structure for other school tools.

Root cause: no single, per-year settings object existed, so every feature stored its own configuration and nothing could be reused across school applications. The fix is this tool: one settings object per school year, readable by every other tool.

6. Requirements

  1. One settings object per school year; the object lives in the year's 0-Setup folder (folder permission: principal only).
  2. Everything is school-year scoped: payments, classes, teachers, lessons, calendar and folder ids belong to this object.
  3. Lessons are created as real objects in the Lessons folder with CAS updates - no lesson data duplicated in settings.
  4. The calendar is an explicit, visible list of dates; the user can build, inspect and correct it without guessing a formula.
  5. Folder id changes that would disconnect existing data require an explicit confirmation with the old and new values shown.
  6. All changes save automatically (allowRequestSave = yes); no manual Save button required for the settings itself.
  7. UI stays understandable without reading documentation - every tab starts with a short explainer.

8. Solution design

8.1 Core invariant

Invariant SSU-1. The schoolSetup field value of the settings object is the ONLY stored definition of the school year. Other tools query the settings object and read recordKind: "schoolSettings" - they never write it (except T1 itself).

8.4 Caller contract table (what other tools read from here)

CallerRequired change / what it reads
ProspectBoard (T2)folderMap (query settings by recordKind) for the convert batch
SchoolConsole (T3)folderMap + schoolName for its tabs and reports; schoolDays for attendance sheets (future)
StudentRecord (T4)class names and teacher names for display; communicationFolderId fallback
Attendance / Progress tools (T5, T6 - future)folderMap, schoolDays[], attendanceRule, lesson requiresAttendance

8.5 Attendance rule derivation

  • all - every lesson requires attendance.
  • first - only the lesson with the earliest startTime.
  • firstAndAfternoon - earliest startTime plus every lesson starting at 12:00 or later.
  • custom - each lesson's own requiresAttendance flag.

17. Test plan - step by step

All tests run in the local test harness (app/test-harness.html) served with python -m http.server 8765 and driven by headless Edge. The harness supports ?sample=1 (fresh sample data), ?tab=<pane> and ?actions=<list> (runs clicks after 500 ms; sub-actions set-input:<id>:<value>, clear-folder:<key>, check:<id>, set-select:<id>:<value>).

17.1 Scenarios

  1. H-01 - renders with sample data. Steps: open the harness with ?sample=1 and each ?tab=. PASS if: every pane renders data without console errors.
  2. H-02 - every button reacts. Steps: run the recorded ?actions= sequences for each button. PASS if: the expected dialog opens / row appears / cell toggles.
  3. H-03 - persistence. Steps: edit a field, wait 500 ms, press "Show log". PASS if: requestSave was accepted and the value survives a reload.
  4. H-04 - role cycle. Steps: switch role to editor / viewer / none. PASS if: write controls disable for read-only roles and nothing throws.
