1. Purpose and governance

Single source of truth for the student record tool. Same governance rules as the tool family.

Core guarantee. Cross-record reads (attendance, progress, communication, contact) are ACL-limited queries with no typeId - the CMS returns only what the acting user may read, so a teacher can never see another lesson's records through this tool.

4. Glossary

TermMeaning

Communication logAn object in the communication folder with recordKind communicationLog.

6. Requirements

  1. Cross reads are query-all + client filter - never a folder the user may not read.
  2. Communication and parent contact tabs are visible only to the principal.
  3. Documents accept a real file upload when requestUpload exists, otherwise a URL.
  4. Every button carries data-act.

17. Test plan - step by step

All tests run in the local test harness (app/test-harness.html) served with python -m http.server 8765 and driven by headless Edge. The harness supports ?sample=1 (fresh sample data), ?tab=<pane> and ?actions=<list> (runs clicks after 500 ms; sub-actions set-input:<id>:<value>, clear-folder:<key>, check:<id>, set-select:<id>:<value>).

17.1 Scenarios

  1. H-01 - renders with sample data. Steps: open the harness with ?sample=1 and each ?tab=. PASS if: every pane renders data without console errors.
  2. H-02 - every button reacts. Steps: run the recorded ?actions= sequences for each button. PASS if: the expected dialog opens / row appears / cell toggles.
  3. H-03 - persistence. Steps: edit a field, wait 500 ms, press "Show log". PASS if: requestSave was accepted and the value survives a reload.
  4. H-04 - role cycle. Steps: switch role to editor / viewer / none. PASS if: write controls disable for read-only roles and nothing throws.
