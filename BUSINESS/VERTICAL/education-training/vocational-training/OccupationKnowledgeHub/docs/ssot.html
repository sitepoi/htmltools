1. Purpose and governance

This document defines one tool and one set of invariants around a private, per-occupation knowledge base for students - and it is the single source of truth for every decision we make about this tool, now and in the future. No decision is considered made until it is written here. Rules of use:

  • Every decision is logged here. Before or together with any change to this tool, the decision is added to section 11 with a date, and the affected section is updated in the same change.
  • The register is append-only. Decision rows are never deleted. A reversed decision is marked "Reversed (date)" with a reason - the original row stays for history.
  • This document wins ties. If this document or the code disagree, the discrepancy is resolved in this document first (with a dated decision), then applied to the code - never the other way around, and never silently left divergent.
  • Check before changing. Before changing any behavior covered here, read the relevant section and the register; after the change, update this document in the same change as the code.
  • Names must be self-explanatory. Every variable, function, and code snippet in any update uses understandable names. No cryptic abbreviations. Short names are allowed only for loop indexes and universally known abbreviations (id, url, api).
  • Acronyms are always expanded next to every use - in prose, tables, and headings. Literal identifiers stay as they are.

Core guarantee. One tool instance answers for exactly one occupation: a student can read the whole dossier, follow the Canadian study path to a real institution, and ask questions without ever seeing another occupation's questions or an unpublished draft.

5. Verified problem and root cause

5.1 Verified evidence

  • 2026-11-14, requester: a student who wants to reach one occupation has to search many sites for what the work looks like, the benefits, the difficulties, which Canadian universities have a faculty or department for it, and how to reach them.
  • 2026-11-14, requester: the same information is written once by an editor and then has to answer the same student questions again and again.
  • 2026-11-14, requester: the content must stay private (visible only inside the CMS to the students who should see it), not published on the open web.
  • 2026-11-14, requester: editors want to add content by hand OR ask the AI to add and update it.

5.2 Current implementation (verified in code)

No tool existed for this need in this repository. The nearest alternatives were a shared document (one long file for every occupation) or a spreadsheet, both of which lose the structure, the per-occupation privacy and the question history.

5.3 Structural flaws

  1. One document for every occupation. Sections cannot be enforced, so editors skip fields and students cannot filter or search per occupation.
  2. No single source per occupation. The AI cannot be grounded on a reliable dossier, so answers drift and contradict the written content.
  3. No question history. Repeated student questions are answered again by a person, and nothing is reused.
  4. No publish gate. Half-written content is shown as if it were finished.

Root cause: the information had no structured, per-occupation home, so it could not be maintained, could not ground an AI answer, and could not collect questions in one place.

6. Requirements

  1. One tool instance answers for exactly one occupation; two instances never share dossier content.
  2. The dossier covers, at minimum: what the occupation is, what the work looks like, work environment, benefits, difficulties with preparation, skills, the education path in Canada, licences and exams, pay, job market, career progression, tools, related occupations, glossary, FAQ and further resources.
  3. The study register stores Canadian institutions with faculty or department, program, level, location, credential, duration, tuition, admission, language, delivery and a way to reach the institution (website, email, phone).
  4. An editor or admin can write every field by hand, and the value is saved into this CMS record without a separate Save button.
  5. An editor or admin can ask the AI to draft or update content; the AI result is shown as a preview and is only written after explicit confirmation.
  6. A student can ask the AI coach free-form questions; answers use the dossier first and clearly mark anything added from general knowledge.
  7. A student can ask a question on a board, any user can answer it, and the answers stay visible with author and time.
  8. A draft dossier is not readable by students; a published dossier is readable by students and visitors with view access.
  9. All external data goes through tool.requestAI and tool.requestObjects; the tool never fetches the network directly and never writes the database outside the SDK.
  10. The tool degrades with a clear message when AI or object access is not configured; the dossier itself still opens.
  11. The tool works on desktop and on a 390 px wide screen with no horizontal scrolling.
  12. Every tool build carries a visible build badge and a console boot line.

8. Solution design

8.1 Core invariant

Invariant OKH-SCOPE. A rendered dossier, a coach answer, a question and a question answer can only ever touch the data of the occupation key this instance resolves to. Content of another occupation is never rendered, and a draft dossier is never rendered to a non-editor.

8.2 Dossier model and write path

// app/OccupationKnowledgeHub.js - the saved value
{
  version: 1,
  occupation: { title, slug, category, oneLiner, summary, tags[], status, updatedAt, updatedBy },
  sections:   { whatItIs, dayInTheLife, workEnvironment, benefits, difficulties, skills,
                educationPath, certification, salary, jobMarket, careerLadder, tools,
                relatedOccupations, glossary, faq, resources },
  programs:   [ { id, institution, faculty, program, level, city, province, credential,
                  duration, tuition, admission, language, delivery, website, email, phone, notes } ],
  contacts:   [ { id, label, name, role, email, phone, website, note } ],
  sources:    [ { id, title, url, note } ],
  chatSessionId: ""
}
  • Text sections are plain text (paragraphs on blank lines). Line sections use Cell | Cell | Cell. The FAQ uses Q: / A: lines.
  • The editor writes directly into the in-memory model and the tool debounces tool.setValue() by 500 ms. There is no Save button - the CMS record is the save.
  • The AI builder asks for ONE JSON object with optional keys, validates every key against the section allowlist, and shows a change preview before applyAiPlan() writes anything.
  • The coach receives the dossier digest inside the prompt. The prompt forbids invented institutions, tuition, deadlines, emails and phone numbers, and requires the prefix "Beyond this dossier:" for anything not in the dossier.
  • Question objects store the whole answer array, so one update adds or removes an answer atomically. The board filters by occupationKey on read.

9. Failure matrix - deterministic outcomes

ScenarioOutcome
AI parameter is off or the AI call failsThe coach bubble shows the error, the typed question stays in the input, the Edit tab keeps the instruction text, and the dossier still reads and prints.
Object access is off or the question type is refusedThe Questions tab shows a setup card with the exact settings, the dossier is unaffected, and no host warning is triggered at boot because the tool never asks for a type it was not allowed to read.
The AI returns prose or broken JSONThe reply is rejected, the instruction text stays, and the user is told to try a more specific instruction. Nothing is written.

The AI returns a program that already existsThe duplicate is skipped by institution + program key and the count does not change.
An editor changes a fieldThe value is saved after 500 ms through tool.setValue(); the save chip shows the time.
A viewer opens a draft dossierThe dossier body is replaced by a "Not published yet" notice and printing is refused with a warning; the question board remains reachable.
The host is read-onlyA read-only banner is shown, the Edit tab is hidden, and every write action refuses with a message.
The occupation slug is emptyThe key falls back to the configured key, then the record id, so the board still groups correctly.
The chat session cannot be createdThe conversation continues in memory, and one console warning names the missing type. The dossier is unaffected.
The question object cannot be createdThe modal stays open with the typed question and an error toast names the reason.
A question belongs to another occupationIt is filtered out before rendering.
A question object has no occupation keyIt is hidden, unless this instance has no key at all (no slug, no configured key, no record id). Privacy wins over convenience.

14. Open questions

Decision points we resolve together before or during implementation. Every answer becomes a dated row in section 11.

  1. Should the question board be shared per occupation or per record? Today the key comes from the occupation slug, so two instances of the same occupation share one board. A per-record board would use the record id only.
  2. Should students answer, or only teachers and admins? Today any logged-in user can answer and a teacher answer is labelled. Teacher-only answering would need a stricter gate.
  3. Should a question wait for approval before it appears? Today it appears immediately. Approval would add a pending status and a moderator view.
  4. Which object type should the board use in production? The default is occupation-questions. The tenant can point the parameter at any type.
  5. Do we need images or diagrams in the dossier? Not in v1. Adding them means a URL field per section plus an upload parameter.
  6. Do we need a catalogue page across occupations? One instance holds one occupation, so a list of occupations needs a separate listing tool or a shared index record.
  7. Should answers notify the student? No notification exists today. The CMS has no notification channel in this tool's SDK surface.
  8. Should the AI be able to answer on the public board? Today the AI drafts an answer for a teacher to review, and the Ask AI tab answers the student directly. Posting AI answers automatically would mix AI content with teacher content.
  9. Should a published dossier be visible on the public website? Today it lives inside the CMS only.
  10. Do we need a second-language version of the interface? The interface is English; dossier content may be written in any language.

18. Risk and side-effect register - push gate

Every risk or side effect of a change that is NOT pushed yet lives here, linked to its release group (section 15). Before every push re-evaluate every OPEN risk of the groups being pushed: solve them one by one (tick the checkbox), or mark the risk Accepted (data-risk-status="accepted") with a reason and the date, and update the Last re-evaluation line inside the risk. A group is push-ready when its tasks are done AND it has no OPEN risks - the task panel shows a PUSH READY badge per group and the open-risk count.

Risks: 0 open - 0 solved - 0 accepted (0% solved)
R-01AI content can be wrong

Applies to: T-OKH-05

What can go wrong: the AI invents a program, a fee or a deadline and an editor applies it without checking.

Likelihood / impact: medium likelihood, high impact on student trust.

Mitigation: the prompt forbids invented facts and empty URLs; every change is previewed; the dossier stays a draft until an editor publishes it.

Last re-evaluation: 2026-11-14 - open; accepted only with an editorial review step before publishing.

R-02Question board reads another occupation's questions

Applies to: T-OKH-07

What can go wrong: a missing or misspelled occupation key mixes two occupations on one board.

Likelihood / impact: medium likelihood, medium impact (information disclosure between occupations).

Mitigation: the key is derived automatically from the slug, then the parameter, then the record id; objects without a key are legacy only; the board filters before rendering.

Last re-evaluation: 2026-11-14 - open; verify with two occupations in the same tenant.

R-03Question writes land in the wrong data category

Applies to: T-OKH-11, T-OKH-13

What can go wrong: the tenant stores question fields inside a category and a flat write is never read back.

Likelihood / impact: medium likelihood, medium impact (answers appear to vanish).

Mitigation: the tool writes into the category it read from, or into questionsDataCategory when the board is empty; the setting is documented in the Edit tab.

Last re-evaluation: 2026-11-14 - open until a real tenant board is verified.

R-04A very large dossier approaches the 1 MB record limit

Applies to: whole group

What can go wrong: hundreds of programs plus long sections make the record too large.

Likelihood / impact: low likelihood, medium impact (save fails).

Mitigation: every section is capped at 20,000 characters, programs at 200, contacts at 60 and sources at 120.

Last re-evaluation: 2026-11-14 - caps in place; a size warning is an idea for v2.

R-05Draft dossier leaking to students

Applies to: T-OKH-08

What can go wrong: a half-written dossier is readable, or an editor loses access to their own draft.

Likelihood / impact: low likelihood, high impact (privacy).

Mitigation: the block is decided in renderPane from the role and the status, and the smoke test covers both sides.

Last re-evaluation: 2026-11-14 - verified in the browser probe (viewer blocked, editor not blocked).

Overall verdict. Safe to demo locally in the harness and safe to publish to a tenant once the field settings in section 8.3 are in place. The only open editorial risk is R-01: an editor must read AI output before publishing it.
