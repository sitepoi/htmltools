PUBLICWEBSITE — MAKE PUBLISHED PAGES RENDER WEBSITE-HTML-TOOL
WIDGETS (WITH THEIR DATA). Pure-text explanation + contract to
hand to the PublicWebsite codebase that publishes the pages
generated by the WebpageBuilder tool.
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

0. CURRENT STATE (verified)

The WebpageBuilder tool now does its part completely:

   - A page may contain WIDGET ISLANDS chosen from the application
     store library, e.g.:

         <div data-gw-app="Food Ordering Cart"
              data-gw-config='{...}'></div>

   - The island markup is written INSIDE the published page content
     (data.htmlPage.code.html), at the exact section position the
     user chose.

   - The builder's own preview runs the widget's real code
     (code.html + code.css + code.js from the store record) and the
     widget renders its full UI. Its DATA does not load in the
     preview because the widget fetches its data over the network
     and the preview sandbox cannot serve it — that is expected.

The published website shows NOTHING for the widget. Reason: the
publishing app does not yet implement the widget island pipeline at
all — it renders the page's own HTML but ignores data-gw-app
islands. The widget code never runs, so there is nothing to show.

This document is the fix contract.

1. WHAT A WEBSITE-HTML-TOOL WIDGET IS

A library item (cmsObjectType
website-html-tool-library-applicationstore) is a self-contained html
tool with three blocks:

   code.html   widget markup (body fragment, NO document tags)
   code.css    widget stylesheet
   code.js     widget behavior

Its JS is written for the CMS tool runtime: it boots through
window.tool.onReady(cb) and/or registers via gw.apps.register(name,
factory). To get its data it performs network requests (fetch) to the
platform/store APIs, or uses window.gw (gw.db / gw.service) when
available. It renders its UI client-side and shows an empty/loading
state until the data arrives — exactly what the builder preview shows.

2. WHERE THE CODE AND DATA COME FROM

Store host (platform-owned): applicationstore.uniconhub.com, Public
API v2, authenticated server-side with x-api-key:

   Catalog list:
     GET {base}/api/v2/objects/website-html-tool-library-applicationstore
     -> array | { items: [...] } | { objects: [...] }

   Record detail (when the list omits code):
     GET {base}/api/v2/objects/website-html-tool-library-applicationstore/{objectId}
     -> { object: {...} }

   ObjectRecord field values live in productData.data_categoriesBased:
     gwAppName      string    island name (== data-gw-app value)
     title          string
     description    string
     category       string
     configSchema   object?   JSON schema
     ssrHtml        string?   pre-rendered markup (optional)
     code           object    { html, css, js } — REQUIRED

The publishing app must resolve island names to records from a
SERVER-SIDE cache of this catalog (refreshed on a schedule). Never
fetch from the browser.

3. WHY "NOTHING APPEARS" — FIX PIPELINE, IN ORDER

   STEP A — SSR (server render, before caching):
     1. Scan the composed page HTML for [data-gw-app] islands.
     2. Resolve each unique widget name to its catalog record.
     3. Fill the island, priority order:
          a. record.ssrHtml -> inject INSIDE the island, mark
             data-gw-ssr="1"
          b. else record.code.html -> inject INSIDE the island, mark
             data-gw-ssr="template"
          c. else leave empty, mark data-gw-ssr="none" (no crash)
     4. Append record.code.css to <head> ONCE per unique widget.
     5. Emit record.code.js ONCE per unique widget, AFTER the page's
        own JS, BEFORE the auto-mount script.
     6. Before any widget JS runs, provide the TOOL SHIM (widgets are
        html tools):

          window.tool = {
            onReady: cb => queue/fire cb({ fields: {...} }),
            onValueChange: fn => {},
            onReadonlyChange: fn => {},
            onUserChange: fn => {},
            getUser: () => ({ id, name, roles } | null),
            param: (name, def) => widget config value
                                  (from data-gw-config), else def,
            getFields: () => ({ ... }),
            notify: () => {},
            resize: () => {},
            isReadOnly: () => true,
            requestObjects: (action, params, cb) => read-only relay
                             (query/get only),
            requestAI: undefined   // must not exist on publish side
          };

   STEP B — HYDRATION (after page scripts):
     1. Widget code.js runs like page js (idempotent, no top-level
        await). It may call gw.apps.register(name, factory).
     2. Auto-mount every [data-gw-app] island (idempotent; mark
        data-gw-mounted="1", never double-mount):
          - config = JSON.parse(data-gw-config) with configSchema
            defaults for missing keys;
          - if a factory is registered, call it with
            { el, config, gw };
          - it hydrates/replaces the SSR markup inside el.
     3. A failing island is isolated (gw:app-error event + console
        warning) and never breaks the page shell.
     4. SPA navigation: unmount on page leave (call returned cleanup
        functions, remove data-gw-mounted), then repeat B1-B3 for the
        next page. Tool-style widgets boot again via onReady.

   STEP C — DATA ("processed properly"):
     The widget fetches its own data. The published page must let it
     succeed:
       1. CORS: every endpoint the widget fetches (store API v2 and/or
          the CMS data API) MUST answer with Access-Control-Allow-Origin
          for the published site origin (or be proxied server-side to
          the same origin — the recommended option).
       2. CSP: the published site's Content-Security-Policy must allow
          connect-src to those hosts (or the same-origin proxy).
       3. Prefer steering widgets to window.gw data APIs
          (gw.db.query / gw.service) so the platform can serve the
          data itself with no extra CORS surface. The real gw SDK is
          present on the published site, so widgets that detect gw and
          use it will just work.

   STEP D — VERIFYING WHAT WENT WRONG (debug order):
     1. Open the published page source: the island
        <div data-gw-app="..."> MUST be present inside the page HTML.
        Missing -> the page was saved from an old builder version;
        re-open and re-save the page in the new builder.
     2. Browser console: widget css/js must be emitted once and must
        run without errors; window.tool must exist BEFORE widget js.
     3. Network tab: the widget's data requests must resolve (not be
        blocked by CORS/CSP and not 401).
     4. If all three are fine, the widget renders and hydrates with
        data — the same UI the builder preview shows, plus live data.

4. SECURITY / CONSISTENCY

   - Island code is library code (trusted at build time); config
     values are DATA — widgets must render them with textContent or
     gw.sanitize, never innerHTML interpolation.
   - SSR output must be DETERMINISTIC (no Math.random/time) — pages
     are cached in Redis/CDN keyed by page version.
   - The tool shim must NOT expose requestAI or any write/upload API.
   - The builder preview is client-side only and does not serve data;
     that is by design.

5. ACCEPTANCE TESTS

   A. A published page with
      <div data-gw-app="Food Ordering Cart" data-gw-config='{}'></div>
      renders, in the SSR HTML, the widget's ssrHtml or code.html
      inside the island; after hydration the island shows the client
      render with data-gw-mounted="1".
   B. The widget's data fetch succeeds on the published site (CORS/CSP
      allow it or it is proxied same-origin) and the menu items load.
   C. Same page cached: SSR output identical across two renders.
   D. Two islands of the SAME widget: css/js emitted once, both
      islands mounted independently.
   E. Unknown island name: page still renders, warning logged, no
      runtime error.
   F. Invalid data-gw-config JSON: island mounts with {} and a
      warning (page unaffected).
   G. SPA navigation away and back: islands unmount cleanly and
      re-mount without duplicates or leaked listeners.
