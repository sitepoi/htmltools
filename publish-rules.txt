SHIP RULES - the end-to-end shipment protocol (GitHub Copilot)

TRIGGER COMMAND (ONE WORD - the user's word for the whole process)
The user says:   SHIP
Copilot then executes THE WHOLE procedure below - phases 0 through 8 - in
one go, with no further confirmation needed beyond this command:
  1. finds every changed tool,
  2. updates each changed tool's SSOT in the same change as the code,
  3. regenerates all 5 satellite documents per changed tool,
  4. captures the screenshots and refreshes the galleries/viewers,
  5. appends the release rows + a new social share set per ship,
  6. runs the verification gate,
  7. commits, bumps the version, and pushes,
  8. prepares the CMS handoff bundle (npm run ship:cms) and reports.
Any other wording (e.g. "prepare the docs", "update the ssot", the old
"PUBLISH AND PUSH" phrase) does NOT include the commit and push - only
"SHIP" does. "SHIP" is THE word; there is no other trigger.

WHEN THIS FILE APPLIES
"SHIP" always triggers the full procedure below.
This file is auto-attached to the chat context like the other *-rules.txt
files - the checklist is always visible.

GOLDEN RULE (never broken)
- "Prepare everything" is NOT a push order. Commit, version and push happen
  ONLY because the user said SHIP in the current conversation.
- If any phase fails, STOP, fix it, and report - never skip a phase to reach
  the push.

CODE PROTECTION RULES (public pages - never broken)
The tool's code is the store's product. Public pages must make it
IMPOSSIBLE - not just hard - for a visitor, scraper or AI to reach it:
- The public webpage (docs/webpage.html and its webpage-export.html) shows
  SCREENSHOTS ONLY. The gallery band IS the demo. Never embed the tool's
  HTML/CSS/JS, the test harness, iframes of the app, or code blocks there.
- Only the PUBLIC design system (webpage.css/js, ssot.css/js,
  presentation.css/js) may ship with public pages - they carry no tool
  logic and no secrets.
- docs/ is the INTERNAL documentation folder. Its index.html, code panes
  and the harness link are for the team - they are never pasted to the
  website, the CMS public web, or any customer-facing surface.
- Screenshots are flat PNGs - code cannot be extracted from them. Capture
  with sample/mock data only, never with real customer data.
- If a future live demo is ever desired, it must run behind the CMS's own
  sandbox (server-side or a hosted instance), NEVER by shipping the source
  to the page.

WHAT THE PUBLISH DOES (end to end)
1. Finds every tool changed since the last push.
2. Re-syncs the dynamic folder names when tools or idea counts changed.
3. Updates each changed tool's SSOT in the same change as the code.
4. Regenerates the 5 AI satellite documents per changed tool (Copilot writes
   them in chat - NO AI gateway is needed).
5. Appends release rows (updates.html + ssot.html) per changed tool.
6. Runs the verification gate - every check MUST pass.
7. Commits, bumps the version, and pushes.
8. Reports the result.

No AI gateway configuration is required in this mode. The scripts still
exist for automation (npm run rel) but the chat workflow does everything
without calling any AI backend.

TOOLS WITHOUT DOCUMENTS YET (first documentation)
When a changed tool has no docs/ folder yet (or its satellites are still
template placeholders), the publish CREATES the full set in the same run:
  - Phase 0.3 creates the 7 files from the templates,
  - Phase 2 fills the SSOT completely from the code,
  - Phase 3 generates all 5 satellites in full,
  - Phase 4 appends the first release row to updates.html + ssot.html.
Expected volume: N changed tools × 7 files (the docs index + SSOT + 5
satellites). Three new tools = 21 files, all completed in one publish run.

    Run and read BOTH:
      git status --short
      git rev-parse '@{push}'
    Purpose: know what changed, what is untracked, and the commit the last
    push ended at (the baseline for "changed since last push").
    Expected: branch main. If git reports an unfinished merge/rebase, STOP.

    Run:
      npm run tools:changed
    Purpose: the authoritative list of tools whose app / listing / reporting

    tool's own part folders (app, listing, reporting) do.

    Run:
      npm run docs:init
    Purpose: idempotent - creates any missing file of the 7 documents in
    every tool's docs/ folder (index.html + SSOT + 5 satellites). Never
    overwrites existing documents.

0.4 Plan with the user
    Show the changed tools and confirm the order of work. If the user only
    said "prepare", STOP after the phases they asked for - do not push.

PHASE 6 - COMMIT AND PUSH (only because the user asked to publish/push)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
6.1 Stage everything
      git add -A
6.2 Commit the changes (code + docs in one commit)
      git commit -m "<the agreed one-line message>"
6.3 Bump the version
      npm version patch
    This bumps package.json (0.1.0 → 0.1.1 → ...) and creates its own commit
    and tag.
6.4 Push with tags
      git push --follow-tags
6.5 Fill the commit hashes
    Run:
      git rev-parse --short HEAD
    If any Phase 4 release-log row still has a placeholder hash, write the
    real one now, commit it with:
      git commit -m "docs: fill release commit hashes" --no-verify
    then:
      git push
6.6 If the push fails
    STOP immediately and report the error. Never retry blindly, never change
    history, never force-push.

PHASE 7 - REPORT
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
After every publish, report:
- the new version number and the commit(s) pushed
- the changed tools and what shipped for each
- the document count: N changed tools × 7 files created/updated (the docs
  index + SSOT + 5 satellites; e.g. 3 first-time tools = 21 files), listed
  per tool
- which documents were created/updated (SSOT sections, satellites, release
  rows, control tower index)
- folder names re-synced (when Phase 1 ran) with the new counts
- anything left for the user (open risks accepted, deferred work, next steps)

PHASE 8 - CMS HANDOFF BUNDLE (prepare only - no CMS calls yet)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
After the push, build the payload bundle the application store CMS will
consume when its import API is ready:
      npm run ship:cms -- <ToolName>     (or --all)
The script writes ship-out/<ToolName>/ with:
  - webpage-export.html  → the website application's related object
  - help.html            → the app's help object
  - presentation.html    → the app's presentation object
  - updates.html         → the app's updates object
  - social.html          → the app's social object
  - code/                → the html tool library folder (html/css/js)
  - manifest.json        → the exact CMS targets per file (object type,
                           object id, field, create vs update)
The script NEVER talks to the CMS. The target mapping + the open questions
for the CMS team live in SHIP-CMS-PLAN.md - read it before asking for the
CMS import API. When the CMS is ready, this phase upgrades from bundle
building to the real upload (still only inside the SHIP run).

DESIGN DECISIONS LOG (agreed in the design discussions - keep them here)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
D-01 The SHIP word: "SHIP" is THE trigger for the full end-to-end
    shipment process (commit, version, push + all doc phases). The older
    "PUBLISH AND PUSH" wording is retired and no longer triggers anything.
D-02 Shared design system: webpage/ssot/presentation design lives ONCE in
    _docs/assets/; a tool differs only by its accent colors and content.
D-03 The public "demo" is a screenshot gallery (5-10 images) - never a
    working tool. Code protection beats interactivity (see the CODE
    PROTECTION RULES).
D-04 One capture, many documents: docs/screenshots/ + screenshots.json
    feed the webpage rows + gallery, the help figures, the social media
    strip, and the index viewer (with its info panel).
D-05 Social sharing is per SHIP: every update appends its own share set to
    docs/social.html (archive via SHARE-SETS markers); shares reference
    the real screenshots/diagrams of that ship.
D-06 CMS integration is planned but NOT active: SHIP Phase 8 prepares the
    bundle (npm run ship:cms) and SHIP-CMS-PLAN.md lists what we need from
    the CMS team (see Phase 8).
D-07 docs/ is internal documentation; public surfaces are only webpage-
    export.html (website) and the social texts + screenshots.

HARD RULES (apply to every phase, no exceptions)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
- Never commit or push without the user's explicit publish/push instruction.
- Never run npm run rel in chat mode - the chat workflow above replaces it
  and must be followed step by step instead. (npm run rel remains available
  for fully automated pushes when an AI gateway is configured.)
- Never pipe node output in this terminal (no | tail / | head / > file) -
  piped node scripts print "stdout is not a tty" and may not run. Run bare.
- Never delete decision-register rows; append-only, reversals are new rows.
- Never overwrite an SSOT with AI output; AI writes satellites only.
- Never invent facts, customer names, or metrics that are not in the sources.
- Names self-explanatory; no cryptic abbreviations; acronyms expanded.
- Hyphen "-", never em dash; no emoji icons in document headers/CSS.
- If a phase fails or a check does not pass, STOP and report - the push waits.
