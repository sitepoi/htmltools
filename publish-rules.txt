PUBLISH AND PUSH RULES - chat-driven publishing protocol (GitHub Copilot)

TRIGGER COMMAND (one stable phrase - use it every time)
The user says:   PUBLISH AND PUSH   (short alias: SHIP)
Copilot then executes THE WHOLE procedure below - phases 0 through 7 - in
one go, with no further confirmation needed beyond this command:
  1. finds every changed tool,
  2. updates each changed tool's SSOT in the same change as the code,
  3. regenerates all 5 satellite documents per changed tool,
  4. appends the release rows,
  5. runs the verification gate,
  6. commits, bumps the version, and pushes,
  7. reports the result.
Any other wording (e.g. "prepare the docs", "update the ssot") does NOT
include the commit and push - only the trigger command does.

WHEN THIS FILE APPLIES
"PUBLISH AND PUSH" (or "SHIP") always triggers the full procedure below.
This file is auto-attached to the chat context like the other *-rules.txt
files - the checklist is always visible.

GOLDEN RULE (never broken)
- "Prepare everything" is NOT a push order. Commit, version and push happen
  ONLY because the user asked to publish/push in the current conversation.
- If any phase fails, STOP, fix it, and report - never skip a phase to reach
  the push.

WHAT THE PUBLISH DOES (end to end)
1. Finds every tool changed since the last push.
2. Re-syncs the dynamic folder names when tools or idea counts changed.
3. Updates each changed tool's SSOT in the same change as the code.
4. Regenerates the 5 AI satellite documents per changed tool (Copilot writes
   them in chat - NO AI gateway is needed).
5. Appends release rows (updates.html + ssot.html) per changed tool.
6. Runs the verification gate - every check MUST pass.
7. Commits, bumps the version, and pushes.
8. Reports the result.

No AI gateway configuration is required in this mode. The scripts still
exist for automation (npm run rel) but the chat workflow does everything
without calling any AI backend.

TOOLS WITHOUT DOCUMENTS YET (first documentation)
When a changed tool has no docs/ folder yet (or its satellites are still
template placeholders), the publish CREATES the full set in the same run:
  - Phase 0.3 creates the 6 files from the templates,
  - Phase 2 fills the SSOT completely from the code,
  - Phase 3 generates all 5 satellites in full,
  - Phase 4 appends the first release row to updates.html + ssot.html.
Expected volume: N changed tools × 6 documents. Three new tools = 18
documents (3 SSOTs + 15 satellites), all completed in one publish run.

    Run and read BOTH:
      git status --short
      git rev-parse '@{push}'
    Purpose: know what changed, what is untracked, and the commit the last
    push ended at (the baseline for "changed since last push").
    Expected: branch main. If git reports an unfinished merge/rebase, STOP.

    Run:
      npm run tools:changed
    Purpose: the authoritative list of tools whose app / listing / reporting
    files changed since the last push (tracked diffs + untracked new files).
    NOTE: a docs-only change does NOT count as a changed tool - only the
    tool's own part folders (app, listing, reporting) do.

0.3 Docs folders complete
    Run:
      npm run docs:init
    Purpose: idempotent - creates any missing file of the 6 documents in
    every tool's docs/ folder. Never overwrites existing documents.

0.4 Plan with the user
    Show the changed tools and confirm the order of work. If the user only
    said "prepare", STOP after the phases they asked for - do not push.

    Add one row per decision made in this change: ID <prefix>-NN in order

2.3 Section 15 - Development task list
    Add/complete tasks in release groups. Group rules: a ONE PUSH group ships
    in a single push; a RELATED group must not be broken across releases.
    Tick checkboxes (data-task-status="done") for the tasks shipped by this

2.4 Section 18 - Risk register

    data-group matching its release group, a level (critical/high/medium/

    must be solved (checked) or accepted with a date + reason in

2.5 Sections 4-10, 12-14, 16-17
    Update the glossary, problem/requirements/options/design/failure matrix/

    plan ONLY where this change affects them. Keep them factual and dated.

2.6 Document version + status
    Bump "Document version" (0.1 → 0.2 → ...) and "Last updated" to today.
    Keep the status chip correct: status-active (work in progress),
    status-implemented (shipped), status-proposal (plan not approved).

2.7 Style rules for every SSOT edit
    - Names self-explanatory, no cryptic abbreviations; acronyms expanded.
    - Hyphen "-", never the em dash. No emoji icons in headers/CSS.
    - Keep the table structure of section 11 (ID, Date, Decision, Rationale,
      Status) - the automated scanners read these rows.
