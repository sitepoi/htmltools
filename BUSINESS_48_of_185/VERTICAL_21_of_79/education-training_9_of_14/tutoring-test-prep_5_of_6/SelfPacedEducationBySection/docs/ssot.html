1. Purpose and governance

This document defines the Self-Paced Education tool and its invariants. The tool is a TYPE 1 html-tool placed on a CMS object: the object's saved value holds the tool state ({config, progress}), the curriculum itself is authored in Curriculum Builder objects and is only READ here. Rules of use:

  • Every decision is logged here. Before or together with any change to this tool, the decision is added to section 11 with a date, and the affected section is updated in the same change.
  • The register is append-only. Decision rows are never deleted. A reversed decision is marked "Reversed (date)" with a reason - the original row stays for history.
  • This document wins ties. If this document or the code disagree, the discrepancy is resolved in this document first (with a dated decision), then applied to the code - never the other way around, and never silently left divergent.
  • Check before changing. Before changing any behavior covered here, read the relevant section and the register; after the change, update this document in the same change as the code.
  • Names must be self-explanatory. Every variable, function, and code snippet in any update uses understandable names. No cryptic abbreviations. Short names are allowed only for loop indexes and universally known abbreviations (id, url, api).
  • Acronyms are always expanded next to every use - in prose, tables, and headings. Literal identifiers stay as they are.

Core guarantee. Student progress, quiz answers and supervisor configuration always live in this CMS record's own saved value, and nothing the tool shares (WhatsApp, email, image) ever leaks query-string or hash tokens out of the CMS - shared links carry origin + pathname only.

5. Verified problem and root cause

5.1 Verified evidence

  • Shared WhatsApp/email status reports built by this tool need a link so the student can continue studying with one tap (round 4, 2026-09-25).
  • The sandboxed iframe cannot read the parent page path itself: document.referrer is empty, the iframe location is about:srcdoc, and window.location.ancestorOrigins gives the ORIGIN only - so the tool cannot know WHICH CMS page it is embedded on (verified 2026-09-25).
  • Without that knowledge, shared links could only point at a generic address, or the admin had to paste a course link per student record - a per-student workload the user explicitly rejected ("course link page will not work, because it is different for every student and it will be workload").

5.2 Current implementation (verified in code)

// SelfPacedEducationBySection.js - getStudyPageUrl(), before round 9
// Priority: CONFIG.coursePageUrl -> studyPageUrl param -> SDK probes
// (getRecordUrl/getParentUrl/...) -> ancestorOrigins[0] -> document.referrer

5.3 Structural flaws

  1. The iframe has no page context. Sandboxing strips the parent path, so any automatic link is a guess unless the host sends the URL.
  2. Manual per-record links do not scale. Setting a course page link per student record is repetitive admin work and drifts out of date.

Root cause: the tool lives in a sandboxed iframe with no visibility of the hosting page path. The correct fix is not guessing inside the iframe but having the CMS host send its own page URL (origin + pathname) through the existing postMessage SDK bridge - and having the tool sanitize it before it ever lands in a shared link.

6. Requirements

  1. Shared links must open the EXACT course page the supervisor was on, for every course, with zero per-record manual setup.
  2. The link value must be safe to embed in WhatsApp, email and images: origin + pathname only, no query string and no hash (they can carry auth tokens, magic links, session ids).
  3. The value is display/share DATA only - never an authorization signal, never a substitute for tool.getUser() role checks.
  4. When the host URL is unavailable, the tool must degrade gracefully through its fallback chain and never break sharing.
  5. The manual Course Page Link Setup field keeps working as the top-priority override (e.g. when the tool sits on a non-course page).
  6. Defense in depth: even if the host sends a full URL by mistake, the tool strips '?' and '#' before the value reaches any shared surface.

8. Solution design

8.1 Core invariant

Invariant INV-URL. Any URL that reaches a shared surface (WhatsApp invite, email call-to-action, report image, share data) is ALWAYS origin + pathname: no '?', no '#', trailing slashes trimmed. getStudyPageUrl is the single funnel - every share surface reads it, and the sanitizer runs on every probed URL.

8.2 Course link resolution (getStudyPageUrl)

// SelfPacedEducationBySection.js - getStudyPageUrl(), priority order
// 1) CONFIG.coursePageUrl (admin override - checked fresh, never memoized)
// 2) tool.getParentPageUrl()   <- CMS host sends origin + pathname
//    then other record-URL probes: getRecordUrl / getParentUrl /
//    getCurrentUrl / getObjectUrl / getRecordLink
//    every probed value is sanitized: trim, split('?')[0], split('#')[0],
//    trailing slashes removed - query AND hash can carry auth tokens
// 3) tool.param('studyPageUrl') (global fallback)
// 4) ancestorOrigins[0] origin, then document.referrer
  • The manual Setup link always wins, so an admin can force a specific course page (e.g. the tool embedded on a non-course page).
  • Probes only call SDK methods that exist and only accept values that look like http(s) URLs - junk values fall through.
  • Because the sandbox cannot read the parent path, the CMS host is the source of truth for the page URL; the tool only sanitizes and shares it.
