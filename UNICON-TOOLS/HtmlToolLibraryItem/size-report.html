Size Report - One Tool Package vs the 1 MB Object Limit

Reference tool: PersonalTaxPreparation - second data point: BrandSetGenerator - target: applicationstore.uniconhub.com - prepared for HtmlToolLibraryItem file-management design - date: 2026-09-25

Firestore allows 1,048,576 bytes (1 MB) per object document, including field names and a small per-field indexing overhead (roughly 32 bytes per field). This report measures real workspace files to answer one question: can one CMS object hold the code, the test harness, the 7 documents, and the screenshots of one tool - and where does the 1 MB run out?

5. Headroom analysis

  • With code + docs only, the larger measured tool leaves about 380 KB of headroom. Docs can roughly double in size before the limit is reached.
  • The JS file is the main growth driver on the code side (98 - 220 KB today). A very large tool (JS 400 KB + HTML 30 KB + CSS 40 KB + harness 50 KB) would still only be about 520 KB - over half the budget, but still fit with all docs.
  • Practical safety cap for the object: 900 KB, leaving room for field-name and indexing overhead plus future growth.
  • Screenshots in the object are impossible at the planned 9-shot gallery: even 3 shots (about 270 KB) would consume the remaining headroom of the bigger tool.

6. Recommendation for HtmlToolLibraryItem storage design

One CMS object per tool can hold: tool definition + code (html/css/js) + test harness + all 7 documents. Screenshots must stay OUT of the object.
  • In the object (text fields): tool details, html/css/js code, test-harness, and the 7 documents (index/help/presentation/social/ssot/updates/webpage). Expected total about 480 - 670 KB, always under 1 MB.
  • Out of the object (media): screenshots upload to the CMS media library / storage via requestUpload, and the documents reference them by URL. This matches the existing SHIP-CMS-PLAN section 2.7 convention.
  • Fallback if no media library yet: a separate screenshots object per tool - but one object per tool can only hold about 8 - 10 shots before it too reaches 1 MB, so the media-library route is the durable answer.
  • Compression options if shots must shrink: PNG to optimized PNG or WebP commonly cuts 40 - 70% of these sizes, and reducing 1440x900 to 1200x750 helps further.
  • Guard in the tool: HtmlToolLibraryItem should show a live size meter of the object payload and warn at 800 KB / block at 950 KB, like the existing translator tool's warning pattern.
