# Tool queue contract — ApplicationStoreItem → factory

The **Tools** tab (build `2026-11-17-2`) turns one application record into the
front door for its html tools: the full catalog is read **from source**, the
owner ticks the tools the application ships, and the selection is stored inside
the application record in queue order.

This file is the contract between that tab and the build/release engine. It
describes what is stored, what is derived, and what the automation phase will
consume. It does **not** claim that automation exists yet — see
[Not built yet](#not-built-yet).

---

## 1. Where the catalog comes from

Nothing from the catalog is embedded in the tool: the three files carry only the
licence **labels** and the status vocabulary. Everything else is loaded at
runtime, in this order, and the header badge names the route that won:

| Order | Route | When it is used |
| --- | --- | --- |
| 1 | `tool.requestObjects('query', { mainObjectType: catalogObjectType })` | only when **Tool Catalog Object Type** is set — an explicitly configured object beats a URL. The first record whose `slug`/`name` matches **Tool Catalog Slug** is read, and its `catalogJson` / `catalog` / `payload` / `json` field is parsed |
| 2 | `tool.requestFetch(catalogUrl)` | the parent CMS relay. Default URL: `../tools-catalog/tool-catalog-bundle.json`, overridable with the **Tool Catalog URL** parameter |
| 3 | `localStorage` cache of the last successful payload | short relay outages; the badge says *cached copy* |
| 4 | **Import JSON** button | fully offline / first install; the file is also cached |

Failures are never silent: the badge turns red and the panel prints the reason
in one sentence. Developer detail goes to the diagnostics log only.

### Bundle shape (`UNICON-TOOLS/tools-catalog/tool-catalog-bundle.json`)

Generated by `npm run catalog:build` from `catalog-data.js` (the SSOT). 97 KB
for 236 ideas, inside the 500 KB relay cap.

```json
{
  "schema": "uniconhub-tool-catalog-bundle",
  "catalogVersion": "1.0.0",
  "generatedAt": "…",
  "subjects": [{ "id": "code", "label": "Code" }, "… 8 total"],
  "groups": [{ "key": "B-bg", "label": "Business / General",
               "categories": [{ "key": "B-G-01", "label": "AI & Automation",
                                "ideas": [{ "id": "B-G-01-a", "code": "B-G-01-a",
                                            "name": "…", "purpose": "…",
                                            "licensing": "subscription-monthly",
                                            "sub": "AI Chat Assistants" }] }] }],
  "built": { "<idea id>": { "folder": "AIChatPresentationBuilder", "path": "…",
                            "docsCount": 7, "docsTotal": 7, "harness": true,
                            "screenshots": 0, "modifiedAt": "…" } },
  "publish": { "tools": { "<tool folder>": { "version": "", "publishedAt": "",
                                             "subjects": { "code": true } } } }
}
```

Two different keys, on purpose:

- `built` is keyed by **idea id** (`B-G-01-b-6`)
- `publish` is keyed by **tool folder** (`AIChatPresentationBuilder`)

The join is `built[ideaId].folder` → `publish.tools[folder]`. If the join is
wrong the publish columns stay empty, so the smoke test asserts every `built`
key exists in the idea list and every entry names a folder.

## 2. What the tab stores (the queue)

Stored in the application record, so it publishes with the application and any
consumer can read it. Only the selection — never the ideas themselves.

```json
"tools": [
  {
    "key": "B-G-01-a",
    "code": "B-G-01-a",
    "name": "Document Q&A Assistant",
    "purpose": "Question answering over company documents and policies",
    "licensing": "subscription-monthly",
    "group": "Business / General",
    "category": "AI & Automation",
    "folder": "",
    "status": "queued",
    "priority": "none",
    "notes": "",
    "addedAt": "2026-11-17T…",
    "updatedAt": "2026-11-17T…"
  }
],
"toolsMeta": { "catalogVersion": "1.0.0", "catalogCount": 236,
               "source": "cached copy", "loadedAt": "…", "updatedAt": "…" }
```

- `key` is the catalog **idea id** — stable across catalog rebuilds.
- `folder` is a remembered hint; the catalog is the truth (`built[key].folder`
  wins when the catalog knows it).
- Array order **is** the queue order. `↑ ↓` move one step, no drag and drop, so
  the order is unambiguous in a JSON diff.
- `notes` is free text for the build queue (scope, blocker, why the priority).
- Limit: 400 entries, deduplicated by `key`.

### Status vocabulary

| id | Meaning |
| --- | --- |
| `queued` | ticked, not triaged yet (default) |
| `planned` | accepted for a build batch |
| `developing` | the factory is writing code |
| `documenting` | code exists, the 7 documents are being written |
| `ready` | built and documented, waiting for the publish step |
| `published` | all 8 publish subjects are in the store |
| `skipped` | deliberately not doing it |

Status is owned by the human. **Sync status from catalog** derives it from
reality instead: `publish 8/8 → published`, `built but docs incomplete →
documenting`, `built and docs complete → ready`, `not built → keeps
queued/planned`. Sync refuses to guess when no catalog is loaded.

### Publish subjects (8)

`code`, `harness`, `screenshots`, `webpage`, `help`, `presentation`, `updates`,
`social`. Completeness = filled subjects / 8, read from
`UNICON-TOOLS/tools-catalog/tool-publish-state.json` through the bundle.

## 3. What the factory reads (automation phase)

**Copy queue JSON** produces exactly the payload a worker needs:

```json
{ "schema": "uniconhub-application-tool-queue",
  "application": "…", "applicationSlug": "…",
  "catalogVersion": "1.0.0", "catalogSource": "cached copy",
  "generatedAt": "…", "subjects": ["code", "…"],
  "tools": [{ "order": 1, "key": "…", "folder": "…", "status": "…",
              "priority": "…", "notes": "…",
              "built": true,
              "docs": { "done": 7, "total": 7 },
              "publish": { "version": "", "publishedAt": "",
                           "subjects": {}, "complete": 0, "total": 8 } }] }
```

Planned execution rules (to be implemented, not implemented today):

1. **One worker per tool**, concurrency capped by a setting, ordered by
   `order` and then `priority` (`high` first). A tool owns its folder; two
   workers never touch the same folder.
2. Each worker runs the existing pipeline in **no-chat mode**: intake →
   plan → build → validate → docs. The queue entry supplies the idea text
   (`name`, `purpose`); `notes` wins over the catalog text when present.
3. A tool is **done** when its 7 documents exist and validate; publishing is a
   separate, deliberate step (dry-run plan → confirm → write → read-back), never
   a side effect of a build.
4. After each subject is published, the worker updates
   `tool-publish-state.json` and the queue entry's `status`; the ledger stays
   the single record of what is in the store.
5. A failed worker stops **its own** tool only, writes the reason into the
   entry's `notes` (or a `lastError` field) and leaves the rest of the batch
   running.

## 4. Verification

| Gate | Command | What it proves |
| --- | --- | --- |
| Structure | `node UNICON-TOOLS/ApplicationStoreItem/_verify.cjs` | harness HTML mirrors the tool, every `$('id')` exists, no `</script`, no embedded catalog rows, the tools pane is wired |
| Runtime | `npm run catalog:check` | boots the real JS in a stub DOM, loads the bundle through the fallback chain, filters, selects, reorders, syncs, removes, clears; asserts the bundle ↔ idea join and the relay size cap |

Both run without dependencies and without a browser.

## Not built yet

  do not.
- Writing `status` back into the store record from a worker.
- Publishing anything from this tab: it **reads** publish completeness. Actual
  store writes stay in the factory release engine and the CMS tools
  (`HtmlToolLibraryItem`, this tool) until the write endpoints are confirmed in
  `DESKTOP-APPS/Html-Tool-Factory/html-tool-factory/docs/CMS-REQUEST--store-write-api.txt`.
