1. Purpose and governance

This document defines the factory: the loop, the contracts and the guards that turn an idea into a working html tool without a human in the loop. It is the single source of truth for every decision about the factory.

  • Every decision is logged here. A decision that is not in section 11 did not happen.
  • The register is append-only. Rows are never deleted; a reversed decision is marked "Reversed (date)" with a reason.
  • This document wins ties. When code and document disagree, the document is corrected first, then the code.
  • Names must be self-explanatory. No cryptic abbreviations outside loop indexes and known acronyms (id, url, api).

Core guarantee. A tool folder that the factory writes is always a valid three file html tool that opens and works, and a run never reports "finished" while work is still open.

Release guarantee (direction change 2026-11-17). A tool that the factory reports as published is readable in the application store with the same build and the same per file stamps that the repository holds at that moment. Publishing never reports success from the request result alone: it re-reads the record and compares stamps. A missing setting, id, type, folder or field stops the action with a named reason before anything is written, so there is no silent no-op anywhere in the release path. The same engine runs from the dashboard and from the repository command line, and the catalog only reads its results.

5. Verified problem and root cause

5.1 Verified evidence

  • Run 2026-10-28-202134-ai-proposal-builder-7730c6: 30 tasks planned, 7 done. Groups AF-2 (2/10), AF-3 (0/10), AF-4 (0/3), AF-5 (0/3) never executed.
  • The same run logged "Implementation pass: 1 done, 3 not done" three times, each failure reason "The answer contained no operations".
  • Tasks in those groups named src/lib/draftRequests.ts and src/components/QuoteTable.tsx, files that cannot exist in a three file html tool.
  • A 3 iteration run ended with status: done while 70 percent of the plan was unbuilt.
  • Only 2 checks per iteration verified the work; nothing measured how complete the tool was.

5.2 Structural flaws

  1. Illegal plan targets. Risk and usability stages wrote task files without the contract, so the tasks were dead on arrival.
  2. No second chance. A task that failed twice was parked as blocked and never retried, so one bad call removed work permanently.
  3. No measure of depth. "No tasks left" counted as finished even when core capabilities were missing.
  4. One tiny task per call. Each AI call carried a single small task, so the run spent calls on renames and ran out of budget before the real work.
  5. No repository context. The prompts contained the SSOT digest but not the repo rules, the publish checklist or past failures.

Root cause: the loop had no unit of work worth a prompt and no definition of done, so it could neither spend its budget efficiently nor tell whether the tool was complete.

6. Requirements

  1. Every generated file must satisfy html-tool-rules.txt: three files plus a harness, build stamps, no framework, no build step, no CDN.
  2. The tool is written into the taxonomy folder of its idea, never into the run folder.
  3. One AI call must carry about one prompt worth of work: the sum of the batch points is close to 100, never above 130.
  4. Every task shows its points in the dashboard and in the generated standard SSOT.
  5. A run may only report finished when every task and every depth item is closed.
  6. A failed task gets a fresh attempt in a later iteration before it is skipped, and its reason is stored as a lesson.
  7. The timeline shows which tasks are being coded while the apply stage runs.
  8. Continue keeps the tool folder; Restart deletes only that run's tool folder and needs a typed confirmation.
  9. No decision blocks the operator from raising the budget in config.local.json.

8. Solution design

8.1 Core invariant

Invariant POINTS. For every apply call, 5 <= sum(points of the tasks in the batch) <= 130, and the batch is applied and validated as one atomic patch. A task above 100 is impossible by construction because the score is clamped.

8.2 Task scoring and batching

estimatePoints(task):
  base = { code: 30, test: 20, doc: 15, chore: 10 }[kind]
  + min(20, files * 5) + min(20, acceptance * 4)
  + 25 if rewrite/refactor/from scratch, +12 if add/build/implement
  - 12 if rename/wording/label, +10 if checklist item
  clamp 5..100

buildBatches(tasks, { targetPoints: 100, maxBatchPoints: 130, maxTasksPerBatch: 6 })
  greedy packing; a trailing batch under 50 points is merged into the previous one
  • Scores are filled in normalizeIncomingTasks, so tasks from any stage are scored on the same scale, and again in applyPoints for old runs.
  • The batch patch is applied atomically; validation runs on every changed file; a failed batch is rolled back as a unit.
  • The model may answer with completed ids; when it omits a task the task is still closed by the batch and the note records what the model claimed.

8.3 Stage order and live step detail

select-idea -> research-ssot -> [ plan-tasks -> risk-review -> resolve-risks
  -> apply-tasks -> run-tests -> usability-review -> improve-product ] x N

context.setStep(patch) lets a stage annotate its own step entry while it runs, so the apply stage publishes its batches (id, points, task ids, status) and the timeline shows what is being coded right now.

8.5 Tool roots and the registry

The factory stops assuming one repository. A configuration array names every folder that may contain tools:

"toolRoots": [
  { "label": "repo", "root": "", "taxonomyFile": "UNICON-TOOLS/tools-catalog/folder-hierarchy-import.json", "writable": true },
  { "label": "external", "root": "D:/PROJECTS/EXTERNAL-TOOLS", "taxonomyFile": "", "writable": false }
]
  • A folder is a tool when it contains an app directory with a matching html, css and js file; listing and reporting parts are accepted like the repository already does.
  • A registry entry carries: slug (folder name, the stable store key), root, path, parts, code files, document files, harness, screenshot count, toolBuild, per file stamps, modifiedAt, optional ideaCode and the store object id from the ledger.
  • An external root is read only unless it is marked writable. Discovery never writes anything.
  • The registry is rebuilt on start and on demand; the dashboard shows every root and every tool with its build stamp.

8.6 Store map - ids are data, not code

Every id the engine needs lives in one versioned file, UNICON-TOOLS/tools-catalog/store-map.json, so the catalogs stay the source of truth for the folder tree and the factory never guesses.

{
  "meta": { "schema": "uniconhub-store-map", "version": "0.0.0" },
  "targets": [
    { "id": "tool", "kind": "tool",
      "cmsObjectType": "", "fieldPath": "productData.data_categoriesBased.html_tool_definition",
      "folderId": "", "slugRule": "repoToolSlug", "enabledField": "",
      "questionRef": "Q-07, Q-08, Q-09, Q-13" },
    { "id": "doc-webpage", "kind": "document",
      "cmsObjectType": "", "fieldPath": "", "folderId": "",

  • An entry is complete only when every field the plan uses is filled. An incomplete entry stops the publish before any write and names the entry id and the question id that answers it.
  • The folder may be given as folderId or as a taxonomy folderCode that the catalog resolves; a code that does not resolve is an error, never a default folder.
  • No cmsObjectType, field id, folder id or slug literal appears in src.

8.7 Publish pipeline - deterministic order

StepWhat happensWrites?
1. CollectRegistry entry, repository stamps, document files, store map rows, ledger rowNo
2. CompareRepository build and stamps against the ledger and, when available, the store recordNo
3. PlanOne row per target: action create, update, enable, disable or skip, with size and diffNo
4. ConfirmOperator confirms the plan in the dashboard, or passes --yes on the command lineNo
5. BumpOne TOOL_BUILD for the release; only the stamps of files whose content changed moveYes, tool files
6. Publish toolCreate when the ledger has no object id, update that id afterwards, then set the enabled switchYes, store
7. Read backRe-read the record by id and compare name, build, stamps and enabled stateNo
8. Publish documentsOnly the documents whose content signature changed, one object per document type, in the order webpage, help, presentation, updates, socialYes, store
9. VerifyRead back every written target; any mismatch marks the release failedNo
10. LedgerWrite the result of every target, including the skipped ones and their reasonYes, ledger
  • A publish is idempotent: the same tool published twice writes once and the second run reports skipped with the reason "no change".
  • The tool is published before its documents, so a document failure never leaves a document pointing at a build the store does not have.
  • The size guard refuses a payload above 900 KB before the request, and names the target and the measured size. Documents are never inlined into the tool record.

8.8 Store client and credentials

  • Node only, no new dependency. Two auth modes in one client: a credential header (preferred) and the legacy token in the URL, so the URL form can be retired without a second code path.
  • Resolution order: environment variable, then gitignored config.local.json, then blocked with MISSING_CREDENTIAL. The value is never written to a run folder, a log line or the dashboard.
  • Settings shows only a masked fingerprint (last four characters and length). The server never returns the value.
  • Retries are bounded and only for transport errors and 429; a 4xx body is surfaced verbatim because it usually names the wrong type or field.

8.9 Document publishing

  • One target per document, each with its own object type, field, folder and slug. A document is published only when the hash of its content differs from the ledger signature.
  • The slug rule is stable (<toolSlug>-webpage and so on) so a re-publish updates the same object instead of creating a second one.
  • A document is never embedded in the tool record; that is what keeps the tool object under the 1 MB limit.
  • Document content is generated by the existing repository generators on request. The publisher ships what exists; it never invents document content.

8.10 Verification and the release ledger

Success is not the HTTP status. A target is published only after a read-back matches the intended state. The ledger row per target:

"": {
  "store": { "objectId": "", "build": "", "stamps": { "html": "", "css": "", "js": "" },
             "enabled": null, "publishedAt": "", "verifiedAt": "", "lastWriter": "factory" },

  • A target that was blocked keeps its block reason, so a later run shows what is still unanswered.

8.11 No silent no-op policy

Every publish action ends in exactly one of three outcomes, and the dashboard shows which:

8.12 Studio - the local repository workspace

Goal: the web interface becomes the development and deployment surface for every tool in the repository, so VS Code is no longer required for routine work. The binding constraint comes first:

  • A page inside the CMS is a sandboxed iframe. It may use the object API and the fetch relay only; it can never read D:\.... The dashboard at 127.0.0.1 is a local process running as the user, so it can. Studio is therefore a local surface: same server, second page at /studio/.
  • One repository read module, src/workspace.js, and it is read only: every path resolves inside the repository root or is refused before any IO, listings stop at 500 entries, a read stops at 1 MB, a search stops at 200 hits over 3000 files. Writes never live here.
  • The tool registry is derived, never typed twice: toolRoots.listTools gives the folders and build stamps, the catalog bundle gives the publish ledger. One label per tool - draft, in-progress, documented (7 of 8 subjects), ready (8 of 8 local), published (the ledger says so).
  • Read routes: GET /api/workspace/tree, /file, /search, /tools, /tasks. They are the same data the future write routes will guard.
  • Preview first. /repo/<path> serves a repository file to the preview iframe with its real content type, so a document renders with its own CSS, JS and images. Every .html opens in the preview by default, including ssot.html and test-harness.html; code is one click away. The route is jailed like every other one and additionally refuses config.local.json, .env*, .git, node_modules, runs, selftest-output and .vscode; the text reader refuses the same names, so a script inside a preview cannot read them either.
  • Tasks means the tool SSOT. The backlog Studio shows is section 15 of the tool's own docs/ssot.html, parsed tolerantly (id, group, title, status, points, priority) and filtered by state. It is not a shell: Studio reads the list, the SSOT stays the place where it is edited.
  • Task drawer contract. There is no separate task store and no task editor in Studio, so a task exists exactly when its block is rendered in section 15. One <div class="task-item"> per task, inside a <section class="task-group">; data-task-id is the only required attribute, data-group files it under a release group, data-task-status takes done, not-started, in-progress or ignored, and .task-title, .task-priority, <strong>Points:</strong> n of m and a checked .task-done-checkbox are read when present. Only rendered markup counts: a block inside an HTML comment or inside <script> / <style> is a template sample and is ignored, because the page does not show it either. This rule was added after AssetDrive listed four template tasks (T-PU-01 to T-PU-03 and a placeholder T-01) that no browser ever displayed.
  • There is no code editor. The AI writes code; Studio shows it, previews it, tests it and approves the diffs. The write rule for later phases: every change is a proposal (path + diff + backup) confirmed in the UI and applied by the server, with a read-back.
  • Serial first. studio.workers defaults to 1, is clamped to 1..8 and can never be 0 (D-HTF-52). The queue executor in P4 starts one tool at a time; parallel work is a later, deliberate change made with the option table in docs/STUDIO-DESIGN.md section 6, not a default.
  • Three columns, one job each. Left: projects (the registry as cards) and the folder tree, switchable, so the VS Code habit and the tool overview sit together. Middle: chat for the selected project. Right: results - file with preview, tasks, search. Selecting a project in the list or any file inside a tool makes it the selected project everywhere.
  • Chat reads, never writes. POST /api/studio/chat builds the context server side (SSOT trimmed to keep its task list, the three code files, the open file, a focus task, attachments) inside studio.chatContextChars (120k default), sends it to the configured provider for studio.chatModel and returns the answer. Nothing in the tool is written; the only write Studio does is its own chat transcript, <tool>/Chats/<id>.json.
