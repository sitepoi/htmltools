1. Purpose and governance

This document defines the factory: the loop, the contracts and the guards that turn an idea into a working html tool without a human in the loop. It is the single source of truth for every decision about the factory.

  • Every decision is logged here. A decision that is not in section 11 did not happen.
  • The register is append-only. Rows are never deleted; a reversed decision is marked "Reversed (date)" with a reason.
  • This document wins ties. When code and document disagree, the document is corrected first, then the code.
  • Names must be self-explanatory. No cryptic abbreviations outside loop indexes and known acronyms (id, url, api).

Core guarantee. A tool folder that the factory writes is always a valid three file html tool that opens and works, and a run never reports "finished" while work is still open.

5. Verified problem and root cause

5.1 Verified evidence

  • Run 2026-10-28-202134-ai-proposal-builder-7730c6: 30 tasks planned, 7 done. Groups AF-2 (2/10), AF-3 (0/10), AF-4 (0/3), AF-5 (0/3) never executed.
  • The same run logged "Implementation pass: 1 done, 3 not done" three times, each failure reason "The answer contained no operations".
  • Tasks in those groups named src/lib/draftRequests.ts and src/components/QuoteTable.tsx, files that cannot exist in a three file html tool.
  • A 3 iteration run ended with status: done while 70 percent of the plan was unbuilt.
  • Only 2 checks per iteration verified the work; nothing measured how complete the tool was.

5.2 Structural flaws

  1. Illegal plan targets. Risk and usability stages wrote task files without the contract, so the tasks were dead on arrival.
  2. No second chance. A task that failed twice was parked as blocked and never retried, so one bad call removed work permanently.
  3. No measure of depth. "No tasks left" counted as finished even when core capabilities were missing.
  4. One tiny task per call. Each AI call carried a single small task, so the run spent calls on renames and ran out of budget before the real work.
  5. No repository context. The prompts contained the SSOT digest but not the repo rules, the publish checklist or past failures.

Root cause: the loop had no unit of work worth a prompt and no definition of done, so it could neither spend its budget efficiently nor tell whether the tool was complete.

6. Requirements

  1. Every generated file must satisfy html-tool-rules.txt: three files plus a harness, build stamps, no framework, no build step, no CDN.
  2. The tool is written into the taxonomy folder of its idea, never into the run folder.
  3. One AI call must carry about one prompt worth of work: the sum of the batch points is close to 100, never above 130.
  4. Every task shows its points in the dashboard and in the generated standard SSOT.
  5. A run may only report finished when every task and every depth item is closed.
  6. A failed task gets a fresh attempt in a later iteration before it is skipped, and its reason is stored as a lesson.
  7. The timeline shows which tasks are being coded while the apply stage runs.
  8. Continue keeps the tool folder; Restart deletes only that run's tool folder and needs a typed confirmation.
  9. No decision blocks the operator from raising the budget in config.local.json.

8. Solution design

8.1 Core invariant

Invariant POINTS. For every apply call, 5 <= sum(points of the tasks in the batch) <= 130, and the batch is applied and validated as one atomic patch. A task above 100 is impossible by construction because the score is clamped.

8.2 Task scoring and batching

estimatePoints(task):
  base = { code: 30, test: 20, doc: 15, chore: 10 }[kind]
  + min(20, files * 5) + min(20, acceptance * 4)
  + 25 if rewrite/refactor/from scratch, +12 if add/build/implement
  - 12 if rename/wording/label, +10 if checklist item
  clamp 5..100

buildBatches(tasks, { targetPoints: 100, maxBatchPoints: 130, maxTasksPerBatch: 6 })
  greedy packing; a trailing batch under 50 points is merged into the previous one
  • Scores are filled in normalizeIncomingTasks, so tasks from any stage are scored on the same scale, and again in applyPoints for old runs.
  • The batch patch is applied atomically; validation runs on every changed file; a failed batch is rolled back as a unit.
  • The model may answer with completed ids; when it omits a task the task is still closed by the batch and the note records what the model claimed.

8.3 Stage order and live step detail

select-idea -> research-ssot -> [ plan-tasks -> risk-review -> resolve-risks
  -> apply-tasks -> run-tests -> usability-review -> improve-product ] x N

context.setStep(patch) lets a stage annotate its own step entry while it runs, so the apply stage publishes its batches (id, points, task ids, status) and the timeline shows what is being coded right now.

14. Open questions

  1. Should a batch ever be split when the model fails twice? Today the whole batch fails and its tasks return to the queue. Splitting it into single tasks on the second attempt could rescue one task while losing the atomicity guarantee.
  2. Should points be measured instead of estimated? After a batch we know the real token cost; feeding that back would calibrate the estimator.

  1. TP-01 - self test. Run npm run selftest. PASS if every check passes and the sample run reaches a terminal state.
  2. TP-02 - source checks. Run npm run check. PASS if every module parses, the dashboard ids match, and the renderers evaluate.
  3. TP-03 - batching. Open a run, look at the Tasks tab. PASS if every task shows points and the Timeline shows each batch with the tasks it coded.
  4. TP-04 - contract. Ask for a change that names app/index.html. PASS if the batch is rejected with the contract reason and the tool folder is unchanged.
  5. TP-05 - continue. Finish a run with open work, press Continue. PASS if tasks reopen, the budget rises, and the run starts again without deleting the folder.
  6. TP-06 - restart. Press Restart, type a wrong id. PASS if nothing is deleted; type the right id and PASS if only the tool folder is gone and the run is back at stage 1.

18. Risk and side-effect register - push gate

Risks: 0 open - 0 solved - 0 accepted (0% solved)
R-01 A DOM shim can pass a tool that a real browser breaks

Applies to: T-01

What can go wrong: the shim is more forgiving than a browser, so a false PASS ships.

Mitigation: the shim only reports what the harness itself claims; visual problems stay out of scope and are covered by the screenshot idea.

Last re-evaluation: 2026-10-28 open

R-02 A whole file rewrite can delete working code

Applies to: T-03

What can go wrong: a rewrite drops an id that the harness or an earlier task depends on.

Mitigation: only above 80 points, contract validation still runs, and the previous version stays in .backup for one click restore.

Last re-evaluation: 2026-10-28 open

R-03 Points are an estimate and can overload one call

Applies to: whole factory

What can go wrong: a 100 point batch of three small tasks can still be heavier than expected.

Mitigation: hard cap of 130 points and 6 tasks, per batch token measurement (T-05) to calibrate.

Last re-evaluation: 2026-10-28 open

R-04 A model that ignores the contract stalls the loop

Applies to: apply-tasks

What can go wrong: every batch fails and the run burns its budget with nothing written.

Mitigation: attempts and retries are bounded, the failure becomes a lesson, and the run ends paused with the reason.

Last re-evaluation: 2026-10-28 open

R-05 Restart deletes the wrong folder

Applies to: restart action

What can go wrong: a bad path removes a neighbouring tool or a parent folder.

Mitigation: deletion is allowed only for the exact recorded tool folder with at least three taxonomy segments, the run id must be typed, and the self test covers the three refusal cases.

Last re-evaluation: 2026-10-28 solved by the guard, kept open until a manual test on a real tool folder.

R-06 The reviewer rejects good work and the loop spins

Applies to: T-09

What can go wrong: a reject rolls the batch back, the same task is planned again, and the batch is rejected for the same reason forever.

Mitigation: max two rejects per batch, then the task is parked for the operator with the reason, and every reject becomes a task with a concrete acceptance line.

Last re-evaluation: 2026-10-29 open

R-07 A checkpoint restore drifts from the SSOT

Applies to: T-08

What can go wrong: the operator edited a file by hand, a restore puts the old file back and the SSOT no longer matches the code.

Mitigation: the restore compares the file on disk with the checkpoint and asks before overwriting a file that changed outside the factory.

Last re-evaluation: 2026-10-29 open

R-08 Best of three plans multiplies planning cost

Applies to: T-14

What can go wrong: three plans per iteration make the cheapest stage the most expensive one.

Mitigation: one call returns all three plans, the option is off when the remaining budget is under 40 percent, and the planner is skipped in the last iteration.

Last re-evaluation: 2026-10-29 open
