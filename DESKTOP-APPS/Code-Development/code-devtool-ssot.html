1. Purpose and governance

This document defines one feature and one set of invariants around Unicon Studio - a single-purpose, VISUAL-FIRST Electron application for web development (static HTML/CSS/JS sites and Next.js projects). The AI chat and the live preview lead the experience; the file explorer, code editor, and terminal are secondary tools that appear only when needed (decision CODE-10). This document is the single source of truth for every decision we make about this feature, now and in the future. No decision is considered made until it is written here. Rules of use:

  • Every decision is logged here. Before or together with any change to this feature, the decision is added to section 10 with a date, and the affected section is updated in the same change.
  • The register is append-only. Decision rows are never deleted. A reversed decision is marked "Reversed (date)" with a reason - the original row stays for history.
  • This document wins ties. If this document or the code disagree, the discrepancy is resolved in this document first (with a dated decision), then applied to the code - never the other way around, and never silently left divergent.
  • Check before changing. Before changing any behavior covered here, read the relevant section and the register; after the change, update this document in the same change as the code.
  • Names must be self-explanatory. Every variable, function, and code snippet in any update uses understandable names. No cryptic abbreviations. Short names are allowed only for loop indexes and universally known abbreviations (id, url, api).
  • Acronyms are always expanded next to every use - in prose, tables, and headings. Literal identifiers stay as they are.

Core guarantee. No file outside the one project folder the user opened can EVER be read or written by the tool, by the AI agent, or by a command the agent runs. Everything below serves this one sentence.

4.3 Structural flaws of the alternatives

  1. VS Code cannot be our product. It is not realistic to rebrand or embed VS Code; its extension surface and its Copilot integration are tied to Microsoft's product decisions.
  2. Browser-only tools cannot touch the disk. A web page cannot read an arbitrary local folder, watch files, or spawn a terminal without a companion local server - which is half of an Electron app anyway.
  3. Tauri breaks the language constraint. Tauri would be lighter, but its backend is Rust - the user asked for JavaScript only.

Root cause: the tool must own a desktop runtime with real file-system and process access, while remaining plain JavaScript end to end - and that is exactly what Electron provides.

5. Requirements

  1. Electron desktop application for Windows, built in plain JavaScript only: no TypeScript build step, no UI framework, no native modules in version 1. Every feature traces to a .js, .html, or .css file.
  2. The user can open any local folder; that folder becomes the project root for the session.
  3. File explorer shows the project tree, tracks external changes, and ignores node_modules, .git, and .next by default (toggleable).
  4. Code editor opens and saves files with tabs, unsaved-change markers, and a conflict guard when the same file is edited from two places.
  5. AI chat with streaming responses; chat history is saved per project and restored on reopen. The chat is one of the two primary surfaces of the app (CODE-10).
  6. Agent mode plans and executes multi-file edits through approved tools; every terminal command the agent wants to run is shown to the user and runs only after approval, with an "Approve all in session" shortcut (CODE-31). The plan, thinking progress, and tool steps show live status symbols - spinner while working, check when done, cross when failed (CODE-32).
  7. Preview pane supports exactly two project kinds: static (HTML/CSS/JS) and Next.js. Saved files trigger a reload. Preview errors are visible, not silent. The preview is the primary center surface of the app (CODE-10).
  8. Terminal view runs multiple instances per folder - VS Code-style instance tabs one level below the folder tabs (CODE-34); each instance has its own session, output, scroll, and command history.
  9. GitHub Copilot-like capabilities: chat, agentic multi-file edits, #file context attachments, workspace search, inline completion (subject to API verification, T-18), slash commands.
  10. Secrets are stored with safeStorage only; nothing leaves the machine except AI API calls, and the UI states the active provider.
  11. No native module builds (no node-pty) in version 1; the dependency list stays short.
  12. Every feature and decision is tracked in this document in the same change as the code.

7. Solution design

7.1 Core invariant

Invariant ROOT-ONLY. Every file path used by the app - from the explorer, the editor, the AI tools, and the terminal - is resolved by project-file-service.js, which rejects absolute paths, .. escapes, and symlink escapes before the disk is touched. There is no other call site that touches fs for project files. The terminal service pins its working directory to the project root and refuses cd outside it when driven by the agent. A code reviewer must be able to check any call site against this invariant in one look.

7.3 AI and agent design

// main/ai/agent-runtime.js - agent loop, authoritative shape
async function runAgentLoop(userRequest) {
  const plan = await provider.plan(userRequest)          // structured steps
  for (const step of plan.steps) {
    emitAgentEvent('step', step)
    let response = await provider.callWithTools(step)    // may emit tool_calls
    while (response.toolCalls.length > 0) {
      for (const call of response.toolCalls) {
        if (call.name === 'run_command') {
          await waitForUserApproval(call)                // never auto-run
        }
        const result = await executeToolCall(call)       // fs + terminal only
        emitAgentEvent('tool', call, result)
      }
      response = await provider.callWithTools(step, response.messages)
    }
  }
  emitAgentEvent('done', collectedFileChanges)           // diff list for review
}
// main/ai/tools.js - every path goes through project-file-service
const toolRegistry = {
  read_file:     (args) => projectFileService.read(args.path),
  write_file:    (args) => projectFileService.write(args.path, args.content),
  edit_file:     (args) => projectFileService.applyStringReplace(args.path, args.find, args.replace),
  list_dir:      (args) => projectFileService.list(args.path),
  search_files:  (args) => projectFileService.search(args.query),
  run_command:   (args) => terminalService.runApproved(args.command) // approval gate
}
  • Every agent write records the before-content and is shown as a per-file diff; the user can accept all or undo all (T-13).
  • The agent writes are refused when the editor holds unsaved changes for that file - the user resolves the conflict first.
  • Streaming uses the provider's stream endpoint; the watchdog cancels stalled calls and the UI always shows a Stop button.

7.5 Preview design

  • Static project: preview-server.js serves the project root on 127.0.0.1 with a random free port; the renderer loads that URL in an iframe; fs:changed reloads it (debounced).
  • Entry pages: a static project may have several root .html files. The toolbar selector picks the entry; full documents are served directly and body-only html-tool files run through the generated wrapper with the mock SDK (CODE-16).
  • Opening a different folder stops the running preview (Stopped state); the preview never serves a stale root.
  • Next.js project: nextjs-runner.js spawns npm.cmd run dev, captures the port from the child output, and streams the dev server log into the preview pane until ready; stop kills the process tree, never leaves orphans.
  • Next.js projects use the dev server's own hot module replacement; the tool's iframe reload on fs:changed applies to static projects only.
  • Console relay: static HTML pages get an injected relay script that forwards console output to the preview console panel; Next.js projects rely on the dev server's built-in error overlay plus the streamed dev server log (T-16).
  • Project kind is auto-detected from package.json and the presence of an entry HTML file, with a manual override. Anything that is neither static nor Next.js gets a clear "project kind not supported" message - it is never attempted (CODE-05).

8. Failure matrix - deterministic outcomes

ScenarioOutcome
The AI requests a path outside the project rootThe path is refused by project-file-service, the refusal is logged, and the agent receives the refusal as the tool result - the run continues.
The agent wants to run a terminal commandThe activity panel shows the exact command with Approve / Approve all in session / Deny buttons. Approve = it runs with the project-root working directory and the row switches to a green "Approved" state; Approve all = this command and every further command in the same run are approved and each appears as approved; Deny = the command does not run and the agent is told.

A terminal instance dies or is killedThat instance shows [ session ended ] and its tab dims; the next command in it starts a fresh session in the project root. Other instances are unaffected.
The user opens a new terminal instanceA new instance tab starts in the same folder (the + button); each instance has its own output, scroll, and command history. Instances keep running while their folder tab is in the background; closing a folder stops all of its instances.
The agent edits a file the editor has unsaved changes forThe dirty tab keeps the user's content and never reloads; the agent's write lands on disk. The user resolves by saving the tab (overwrites) or re-editing (L-11).

The Next.js dev server fails to startThe dev server log is surfaced in the preview pane; the preview shows the error and the Start preview button re-appears as Restart; the app remains usable.
The project folder is deleted while it is openThe explorer shows a missing-folder state; every file operation refuses with a clear message.
A saved file changes outside the toolThe watcher event reloads the editor content (if clean) and refreshes the preview; a dirty editor keeps its unsaved content and warns instead.

The Copilot API cannot authenticateThe exact provider error appears in the chat bubble and in the Settings test result; nothing is sent twice and nothing partial is stored.
Monaco or its workers fail to loadThe editor status line shows the failure; chat and preview keep working; the app server log shows the failing path.
The SSOT document fails to load in the appThe overlay iframe shows the server error; the app keeps working and the document remains available next to the app folder.
An MCP server is unreachable or times outThe agent reports the server failure in the tool activity and continues with the built-in tools; the settings screen shows the configured server list for correction.
The build cannot download the rcedit tool (GitHub unreachable)The build fails with a clear download error; after one successful build the tool is cached in build/rcedit and later builds work offline.
A folder tab is closed while its preview or terminal runsThe tab closes; that folder's preview and terminal session stop; every other tab keeps its own session untouched.
Switching folders with unsaved editor tabsThe shell confirms first; after approval the editor tabs close because they belong to the previous folder.
A broadcast listener throws (shared emit loop)The preload wrapper isolates each listener with try/catch (CODE-27); the failing listener logs an error and every other listener still runs.
