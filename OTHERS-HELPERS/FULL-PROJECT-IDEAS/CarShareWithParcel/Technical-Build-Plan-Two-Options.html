Technical Build Plan and Architecture Decision

Separate Next.js Marketplace App
Two build options, detailed task list, comparison and decision

The marketplace is a completely separate Next.js application - not part of the HTML tool framework. Two architecture options are compared on MVP speed, cost, maintenance and scale, with a clear decision for short-term and long-term maintainability.

1What We Are Building

  • Separate app, separate repo folder: a standalone Next.js 15 project marketplace-next/ with its own package.json, deploy pipeline and database. It never imports or depends on the UniconHub HTML tool framework.
  • Scope for the pilot: three BC corridors, one role per user (sender or carrier), cost-sharing quotes, trip listings, parcel listings, matching, escrow payment, QR handover, delivery proof, ratings, dispute cases, admin console, insurance add-on.
  • Out of scope at launch: passenger seats, multi-currency, interprovincial lanes, native mobile apps (responsive web first), public API for e-commerce (phase 2).
  • Regional constraint baked in: corridor allow-list enforced in code - Victoria requires ferry-terminal handover; everything stays inside BC.

2Option A - Next.js Full-Stack Monolith

OPTION A One Next.js app + managed services RECOMMENDED

Stack: Next.js 15 App Router (React 19, TypeScript) on Vercel; Supabase for Postgres, Auth, Storage and row-level security; Stripe Connect for escrow-style destination charges; Resend for email; Vercel Cron for scheduled jobs; Sentry + PostHog for errors and analytics; Tailwind for UI.

Shape: one deployable. UI, server actions and route handlers live side by side. Code is organised as internal domain modules (identity, corridors, parcels, trips, matching, payments, evidence, insurance, disputes, admin) with repository interfaces between them and the database.

WorkloadHow it runs
Public pages (corridors, pricing, legal)Server components, ISR/static
Authenticated flows (post parcel, accept trip)Server actions + route handlers
MatchingPostgres query + scheduled cron sweep (every 5 min)
Payments and payoutsStripe Connect webhooks handled in one route
NotificationsResend + in-app table, cron digest
Admin consoleRoute group /admin with role gate
Strengths: fastest to MVP (6-8 weeks solo); one deployment; one logging/error surface; one set of types end to end; cheapest at pilot scale (~$45-90/month all-in); lowest cognitive load; easiest for one or two maintainers; Supabase gives auth, storage, RLS and backups without building them.
Weaknesses: serverless limits (long jobs, cron granularity); Vercel + Supabase coupling; heavy background work (bulk payouts, PDFs, matching at scale) needs queues later; single repo means a bad deploy touches everything.

3Option B - Next.js + Separate Backend Service

OPTION B Next.js frontend + NestJS API + workers

Stack: Next.js 15 frontend on Vercel (or Cloudflare); NestJS REST API on Railway or Fly.io; Postgres on Neon; Redis + BullMQ workers for matching, notifications, payouts and PDF generation; S3-compatible storage; Clerk or Auth0 for identity; Stripe Connect; separate admin app or route group calling the API; OpenAPI contract shared as a package.

Shape: three deployables (web, api, worker) plus infrastructure. The frontend holds no business logic beyond display; every mutation crosses the API boundary.

Strengths: independent scaling of API and web; real background workers (retries, scheduled payouts, long jobs); clean service boundaries for a larger team; API reusable by a future mobile app; no Vercel serverless ceiling; can run workers where it is cheap.
Weaknesses: 2-3x MVP time (12-16 weeks solo); three deploy pipelines and environments to keep in sync; duplicated types unless a shared contract package is maintained; Redis and worker ops; higher cost at pilot scale (~$120-250/month); every feature needs frontend + API + tests; more places for auth and validation bugs.

6Decision - Short Term and Long Term

DECISION: build Option A now, structured as a modular monolith

Short term (0-12 months): Option A wins decisively. It gets the pilot live in 6-8 weeks, costs under $100/month, and keeps one person able to maintain every part. Every extra service in Option B is a place the pilot can break while it still has almost no users.

Long term (12+ months): Option A remains the better maintainability choice for a team of 1-3. Option B only wins when there is workload separation that genuinely matters - bulk payouts, heavy matching, a mobile app team, or 5+ developers. Those are scale problems, not launch problems.

How to keep the door open: write the domain layer as modules with repository interfaces and an append-only event table (domain_events). Business rules never live in React components. That makes an extraction to Option B a mechanical move rather than a rewrite.

TriggerAction
More than ~5,000 parcels/month or sustained cron timeoutsExtract matching and payout jobs into a worker service (start of Option B)
A mobile app or public e-commerce API becomes a committed roadmap itemExtract the API layer; keep the web as a client
Team reaches 5+ developers with separate frontend/backend ownershipFull Option B split with an OpenAPI contract
Regulatory requirement for data residency or isolated processingMove the affected module to its own service

7Data Model and Core Flows

Core tables

  • users, verifications - identity, role, status, trust score.
  • corridors, handover_hubs - distance band, ferry flag, allowed size bands.
  • parcels - sender, corridor, size band, declared value, insurance, prohibited declarations, state.
  • trips - carrier, corridor, window, capacity by band, state.
  • matches - parcel + trip + reserved capacity + state.
  • payments, payouts, ledger_entries - escrow intent, capture, refund, payout, reconciliation.
  • evidence - pickup/delivery photos, QR scan events, GPS points, timestamps.
  • disputes, claims, incidents - case state, evidence bundle, decisions.
  • domain_events - append-only log for audit and future extraction.

Parcel state machine

draft -> listed -> matched -> paid_escrow -> picked_up -> in_transit -> delivered -> released, with terminal branches cancelled, refused, disputed, refunded. Every transition is server-side only and writes a domain event.

Trip state machine

draft -> listed -> accepted -> active -> completed, branches cancelled, incident.

Money flow

  1. Sender pays contribution + service fee + optional insurance into escrow at match acceptance.
  2. Funds are held (Stripe destination charge with delayed capture or separate ledger).
  3. Delivery code + photo + GPS release funds to the carrier; the service fee stays with the platform.
  4. Refusal or cancellation before pickup refunds fully; dispute freezes release until resolution.

10Migration Path from A to B (if ever needed)

  1. Keep repositories behind interfaces from day one; no SQL in React components.
  2. Emit every state change to domain_events; a future service consumes the log instead of rewriting history.
  3. Move one module at a time (matching first, then payouts), keeping the Next.js route as a thin proxy during the transition.
  4. Publish an OpenAPI contract as soon as a second client exists.
  5. Only then split auth and admin. Big-bang rewrites of a working pilot are the failure mode this plan exists to prevent.
