PKF SR&ED Claim Preparation
T661 Document Preparation Rulebook
Narrative, scoring, citation, humanization, and prep-document rules for any project
Version: 1.0 | Date: 16 September 2026 | Reference project: OpusChart (fiscal year 1 July 2024 to 30 June 2025)

1 - Purpose and Scope

This rulebook captures the full method used to turn a human-written SR&ED narrative into a send-ready T661 preparation document. It applies to every future project. It covers:

  • the inputs you must collect before starting;
  • the hard constraints of the current T661 form;
  • the five-file document model and what each file is for;
  • claim accuracy rules, citation rules, and humanization rules;
  • the scoring model used to compare versions;
  • the required structure of the T661 prep document;
  • print layout rules;
  • the step-by-step pipeline and verification workflow;
  • the audit readiness checklist;
  • worked pitfalls from the OpusChart project.
Absolute rule: the original human-written narrative is never modified. Every derived document is a new file. The original stays byte-for-byte as the source of truth.

5 - Claim Accuracy Rules

Every statement in the narrative must survive a CRA technical review. These rules were learned the hard way during the OpusChart work.

RuleExplanationOpusChart example
Never claim what is not in the records A claim with no matching task or record is removed or reworded, never kept. Spreadsheets were claimed as a tool used; the original narrative only said manual reconciliation effort remained. Reworded to say that.
Verify every count against the data Counts of screens, tasks, sprints, hours come from the export, not from memory. Nine screens became eight after counting subtasks 359 to 366.
Dates must match the records Month and year claims are checked against task dates. Vacation work was in January and February 2025, not February alone.
Remove trigger vocabulary Words that signal routine work to a reviewer: debugging, routine, bug fixing. Frame the same work as investigation of inconsistencies. The original narrative used debugging for what became investigation-driven fixes.
No profitability claims Business or financial outcomes do not belong in a technological narrative. Profitability statements removed from the corrected text.
Unfinished work is investigation only If a capability was not completed in the year, say exactly that. Never imply the result exists. AI recommendation capability: no recommendation capability was completed; the work was research and a prototype.
Payment providers are context only External services like Stripe are inputs to the system, not the advancement. Stripe events are framed as external payment events the internal state machine reconciles.
Cite the correct record A citation must point to the task that actually contains the work. A UI question task was replaced by the task that actually recorded the work.
Claim only what was done Testing or documentation claims must match the records actually present. Manual and automated testing became manual testing and production-update records, because the automation tasks live on a different board.
State the base condition The narrative must establish that the project started from an existing state with unresolved manual effort. OpusChart was an existing application whose continued development addressed the remaining manual effort.
Respect the fiscal year Only work inside the claim period is described as performed in-year. All 217 tasks fall inside 1 July 2024 to 30 June 2025.

6 - Citation Rules

  • Task IDs appear in parentheses immediately after the claim they support: (task 370).
  • Ranges use the to form: (tasks 66 to 69), (task 358, subtasks 359 to 366).
  • Time annotations are included for significant tasks: (task 367, 45 hours 54 minutes).
  • Date annotations are included for key validations: (tasks 1242, 1243, January 2025).
  • Every citation is verified against the export before the document is considered done. Zero missing or wrong IDs is the acceptance bar.
  • Citations live only in the cited annex version (Part 2). The pasteable form text has none.
  • Meta-references to the task system, such as the work is recorded in N tasks across M sprints, belong to the annex only, never to the form text.
  • The full task list annex lists every task: ID, name, sprint, status, completed date, time tracked.

7 - Humanization Rules

The pasteable text must not read like generated prose. A CRA reviewer has seen thousands of claims; generated structure is a credibility risk. Rewrite until the tells are gone while keeping every fact, date, and citation intact.

Do not use

PatternExample to avoidReplacement
Enumeration scaffolding A second uncertainty... A third uncertainty... Finally... Permissions were another open question. Billing automation raised its own questions.
Parallel triads Each observation was analyzed, the model was revised, and the outputs were re-validated. Each failure was traced to the calculation rule that caused it, that rule was revised, and the outputs were checked again.
Hypothesis framing We treated each calculation model as a hypothesis tested against real scenarios. The recalculation work happened as a series of fixes driven by real failures.
Metaphors Served as validation checkpoints for the broader architecture. Each produced inconsistencies during the period, and fixing each one guided the next refinement.
Symmetric closing triads Scalability, consistency, and reliability continue to present technological challenges. Open questions remain. How forecasting scales, whether calculations hold up, and whether AI recommendations are reliable are all still under investigation.
Meta-references in form text The work is recorded in 217 tasks across 23 sprints. Keep this sentence in the annex only.
Generated-sounding jargon A change in any input now propagates consistently through resource forecasts. When an input changes, resource forecasts, project costs, and remaining budget balances update consistently.

Do use

  • Failure-driven narrative: start paragraphs from the concrete problem that occurred.
  • Real bug details with dates: a January 1 holiday was saved as the previous year; employees with multiple assignment lines had doubled hours.
  • Varied sentence length and plain transitions between topics.
  • First person plural with actual work verbs: we built, we tested, we fixed.
  • The same humanized wording in both the pasteable version and the cited version, so the two stay aligned sentence for sentence.

Uncertainty framed technologically10Uncertainty is about models and calculations, not business outcomes
Base state and standard-practice contrast10Existing state described, and why standard tools could not do it

Advancements technological, not business10Advancements are technical capabilities

Vocabulary clean5No trigger words, no generated-sounding phrasing
External services framed as context only5Stripe and similar providers are inputs, not the advance

Worked example: OpusChart original version scored 62 of 100; the corrected pasteable version scored 91 of 100.

Task relatedness rubric

ComponentMaxMeasures
Claims supported by the task log100Share of narrative claims that have a matching task record
Traceability100Share of claims that cite their record directly
Consistency with records100Dates, counts, and statuses match the export

The components are aggregated with weighting; claim support and traceability weigh heavier than consistency. Worked example: OpusChart original 43, corrected 82.

Theme evidence weights and overall score

Evidence is scored per theme and combined. Overall score = 70 percent theme evidence plus 30 percent investigation quality.

ThemeWeight
Calculations and budget model25%
Budget and rates20%
Holidays and dates10%
Permissions15%
Billing15%
AI assistance15%

Adapt the theme list per project: it reflects what the work was actually about, as found in the task export.

Any theme scoring below full marks gets a roadmap section: ordered tasks that raise the score, each with its expected gain and a target of 90 plus. The roadmap items are things the claimant must do in the source data, not things the writer can patch in the document.

9 - Required Structure of the T661 Prep Document

  1. Header meta block: claim year, date, source files, claimant placeholders.
  2. Part 1 - Directly pasteable version: one body per form line (242, 244, 246) with no citations, a live word counter under each heading (green inside the limit, red over), and a copy-text button per line.
  3. Part 2 - Evidence citation version: the same text with task-ID citations. This is the technical annex for CRA reviews; it is not pasted into the form.
  4. Version comparison: the filing readiness table and the task relatedness table, original version against the pasteable version.
  5. Audit package: claimant identification table (name, business number, fiscal year end, claim year, project title, technical contact), the evidence checklist mapped to T661 lines 270-282, and the personnel summary (role, tracked hours, assumed SR&ED hours).
  6. Annex A - Full task list: the complete task export rendered as a table with ID, task, sprint, status, completed date, time tracked, plus a task count line.

The annex task list is rendered from a companion data file (opus-tasks-annex.js in the reference project) generated from the task export. If the HTML is sent as HTML, the companion file must travel with it. Printing to PDF makes the document self-contained.

10 - Print Layout Rules

  • Never put break-inside: avoid on whole sections. A section taller than the remaining page is pushed to the next page, which is how a page ends up holding only the document header.
  • Allow the first section to flow directly after the header on page 1.
  • Start each major part on a fresh page with break-before: page; the first part starts naturally.
  • Keep break-inside: avoid on small units: paragraphs, headings, banners, line headers, and table rows.
  • Keep headings with their next content using break-after: avoid.
  • Wrap long table header rows in thead so the header repeats on every printed page of the task list.
  • Hide screen-only elements in print: buttons, dividers, progress trackers, working sheets.
  • Verify by printing to PDF and checking the text of every page; page 1 must contain content, not just the header.

12 - Verification Workflow

Technical checks used on every step, in order:

  1. Annex data generation: a short script reads the task export JSON and writes a JS file of the form var OPUS_TASKS = [[id, name, sprint, status, date_done, time_spent], ...]; using UTF-8. The prep document loads this file and renders the table; if the file is missing, the table shows a fallback message instead of failing.
  2. Script syntax: extract inline script blocks and run them through node --check.
  3. Headless render: open the document in a headless browser and confirm the rendered task row count equals the export count, and the word counters show the right numbers.
  4. Print QA: print to PDF and inspect the text of every page, verifying page 1 contains content and the annex table header repeats.
  5. Text hygiene scan: no em dashes, no emojis, hyphen used instead of em dash everywhere, per the house document style.
  6. Citation cross-check: extract every task ID from the cited version and diff against the export IDs, including range endpoints.

13 - Audit Readiness Checklist

Before filing, confirm each of these exists or is consciously deferred:

ItemStatus rule
Claimant identification Legal name, business number, technical contact filled in by the claimant. Placeholders like [To be completed] must be gone before sending.
Time sheets (line 271) Task tracking with hours, already in the export.
Design of experiments (line 272) Usually the biggest gap. Create a hypothesis-and-result log from the task comments before filing.
Source code (line 274) Repository access; a commit history summary for the claim period can be added later.
Progress reports and minutes (line 276) Task comments and meeting records from the task system.

14 - Pitfalls Learned (OpusChart)

  • Unsupported tool claim: the narrative implied spreadsheets were part of the work. The records showed manual reconciliation effort only. The claim was reworded to what the original actually said.
  • Wrong count: the corrected text said nine screens; the subtask list contains eight.
  • Wrong period: vacation workflow work was in January and February 2025, not February alone.
  • Wrong citation: one claim cited a task that merely asked a UI question; the correct task was the one recording the work.
  • Overclaimed testing: automated testing tasks live on a different board, so the text was corrected to manual testing and production-update records.
  • AI overclaim: the original said the AI work demonstrated potential; reality was research plus an unfinished prototype. The corrected text says no recommendation capability was completed.
  • Deleted form line: line 240 was included until the actual form was checked; it no longer exists.
  • Empty first print page: break-inside: avoid on whole sections pushed the first section to page 2, leaving page 1 with only the header.
  • Generated prose tells: the first corrected draft was accurate but read as generated; the humanization pass fixed it without changing any fact.
