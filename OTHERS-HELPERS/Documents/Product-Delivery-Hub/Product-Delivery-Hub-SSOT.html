1. What changed in version 2

One record type. One queue. Three actions.

Version 1 defined eight object types, test suites, runs, releases and cycles. That was over-engineered for the problem. Version 2 keeps one object type and one flow: add a finding, turn it into a task, apply it, mark it done.

Everything else is a field, a filter or a page you already have. No suites, no runs, no release entity, no cycles, no registry objects.

Version 1Version 2
8 object types1 object type
Work items, tasks, suites, runs, releases, cycles, products, instancesOne record called a work item, with a kind and an optional parent
Suites and runs to record testingA static checklist page. Every failed point becomes a finding
Release entity with a gateA saved filter: open blockers
Instance registry with config hashesTwo optional fields: application and reported build
Product registry object typeProduct dropdown fed by the existing tool catalog
49 build days12 to 15 build days

The test of a good simplification: a new tester can understand the whole system in two minutes, and you can answer "what is open" with one filter.

2. The design rule

This is a queue, not a platform. Every feature must pass one of these three tests, or it does not get built:

  1. It helps someone add a finding faster.
  2. It helps someone decide what to work on next.
  3. It helps someone prove the work is done.

Anything else is a later decision. Capacity planning, test coverage maths, release sign-off workflows and instance configuration tracking are all real needs, but they are not needed to stop the current mess. They are listed in section 11 with the trigger that would justify each one.

Sixteen fields. No field is added unless it passes the rule in section 2 and is written into this table first.

What the two build fields mean. There is one deployment path: the source folder is pasted into the Application Store Tool Library, and every app and tenant reads that copy. A fix therefore exists only when the Tool Library holds it. reportedBuild is the badge read where the problem was seen. toolLibraryBuild is the badge in the Tool Library after the fix. Closing needs the second to be newer than the first.

5. Statuses and the three actions

StatusMeaningWho moves it there
newAdded, not looked atReporter
acceptedReal, prioritised, has an ownerLead or manager at triage
workingSomeone is applying the changeOwner
doneLives in the Tool Library at a newer build, and the close is recorded by a named checker or marked as a self-checkOwner sets the Tool Library build, a checker confirms or the owner closes with the self-check mark

5.1 The three actions in the app

Add findingFour required inputs: title, detail, product and reported build. Proof optional. Under 30 seconds.
Turn into taskOne click on a finding. Creates a task with the same product and a parent link. The lead sets the owner and severity.
Apply and closeThe owner moves the task to working, fixes the source, pastes the files into the Application Store Tool Library, sets toolLibraryBuild, then closes. A second person may set checkedBy; if the owner closes alone, the record is marked self-checked.

Two hard rules only: a finding cannot be done until the Application Store Tool Library shows a build newer than the reported one, and every close records who checked it. Everything else is optional.

Self-check is allowed, and labelled. One person may report, create the task, fix it and close it. When checkedBy equals owner, the queue marks the row as self-checked and the weekly export counts those rows separately. Nothing is blocked; a self-check simply never counts as an independent verification.

The Hub item says what and who. The tool SSOT says how and why. When an item is done, the owner updates the tool SSOT in the same change if behaviour changed. No copying in either direction.

9. Testing without suites and runs

A run record exists to count pass and fail. You do not need to count. You need to know what is broken. So the checklist becomes a page, and every failed point becomes a finding.

StepWhat happens
1. Open the checklistSmoke checks first, then the 12 attacks. One line each, plain language.
2. Run each checkPass: move on. Fail: press the small button next to the check.
3. The button prefills a findingTitle is the check name, product and reported build are filled, detail is the expected result. The tester adds what actually happened and a screenshot.
4. FinishNo run record, no summary document. The findings are the evidence.

What you lose: pass-rate charts and coverage percentages. What you keep: every defect, its reported build, its proof and its owner.

10. Releases without a release entity

Publishing already exists. The Hub does not need to model it. A release conversation becomes a filter:

Before publishing a productOpen items with severity blocker for that product must be zero.
Filterproduct = X and status is not done or rejected and severity = blocker
If the filter is emptyPublish. The manager still decides; the filter only removes the argument.
After publishingNothing to update in the Hub. The item is already done and checked.

One exception: if a product is published while it has open blockers, the manager records why in the item's detail. That is the only release documentation required.

18. The per-item tool: Work Item Prompt Builder

One record in, one build prompt out.

Every work item carries a small tool that turns its own record into a prompt an AI developer can execute. It is the only part of this system that touches the code folder, and it never keeps a second copy of the record.

PropertyDecision
Tool typeTYPE 1 object-level html tool, built to html-tool-rules.txt
Mounted onThe data part of every record in product-work-items-uniconbaseapps
ReadsThe record through tool.getFields(). No requestObjects, no lookup, no list screen.
ProducesOne plain-text build prompt, ready to paste into Copilot chat in this repository
WritesOnly its own state with tool.setValue. It never writes the work item.
Closing the loopAfter the fix is pasted into the Application Store Tool Library, the owner records toolLibraryBuild on the item. The tool does not do that for them.

Why a tool on the record instead of another app. The record already holds the title, the detail, the product, the build and the proof. A separate app would need a list, a lookup and a copy of the same data, and the copy would go stale. The tool has no screen of its own beyond the record it sits in.

18.1 What the developer fills in

InputSourceRule

toolNameDeveloperPascalCase folder name, for example WorkItemPromptBuilder.
taxonomyPathDeveloperWhere the tool folder belongs, for example BUSINESS/GENERAL/it-development/testing-qa.
classPrefixDeveloperTwo or three lower-case letters plus a hyphen, unique in the repository.
toolPathDeveloper, change mode onlyThe existing tool folder to change.
extraInstructionDeveloper, optionalAnything the work item does not say. Empty is allowed.

19. The build prompt, copy ready

This is the exact text the tool produces. Paste it into Copilot chat in this repository with every placeholder replaced. It is the contract between a work item and the code: if a rule changes, change it here first, then update the tool's embedded default.

19.1 How to use it

1. Fill the placeholdersThe tool does this from the record. By hand, replace every {{NAME}} and delete the line if the value is unknown.
2. Paste into a new chatOne work item per chat. Do not mix two work items, the report becomes ambiguous.
3. Let it read the rulesThe prompt orders the four rule files first. Do not skip that step to save time.
4. Check the reportThe last line must give a build stamp and the exact place to look. Anything else is not finished.

BEHAVIOUR
  1. Record read
     Read tool.getFields() first, then the onReady fields argument, then
     productData.data_categoriesBased, then objectData.data_categoriesBased.
     Read: key, kind, title, detail, product, application, severity,
     reportedBuild, proof, owner, status. Never throw when a field is missing.
  2. Summary
     A read-only card: key and kind chip, title, product and application,
     severity, reportedBuild, owner, status, detail, proof as a link when it is
     a URL. Show an inline warning line when key, title or detail is blank.
  3. Inputs, persisted in the tool value
     mode (new-tool or change-existing), toolName, taxonomyPath, classPrefix,
     toolPath (change mode only), extraInstruction (optional).
     Prefill from params on first load, then remember the last values.
  4. Generate
     Replace every {{PLACEHOLDER}} in the template. A missing value becomes
     "not set" or "not recorded". A generated prompt must never contain an
     unresolved double-brace placeholder, "undefined" or "null".
     Show the character count and the build of the tool that produced it.
  5. Copy and download
     Copy puts the whole prompt on the clipboard, with a select-all fallback
     when the clipboard API is blocked. Download saves
     <key>-build-prompt.md.
  6. Read-only mode
     Generate, Copy and Download stay active. The six inputs become disabled.
  7. Params, all optional, all declared
     buildPromptTemplate (admin override of the prompt text), defaultMode,
     defaultTaxonomyPath, allowAi (reserved, off by default).
     Call reportMissingParams only when a parameter is genuinely required and blank.
  8. No side effects
     No requestObjects call. No write to the host record. Only tool.setValue for
     the tool's own state.

TEMPLATE
  Embed the section 19 prompt verbatim as the built-in default.
  Use a normal string built from an array of lines joined with "\n", never a
  template literal, so backticks and dollar-brace inside the prompt can never
  break the build.
  Escape any sequence that would close the script tag.
  When buildPromptTemplate is set, use it and show "custom template" in the UI,
  with a button that resets to the built-in default.

UI

  One column below 900 px.
  One accent colour, light surfaces, body text 12 to 14 px.

  Header badge "tool build YYYY-MM-DD-rN".
