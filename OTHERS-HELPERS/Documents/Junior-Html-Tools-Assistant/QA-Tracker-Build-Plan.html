QA Tracker: Build Plan and Scaling Model
What to build, in what order, and how it holds up with more testers and developers
Document: QA-2026-02 | Prepared: 2026-11-04 | Version: 1.0

1. What to build, in one view

One system, five parts, six weeks for one developer

A central issue tracker, a test run recorder, a checklist library, a tool and instance registry, and a thin reporter that pre-fills context. Everything reads and writes the same four object types.

Build order matters more than completeness. The first usable version is issues only. Runs, checklists and the instance matrix come after the habit exists.

Part What it is Build in Why it comes there
1. Issue tracker List, filters, detail, create, assignment, comments, evidence, CSV export Phase 1 It removes the mess on day one, before any advanced concept exists
2. Test runs One record per session against one build, with per-check results Phase 2 Turns testing from prose into data and unlocks the flags
3. Checklists Versioned scripts: smoke, 12 attacks, tool acceptance, vertical addenda Phase 2 Makes runs comparable between people and weeks
4. Registry Tools and instances, current build, config hash, last run, flags Phase 3 Generates the queue automatically instead of by memory
5. Reporter One button, prefilled tool, build, application, placement, config hash Phase 4 Makes reporting a 60-second action instead of a form-filling task

E5 Runs Run recorder, pass or fail per check, issue creation from a failed check, verdict 2 to 3 days One run produces a complete result set and linked issues
E6 Registry and flags Tool import, instance list, build and config change detection, the four flags 2 to 3 days The queue is generated, not chosen

3. Six-week delivery plan

Week Delivers Use it for Status
1 E0, E1, E2 The junior starts recording real findings in the tracker instead of a file Usable
2 E3, E8 partial You triage in ten minutes a day; the first weekly export exists Usable
3 E4, E5 Test runs replace free-text reports; issues link to checks Usable
4 E6 The queue is generated from builds and config changes Cutover
5 E7 Reporting from the harness and the tool; context fills itself Rollout
6 Hardening, import of the temporary file, cleanup One system, no parallel file Done

Do not wait for week 6 to start. Week 1 is already usable. The temporary single file from the task list is imported in week 2 and deleted in week 6 at the latest. One file, then nothing.

4.2 Lanes, not a free-for-all

With one tester, the queue is just "what changed". With three, unclaimed work collides. Split the work into lanes, and give each person a lane.

Lane typeExampleRule
By tool familyFinance tools, Education tools, Operations toolsOne tester owns each family. They become the expert.
By applicationRestaurant app, Clinic appUsed for application smoke and instance acceptance
By change typeNew builds, new configurations, reported bugsHandled first by whoever owns the tool family
UnassignedAnything not yet in a laneOnly the QA lead may assign from here

4.3 Capacity model

One quick pass is about 25 minutes. At 10 productive testing hours per week, that is roughly 10 to 13 passes including re-tests and reporting. Use this table to decide when to add a person.

Library size Cycle target Passes per week Testers at 10 h/week Alternative
50 tools5 weeks101One tester also does content work
150 tools5 weeks303Or 1 full-time tester, or a 10-week cycle
300 tools6 weeks505Automation of the smoke tier becomes mandatory
500 tools8 weeks636Human testing only on changed tools and new features

The formula: weekly passes = tools divided by cycle weeks. Testers = weekly passes divided by about 12. Everything else is arithmetic, not judgement.

4.4 What actually breaks first

SymptomCauseFix
Two testers report the same bugNo lanes and no duplicate searchLanes plus a "similar issues" list before create, plus merge
Nobody knows who tests whatQueue built from memoryThe flags generate it; the lane decides the owner
Same tool retested by two peopleNo "in progress" claim on a runClaim a run for 2 hours; others see it and move on
Triage becomes a full-time jobEvery finding has to be read in fullRequired fields and severity proposal; triage is confirm or reject, not investigation
Test data differs per testerEveryone invents their own recordsOne shared data pack per vertical, three states, reset instructions

5. Scaling to more developers

RuleDetail
Tool ownershipEvery registry record has one owner. Unowned tools go to a named person, never to "the team".
WIP limitThree open issues in progress per developer. A fourth means something is waiting, not working.
Definition of readyBuild number, changelog line, deployed to the test tenant, checklist updated. Without all four, a run is not scheduled.
Definition of doneFixed in a build, verified by a tester on that build, no open blocker in the same area.
No self-verificationThe person who fixed it cannot mark it verified. That rule scales by itself.
Assignment, not grabbingThe QA lead assigns from triage. Developers do not pick their favourite bug.
One question in the ticketIf a developer needs clarification, it goes in the issue. The answer stays with the issue.

Why WIP limits matter more than velocity reports: with three developers and no limit, everyone starts five things, nothing is verified, and the release gate is permanently red. Three in progress each finishes work instead of accumulating it.

6. Technical rules that make it scale

RuleWhyHow
IDs only, no text joinsRenaming a tool must not orphan its issuestoolId, appId, instanceId, runId
Optimistic concurrencyTwo people editing one issue overwrite each other silentlyA rev number on every record; reject a stale write and reload
Server-side filtersLoading all issues stops working at a few hundredQuery by status, assignee, tool, lane, age; never fetch everything
Pagination everywhereLarge lists freeze the browserCap 50 per page, "load more", show N of M
Counts as query resultsCached counters driftCompute counts on the filtered set, or recompute the cache on write
Append-only timelineHistory is the audit trailNever edit or delete a timeline entry
Attachments are URLsBase64 in objects kills performanceUpload to storage, keep the URL, max two per issue
One adapter boundaryYou may outgrow CMS objectsThe UI calls a repository interface. Today the CMS implements it; later a SQL service can, without touching the UI.

6.1 When to move off CMS objects

SignalMove to a dedicated service
Open issuesAbove roughly 2,000, or a filtered list takes over one second
Concurrent usersAbove roughly 20, or write conflicts appear daily
Reporting needsCross-record aggregation that the platform cannot index
AutomationCI must create runs and close issues without a logged-in browser

None of these is likely in the first year. The adapter boundary exists so the move is a two-week project, not a rewrite.

7. The real scaling lever: automate the first tier

Human testing should never cover level 1. A script can open every tool, check that it loads, watch the console, capture a screenshot and record a run. That is the tier that grows with the library and costs nothing per tool.

Tier Covered by Runs Frequency
1. LoadScript: opens, renders, no console error, screenshotAll toolsEvery build, automatically
2. Quick passHuman: 12 attacks plus acceptance listChanged tools and rotating sampleWeekly
3. Deep passHuman: full checklist, data extremes, rolesOne quarter of the libraryQuarterly
4. ExploratoryHuman: new features, confusing flowsWhatever changed or was reportedContinuous

The scaling rule: when the library doubles, first automate more of tier 1, then add a tester. Automation is linear in tools; people are linear in judgement.

8. Notifications and reporting at scale

EventDeliveryRule
Blocker or critical createdImmediate to tool owner and managerOnly these two severities interrupt anyone
Everything else newDaily digest, 08:00One message per person: assigned, new in lane, aging items
Issue aged over 14 daysDaily digestClose, fix or park; no silent aging
Build released without a runWeekly to managerpublishedUntested list
Weekly summaryFriday, one pageFour numbers only

No per-event email. Ten testers creating twenty issues a day produces two hundred messages and everyone stops reading. Digest by default, interrupt only for blockers.

9. What does not change as you grow

  • One register. No spreadsheet, no document per run, no bug in chat.
  • One record per issue and one record per run.
  • Build number on every run and every issue.
  • The reporter never lists or manages anything; it only creates.
  • Severity is proposed by the reporter and confirmed by the manager.
  • The person who fixed it never verifies it.
  • The four numbers in the weekly review.

If a change makes the model need a meeting to explain, it is not a scaling improvement. The system should get simpler to use with every addition, not more detailed to operate.

10. Risks and controls

RiskImpactLikelihoodControl
Building all six weeks before anyone uses it High High Week 1 is usable; the junior starts there. No big-bang release.
Two people overwrite one issue Medium High rev field and stale-write rejection from day one
The tracker becomes the product instead of the tools High Medium Six views, four object types, no custom workflows. Every new field needs a reason in writing.
Lanes create silos and nobody can cover for each other Medium Medium Every lane has a named backup; rotating sample crosses lanes
Test data is inconsistent between testers Medium High Shared data packs per vertical, three states, reset instructions
Notification noise kills adoption Medium High Digest by default, interrupt for blockers only
