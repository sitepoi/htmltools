Tool QA Tracker
How to manage test results, bugs and feature requests for every tool
Document: QA-2026-01 | Prepared: 2026-11-04 | Version: 1.0

1. The recommendation

Mixed, exactly as you described, with one hard boundary

Build one central tracker application that owns the registry of every tool, the test checklists, the test runs and the issues. Then add a thin reporter inside the tool host or the test harness that only creates a record and attaches its own context. Never build a second tracker inside each tool, and never store issues in the tool's saved value.

The hard boundary: the central tracker is for internal QA only. No tenant data, no customer records, no screenshots from a live tenant. Customer-facing reporting, if you ever need it, is a separate channel that keeps data inside the tenant.

Why this fits your situation: you already have the tool registry in catalog-data.js, the publish state per tool, the 8-subject completeness model, the TYPE 3 listing-tool pattern for collections and the TYPE 1 object-viewer pattern for a single record. Nothing new has to be invented; the work is assembling four existing pieces and adding one small reporter.

2. Why the three simpler options are not enough

Option What happens in practice Verdict
Embedded only
(a panel inside every tool)		 Each tool gets its own mini tracker. Fifty tools means fifty places to look. No cross-tool queue, no weekly report, no triage view. Every tool change risks breaking reporting. Reject as the whole solution
Separate only
(one app, no reporter)		 The junior leaves the tool, finds the app, finds the tool in a list, retypes the build number and the context. Most reports lose the details that make them fixable. Workable but slow
Documents
(spreadsheet per tool, docs per run)		 Exactly the mess you are trying to end: duplicated rows, stale files, no counts, nobody knows which version was tested. Reject
Issues in the tool's saved value The 1MB field limit, issues travel with a copy of the tool, no querying across tools, and a corrupted value takes the issues with it. Reject
Mixed model One source of truth for the queue, plus a two-click report from inside the tool with its own context attached. Choose

3. Architecture: four components

1. Registry One record per tool. Slug, code, folder, build, docs, screenshots, publish state. Seeded from the repo and refreshed, never typed by hand.
+
2. Tracker (central app) The only queue. Issues, checklists, runs, triage, filters, roll-ups, exports. Built as a TYPE 3 listing tool.
+
3. Thin reporter A button and a small form. It sends tool slug, build, role, browser, viewport and the description. It does not list or manage anything.

The fourth component is the registry feed: the repo scan writes tool-registry.json, the tracker imports it, and the tracker exports tool-quality-state.json that the catalog build reads. One direction each way, no two-way sync.

Component Lives where Owns
RegistryCMS object type tool-registry-uniconbaseappsTool identity, code, folder, current build, publish snapshot
Issue logCMS object type tool-dev-issues-uniconbaseappsBugs, feature requests, tasks, questions, evidence, timeline
ChecklistsCMS object type tool-test-checklists-uniconbaseappsVersioned test scripts, shared across tools
Test runsCMS object type tool-test-runs-uniconbaseappsOne record per session against one build, with per-check results
Tracker UIApplication-level TYPE 3 listing toolViews, triage, filters, exports
ReporterTest harness first, tool template second, CMS host shell optionalContext capture and record creation only

Do not merge issues and runs. A test run is "I tested build X against checklist Y, 18 passed, 2 failed". An issue is "this specific thing is wrong, here is how to reproduce it". One run can create three issues; one issue can be found by three runs. Mixing them makes both unusable.

Found in build: 2026-10-28-r3. Severity: major. Status: triaged.

5. The thin reporter

One button. One small form. It captures context automatically and creates one record. It never lists, filters, triages or stores anything else.

5.1 What it captures automatically

Captured

  • Tool slug and tool build
  • Current user id, name and role
  • Browser, viewport width, language
  • The screen or step the user was on
  • Last console error, if captured
  • Timestamp

Never captured

  • Saved field values or record content
  • Customer or tenant names
  • Object names, addresses or personal data
  • Files attached in a production tenant
  • Anything the user did not type on purpose

5.2 Where the button lives, in order of preference

# Place Effort Verdict
1 Test harness shell One template change, then regenerate harnesses Start here the junior tests in the harness anyway, and no production code changes
2 Tool template A shared snippet in every new tool, about 120 lines Next gives real users and testers the same button
3 CMS host shell around the iframe Platform change plus a boot message contract from each tool Best long term one implementation, all tools, no retrofit
4 Inside the tool's own UI Per tool, plus every tool change risks reporting Avoid duplicates the shell and multiplies maintenance

5.3 The boot contract that makes option 3 possible

Every tool already shows TOOL_BUILD and logs [TOOL:BOOT] build .... Add one line so the host can read it:

Message from tool to host, on ready
{ source: "uniconhub-tool", type: "boot", slug: "PersonalTaxPreparation", build: "2026-10-28-r3" }
No tenant data, no saved values, no user details. The host then knows which tool and build it is showing, and can open the reporter with both fields already filled.

This is the cheapest possible integration: one message, no API, no schema, works for all 50 tools the moment they are rebuilt.

5.4 Degradation rules

  • If object create is not allowed, the button hides. It never shows a broken form.
  • If the network or the create call fails, the text of the report is copied to the clipboard and shown in a box, so nothing is lost.
  • If the role is viewer, the button hides.
  • If the tool is running in a production tenant, the button is hidden by configuration. Reporting is a test-tenant feature.

6. The central tracker

Build it as a TYPE 3 application-level listing tool. It reads and writes objects through requestObjects, keeps only UI state in its own saved value, and uses the existing patterns from the catalog page: filters, sortable columns, a right-side detail pane, load more.

6.1 Six views, no more

ViewWhat it answersBuilt from
My queueWhat do I test or fix next?Issues assigned to me plus tools flagged untestedSinceBuild
Triage inboxWhat is new and needs a decision?Issues with status new, oldest first, grouped by tool
Tools matrixWhich tool is healthy, stale or blocked?One row per registry record, with counts and flags
Tool detailWhat is the history of this one tool?Issues plus runs, newest first, with the current build at the top
RunsWhat was tested, on which build, by whom?Run records, filterable by tool and date
Weekly reportWhat changed this week?Counts by tool and severity, plus the export

6.2 The three flags that do the real work

Flag Rule Why it matters
untestedSinceBuildThe registry's current build is newer than the last run's buildThis is the entire junior queue, generated automatically. Nobody decides what to test by memory.
publishedUntestedPublish state has a version, but no passing run exists for that buildCatches the worst case: something is live and nobody tested the build that shipped.
openBlockersAny issue with severity blocker or critical, status not closed or rejectedStops a release conversation in one line.

6.3 Status flow and who may do what

ActionWhoRule
Create issue or runReporter, editor, managerAlways allowed. Severity is a proposal, not a decision.
Set severity and priorityOwner or managerOnly here. Prevents a junior labelling everything critical.
AssignOwner or managerUsually to the person who fixes it, not the tester.
Mark fixedDeveloper or ownerRequires fixedInBuild.
Mark verified and closedTester, on a second runNever the person who fixed it. That is the whole point of verification.
DeleteNobodyUse rejected or duplicate. History is append only.

One queue, one register. After phase 1 there is no spreadsheet, no document per run and no chat message that contains a bug. If a finding is not in the tracker, it does not exist. That single rule is what keeps the junior's work from turning into a pile of files.

6.4 HtmlToolLibraryItem: the right per-tool surface, not the tracker

You already have the perfect place to see and report the issues of one tool: the HtmlToolLibraryItem editor that holds details, HTML, CSS, JS, preview, documents, screenshots and versions. It should get a QA tab. It should not become the tracker.

Belongs in HtmlToolLibraryItem Belongs in the central tracker
A Report button in the header, always one click away The queue of what to test next
This tool's open issues, newest first, with severity and status Triage across all tools, oldest first
This tool's test runs and the last tested build The tools matrix and the three flags
Verify fixed on the build that is open in the editor Weekly counts, exports and reports
Current build shown next to the code version Severity rules, assignment and release decisions

Why the tab is cheap. The tool already writes child objects for documents and for code versions. QA records are one more child type, queried by the tool record id. Nothing in the tool's own saved value changes, so the 1MB budget and the existing code path stay untouched.

DetailDecision
Object typetool-qa-issues-uniconbaseapps, scope shared, plus tool-qa-runs-uniconbaseapps
Link keytoolId (the tool record id) plus toolSlug and toolName for readability
Build numberParsed from the JS TOOL_BUILD constant when the editor saves, cached as a read-only currentBuild on the record; every issue and run carries it
PermissionsCreating an issue is allowed even when the tool record is read-only, because the issue is a different object. Triage, severity and assignment stay with the owner or manager.
IsolationThe QA tab loads on first open, is behind a param, and never blocks the code tabs. If the object API is unavailable, the tab shows a message and the rest of the editor works exactly as before.
CostAbout 2 to 4 days for the tab and the report form, 3 to 5 days for the board

Why it cannot be the only place. HtmlToolLibraryItem is an object-level tool, so it shows one tool at a time. It cannot answer "what do I test today", "which tools were published without a run" or "what is new across all tools". Those are the questions the junior and the manager ask every morning, and they need one application-level view.

No extra object per application. You create one new object type and one application-level board in the Application Store. Records appear only when someone reports something. Applications that use a tool do not get their own copies; QA belongs to the tool record, not to the place where the tool is mounted.

Never duplicate the truth. Tool identity and publish state belong to the catalog. QA findings belong to the tracker. Each side keeps a read-only snapshot of the other and refreshes it on demand. The moment both sides can edit the same field, you have two truths and the old mess returns.

11. Application or tool: choose the unit of testing

Neither alone. Test the instance.

A tool is reusable and configurable. An application bundles tools and may use the same tool several times in different objects. What a user actually experiences is one tool instance: one tool, inside one application, at one placement, with one configuration. That is the unit to test, report on and assign.

11.1 Three levels, three questions

Level Identity Owns Question it answers Run
Tool
(library item)		 toolId Code, build, defaults, docs, test harness Does the tool work at all? Harness or reference instance, about 20 minutes
Instance
(tool mounted in an application)		 appId + toolId + placement Configuration, field settings, object types, permissions at that placement Does this configuration work with this application's data? Instance acceptance, 15 to 25 minutes
Application appId Data model, workflows across tools, roles, folders Can a user complete the application's main job? Application smoke, 10 to 20 minutes

Why not tool only

A tool can pass its harness and fail in a vertical, because the configuration, the object types or the field settings differ. That failure is invisible at tool level.

Why not application only

The same tool appears in many applications. Testing by application retests it twenty times, produces duplicate tickets, and leaves you unable to say whether the fault is the tool or the configuration.

11.2 The identity rule

instanceId = appId + toolId + placement, where placement is the object type and the field the tool is mounted on. Placement belongs in the key because one application may bundle the same tool several times, at different levels, with different configurations.

Store a configHash as well: a hash of the tool parameters and field settings only. Never the values, never secrets, never customer data. When the hash changes, the instance counts as untested again.

11.3 The scope field that makes triage fast

ScopeHow you knowWhat it means
toolFails in the harness or in the reference instanceFix once, verify everywhere. Highest priority.
instanceFails only in this application, or only with this configurationFix the configuration or the placement, not the code.
dataFails only on one record or one data shapeData problem. No code change.
applicationSeveral tools fail together, or roles and flows breakApplication-level integration, not a tool defect.

11.4 Triage in four questions

  1. Does it fail in the harness with the default settings? Then it is a tool issue.
  2. Does it also fail in a second application using the same tool? Then it is probably a tool issue.
  3. Does it fail only here, with this configuration? Then it is an instance issue.
  4. Does it fail only on this record? Then it is a data issue.

11.5 Checklists that scale

Do not write a checklist per application. Build each run from three layers:

BaseThe tool checklist, shared by every instance: the 12 attacks plus the tool acceptance lines. About 20 minutes.
Vertical addendumChecks for a category or application type, for example restaurant-specific fields. About 10 minutes.
Configuration checksFive to ten checks generated from the instance parameters. About 10 minutes.

11.6 Flags at the right level

untestedSinceBuildTool level: the build changed.
untestedSinceConfigInstance level: the configuration hash changed.
appSmokeStaleApplication level: a tool was added, removed or moved, or the field model changed.
publishedUntestedInstance level: the application is live with a configuration that has no passing run.

Do not retest everything. Test changed tool builds, changed configurations, changed application structures, plus one rotating sample per week. The flags produce that list; nobody decides it from memory.

11.7 Where each report comes from

HtmlToolLibraryItemTool-level report: build, code context and harness result. Scope defaults to tool.
Reporter inside a running instanceInstance-level report: carries appId, placement, configHash and build. Scope defaults to instance.
Central boardEverything: tools matrix, instances matrix and applications matrix.

11.8 Easy mode: the minimum you actually run

The model stays detailed; the daily work must not be. Hide it behind these defaults and nobody has to think about application, tool, placement or scope while testing.

DefaultRule

Three checklistsSmoke, 5 minutes. The 12 attacks, 15 minutes. The tool acceptance list from its own SSOT, 5 minutes. Nothing else.
Two pass depthsA quick pass of 20 to 25 minutes on every change. A deep pass of 45 minutes once per quarter, per tool.

One formWhat happened, what you expected, what you did, screenshot. Tool, build, application, placement and scope are prefilled.

11.10 The only four numbers in the weekly review

Open blockersAnything that stops a release. Target zero before publishing.
Tools untested since buildThe real backlog. Should trend down every week.
Instances untested since configConfigurations that changed but were not re-checked.
Issues older than 14 daysAnything aging without a decision. Close it, fix it or park it.

11.11 Six rules that keep it small

  1. Do not test every configuration permutation. One representative configuration per vertical.
  2. Do not test features that are not in the acceptance list. The list is the contract.
  3. Do not reopen a closed issue. Create a new one and link it.
  4. Do not report taste as a bug. It is an improvement, low priority, batched once a week.
  5. Do not retest an unchanged tool because it feels risky. The flag decides.
  6. Do not write a document per run. The run is the document.

The one sentence to remember: you do not manage the model, you manage three lists - what to test, what is waiting for triage, and what is waiting for verification. The registry, the flags, the counts and the weekly report are calculated, never maintained by hand.
