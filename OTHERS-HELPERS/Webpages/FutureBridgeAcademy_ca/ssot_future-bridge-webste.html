1. How to use this document

  • Order of truth: business plan (facts about the company) → this SSOT (what we say publicly and how) → page code.
  • Before writing any page copy: check sections 4 and 5. If a service is not in the "live today" table, it must be labelled as coming.
  • Before building a page: check section 10 for its slug, phase and status, and section 11 or 12 for its required sections.
  • Before shipping a page: run the definition of done in section 15.0 (tick every box for that page).
  • When something changes: update this document in the same session, bump the version, and add a change log row (section 17).
  • Task checkboxes below are live: they save in your browser (localStorage) so you can use this file as the working board.
Hard rules that never bend: no prices on the website; no invented numbers, results or testimonials; nothing described as running unless it is in the "live today" table; no student names or photos without written parental consent.

5. Content rules and banned claims

  1. No prices anywhere. No numbers, no currency symbols, no "from $X", no package tables. Free things carry the word "Free". Paid things are described and the page says we explain costs before anything is agreed.
  2. Live means live. A service may only be presented as running if it appears in table 4.1. Everything else carries a "Coming with the centre" style label.
  3. No invented evidence. No made-up statistics, no percentages of students who improved, no testimonials, no ratings, no awards, no partner logos, no dates that are not confirmed.
  4. No invented sizes. No group size, class size, ratio, lesson length or number of students.
  5. No free assessment promise. The way in is described as "a short assessment and a goal conversation". Do not call it free.
  6. Two processes stay separate. The free monthly mock exams and the CEMC contest track are never mixed in one sentence as if they were the same thing.
  7. Language: plain English, short sentences, no hype, no exclamation marks, hyphens rather than long dashes.
  8. Every page ends with one call to action that leads to the free funnel (join a free lesson, come to a free mock exam, join the community) or to contact.
  9. Consent first. No student name, photo, quote or work sample without written parental consent on file.
  10. Accessibility: alt text on every image, readable contrast, keyboard reachable controls, motion respecting the system setting.
Removed claims - do not reintroduce: "six learners per lesson"; "free assessment"; "60 minute small-group lesson"; "fortnightly one-to-one mentor session"; "termly showcase"; parent testimonial quotes; confidence and habit percentage bars presented as real data; essay competition preparation and software club presented as currently running; any fixed group size; any price. Also parked and removed on 16 October 2026: online mock exam (it does not exist), study hall, summer programme and books and materials - see section 4.4 before putting any of them back.

6. Website plan: objectives and phases

6.1 Objectives (in priority order)

  1. Fill the free funnel. Turn visitors into free-lesson attendees, mock exam participants and community members.
  2. Be honest and clear. A parent must be able to tell in ten seconds what is free, what is coming, and what happens next.
  3. Build trust for the centre. Show that a real programme with a real plan is behind the free offer.
  4. Be findable locally. Rank for city and subject searches once city pages exist.
  5. Recruit volunteers and mentors. A second audience that the site serves deliberately, not by accident.

9. Technical contract and conventions

9.1 Page fragment rules (CMS embed)

  • One parent <div> per page, carrying the shared class fba-page plus its own page class (for example class="fba-page fba-home").
  • No <!DOCTYPE>, <html>, <head> or <body> tags. No document-level scripts or stylesheets.
  • No <header>, <footer> or <nav> element tags anywhere in a page. The central header and footer components own that.
  • No footer, no second call to action band duplicated from another page: shared components come from the central stylesheet (next item).
  • Central stylesheet: the shared design system lives in header-footer/header.html, which is loaded on every page. It holds the colour tokens on :root, the page base styles, every shared component (wrap, kicker, section head, buttons and button row, pills, tags, ticked list, highlighted list with icon tile, note callout, call to action band, scroll reveal and the small-screen button rules) and the whole header chrome including the mega menu panels. Pages must NOT repeat any of those rules.
  • Page CSS keeps only layout specific to that page (hero, card grids, steppers, report card, FAQ layout, section paddings).
  • Reset specificity rule: the shared reset uses :where() so it carries zero specificity. That is what lets a component rule set its own margin and padding. Never reintroduce a reset like .fba-page p { margin: 0 }, which silently overrides every component that is a paragraph or a list.
  • All page CSS scoped to the page prefix. No global selectors, no bare element styling outside the scope.
  • Vanilla JavaScript only, in one IIFE, idempotent, no external libraries, no top-level await, reduced motion respected. Page scripts add the shared class fba-js to their root.
  • Page must still read correctly with JavaScript disabled (tabs and filters degrade to visible content).
  • Tokens are the only colour source: use var(--fba-...), never a hard-coded hex in a page.
  • No prices, no student data, no third-party trackers embedded in page code.

9.3 Links, forms and data

  • Internal links use the route form only: / for the home page, /how-it-works, /about-us, /contact for the rest. No .html in any link, no relative file paths, and no link to a page that is not reserved in section 9.2. A link to a section of another page is written /#fba-programs; a link inside the same page is written #fba-journey.
  • Every form uses the CMS form contract (form marker, honeypot field, status message, bound handler) and posts to the CMS form endpoint.
  • Form submissions notify a real inbox and are stored in the CMS, so nothing depends on a personal email account.
  • No student data is collected on public pages beyond what a form genuinely needs.

9.4 Quality gate before publishing any page

  • Preview it locally first: open test-harness.html (built by build-test-harness.js) and check the page with the central header and footer around it, at full width and at 1024, 768 and 390 px.
  • Link check: every internal link uses the route form from section 9.2 and points at a page that exists or is planned. The harness maps those routes back to the local files, so links stay clickable before the CMS pages exist.
  • Structure check: no document tags, no chrome tags, balanced markup, every CSS selector scoped.
  • Script check: syntax valid, idempotent, no console errors on load or on re-navigation.
  • Responsive check: 1440px, 1024px, 500px, and a narrow phone width.
  • Accessibility: keyboard path through every control, focus visible, alt text, contrast, reduced motion.
  • Accuracy: every claim traced to section 4 of this document.
  • Link check: no link to a page that does not exist, or to a placeholder file.

9.5 Header navigation, the mobile drawer and the footer (built 16 October 2026)

  • The header is a mega menu. Six top level items only - Home, Start here, Programmes, Volunteer, About, Contact - plus the "Join a free lesson" button, so the bar stays scannable. Four of them open a full width panel: Start here, Programmes, Volunteer, About.
  • The panels carry the depth. The ten core pages sit inside the panels with a one line description each, and the Volunteer panel lists all ten role pages in two columns. Every page stays reachable from the header, and no panel links to a page that does not exist (the "everything we run" material stays on the programmes page).
  • Every panel ends with a feature tile: a dark card with a tag, a title, one line of copy and an arrow, used for the one action we most want from that section (volunteer, start a free lesson, apply to volunteer, see all programmes).
  • Panel visuals: every panel opens as a light rounded surface (white fading to very light blue, bottom corners 26px) with a four pixel brand gradient rule along its top edge and a faded dot pattern behind the content. Each link is a card holding an icon tile (36px, 34px in the Volunteer panel and the three column panel), a bold label and one short description line; on hover the card lifts, gains a soft shadow and the icon tile fills with the brand gradient. Every panel's feature tile carries a free stock photo (Pexels licence, hotlinked from images.pexels.com at width 600 and recorded in changelog 1.16) under a dark brand wash, so the copy stays readable and a photo that never loads degrades to the brand gradient; the tile keeps generous padding (30px sides, up to 18px between copy blocks) because the panel column is narrow. If the photo is ever removed, the wash alone still looks intentional. The icons are 22 inline SVG symbols in a hidden sprite inside the header (fba-hd-sprite with fba-i-* ids), so there is still no library, no icon font and no extra request; the three column panel uses slightly smaller type so its titles stay on one line.
  • Behaviour: hover opens on desktop after a short delay and closes on leave; click, Enter or Space toggles; the trigger carries aria-expanded and aria-controls and the panel is a role="region" with an aria-label; Escape closes the open panel first and then the drawer; a click outside or focus leaving the panel closes it; the script is idempotent and its window listeners are bound once.
  • Mobile: below 1120px the same markup becomes an accordion inside the drawer - each panel is a tappable row with a rotating caret that expands in place, and every row keeps its icon tile with a hairline divider between rows; the drawer scrolls (max-height calc(100vh - 96px)) because it now holds twenty links, and it closes on any link tap, on Escape and when the viewport goes back to desktop.
  • Current page highlight: every link carries data-page; the active link is styled and marked aria-current="page", and the trigger of the section the visitor is in gets the same active underline through data-mega-pages.
  • Footer: a volunteer band at the top ("Volunteers run this programme", the any city in Canada and training facts, Apply to volunteer, See the ten roles), then five columns - brand, Explore (all ten pages), Volunteer (apply, all ten roles, and four popular role definitions), Running now, and Start here with the join button and the programme inbox - then the bottom bar. The grid drops to two columns at 1180px and one at 600px.
  • CMS menu JSON: main-menu.json in this folder mirrors the header exactly for the CMS mobile menu: one menus array of six top level items (id, label, url) where four carry a children array, giving 33 links over 20 unique routes. Ids are unique slugs (children are namespaced <parent>-<slug>), every url is in route form (never .html), and the two volunteer anchors #fba-volunteer-positions and #fba-volunteer-form are included. When the header changes, this file changes with it: a script check asserts that every route in the header appears in the JSON and the other way round.
