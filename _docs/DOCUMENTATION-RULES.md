# Documentation rules for UniconHub html-tools

This is the canonical **rules document** for the tool documentation system.
`publish-rules.txt` remains the end-to-end SHIP protocol; the templates in
`_docs/templates/` remain the structural source; the generators in `scripts/`
enforce the repeatable parts. When this document and a template disagree about
a rule, fix the template and this document in the same change.

## Why this document exists

Before this file, the rules were split between:

- `_docs/templates/README.md` - what each document is and how it is maintained;
- the instructional comments inside `_docs/templates/_*.html`;
- `publish-rules.txt` - the SHIP phases and verification gates;
- `_docs/assets/*.js` and the generator scripts - the behavior that is actually
  enforced.

There was no single readable rules entry point. This file is that entry point.

## Documents per tool

| File | Role | Maintenance |
| --- | --- | --- |
| `docs/index.html` | One-page shell with menu, code panes, screenshots viewer and harness. Data-only per tool. | Generated from `_index-template.html`; code/shots payloads refreshed by scripts. |
| `docs/ssot.html` | Single source of truth: purpose, capabilities, requirements, design, decisions, tasks, tests, risks, releases. | Edited with every code change. The SSOT wins ties. |
| `docs/webpage.html` | Marketing webpage fragment. | Generated on SHIP. |
| `docs/help.html` | User help. | Generated on SHIP. |
| `docs/presentation.html` | Marketing deck. | Generated on SHIP. |
| `docs/social.html` | Social and WhatsApp share kit. | Generated on SHIP. |
| `docs/updates.html` | User-facing release history. | `npm run rel` appends rows; Highlights generated on SHIP. |
| `docs/profiles.html` | Optional profile/preset copy page with a browser-local usage reminder. | Generated by `npm run docs:profiles -- <Tool>` when the tool has `profiles/index.json`. |

The seven core documents are created by `npm run docs:init`. The optional
Profiles document is also created by `docs:init` when a tool has a `profiles/`
folder, and can be refreshed independently.

## Authority order

1. `docs/ssot.html` for decisions about one tool.
2. This rules document for documentation structure and profile governance.
3. `publish-rules.txt` for the SHIP process and verification gates.
4. Templates and shared assets for structure and behavior.
5. Generated satellites are derived. When they disagree with the SSOT, the
   SSOT wins and the satellite is regenerated.

The decision register in SSOT section 11 is append-only. Never delete a
decision row. Mark a reversed decision as `Reversed (date)` with a reason.

## Profile configuration rule

A tool has a **profile configuration** when either condition is true:

- it declares a `profileConfig` CMS parameter; or
- it contains a `profiles/` preset library (normally with `index.json`).

Every tool with a profile configuration MUST:

1. Keep a **Profile configuration usage** register in SSOT section 4.1.
2. Add a `profile-usage` release group in SSOT section 15.
3. Put `data-task-type="profile-usage"` on every task in that group.
4. Keep the preset library, `docs/profiles.html`, and the test-harness preset
   selector in sync in the same change.
5. Test every segment and verify that switching a segment does not delete
   saved answers.
6. Record the selected profile in section 4.1 when an application CMS
   configuration starts using it.

The copy page (`docs/profiles.html`) is convenience only. The status control on
its cards is stored in that browser and is not shared. **SSOT section 4.1 is the
authoritative usage register.**

### Profile usage status vocabulary

| Status | Meaning |
| --- | --- |
| `not-reviewed` | No decision yet. |
| `available` | Usable preset, but not selected by an application. |
| `planned` | Selected for a future application. |
| `in-use` | A real application CMS configuration depends on it. |
| `retired` | Kept for history, no longer selected. |

A status change is made in the same change as the application configuration
change, with a dated decision in section 11 when the selection is meaningful.

### Profile task type

```html
<section class="task-group" data-release-group="profile-usage">
  <div class="task-item"
       data-task-id="T-PU-01"
       data-task-type="profile-usage"
       data-group="profile-usage">
    ...
  </div>
</section>
```

The minimum profile-usage tasks are:

1. register every profile and its status in section 4.1;
2. keep `docs/profiles.html` current;
3. keep the harness preset selector current;
4. test every segment and answer preservation;
5. keep the SSOT, index, profiles and rules templates aligned.

## Stable ids

- Segment `key` is stored as `segmentKey`; never rename it after records exist.
- Question-set `key` is stored in `profileKeys`; keep it stable.
- Field `id` is the answer key. Changing an id starts a new answer; old values
  remain under the old id.
- Section `id` must be unique within a question set.
- Renaming a label is safe; renaming an id is a data migration, not a copy edit.

## Commands

```text
npm run docs:init                         create missing core docs
npm run docs:init -- --refresh-shells     rebuild docs/index.html shells
npm run docs:index-code -- <Tool>         refresh code panes + Profiles page
npm run docs:index-shots -- <Tool>        refresh screenshots viewer payload
npm run docs:profiles -- <Tool>           build docs/profiles.html + menu item
npm run docs:generate -- <Tool>           regenerate AI satellites on SHIP
npm run ssot:check                        verify shared assets links
npm run rel                               full SHIP flow
```

For the CustomerProfile preset payload inside the test harness:

```text
node app/build-harness-presets.js
```

Run it after changing `profiles/index.json` or any preset JSON. The harness
selector calls the same `profileConfig` parameter the CMS uses.

## Template changes

- Change shared LOOK and BEHAVIOR in `_docs/assets/` once.
- Change document STRUCTURE in `_docs/templates/` and update this rules file.
- Change the repeatable data generation in `scripts/init-docs.js`,
  `scripts/refresh-docs-index.js` or `scripts/build-profile-docs.js`.
- Never add per-tool inline styles or scripts to the generated documents.
- Keep the `GENERATED-START` / `GENERATED-END` regions as the output contract.
- Keep the hyphen `-`; do not use em dashes.
- No emoji icons in document headers or CSS.

## Adding a new flexible tool

1. Run `npm run docs:init`.
2. Add the app's `profiles/index.json` and preset files when it has a profile
   library.
3. Run `npm run docs:profiles -- <Tool>` to create the copy page and index
   menu item.
4. Fill SSOT section 4.1 and add the `profile-usage` task group.
5. Add the app to the SSOT template's examples only when a new reusable
   pattern exists; otherwise use the existing segment/profile rules.
6. Run the tool's QA, `npm run ssot:check`, and the SHIP verification gates.

## Known follow-ups

- Profile usage status is still manual in SSOT; browser-local reminders are
  deliberately non-authoritative.
- The profiles page generator reads a tool's own `profiles/index.json`; tools
  with a different profile format need an adapter, not a page fork.
- New profile-aware templates must be checked against
  `scripts/check-ssot-assets.js` so shared asset links stay valid.
