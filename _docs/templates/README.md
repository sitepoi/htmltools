# Tool Documentation Templates - `_docs/templates/`

This folder is the **template home for the whole documentation system** of the
html-based tools store. Every tool folder gets a `docs/` folder with seven
documents, all of them born from these templates. Develop new capabilities
**here first** - the generators in `scripts/` copy these templates, so an
improvement made here applies to every tool after the next run.

## The seven documents per tool

| File | What it is | How it is maintained |
| --- | --- | --- |
| `docs/index.html` | One-page shell with a thin left menu - it loads every document, the tool's HTML / CSS / JS code (embedded with a Copy button), the SCREENSHOTS VIEWER (MEDIA menu - large preview with prev/next, an info panel below and a thumbnail strip) AND the test harness into a full-page pane, so you open ONLY this page to review the whole tool. CENTRALIZED: the per-tool file carries only its data (menu + two JSON payloads) - design and behavior live ONCE in `_docs/assets/index.css` + `index.js`. | Generated by `npm run docs:init` from `_index-template.html`; the test-harness menu item appears only when the tool has `app/test-harness.html`. The embedded code is refreshed with `npm run docs:index-code -- <ToolName>` (or `--all`) and the screenshots payload with `npm run docs:index-shots -- <ToolName>` after captures - `npm run rel` does both automatically for changed tools. |
| `docs/ssot.html` | Single source of truth - features, tasks, decisions, risks, test plan, release log. Everything about the tool. | Written and maintained by hand (or with AI help), updated in the SAME change as the code. `npm run rel` appends release-log rows and stamps pushed tasks. |
| `docs/webpage.html` | Fancy marketing webpage fragment for the UniconHub website. Content block only - paste the whole file into the webpage content tool. The design comes from the SHARED webpage design system; the page carries only its own accent colors, content and live demo. | Generated by AI from the code + SSOT + AI chat + ideas catalog (`npm run rel` regenerates the region between the GENERATED markers when the tool changed in the push). |
| `docs/help.html` | User help - overview, before-you-start, step-by-step, FAQ, troubleshooting, plus a fixed "6. What it looks like" screenshot figures section (filled by `docs:init` from the real shots; absent when the tool has none). | Generated by AI from the same sources. |
| `docs/presentation.html` | Marketing presentation deck (9 slides, prev/next, PDF export via print). | Generated by AI from the same sources. |
| `docs/updates.html` | Update history for users, newest first. | Rows are appended **automatically by `npm run rel`** for every push in which this tool changed; the Highlights section is regenerated by AI. |
| `docs/social.html` | Social media + WhatsApp share kit with copy buttons. EVERY SHIP appends its own share set (newest kit between the GENERATED markers, older ships archived under SHARE-SETS markers) and a fixed "Media to attach" strip shows the real screenshot thumbnails. | Generated by AI from the same sources. |

## Where the parts live

- `_ssot-template.html`, `_webpage-template.html`, `_help-template.html`,
  `_updates-template.html`, `_presentation-template.html`,
  `_social-template.html`, `_index-template.html` - the templates
  themselves (`_index-template.html` builds the per-tool docs shell).
- `../assets/` - the shared runtime used by the generated documents:
  - `ssot.css` + `ssot.js` - design + behavior of `ssot.html`, `help.html`,
    `updates.html` (tabs, task panel, statistics, checkbox persistence,
    push gate, TOC sidebar).
  - `presentation.css` + `presentation.js` - the deck engine of
    `presentation.html`.
  - `webpage.css` + `webpage.js` - the shared marketing page design system
    of `webpage.html` (see next section).
  - `index.css` + `index.js` - the centralized docs index engine of
    `index.html` (menu, code panes, screenshots viewer).
  - `social.html` is fully self-contained (own styles + copy script)
    because it is pasted into the CMS or shared directly.

## Shared design layer - edit once, applies to ALL documents

The CSS and JS live ONCE in `_docs/assets/` and every generated document
links to that single copy (relative path computed per tool). This means:

- Editing `_docs/assets/ssot.css` restyles ALL 50 SSOTs + all help and
  updates documents instantly - no regeneration, no per-file edits.
- Editing `_docs/assets/ssot.js` upgrades the behavior (tabs, task panel,
  push gate, checkbox persistence) of every SSOT at once.
- Editing `_docs/assets/presentation.css` / `presentation.js` upgrades
  every marketing deck at once.
- Editing `_docs/assets/webpage.css` / `webpage.js` upgrades the design
  and behavior of every tool's marketing webpage at once.

## Webpage design system (docs/webpage.html)

Every tool's marketing page uses ONE stable design (`wp-` classes) from
`_docs/assets/webpage.css` + `webpage.js`. The design is IDENTICAL across
tools on purpose: when several pages are pasted together on the website
they never fight. What differs per tool:

1. **Accent colors** - the only visual identity a tool brings. The page's
   tiny inline `<style>` sets `--wp-accent` / `--wp-accent-2` on `.wp-page`;
   `npm run docs:init` extracts them from the tool's own CSS `--primary`
   (fallback indigo).
2. **Content** - the region between the GENERATED-START / GENERATED-END
   markers: stats, benefits, highlight rows, how-it-works, comparison,
   testimonials, FAQ. AI-generated from the SSOT + code.
3. **Screenshot gallery - the protected "demo"** - the gallery band is the
   ONLY interactive part: a grid of the tool's real screenshots (5-10
   images) that opens a full-screen lightbox (prev/next, keyboard,
   counter) via `webpage.js`. The tool's code is NEVER embedded in the
   public page, so no visitor, scraper or AI can reach the source from
   the website. Never replace the gallery with iframes or code blocks.
4. **Screenshots** - `docs/screenshots/01-09*.png`, captured with
   `npm run screenshots -- <ToolName>` (headless Edge with sample data;
   the page shots need the harness `?page=` query param; duplicate pages
   are detected and deleted). The highlight
   rows use shots 01 and 03, and a third "Works where you are" row shows
   the portrait 02 in a `wp-visual wp-visual-mobile` box (the row is
   removed automatically when the mobile shot does not exist). A missing
   shot renders a "Screenshot coming soon" plate instead of a broken
   image.

For the website: `npm run webpage:export -- <ToolName>` produces
`docs/webpage-export.html` - the same page with `webpage.css` and
`webpage.js` INLINED, ready to paste anywhere (replace the two `[CTA link]`s
with real store links).

Rules of the design system:
- Change the DESIGN in `_docs/assets/webpage.css` / `webpage.js` - once,
  for all tools. Never per page.
- Change a tool's COLOR in its inline accent `<style>` block - never in the
  shared css.
- Never add per-tool `<style>` blocks or new class prefixes in the
  generated region; write content only.

## Screenshots - one capture, many documents

`npm run screenshots -- <ToolName>` captures the tool's test harness (with
sample data) into `docs/screenshots/` and writes `screenshots.json` - the
manifest with each shot's label, page, viewport, REAL pixel dimensions
(read from the PNG header) and capture time. Shots are BARE: the capture
passes `?bare=1` so the harness toolbar is hidden and the images show the
real app only. The same PNGs feed:

1. **docs/index.html viewer** - the MEDIA menu item shows a large preview
   with prev/next, an info panel below (file, shot label, page, viewport,
   dimensions, capture time, and which docs use the shot) and a thumbnail
   strip. The data is the SCREENSHOTS-PAYLOAD embedded by `docs:init` and
   refreshed with `npm run docs:index-shots -- <ToolName>`.
2. **docs/webpage.html** - highlight rows (shots 01, 02, 03) plus the
   screenshot GALLERY band (all shots, lightbox viewer).
3. **docs/help.html "6. What it looks like"** - fixed figures outside the
   GENERATED markers; `docs:init` fills them from the real shots.
4. **docs/social.html "7. Media to attach"** - the thumbnail strip that
   the team attaches to the social posts of the latest ship.
5. **Other documents when useful** - presentation slides, updates notes or
   social visual ideas may embed `screenshots/<file>` paths; any doc that
   references a shot shows up in the viewer's "Used in" row (refresh the
   payload after such a change).

Shell migration (after a template change): `npm run docs:refresh-shells`
regenerates every `docs/index.html` from the template and inserts the help
and social shell sections where they are missing - never touching the
AI/hand-written content of the other documents.

## The SHIP process (end to end)

"SHIP" is the one-word trigger for the full shipment protocol in
`publish-rules.txt`: SSOT update + satellite regeneration + screenshots +
release rows + a new social share set + verification gate + commit, version
bump and push + the CMS handoff bundle (`npm run ship:cms`, see
`SHIP-CMS-PLAN.md`). The bundle prepares webpage/help/presentation/updates/
social + the tool code for the application store CMS - no CMS
communication is made until the CMS import API is ready.

Verify the links anytime with:

- `npm run ssot:check` - reports any document that does not link the shared
  assets (must print "Shared assets check OK"; a webpage.html still on the
  old self-contained format is reported as a warning and should be rebuilt
  with `npm run docs:init`).

Structural HTML changes (a new SSOT section, a new slide order) are a
different layer: the templates in this folder are the source for NEW
documents (`npm run docs:init`), while existing documents keep their own
content sections and are edited in place. Rule of thumb: change the shared
assets for LOOK and BEHAVIOR, change the templates for the STRUCTURE of new
documents.

## Placeholders

The generators (`scripts/init-docs.js`, `scripts/generate-docs.js`) replace
these placeholders:

- `[FEATURE NAME]` - the tool display name (e.g. AI Chat Presentation Builder).
- `[DATE]` - today's date (YYYY-MM-DD).
- `[CODE]` - the tool's decision-ID prefix (e.g. D-AICPB); rows in section 11
  are numbered `[CODE]-01, [CODE]-02, ...` forever. Append-only.
- `[ASSETS_RELATIVE]` - relative path from the generated `docs/` folder to
  `_docs/assets/` (computed automatically per tool).
- `[SSOT FILE]` - link target for the tool's SSOT (`ssot.html`).
- `[CSS_CLASS]` - the scoped class prefix of the marketing page
  (kebab-case tool name) so its styles never leak into the website.
- Every other `[PLACEHOLDER]` is content YOU write (or the AI writes during
  generation).

`<!-- GENERATED-START -->` / `<!-- GENERATED-END -->` markers delimit the
region that `generate-docs.js` replaces with AI output - keep the structure
of that region as the output contract.

## Workflow

1. **Initialize**: `npm run docs:init` creates `docs/` (the seven documents,
   index.html included) for every tool folder that does not have them yet.
   Run it once now; it is idempotent and only creates missing files.
2. **Work**: edit `docs/ssot.html` together with the code - decisions in
   section 11, tasks in section 15, risks in section 18. The task panel,
   progress bars and push gate update themselves in the browser.
3. **Regenerate**: `npm run docs:generate <ToolName>` regenerates the four
   AI satellites (webpage, help, presentation, social) for one tool.
   `npm run docs:generate -- --changed` regenerates every tool that changed
   since the last push. `--dry-run` prints what would happen without asking
   the AI or writing files.
4. **Release**: `npm run rel` does everything - it finds the tools that
   changed since the last push, appends release rows to their
   `ssot.html` + `updates.html`, stamps shipped tasks, regenerates the
   satellites with AI, rebuilds the SSOT control tower (`_docs/index.html`),
   then commits and pushes. `--dry-run` prints the whole plan first.

## Rules

- The SSOT is the source of truth. The other five documents are satellites:
  when they disagree with the SSOT, the SSOT wins.
- A decision that is not in section 11 did not happen. The register is
  append-only.
- No code change without the document change, in the same change.
- Names must be self-explanatory, no cryptic abbreviations.
- Hyphen `-`, never the em dash `—`, in all documents. No emoji icons in
  document headers or CSS.

## AI sources used during generation

`generate-docs.js` feeds the AI: the tool's code (`app/`, `listing/`,
`reporting/`), its SSOT, its update history, the tool-ideas catalog entry
(purpose, users, TAM/SAM/SOM, licensing), the taxonomy path (category and
subcategory), and this project's AI chat transcripts. The AI backend order
is the same as in `scripts/releaseContext.js` - the UniconHub AI gateway,
then an OpenAI-compatible endpoint, then local Ollama.
